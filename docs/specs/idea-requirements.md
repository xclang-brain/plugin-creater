# アイデア創出の要件

ユーザーが、クリエイターのアイデア創出スキル（`make-idea`）を使ってアイデアを作るとき、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第5章）。生成プラグインを作る流れは [作る流れの要件](creation-requirements.md)、試験は [試験の要件](test-requirements.md) で定める。

## 1. 6つの柱

アイデア創出スキルは、次の6つの柱の順にアイデアを作る（憲章 第25条）。柱の名前・順番・中身は、開発者の承認なしに変えない。中身は、開発者が示したとおりに次に書く。

| 柱 | 中身 |
| --- | --- |
| 1. 制限の決定 | 何のために、どの範囲でアイデアを考えるかを定める。制限のない状態で、ただアイデアを出そうとしない |
| 2. 徹底的な事前調査 | 制限の中で考えられる関連情報を、できる限り幅広く、時間をかけて調べる。世の中にある作品を集め、その中から評価を受けているものを掘り下げる。アイデアはゼロから生まれるのではなく、既にあるものの組み合わせから生まれると捉える。速くするため、複数のエージェントで並列に調べる |
| 3. 本質の見極め（なぜなぜ分析） | 集めた作品に対し、「なぜ評価されているのか」「なぜこの形なのか」と、できる限り多くの疑問を投げかける。なぜなぜ分析を重ね、表面的な特徴の奥にある本質を探る。一人で完結させず、複数のエージェントで互いの分析に意見を出し合って、本質を磨く。洗練された本質をたくさん用意する |
| 4. 本質の掛け合わせによるアイデア創出（壁打ち） | 本質の中から使えそうな2〜4個を選んで掛け合わせ、新しいアイデアを作る。評価されている作品をそのまま持ち寄るだけでは、新しいアイデアにはならない。本質を捉えていないものは、いくら組み合わせても良いアイデアにはならない。できる限り多くの案を作り、案を作ったエージェントとは別のエージェントに案をぶつけて意見を受け取る。このやり取りを繰り返して洗練させる。壁打ちしてだめなら別の組を選び、それでもだめなら掛け合わせる数を変える |
| 5. アイデアの説明（第三者目線） | 良いアイデアを作るだけで終わらず、その良さを他者に伝える。説明を第三者に見てもらい、伝わる点と伝わりにくい点を確かめる。指摘をもとに説明を磨き、アイデアの価値が正しく伝わる状態にする |
| 6. 知識・経験の蓄積 | 一通りの作業を終えてアイデアを作った後に振り返り、事前調査で学んだこと、気づいたこと、うまくいったこと、失敗したことを、知識・経験として蓄積する。ログのように全部を残さず、本質を見極めて洗練した形で残す。蓄積した知識・経験は、次からのすべての柱で活かす |

- 目的：AI の実現力が高まる中で、価値のあるアイデアを生み出し、その良さを他者に伝えられる状態にする。
- 柱の中の数は、すべてパラメーター（REQ-062）である。

## 2. 始める

### REQ-052 アイデア創出を頼む

- 要件：ユーザーは、チャットで「〇〇のアイデアを考えて」のように頼むか、`/plugin-creator:make-idea` で、アイデア創出を始められる。始まると、アイデア創出スキルは、使うパラメーターの値、知識・経験の件数、データの置き場所を示す。プラグインを作る頼み、作ったプラグインの試験の頼み、いまその仕事そのものをしてほしい頼みでは、アイデア創出は始まらない。
- 根拠：憲章 第4条、第25条、第27条
- 受け入れ基準：
  - アイデアを考えてほしいと頼むと、アイデア創出が始まる。
  - 始まりに、パラメーターの値、知識・経験の件数、データの置き場所が示される。
  - プラグインを作る頼み、試験の頼み、仕事そのものの頼みでは、アイデア創出が始まらない。

### REQ-053 始められないとき・答えが来ないとき

- 要件：アイデア創出スキルは、次のとき、推測で進めずに止まる。
  - 質問のツールがない起動（`-p`、`--no-ask-user`）：対話モードで起動し直すよう示し、始めない。
  - 同じ会話で make-plugin か test-plugin を使っていた：`/clear` してから頼み直すよう示し、始めない。
  - 質問に答えが来なかった（取り消した、autopilot）：何を聞きたかったかと続け方を示して止まる。
  - パラメーターのファイルが読めない、または値が範囲の外（REQ-062）：どの項目かを示して止まる。
- 根拠：憲章 第25条（制限の決定はユーザーが行う）、第27条
- 受け入れ基準：
  - `-p` で頼むと、起動し直すよう示され、始まらない。
  - make-plugin を使った同じ会話で頼むと、`/clear` するよう示され、始まらない。
  - 質問を取り消すと、聞きたかったことと続け方が示されて止まる。
  - 範囲の外の値を書くと、その項目が示されて止まる。

## 3. 6つの柱

### REQ-054 制限の決定

- 要件：アイデア創出スキルは、何のために、どの範囲でアイデアを考えるかを、ユーザーに聞いて決める。
  - 聞くこと：目的（何に困っているか）、対象の範囲（業務、道具、環境）、必ず満たす条件、あれば望ましい条件、良いアイデアかを決める観点。
  - 頼みの文や前の回の制限で分かることは聞き直さず、分かったこととして示して確かめる。
  - ユーザーが「決まっていない」と答えたことを、推測で埋めない。
  - 決めた制限を一覧で示し、ユーザーがよいと答えてから次の柱に進む。
- 根拠：憲章 第25条（6つの柱の1）
- 受け入れ基準：
  - 上の5つが、聞かれるか、頼みの文から分かったこととして確かめられる。
  - 決めた制限の一覧が示され、ユーザーがよいと答えるまで事前調査が始まらない。
  - 制限のファイルに、ユーザーが答えていない条件がない。

### REQ-055 徹底的な事前調査

- 要件：アイデア創出スキルは、制限の中の作品（公開のプラグイン、スキル、ツール、製品、手法、記事など）を、Web で幅広く集め、評価を受けているものを掘り下げる。
  - 始める前に、集める件数、掘り下げる件数、同時に動かすエージェントの数、起動するエージェントの数の見込みを示し、ユーザーが続けると答えてから始める。
  - 集めるのは、複数のエージェントが並列に行う。
  - 作品は、Web で URL を確かめたものだけを数える。重なりは除く。
  - 終わったら、集めた件数、掘り下げた件数、一覧のファイルの場所を示す。
- 根拠：憲章 第25条（6つの柱の2）、第26条
- 受け入れ基準：
  - 始める前に、件数と起動の数の見込みが示され、続けると答えるまで調べない。
  - 集めた作品が、パラメーターの件数以上あり、すべてに URL がある。
  - 集めるエージェントが、パラメーターの数だけ並列に起動される。
  - 掘り下げた作品に、評価の手がかりと引用がある。

### REQ-056 本質の見極め（なぜなぜ分析）

- 要件：アイデア創出スキルは、掘り下げた作品ごとに「なぜ評価されているのか」「なぜこの形なのか」を重ね、本質を見極める。
  - なぜなぜ分析は、パラメーターの数以上のエージェントが、互いを見ずに行う。そのあと、互いの分析に意見を出し合い、出し直す。
  - 本質は、目的（何のためか）と仕組み（どうやって満たすか）で書き、裏づけの作品と引用を付ける。目的と仕組みで書けないものは、印を付けて残す。
  - 本質を、パラメーターの数以上用意する。足りないときは、数と理由を示し、作品を足して続けるか、今の数で進むかを聞く。
  - 終わったら、本質の数と一覧のファイルの場所を示す。
- 根拠：憲章 第25条（6つの柱の3）、第26条
- 受け入れ基準：
  - なぜなぜ分析のエージェントが、パラメーターの数以上起動され、出し合いの前に互いのファイルを読んでいない。
  - 本質の一覧に、パラメーターの数以上の本質があり、それぞれに裏づけの作品がある。
  - 言い換えにすぎない本質が、別の本質として数えられていない。

### REQ-057 本質の掛け合わせによるアイデア創出（壁打ち）

- 要件：アイデア創出スキルは、本質の一覧から、一度に2〜4個（パラメーター）を選んで掛け合わせ、アイデアの案を作り、壁打ちする。
  - 案を作るエージェントと、壁打ちの相手のエージェント（パラメーターの数以上）は別にする。相手は、互いを見ずに、案ごとに通すか通さないかと理由を返す。
  - 案を作るエージェントは、指摘を受けて案を直す。相手は、直した案をもう一度判定する。往復の回数はパラメーターである。
  - 相手の過半数が通した案を、通った案とする。
  - 組の案が1つも通らなければ、別の組を選ぶ。同じ数でパラメーターの組数だけ続けてだめなら、掛け合わせる数を変える（初期値は 3 → 4 → 2 の順）。最後の数でもだめなら、それまでの結果を示し、続けるかを聞く。
  - 壁打ちした案の数がパラメーターの総数に届いたら止め、通った案の一覧を示す。
- 根拠：憲章 第25条（6つの柱の4）、第26条
- 受け入れ基準：
  - どの組も、掛け合わせた本質の数がパラメーターの範囲の中にある。
  - 壁打ちの相手が、案を作るエージェントとは別に、パラメーターの数以上起動される。
  - 1つも通らなかった組の次に、別の組が選ばれる。続けてだめなら、掛け合わせる数が決まった順に変わる。
  - 壁打ちした案の数が、パラメーターの総数以上になる（ユーザーが途中で止めたときを除く）。

### REQ-058 説明するアイデアを選ぶ

- 要件：アイデア創出スキルは、通った案の一覧を番号つきで示し、説明するアイデア（パラメーターの数まで）と、選んだ理由をユーザーに聞く。ユーザーの選び方と理由は、知識・経験の蓄積（REQ-060）の材料にする。
- 根拠：憲章 第25条（6つの柱の5と6）。良いアイデアかの最後の判断は人が行う
- 受け入れ基準：
  - 通った案の一覧が示され、ユーザーが選んだアイデアだけが説明される。
  - 選んだ理由が、振り返りの材料に入っている。

### REQ-059 アイデアの説明（第三者目線）

- 要件：アイデア創出スキルは、選ばれたアイデアごとに、その良さが他者に伝わる説明を書く。
  - 説明は、誰が、どの場面で、何に困っていて、このアイデアで何が良くなるかを、作る過程を知らない人が読んで分かるように書く。長さの上限はパラメーターである。
  - 説明を読む第三者のエージェント（パラメーターの数以上）には、説明の文だけを渡す。作る過程（作品、本質、壁打ち）は渡さない。
  - 読み手は、自分の言葉での言い直し、誰がどの場面で使うか、何がうれしいか、分からなかった言葉を返す。意図と違えば直し、新しい読み手でもう一度確かめる。直す回数はパラメーターである。
  - 終わったら、説明のファイルの場所と、読み手の指摘で直したことを示す。
- 根拠：憲章 第25条（6つの柱の5）、第26条
- 受け入れ基準：
  - 説明のファイルが、選ばれたアイデアごとにある。
  - 読み手のエージェントが、パラメーターの数以上起動され、説明の文のほかに作る過程を受け取っていない。
  - 読み手の言い直しが、説明の意図と合っている。合わなかった点は、直した記録がある。

### REQ-060 知識・経験の蓄積

- 要件：説明が終わると、アイデア創出スキルは、この回を振り返り、知識・経験として残す。
  - 振り返りは、パラメーターの数以上のエージェントが、互いを見ずに「なぜうまくいったか」「なぜだめだったか」を問い、本質を見極める。
  - 残すのは、本質の1文に、裏づけの具体例1件、出典（どの回のどの記録か）、使う柱、得た制限（分野を問わないか）、得た日、確かさ（ユーザーが確かめたか）を添えた項目である。記録を丸ごと残さない。
  - 今ある項目と比べ、足す・まとめて直す・消すの候補にする。全体を書き直さない。
  - 候補を番号つきで示し、ユーザーが外した番号のほかを保存する。保存する前に、社名・製品名・数値などの具体は、一般的な言い方に直すか、ユーザーに確かめる。
  - ファイルが大きさの上限（パラメーター）に近づいたら、まとめる・消す候補を示す。
- 根拠：憲章 第25条（6つの柱の6）、第26条
- 受け入れ基準：
  - 振り返りのエージェントが、パラメーターの数以上起動される。
  - 保存した項目が、上の形をすべて持つ。
  - ユーザーが外した番号の候補は、保存されない。
  - 知識・経験のファイルが、大きさの上限より小さい。

### REQ-061 知識・経験を活かす

- 要件：アイデア創出スキルは、どの柱でも、始めにその柱の知識・経験を読み、今の制限に合う項目を使う。使った項目と、それで変えた判断を、その柱の記録に残す。
- 根拠：憲章 第25条（6つの柱の6。蓄積した知識・経験は、すべての柱で活かす）
- 受け入れ基準：
  - 知識・経験がある状態で始めると、各柱の記録に、使った項目と変えた判断がある。
  - 別の分野の制限で得た項目が、分野を問わない項目のほかは使われていない。

## 4. パラメーター

### REQ-062 パラメーター

- 要件：6つの柱の中の数は、すべてパラメーターのファイル（JSON）で変えられる。初めて使うとき、アイデア創出スキルは、既定のファイルをデータの置き場所に写す。ユーザーは、写したファイルを書き換える。既定の値は次のとおり（「以上」は、少なくともこの数を行うこと）。

  | 柱 | パラメーター | 既定 | 決めた人 |
  | --- | --- | --- | --- |
  | 徹底的な事前調査 | 集める作品の数 | 100以上 | 開発者 |
  | 徹底的な事前調査 | 同時に調べるエージェントの数 | 4 | AI |
  | 徹底的な事前調査 | 掘り下げる作品の数 | 30 | AI |
  | 本質の見極め | 本質の数 | 30以上 | 開発者 |
  | 本質の見極め | なぜなぜ分析をするエージェントの数 | 2以上 | 開発者 |
  | 本質の見極め | なぜを重ねる段の上限 | 5 | AI |
  | 本質の見極め | 意見を出し合う往復の数 | 1 | AI |
  | 本質の掛け合わせ | 一度に掛け合わせる本質の数 | 2〜4 | 開発者 |
  | 本質の掛け合わせ | 掛け合わせる数を変える順 | 3 → 4 → 2 | AI（開発者の例から） |
  | 本質の掛け合わせ | 同じ数で試す組の数 | 3 | AI（開発者の例から） |
  | 本質の掛け合わせ | 壁打ちの相手のエージェントの数 | 2以上 | 開発者 |
  | 本質の掛け合わせ | 1つの組から作る案の数 | 10 | AI |
  | 本質の掛け合わせ | 壁打ちする案の総数 | 100以上 | AI |
  | 本質の掛け合わせ | 壁打ちの往復の数 | 2 | AI |
  | アイデアの説明 | 説明を読む第三者のエージェントの数 | 2以上 | 開発者 |
  | アイデアの説明 | 説明するアイデアの数の上限 | 3 | AI |
  | アイデアの説明 | 説明を直す回数の上限 | 2 | AI |
  | アイデアの説明 | 説明の長さの上限（文字） | 4000 | AI |
  | 知識・経験の蓄積 | 振り返りのエージェントの数 | 2以上 | AI（開発者の指示から） |
  | 知識・経験の蓄積 | 知識・経験のファイル1つの大きさの上限（バイト） | 16000 | AI |

  値の扱い：
  - 数でない、0以下、範囲の下が上より大きい、知らない項目がある：使わずに、どの項目かを示して止まる。
  - エージェントの数（なぜなぜ分析、壁打ちの相手、読み手、振り返り）が2未満：止める。2者以上で行うことが柱の中身であるため。
  - 一度に掛け合わせる数の下限が2未満、本質の数が掛け合わせる数の上限より小さい：止める。
  - 件数や個数を既定より小さくした：そのまま使い、始めに示す。
- 根拠：憲章 第26条。既定の値の根拠は [アイデア創出の設計](../design/idea.md) 4章
- 受け入れ基準：
  - 初めて使うと、既定のファイルがデータの置き場所に写される。
  - ファイルの値を変えると、その柱の数が変わる。
  - 上の止める値を書くと、その項目が示されて止まる。

## 5. 記録と続け方

### REQ-063 データの置き場所

- 要件：アイデア創出スキルは、パラメーターのファイル、知識・経験、回ごとの記録を、ユーザーのホームフォルダの下の決まったフォルダ（`~/.plugin-creator/make-idea/`）に置く。リポジトリや作業フォルダには置かない。外には送らない。消し方は README に書く。
- 根拠：憲章 第27条。知識・経験は回を重ねるほど価値が増すので、消えにくい場所に置く。業務の情報を含みうるので、手元だけに置く
- 受け入れ基準：
  - 1回の実行で作るファイルが、すべてこのフォルダの中にある。
  - README に、置き場所と消し方がある。

### REQ-064 続きから始める

- 要件：途中で止まった回があるとき、アイデア創出スキルは、始まりに、その回を続けるか、新しく始めるかを聞く。続けるときは、止まった柱の続きから進む。会話が自動で要約された後も、記録から今の柱を確かめて続ける。
- 根拠：憲章 第25条。1回の実行は長く、利用枠の上限や会話の要約で止まりうる
- 受け入れ基準：
  - 柱の途中で止めて新しい会話で頼むと、続けるかが聞かれ、続けると止まった柱から進む。

## 6. 分離

### REQ-065 機能の分離

- 要件：アイデア創出スキルは、make-plugin と test-plugin の仕組み（クリエイターの画面、ヒアリングの記録、`plugin-creator_` で始まるツール、読み取り役と作業エージェント）を使わない。終わりに、作ったアイデアでプラグインを作るときは、`/clear` してから make-plugin に頼むよう示す。make-plugin と test-plugin の振る舞いは、アイデア創出スキルを足す前と変わらない。
- 根拠：憲章 第27条
- 受け入れ基準：
  - アイデア創出の間に、`plugin-creator_` で始まるツールが呼ばれず、ヒアリングの記録ができない。
  - 終わりに、`/clear` してから make-plugin に頼むよう示される。
  - クリエイターの既存の試験が、アイデア創出スキルを足す前と同じく通る。
