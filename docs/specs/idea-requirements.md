# アイデア創出の要件

ユーザーが、クリエイターのアイデア創出スキル（`make-idea`）を使ってアイデアを作るとき、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第5章）。生成プラグインを作る流れは [作る流れの要件](creation-requirements.md)、試験は [試験の要件](test-requirements.md) で定める。

## 1. 6つの柱

アイデア創出スキルは、次の6つの柱の順にアイデアを作る（憲章 第26条）。柱の名前・順番・中身は、開発者の承認なしに変えない。中身は、開発者が示したとおりに次に書く。

| 柱 | 中身 |
| --- | --- |
| 1. 制限の決定 | 何のために、どの範囲でアイデアを考えるかを定める。制限のない状態で、ただアイデアを出そうとしない |
| 2. 徹底的な事前調査 | 制限の中で考えられる関連情報を、できる限り幅広く、時間をかけて調べる。世の中にある作品を集め、その中から評価を受けているものを掘り下げる。アイデアはゼロから生まれるのではなく、既にあるものの組み合わせから生まれると捉える。速くするため、複数のエージェントで並列に調べる |
| 3. 本質の見極め（なぜなぜ分析） | 集めた作品に対し、「なぜ評価されているのか」「なぜこの形なのか」と、できる限り多くの疑問を投げかける。なぜなぜ分析を重ね、表面的な特徴の奥にある本質を探る。一人で完結させず、複数のエージェントで互いの分析に意見を出し合って、本質を磨く。洗練された本質をたくさん用意する |
| 4. 本質の掛け合わせによるアイデア創出（壁打ち） | 本質の中から使えそうな2〜4個を選んで掛け合わせ、新しいアイデアを作る。評価されている作品をそのまま持ち寄るだけでは、新しいアイデアにはならない。本質を捉えていないものは、いくら組み合わせても良いアイデアにはならない。できる限り多くの案を作り、案を作ったエージェントとは別のエージェントに案をぶつけて意見を受け取る。このやり取りを繰り返して洗練させる。壁打ちしてだめなら別の組を選び、それでもだめなら掛け合わせる数を変える |
| 5. アイデアの説明（第三者目線） | 良いアイデアを作るだけで終わらず、その良さを他者に伝える。説明を第三者に見てもらい、伝わる点と伝わりにくい点を確かめる。指摘をもとに説明を磨き、アイデアの価値が正しく伝わる状態にする |
| 6. 知識・経験の蓄積 | 一通りの作業を終えてアイデアを作った後に振り返り、事前調査で学んだこと、気づいたこと、うまくいったこと、失敗したことを、知識・経験として蓄積する。ログのように全部を残さず、本質を見極めて洗練した形で残す。蓄積した知識・経験は、次からのすべての柱で活かす |

- 目的：AI の実現力が高まる中で、価値のあるアイデアを生み出し、その良さを他者に伝えられる状態にする。
- 柱の中の数は、すべてパラメーター（REQ-073）である。
- 制限は、事前調査の範囲が無限に広がらないようにするための取っかかりである。できたアイデアが制限の範囲から外れてもよい。柱3から後では、制限を使わない（開発者の考え）。
- 良いアイデアとは、新しさがあり（これまでにない）、誰かにとても役立ち、その人や世の中にとって価値があるものである。壁打ちと、説明するアイデアの選択は、この3つ（新しさ、役立つか、価値）で判定する（開発者の考え）。
- 柱の中身は、この表の文のとおりに手順へ写す。縮めて写すと、言葉が抜けて手順に届かないためである（「時間をかけて」が抜け、事前調査が約8分で終わった）。

## 2. 始める

### REQ-063 アイデア創出を頼む

- 要件：ユーザーは、チャットで「〇〇のアイデアを考えて」のように頼むか、`/plugin-creator:make-idea` で、アイデア創出を始められる。始まると、アイデア創出スキルは、使うパラメーターの値、知識・経験の件数、データの置き場所を示す。プラグインを作る頼み、今あるプラグインを直す頼み、作ったプラグインの試験の頼み、いまその仕事そのものをしてほしい頼みでは、アイデア創出は始まらない。
- 根拠：憲章 第4条、第26条、第28条
- 受け入れ基準：
  - アイデアを考えてほしいと頼むと、アイデア創出が始まる。
  - 始まりに、パラメーターの値、知識・経験の件数、データの置き場所が示される。
  - プラグインを作る頼み、直す頼み、試験の頼み、仕事そのものの頼みでは、アイデア創出が始まらない。

### REQ-064 始められないとき・答えが来ないとき

- 要件：アイデア創出スキルは、次のとき、推測で進めずに止まる。
  - 質問のツールがない起動（`-p`、`--no-ask-user`）：対話モードで起動し直すよう示し、始めない。
  - 同じ会話で make-plugin・change-plugin・test-plugin のどれかを使っていた：`/clear` してから頼み直すよう示し、始めない。
  - 質問に答えが来なかった（取り消した、autopilot）：何を聞きたかったかと続け方を示して止まる。
  - パラメーターのファイルが読めない、または値が範囲の外（REQ-073）：どの項目かを示して止まる。
- 根拠：憲章 第26条（制限の決定はユーザーが行う）、第28条
- 受け入れ基準：
  - `-p` で頼むと、起動し直すよう示され、始まらない。
  - make-plugin を使った同じ会話で頼むと、`/clear` するよう示され、始まらない。
  - 質問を取り消すと、聞きたかったことと続け方が示されて止まる。
  - 範囲の外の値を書くと、その項目が示されて止まる。

## 3. 6つの柱

### REQ-065 制限の決定

- 要件：アイデア創出スキルは、何のために、どの範囲でアイデアを考えるかを、ユーザーに聞いて決める。
  - 聞くこと：目的（何に困っているか、何を良くしたいか）と、対象の範囲（業務、道具、環境）の2つだけ。満たすべき条件や良さの観点は聞かない。良さは、どの回も1章の3つで判定するためである。
  - 頼みの文や前の回の制限で分かることは聞き直さず、分かったこととして示して確かめる。
  - ユーザーが「決まっていない」と答えたことを、推測で埋めない。
  - 決めた制限を一覧で示し、ユーザーがよいと答えてから次の柱に進む。
  - 決めた制限は、事前調査の範囲を決めるためだけに使う。柱3から後のエージェントには渡さず、判定にも選び方にも使わない。
- 根拠：憲章 第26条（6つの柱の1）、1章の開発者の考え
- 受け入れ基準：
  - 目的と範囲が、聞かれるか、頼みの文から分かったこととして確かめられる。ほかの項目は聞かれない。
  - 決めた制限の一覧が示され、ユーザーがよいと答えるまで事前調査が始まらない。
  - 制限のファイルに、ユーザーが答えていない条件がない。
  - 柱3から後のエージェントが、制限のファイルを読んでいない。

### REQ-066 徹底的な事前調査

- 要件：アイデア創出スキルは、制限の中の作品（公開のプラグイン、スキル、ツール、製品、手法、事例、研究など）を、ディープリサーチのように、時間をかけて、できる限り幅広く深く調べる。ディープリサーチとは、調べる計画を立て、多くの情報源を並列に検索して元のページを読み、足りないところを見つけて調べ直し、引用つきでまとめることを繰り返す調べ方である（開発者の考え）。
  - 始める前に、集める件数、調べ直しの回数、同時に動かすエージェントの数、起動するエージェントの数の見込みを示し、ユーザーが続けると答えてから始める。
  - 調べる計画（切り口と問い）を立ててから集める。切り口には、制限に近い分野と、同じ困りごとを別の分野でどう解いているかなどの遠い分野の両方を入れる。
  - 集めるのは、複数のエージェントが並列に行う。作品は、元のページを読んで確かめたものだけを数える。重なりは除く。
  - 集めたあと、足りない切り口や浅いところを見つけて調べ直す。調べ直しの回数はパラメーターである。それでも件数が足りなければ、数と理由を示し、もう一度集めるか、今の数で進むかを聞く。
  - 集めた作品はすべて、評価の手がかり（利用者の数、レビュー、受賞、採用例、論文の引用など）を元のページで確かめる。何があれば評価を受けているとするかは、作品の種類ごとに決めて記録する。
  - 評価を受けていると確かめた作品は、すべて掘り下げる。件数を決めて選ばない。掘り下げでは、1件ごとに複数の情報源（数はパラメーター）を読み、なぜ評価されているのかの材料（利用者の声、レビュー、論文の評価、採用の理由など）を引用つきで集める。
  - 終わったら、集めた件数、評価を確かめた件数、掘り下げた件数、読んだページの数、かかった時間、一覧とまとめのファイルの場所を示す。
- 根拠：憲章 第26条（6つの柱の2。「できる限り幅広く、時間をかけて調べる」「評価を受けているものを掘り下げる」）、第27条
- 受け入れ基準：
  - 始める前に、件数と起動の数の見込みが示され、続けると答えるまで調べない。
  - 調べる計画のファイルがあり、集めた後に調べ直した記録がある。
  - 集めた作品が、パラメーターの件数以上あり、すべてに確かめた URL がある。
  - 集めるエージェントが、パラメーターの数だけ並列に起動される。
  - 評価を受けていると確かめた作品が、すべて掘り下げられている。掘り下げた作品ごとに、パラメーターの数以上の情報源と、評価の裏づけの引用がある。
  - 読んだページの数と、かかった時間が示される。

### REQ-067 本質の見極め（なぜなぜ分析）

- 要件：アイデア創出スキルは、掘り下げた作品ごとに、「なぜ評価されているのか」「なぜこの形なのか」など、できる限り多くの疑問を投げかけ、なぜなぜ分析を重ねて、表面的な特徴の奥にある本質を見極める。
  - 問いは「なぜ評価されているのか」から始め、答えは柱2で集めた評価の材料（引用）にもとづいて書く。
  - 「それはなぜか」を重ねる。各段は前の段の問いへの答えで、根拠（引用か作品の番号）を付ける。道具の機能を言い換えただけの段で止めず、人の困りごとか仕組みの原理に届いたら止める。段の数の上限はパラメーターである。
  - なぜなぜ分析は、パラメーターの数以上のエージェントが、互いを見ずに行う。分析したエージェントが、自分でファイルに書く。ほかのエージェントが縮めて書き写さない。
  - そのあと、互いの分析に意見を出し合い、出し直す。意見では、根拠の弱さ、言い換え、見落とし、抽象的すぎる本質に加えて、なぜの浅さ（機能の言い換えで止まっている、前の段の答えになっていない）を指摘する。
  - 本質は、目的（何のためか）と仕組み（どうやって満たすか）で書き、たどり着いた「なぜ」の連なり、裏づけの作品と引用を付ける。目的と仕組みで書けないものは、印を付けて残す。
  - 本質を、パラメーターの数以上用意する。足りないときは、数と理由を示し、作品を足して続けるか、今の数で進むかを聞く。
  - 終わったら、本質の数、一覧のファイルの場所、かかった時間、本質の例（「なぜ」の連なりつきで2つ）を示す。
- 根拠：憲章 第26条（6つの柱の3）、第27条
- 受け入れ基準：
  - なぜなぜ分析のエージェントが、パラメーターの数以上起動され、出し合いの前に互いのファイルを読んでいない。分析のファイルは、分析したエージェントが書いている。
  - 分析の各段が前の段の答えになっていて、根拠がある。最初の問いが「なぜ評価されているのか」である。
  - 本質の一覧に、パラメーターの数以上の本質があり、それぞれに「なぜ」の連なりと裏づけの作品がある。
  - 言い換えにすぎない本質が、別の本質として数えられていない。

### REQ-068 本質の掛け合わせによるアイデア創出（壁打ち）

- 要件：アイデア創出スキルは、本質の一覧から、一度に2〜4個（パラメーター）を選んで掛け合わせ、新しいアイデアの案を作り、壁打ちする。
  - 組は、新しさと価値につながるように選ぶ（例：根拠のある困りごとにたどり着いた本質と、別の分野の仕組みの原理の本質を組む）。選んだ理由は、案を作る前に記録する。制限は使わない。
  - 案を作るエージェントには、制限も場面の例も渡さない。案ごとに、誰のどんな困りごとか（出典を付ける。出典がなければ「仮説」と印を付ける）、何をするか、掛け合わせた本質がどう効くかを書く。
  - 案ごとに、いちばん近い既存のもの（製品、OSS、論文、特許など）を Web で探す。探すエージェントは、案を作るエージェントとも壁打ちの相手とも別にする。複数の言い方で探し、使った検索語と見たページを記録する。
  - 壁打ちの相手のエージェント（パラメーターの数以上）は、案を作るエージェントとは別にする。相手は、互いを見ずに、案ごとに次の3つで判定し、通すか通さないかと、理由と直し方を返す。3つともそろった案だけを通す。制限は判定に使わない。
    - 新しさ：いちばん近い既存のものとの違いが、案の価値の中心になっているか。
    - 役立つか：根拠のある困りごとに効くか。
    - 価値：その人や世の中にとっての大きさに、根拠があるか。
  - 相手のうち1体は、その案がだめな理由をいちばん強く示す役にする。自分の案や似た文を甘く見る偏りを減らすためである。
  - 案を作るエージェントは、指摘を受けて案を直す。相手は、直した案をもう一度判定する。このやり取りを、指摘がなくなるか、往復の上限（パラメーター）に届くまで繰り返す。
  - 相手の過半数が通した案を、通った案とする。
  - 組の案が1つも通らなければ、別の組を選ぶ。同じ数でパラメーターの組数だけ続けてだめなら、掛け合わせる数を変える（初期値は 3 → 4 → 2 の順）。最後の数でもだめなら、それまでの結果を示し、組を選び直すか、止めて後で続けるか、（通った案があれば）説明に進むかを聞く。
  - 壁打ちした案の数がパラメーターの総数に届いたら止め、通った案の一覧を示す。通った案が1つもないうちは止めない（説明する案がないと、アイデアの説明の柱を行えないため）。
- 根拠：憲章 第26条（6つの柱の4）、第27条、1章の開発者の考え
- 受け入れ基準：
  - どの組も、掛け合わせた本質の数がパラメーターの範囲の中にあり、組を選んだ理由が案より先に記録されている。
  - 案を作るエージェントと壁打ちの相手が、制限のファイルを読んでいない。
  - 組ごとに、いちばん近い既存のものを探した記録（検索語と見たページ）がある。
  - 壁打ちの判定が、案ごとに3つの観点で、根拠つきで書かれている。
  - 壁打ちの相手が、案を作るエージェントとは別に、パラメーターの数以上起動される。
  - 1つも通らなかった組の次に、別の組が選ばれる。続けてだめなら、掛け合わせる数が決まった順に変わる。
  - 壁打ちした案の数が、パラメーターの総数以上になる（ユーザーが途中で止めたとき、説明に進むと答えたときを除く）。
  - 通った案が1つもないまま、アイデアの説明に進まない。

### REQ-069 説明するアイデアを選ぶ

- 要件：アイデア創出スキルは、通った案のうち組をまたいで重なるものをまとめ、新しさ、役立つか、価値の3つで比べた順に、番号つきで示す。上位の案（パラメーターの数まで）には、3つの観点の評価の要点と、いちばん近い既存のものを添える。ほかの案は名前と1行にし、詳しい中身のファイルの場所を示す。そのうえで、説明するアイデア（パラメーターの数まで）と、選んだ理由をユーザーに聞く。ユーザーの選び方と理由は、知識・経験の蓄積（REQ-071）の材料にする。
- 根拠：憲章 第26条（6つの柱の5と6）。良いアイデアかの最後の判断は人が行う。1章の開発者の考え
- 受け入れ基準：
  - 通った案が3つの観点で比べた順に示され、上位の案に評価の要点といちばん近い既存のものがある。
  - ユーザーが選んだアイデアだけが説明される。
  - 選んだ理由が、振り返りの材料に入っている。

### REQ-070 アイデアの説明（第三者目線）

- 要件：アイデア創出スキルは、選ばれたアイデアごとに、その良さが他者に伝わる説明を書く。
  - 説明は、誰が、どの場面で、何に困っていて、このアイデアで何が良くなるかを、作る過程を知らない人が読んで分かるように書く。似たものとの違いには、柱4で探したいちばん近い既存のものも使う。長さの上限はパラメーターである。
  - 説明を読む第三者のエージェント（パラメーターの数以上）には、説明の文だけを渡す。作る過程（作品、本質、壁打ち）は渡さない。
  - 読み手は、自分の言葉での言い直し、誰がどの場面で使うか、何がうれしいか、分からなかった言葉を返す。意図と違えば直し、新しい読み手でもう一度確かめる。直す回数の上限はパラメーターである。上限まで直したときも、最後の版を新しい読み手に読ませてから終える。
  - 終わったら、説明のファイルの場所と、読み手の指摘で直したことを示す。
- 根拠：憲章 第26条（6つの柱の5）、第27条
- 受け入れ基準：
  - 説明のファイルが、選ばれたアイデアごとにある。
  - 読み手のエージェントが、パラメーターの数以上起動され、説明の文のほかに作る過程を受け取っていない。
  - 読み手の言い直しが、説明の意図と合っている。合わなかった点は、直した記録がある。

### REQ-071 知識・経験の蓄積

- 要件：説明が終わると、アイデア創出スキルは、この回を振り返り、知識・経験として残す。
  - 振り返りは、パラメーターの数以上のエージェントが、互いを見ずに「なぜうまくいったか」「なぜだめだったか」を問い、本質を見極める。
  - 残すのは、本質の1文に、裏づけの具体例1件、出典（どの回のどの記録か）、使う柱、得た制限（分野を問わないか）、得た日、確かさ（ユーザーが確かめたか）を添えた項目である。記録を丸ごと残さない。
  - 今ある項目と比べ、足す・まとめて直す・消すの候補にする。全体を書き直さない。
  - 良さを1章の3つ（新しさ、役立つか、価値）のほかで判定する項目（例：制限に合うものが良い、手元ですぐ試せるものが良い）は作らない。
  - 候補を番号つきで示し、ユーザーが外した番号のほかを保存する。保存する前に、社名・製品名・数値などの具体は、一般的な言い方に直すか、ユーザーに確かめる。
  - ファイルが大きさの上限（パラメーター）に近づいたら、まとめる・消す候補を示す。
- 根拠：憲章 第26条（6つの柱の6）、第27条
- 受け入れ基準：
  - 振り返りのエージェントが、パラメーターの数以上起動される。
  - 保存した項目が、上の形をすべて持つ。
  - ユーザーが外した番号の候補は、保存されない。
  - 知識・経験のファイルが、大きさの上限より小さい。

### REQ-072 知識・経験を活かす

- 要件：アイデア創出スキルは、どの柱でも、始めにその柱の知識・経験を読み、今の制限に合う項目を使う。使った項目と、それで変えた判断を、その柱の記録に残す。
- 根拠：憲章 第26条（6つの柱の6。蓄積した知識・経験は、すべての柱で活かす）
- 受け入れ基準：
  - 知識・経験がある状態で始めると、各柱の記録に、使った項目と変えた判断がある。
  - 別の分野の制限で得た項目が、分野を問わない項目のほかは使われていない。

## 4. パラメーター

### REQ-073 パラメーター

- 要件：6つの柱の中の数は、すべてパラメーターのファイル（JSON）で変えられる。初めて使うとき、アイデア創出スキルは、既定のファイルをデータの置き場所に写す。ユーザーは、写したファイルを書き換える。既定の値は次のとおり（「以上」は、少なくともこの数を行うこと）。

  | 柱 | パラメーター | 既定 | 決めた人 |
  | --- | --- | --- | --- |
  | 徹底的な事前調査 | 集める作品の数 | 100以上 | 開発者 |
  | 徹底的な事前調査 | 同時に調べるエージェントの数 | 4 | AI |
  | 徹底的な事前調査 | 調べ直しの回数 | 2 | AI |
  | 徹底的な事前調査 | 掘り下げで1件に読む情報源の数 | 3以上 | AI |
  | 徹底的な事前調査 | 1体が掘り下げる作品の数 | 5 | AI |
  | 本質の見極め | 本質の数 | 30以上 | 開発者 |
  | 本質の見極め | なぜなぜ分析をするエージェントの数 | 2以上 | 開発者 |
  | 本質の見極め | なぜを重ねる段の上限 | 5 | AI |
  | 本質の見極め | 意見を出し合う往復の数 | 1 | AI |
  | 本質の掛け合わせ | 一度に掛け合わせる本質の数 | 2〜4 | 開発者 |
  | 本質の掛け合わせ | 掛け合わせる数を変える順 | 3 → 4 → 2 | AI（開発者の例から） |
  | 本質の掛け合わせ | 同じ数で試す組の数 | 3 | AI（開発者の例から） |
  | 本質の掛け合わせ | 壁打ちの相手のエージェントの数 | 2以上 | 開発者 |
  | 本質の掛け合わせ | 1つの組から作る案の数 | 10 | AI |
  | 本質の掛け合わせ | 壁打ちする案の総数 | 100以上 | AI |
  | 本質の掛け合わせ | 壁打ちの往復の上限 | 3 | AI |
  | アイデアの説明 | 選ぶ一覧で詳しく示す案の数 | 10 | AI |
  | アイデアの説明 | 説明を読む第三者のエージェントの数 | 2以上 | 開発者 |
  | アイデアの説明 | 説明するアイデアの数の上限 | 3 | AI |
  | アイデアの説明 | 説明を直す回数の上限 | 2 | AI |
  | アイデアの説明 | 説明の長さの上限（文字） | 4000 | AI |
  | 知識・経験の蓄積 | 振り返りのエージェントの数 | 2以上 | AI（開発者の指示から） |
  | 知識・経験の蓄積 | 知識・経験のファイル1つの大きさの上限（バイト） | 16000 | AI |
  | 知識・経験の蓄積 | まとめ始める大きさの割合（%） | 80 | AI |

  値の扱い：
  - 数でない、0以下、範囲の下が上より大きい、知らない項目がある：使わずに、どの項目かを示して止まる。
  - エージェントの数（なぜなぜ分析、壁打ちの相手、読み手、振り返り）が2未満：止める。2者以上で行うことが柱の中身であるため。
  - 一度に掛け合わせる数の下限が2未満、本質の数が掛け合わせる数の上限より小さい：止める。
  - 1体が掘り下げる作品の数が20より大きい、まとめ始める大きさの割合が100より大きい：止める。1体が書くファイルが読める大きさを超えるため、割合は100までであるため。
  - 選ぶ一覧で詳しく示す案の数が、説明するアイデアの数の上限より小さい：止める。選べる案に、比べる材料がなくなるため。
  - 件数や個数を既定より小さくした：そのまま使い、始めに示す。
- 根拠：憲章 第27条。既定の値の根拠は [アイデア創出の設計](../design/idea.md) 4章
- 受け入れ基準：
  - 初めて使うと、既定のファイルがデータの置き場所に写される。
  - ファイルの値を変えると、その柱の数が変わる。
  - 上の止める値を書くと、その項目が示されて止まる。

## 5. 記録と続け方

### REQ-074 データの置き場所

- 要件：アイデア創出スキルは、パラメーターのファイル、知識・経験、回ごとの記録を、ユーザーのホームフォルダの下の決まったフォルダ（`~/.plugin-creator/make-idea/`）に置く。リポジトリや作業フォルダには置かない。外には送らない。消し方は README に書く。
- 根拠：憲章 第28条。知識・経験は回を重ねるほど価値が増すので、消えにくい場所に置く。業務の情報を含みうるので、手元だけに置く
- 受け入れ基準：
  - 1回の実行で作るファイルが、すべてこのフォルダの中にある。
  - README に、置き場所と消し方がある。

### REQ-075 続きから始める

- 要件：途中で止まった回があるとき、アイデア創出スキルは、始まりに、その回を続けるか、新しく始めるかを聞く。続けるときは、回の今の柱と次にすることを示し、ユーザーが「続けて」と答えてから、止まった柱の続きから進む。会話が自動で要約された後も、記録から今の柱を確かめ、聞き直さずに続ける。
- 根拠：憲章 第26条。1回の実行は長く、利用枠の上限や会話の要約で止まりうる
- 受け入れ基準：
  - 柱の途中で止めて新しい会話で頼むと、続けるかが聞かれ、続けると止まった柱から進む。新しい回のフォルダは作られない。

## 6. 分離

### REQ-076 機能の分離

- 要件：アイデア創出スキルは、make-plugin・change-plugin・test-plugin の仕組み（クリエイターの画面、ヒアリングの記録、`plugin-creator_` で始まるツール、読み取り役と作業エージェント）を使わない。終わりに、作ったアイデアでプラグインを作るときや、今あるプラグインに足すときは、`/clear` してから make-plugin・change-plugin に頼むよう示す。make-plugin・change-plugin・test-plugin の振る舞いは、アイデア創出スキルを足す前と変わらない。
- 根拠：憲章 第28条
- 受け入れ基準：
  - アイデア創出の間に、`plugin-creator_` で始まるツールが呼ばれず、ヒアリングの記録ができない。
  - 終わりに、`/clear` してから make-plugin・change-plugin に頼むよう示される。
  - クリエイターの既存の試験が、アイデア創出スキルを足す前と同じく通る。

## 7. 試験

### REQ-077 アイデア創出の試験

- 要件：アイデア創出スキルの試験では、次の2つを確かめる。
  - 柱で示したプロセスどおりにアイデアが作られたか。件数と形式だけでなく、中身も確かめる。例えば、調べる計画と調べ直しの記録があるか、掘り下げた作品に評価の裏づけがあるか、なぜの各段が前の段の答えになっていて根拠があるか、分析のファイルを分析したエージェントが書いたか、壁打ちの判定が3つの観点で根拠つきで書かれているか、柱3から後で制限を使っていないか。
  - できたアイデアが素晴らしいか。アイデアを作ったのとは別の AI が、いちばん近い既存のものを改めて探し、新しさ、役立つか、価値を判定する。ほぼ同じ既存のものが見つかった、困りごとに根拠がない、などのときは不合格にする。最後の判断は開発者が行う。
- 根拠：開発者の指示（2026-10-28）、憲章 第26条
- 受け入れ基準：
  - 流れの試験の結果に、柱ごとの中身の確認と、できたアイデアごとの良さの判定（いちばん近い既存のもの、3つの観点の判定と根拠、合否）がある。
  - 良さを判定する AI は、アイデアを作った回の記録の判定を見ずに、自分で既存のものを探している。
