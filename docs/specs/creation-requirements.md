# 作る流れの要件

ユーザーがクリエイターをインストールしてから、生成プラグインを受け取るまでに、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第5条、第12条〜第16条、第18条）。受け取った生成プラグインの振る舞いは、[出力の要件](output-requirements.md) で定める。受け取った生成プラグインを試験するときの振る舞いは、[試験の要件](test-requirements.md) で定める。

クリエイターが質問してユーザーからナレッジを引き出すやり取りを、ヒアリングと呼ぶ。

## 1. 使い始める

### REQ-023 クリエイターのインストール

- 要件：ユーザーは、クリエイターを Copilot CLI にインストールできる。インストールは、マーケットプレイスを通して行う（クリエイターのリポジトリかフォルダを `copilot plugin marketplace add` で登録し、`copilot plugin install plugin-creator@plugin-creator` でインストールする）。チャットで作業の自動化を頼むと、クリエイターの対話が始まる。使うには、次の準備が要る。この準備は、クリエイターの README に書かれている。
  - Copilot CLI の試験的機能を有効にする（初めて使うときに `copilot --experimental` で起動する。次からは付けなくてよい。起動した後なら `/settings experimental on`）。
  - クリエイターを読み込むときにチャットに出る確認を許可する。確認で、常に許可する選択肢（always allow）を選ぶと、同じ作業フォルダで次に起動したときは確認が出ない。

  準備をしていないときにチャットで頼むと、直し方が示され、対話は始まらない。

  クリエイターは、次のときにヒアリングの答えを推測で埋めず、止まる。README にも、この2つが書かれている。
  - 質問に答えが来なかったとき（質問を Ctrl+D で断った、Esc で閉じた、autopilot で動かしている）：何を聞きたかったかと、続けるやり方（チャットに答えを書く、autopilot を切る）を示して止まる。答えが来なかった項目は、まだ答えていないものとして扱う。
  - 質問のツール（`ask_user`）がない起動（`-p`、`--no-ask-user`）：直し方（これらを付けずに対話モードで起動する）を示し、ヒアリングを始めない。
- 根拠：憲章 第5条、第9条1項。Copilot CLI 1.0.98〜1.0.101 では、クリエイターの画面を出す仕組みは試験的機能で、有効にしないと使えない。フォルダを直接指定するインストール（`copilot plugin install <フォルダ>`）は、1.0.102 で「将来は廃止」と表示される。手元のフォルダのマーケットプレイスからインストールすると、この表示は出ず、フォルダはコピーされずにそのまま読まれる。`-p` と `--no-ask-user` では質問のツールがない。質問を断ったときと autopilot では、「ユーザーは不在なので自分で判断して進め、本当にあいまいなときだけ止まる」よう求める答えが返る（[ヒアリングの設計](../design/hearing.md) 2.1）
- 受け入れ基準：
  - Copilot CLI でクリエイターをインストールできる。
  - README の準備をしてチャットで作業の自動化を頼むと、クリエイターがナレッジを引き出す質問を始める。
  - README に、上の準備と、答えが来ないときと質問のツールがない起動での振る舞いが書かれている。
  - 準備をしていないときにチャットで頼むと、直し方が示される。
  - 質問を Ctrl+D で断るか Esc で閉じると、聞きたかったことと続けるやり方が示されて止まり、生成されない。
  - autopilot で頼むと、聞きたかったことと続けるやり方が示されて止まり、生成されない。
  - `-p` か `--no-ask-user` を付けて起動して頼むと、直し方が示され、ヒアリングが始まらない。

### REQ-037 会話例

- 要件：ユーザーは、クリエイターと模擬のユーザーのやり取りの例（会話例）を読める。会話例は、クリエイターの試験（外側の EVAL）で点数の高かった会話で、次が載っている。
  - 模擬のユーザーの最初の頼み方
  - クリエイターの質問と、模擬のユーザーの答えの全文
  - 模擬のユーザーが聞かれないと話さないことにしていた決まりと、それを引き出した質問の印
  - 試験の条件と点数

  会話例の初めには、AI が演じたユーザーとの会話であることと、クリエイターのどの版の会話かが書いてある。会話例は、クリエイターの版を上げるたびに、その版の試験の会話から作り直される。会話例は、クリエイターの README から開けるページと、クリエイターの画面（REQ-044）の両方で見られる。どちらも同じファイルである。
- 根拠：憲章 最大の目的、第9条1項／ナレッジ「ユーザー役の AI で人を模擬するときの注意」／[試験の設計](../design/testing.md) 6章。ユーザーは、何を伝えればよいか分からず不安になることがある。うまくいったやり取りを見れば、何を伝えればよいかが分かり、どんな試験をしたかも分かる
- 受け入れ基準：
  - クリエイターの README から会話例を開ける。
  - クリエイターの画面から、同じ会話例を開ける。
  - 会話例に、上の4つが載っている。
  - 会話例の初めに、AI が演じたユーザーとの会話であることと、クリエイターの版が書いてある。
  - 会話例に書かれた版が、今のクリエイターの版と同じである。

## 2. ナレッジを引き出す

### REQ-015 項目ごとの質問

- 要件：クリエイターは、次の項目を、項目ごとにユーザーに質問する。答えがあいまいなときは、具体的に聞き直す。
  - 作業の目的
  - 頼む場面と言い方
  - 受け取るもの
  - 進め方
  - 成果物
  - 合否の決め方
  - 決まった書き方やルール
  - 守らないと困ること
  - 使う道具と環境（ツール、コマンド、外部のシステム）
  - いつもと違うとき（例外的な場合、困ったときの扱い）

  ファイルや前回の1回の話から分かった項目は、分かったことを示して、違うところと足りないところを聞く。この聞き方も、その項目を質問したことに数える。

  ユーザーが疲れや急ぎの様子（「早く」「まだ？」と言う、答えが短くなる）を見せたら、クリエイターは残りの項目を示し、次の3つから選んでもらう。どれを選んでも、残りの項目は飛ばさない。
  - このまま続ける
  - 残りを手早く聞く（1項目に1問、聞き直しは1回まで）
  - ここでやめて後で続ける

  やめるときは、前の会話に戻って続けるやり方（Copilot CLI を `--continue` を付けて起動する）が示される。

  ユーザーが「質問しないで作って」のように、聞かずに作るようはっきり頼んだときも、クリエイターは推測で埋めて作らない。聞かないと仕事の決まりが生成プラグインに入らないことを1文で伝え、上と同じ3つから選んでもらう。このときは「ここでやめて後で続ける」をおすすめとして示す。
- 根拠：憲章 第4条、第23条／ナレッジ「人からナレッジを引き出す手法」（インタビュー）、「スキル」、「実例：組み込み機器のプリントデバッグ」／SWEBOK の要求の出どころ（目的、業務のルール、動かす環境）／Anthropic の skill-creator（呼ばれる場面、出力の形、例外的な場合、成功の基準、依存するもの）／文字のチャットでのヒアリングは対面より時間がかかり、疲れると「はい」と答えやすくなる（[ヒアリングの設計](../design/hearing.md) 5.6）
- 受け入れ基準：
  - 対話の中で、上の項目がすべて質問されている。分かったことを示して、違うところと足りないところを聞いた項目も、質問されたものとする。
  - 「普通の書き方です」のようなあいまいな答えには、具体的に聞き直している。
  - 疲れや急ぎの様子を見せると、残りの項目と、3つの選び方が示される。
  - 手早く聞くことを選んでも、残りの項目がすべて質問される。
  - やめることを選ぶと、続けるやり方が示される。`--continue` を付けて起動し直すと、やめたところから続く。
  - 「質問しないで作って」と頼むと、聞かないと仕事の決まりが入らないことと、3つの選び方（「ここでやめて後で続ける」がおすすめ）が示される。推測で埋めて生成されない。

### REQ-016 実際の1回をたどる

- 要件：クリエイターは、ユーザーに、最近実際にやった1回の作業を、最初から順に話してもらう。話の中に出てきた手順や決まりのうち、まだ聞いていないものを、その場で聞く。まだやったことのない作業では、「初めてやるとしたら、最初に何をしますか」と聞き、想定の1回を順に話してもらう。

  最初の頼みの文に作業の流れが順を追って書かれているときは、クリエイターは、頼みの文から理解した流れを質問の中に示し、最近実際にやった1回でしたことのうち、その流れに書かれていないことだけを聞く。頼みの文に書かれた流れを、もう一度書くようには求めない。まだやったことのない作業では、初めてやるとしたら、その流れのほかに何をするかを聞く。
- 根拠：憲章 第4条、第9条1項／ナレッジ「人からナレッジを引き出す手法」（シナリオ）。本人が当たり前だと思っていることは、項目ごとの質問では話されにくい。頼みの文に書いた流れを最初から書くよう求められると、ユーザーは頼みの文が伝わっていないと受け取る（[試験の設計](../design/testing.md) 6.7 の試験で、ユーザーが頼みの文をもう一度貼り付けた）
- 受け入れ基準：
  - 対話の中で、実際の1回をたどってもらう質問がある。
  - 項目ごとの質問では出てこない、その分野に固有の決まりも、生成プラグインに組み込まれる。
  - まだやったことがないと答えると、想定の1回をたどってもらう質問がある。
  - 頼みの文に作業の流れを順に書いて頼むと、その流れが質問の中に示され、その流れに書かれていないことを聞かれる。頼みの文に書いた流れを、最初から書くようには聞かれない。

### REQ-017 ファイルを読んで確かめる

- 要件：ユーザーが過去の成果物や作業のファイルを示すと、クリエイターはそれを読み、そこから分かる決まりを「〜という決まりですか？」とユーザーに確かめる。確かめて正しいと答えられたものだけを、ナレッジとして使う。
- 根拠：憲章 第4条／Anthropic の skill-creator（例のファイルを聞く）
- 受け入れ基準：
  - 示したファイルから読み取った決まりが、確認の質問として示される。
  - 違うと答えた決まりは、生成プラグインに組み込まれない。

### REQ-026 画面で設定したいこと・見たいこと

- 要件：クリエイターは、生成プラグインの Web管理画面について、次を質問する。答えは、画面のうち作業ごとに違う部分になる（REQ-031）。
  - 開始前に設定したいこと
  - 実行中に見たいこと
  - 終わった後に見たい結果と、その見せ方

  答えは、クリエイターが用意した画面の部品（入力欄、値の一覧、表、進み具合、文章、画像、ファイルへのリンク）の中で決め、生成する前の見本（REQ-027）で確かめる。用意のない表示を望まれたときは、近い部品が示される。
- 根拠：憲章 最大の目的、第15条1項〜3項、第20条〜第22条
- 受け入れ基準：
  - 対話の中で、上の3つが質問されている。
  - 答えた設定と表示が、生成プラグインの Web管理画面にある。
  - 用意のない表示を望むと、近い部品が示される。

## 3. 既存の資産を探す

### REQ-018 ユーザーの資産

- 要件：クリエイターは、生成プラグインに使えるユーザーの資産（テンプレート、スクリプト、過去の成果物など）がないかを質問する。あるものは、生成プラグインで流用する。
- 根拠：憲章 第12条2項・4項／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 対話の中で、既存の資産を聞く質問がある。
  - ユーザーが示した資産が、生成プラグインに組み込まれて使われる。

### REQ-019 標準機能と公開のプラグイン

- 要件：クリエイターは、作業の一部が Copilot CLI の標準機能や、公開されているプラグイン（Awesome Copilot など）で済まないかを調べる。使えるものがあれば、ユーザーに示し、使うかどうかを選んでもらう。自作するのは、それでも足りない部分だけにする。
- 根拠：憲章 第12条3項・4項／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 標準機能や公開のプラグインで済む部分があるとき、それがユーザーに示される。
  - ユーザーが使うと選んだものは、自作されない。

## 4. 確かめてから作る

### REQ-020 生成する前の確認

- 要件：生成する前に、クリエイターは、引き出したナレッジの一覧と、生成プラグインの振る舞いの案（何を受け取り、どう進め、何を成果物にし、何で合否を判定するか）と、EVAL の課題と合否の基準（REQ-038）を示す。これらは、クリエイターの画面でも見られる（REQ-044）。ユーザーが直したり足したりして、よいと答えてから生成する。ユーザーが直したときは、指摘の文言をそのまま残さず、目的に沿って案を直す。
- 根拠：憲章 第4条、第7条、第9条2項、第17条1項、第18条／ナレッジ「人からナレッジを引き出す手法」（試作品）、「人間と AI のコミュニケーション」。振る舞いの案は、生成プラグインの仕様に当たる
- 受け入れ基準：
  - 生成の前に、ナレッジの一覧、振る舞いの案、EVAL の課題と合否の基準が示される。
  - ユーザーが直した内容が、生成プラグインに反映される。
  - ユーザーがよいと答えるまで、生成されない。
  - 直した後の案に、「〜ではない」のように指摘を打ち消すだけの文がない。

### REQ-027 画面の見本

- 要件：生成する前の確認（REQ-020）で、クリエイターは、Web管理画面の見本をブラウザーで開いて見せる。見本には仮のデータが入っていて、作業ごとに違う部分（REQ-026）も入っている。ユーザーが直したり足したりしたら、見本を直して見せ直す。
- 根拠：憲章 第15条／ナレッジ「人からナレッジを引き出す手法」（試作品）。画面は、文章では良し悪しを判断しにくい
- 受け入れ基準：
  - 生成の前に、Web管理画面の見本がブラウザーで示される。
  - 見本に、ユーザーと決めた作業ごとの設定と表示が入っている。
  - 見本を見てユーザーが直した内容が、生成プラグインの画面に反映される。

## 5. 受け取る

### REQ-021 作る場所

- 要件：生成プラグインは、今の作業フォルダの中の新しいフォルダに、git のリポジトリとして作られる。生成プラグインのファイルは、作業フォルダの外には作られない。クリエイターがヒアリングの途中経過を残す記録は、Copilot CLI の設定フォルダの中に置かれ、手元の外には出ない。クリエイターは、生成プラグインを GitHub に公開するなど、手元の外に出る操作をしない。GitHub のリポジトリは、ユーザーが作る。ユーザーが承認した質問の改善案の起票（REQ-049）だけは、クリエイターが行う。
- 根拠：憲章 第6条1項、第24条2項
- 受け入れ基準：
  - 作業フォルダの中に、git のリポジトリとして生成プラグインのフォルダができる。
  - 生成したとき、作業フォルダの外や GitHub には、生成プラグインのファイルが何も作られない。
  - ヒアリングの途中経過の記録は、Copilot CLI の設定フォルダの中にだけ作られる。

### REQ-022 できたことの説明

- 要件：生成が終わると、クリエイターは次を示す。
  - 生成プラグインのフォルダの場所
  - 組み込んだナレッジ
  - 流用した資産。公開のプラグインを使うときは、そのプラグインの入れ方
  - 生成プラグインが自分のリポジトリに Issue を起票できるようにする手順（GitHub に公開し、マニフェストの `repository` にそのリポジトリを書き、書いた後の `plugin.json` を Copilot CLI に読ませ、gh を入れてログインする。[出力の要件](output-requirements.md) REQ-014）
  - 構造の検査と部品の試験の結果（REQ-039）
  - 試験のしかた。構造の検査と部品の試験は、生成プラグインのリポジトリの1つのコマンドで動かせること。EVAL は、クリエイターに試験を頼むと行われ、AI クレジットを使うこと（[試験の要件](test-requirements.md)）
- 根拠：憲章 第4条、第12条、第17条、第24条2項
- 受け入れ基準：
  - 生成の後に、上の6つが示される。

### REQ-028 費用の低いモデルでも同じ画面

- 要件：ユーザーが Copilot CLI で費用の低いモデルを選んでも、生成プラグインの Web管理画面は、思考力の高いモデルを選んだときと同じ品質でできる。画面のファイルを書く仕事は、どちらのときも費用の低いモデルで行われる（REQ-046）。
- 根拠：憲章 第15条1項・2項、第16条2項／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - Copilot CLI で費用の低いモデルを選んだときも、思考力の高いモデルを選んだときも、生成プラグインの Web管理画面が、出力の要件のうち画面に関わる要件（REQ-005〜REQ-009、REQ-012、REQ-029〜REQ-031）の受け入れ基準をすべて満たす。

## 6. 既存のプラグインを作り直す

ユーザーが既存のプラグインを示したときの振る舞いを定める。ここに書いていないことは、1〜5と同じである。

### REQ-032 作り直しを頼む

- 要件：ユーザーは、チャットで手元の既存のプラグインのフォルダを示して、作り直しを頼める。受け取るのは、Copilot CLI で読み込めるプラグイン（Agent Plugins の形式と、Copilot CLI の以前の形式）である。GitHub にあるプラグインは、ユーザーが先に手元へ取ってくる。
- 根拠：憲章 第4条、第13条1項／Copilot CLI プラグインリファレンス
- 受け入れ基準：
  - フォルダを示して作り直しを頼むと、クリエイターがそのプラグインを読み、作り直しの対話を始める。
  - Agent Plugins の形式のプラグインも、以前の形式のプラグインも作り直せる。

### REQ-033 読み取ったことを確かめる

- 要件：クリエイターは、既存のプラグインを読み、次を示して確かめる。
  - できていたこと（何を頼むと、何をするか）の一覧。最初はすべて引き継ぐことにしておき、ユーザーが要らないと答えたものだけを外す。
  - 読み取った決まり。「〜という決まりですか？」と確かめ、正しいと答えられたものだけをナレッジとして使う（REQ-017 と同じ）。
- 根拠：憲章 第10条、第13条2項
- 受け入れ基準：
  - できていたことの一覧が示される。
  - 要らないと答えたものは、作り直したプラグインにない。それ以外は、作り直した後もできる。
  - 読み取った決まりが確認の質問として示され、違うと答えた決まりは組み込まれない。

### REQ-034 足りないナレッジを聞く

- 要件：クリエイターは、既存のプラグインから読み取って確かめた項目を、項目ごとの質問（REQ-015）で聞き直さない。分からなかった項目だけを質問する。実際の1回をたどる質問（REQ-016）と、画面で設定したいこと・見たいことの質問（REQ-026）は、作り直しでも行う。プラグインに書かれていない、本人には当たり前のことを引き出すためである。
- 根拠：憲章 第13条2項／ナレッジ「人からナレッジを引き出す手法」
- 受け入れ基準：
  - 読み取って確かめた項目を、もう一度質問しない。
  - 実際の1回をたどる質問と、画面で設定したいこと・見たいことの質問がある。

### REQ-035 引き継ぐことと変わることの確認

- 要件：生成する前の確認（REQ-020）で、クリエイターは、作り直しのときは次も示す。
  - 引き継ぐこと（できていたことと、流用する部品。既存のスクリプトや MCP サーバーなどのうち、作り直した後も使えるものは、作り直さずに流用する）
  - 変わること（生成プラグインの条項を満たすために、足したり変えたりすること。例：統括・作業・検証のエージェントに分かれる、Web管理画面が付く）
- 根拠：憲章 第12条4項、第13条1項
- 受け入れ基準：
  - 生成の前に、引き継ぐことと変わることが示される。
  - 流用すると示した部品は、作り直されていない。

### REQ-036 作り直したプラグインの受け取り

- 要件：作り直したプラグインは、REQ-021 と同じく、作業フォルダの中の新しいフォルダに作られる。元のプラグインのフォルダは変えない。できたことの説明（REQ-022）では、元のプラグインから変わったことと、作り直したものを元のリポジトリに入れ替えるやり方も示す。
- 根拠：憲章 第13条1項
- 受け入れ基準：
  - 作業フォルダの中に、git のリポジトリとして新しいフォルダができる。
  - 元のプラグインのフォルダの中身が、作り直しの前と後で変わっていない。
  - 生成の後に、変わったことと、元のリポジトリに入れ替えるやり方が示される。

## 8. クリエイターの画面

### REQ-043 決まったことの一覧

- 要件：クリエイターとの対話が始まると（作る対話でも、試験を頼んだときでも）、チャットにクリエイターの画面の URL が示される。ユーザーはブラウザーでこの画面を開き、対話で決まったこと（引き出したナレッジと、流用する資産）の一覧を見られる。一覧は、対話が進むと、ページを再読み込みしなくても増える。項目ごとの質問（REQ-015）の項目のうち、まだ聞いていないものも分かる。画面は見るだけで、答えや直しはチャットで行う。画面には仕事のナレッジや資産の情報が出るので、Copilot CLI を動かしているマシンのブラウザーからしか開けない。
- 根拠：憲章 第18条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」（ユーザーの方針）
- 受け入れ基準：
  - 対話が始まると、チャットに URL が示され、開くと画面が表示される。
  - チャットで答えて決まったことが、再読み込みしなくても一覧に出る。
  - まだ聞いていない項目が、聞いた項目と分けて示される。
  - 生成する前の確認（REQ-020）で示すナレッジの一覧と、画面の一覧の中身が同じである。
  - 画面には、答えや直しを入力する欄がない。
  - 同じマシンのブラウザーからは開け、ほかのマシンからは開けない。
  - Copilot CLI を終えると、クリエイターの画面のサーバーのプロセスが残らない。

### REQ-044 画面で見られるもの

- 要件：クリエイターの画面では、一覧（REQ-043）に加えて、次を見られる。
  - 生成する前の確認（REQ-020）で示すもの：ナレッジの一覧、振る舞いの案、Web管理画面の見本（REQ-027）、EVAL の課題と合否の基準（REQ-038）
  - 生成プラグインの試験の結果（REQ-039〜REQ-042）
  - 会話例（REQ-037）

  よいと答えることや、試験を頼むことは、チャットで行う。試験の案内（次に何をすればよいか）も、チャットで示す。
- 根拠：憲章 最大の目的、第9条1項、第18条
- 受け入れ基準：
  - 生成する前の確認のとき、上の確認で示すものが、すべて画面で見られる。
  - 試験を行うと、その結果が画面で見られる。構造の検査と部品の試験は段階ごとの合否が、EVAL は基準ごとの合否、あり・なしの点数とその差、使った AI クレジットが見られる。
  - 画面から会話例を開ける。

## 9. モデルの使い分け

クリエイターの仕事を、推論の重さに合わせて、どのモデルで行うかを定める（憲章 第16条）。

### REQ-045 対話のモデル

- 要件：ユーザーとの対話（質問、生成する前の確認、できたことの説明）と、作る中で高い推論力が要る判断（生成プラグインの部品の分け方など）は、ユーザーが Copilot CLI で選んだモデルで行われる。ユーザーは、選ぶモデルを変えれば、これらを行うモデルを変えられる。
- 根拠：憲章 第16条2項／Copilot CLI コマンドリファレンス（`/model`）
- 受け入れ基準：
  - 実行の記録で、ユーザーへの質問、生成する前の確認、できたことの説明、部品の分け方の判断が、ユーザーが選んだモデルで行われている。
  - 選ぶモデルを変えて始めると、変えたモデルで対話が行われる。

### REQ-046 ファイルを書くモデル

- 要件：生成する前の確認で決まった内容に沿って、生成プラグインのファイルを書く仕事は、ユーザーが選んだモデルによらず、費用の低いモデルで行われる。ただし、ユーザーがモデルを Auto（Copilot CLI がモデルを自動で選ぶ設定）にしているときは、この仕事も Auto が選んだモデルで行われる。
- 根拠：憲章 第16条2項／ナレッジ「マルチエージェントの強み」（AI クレジットの最適化）／Copilot CLI コマンドリファレンス（カスタムエージェントのモデル。モデルが Auto のときは、サブエージェントも同じモデルになる）
- 受け入れ基準：
  - Auto 以外のどのモデルを選んで生成しても、実行の記録で、生成プラグインのファイルを書く仕事が、費用の低いモデルで行われている。

### REQ-047 モデルの選び方の説明

- 要件：ユーザーがクリエイターの説明書き（README）を読むと、次が書かれている。モデルの選び方は、この説明書きで知らせ、対話の中では知らせない。
  - 仕様を決める対話には、思考力の高いモデルが向いていること
  - モデルは `/model` で変えられること
  - モデルを Auto にしていると、ファイルを書く仕事も同じモデルになること
- 根拠：憲章 第9条1項、第16条2項
- 受け入れ基準：
  - README に、上の3つが書かれている。
  - 対話の中で、モデルの選び方が示されない。

## 10. 質問の改善

### REQ-049 質問の改善案

- 要件：生成が終わったときと、ユーザーに頼まれた試験（[試験の要件](test-requirements.md)）が終わったとき、クリエイターは、対話の記録と試験の結果を振り返り、自分の質問の足りなかったところを、次の観点で洗い出す。
  - その項目をヒアリングしたのに出ず、後からユーザーが自分から話したことと、生成する前の確認で足されたこと（ヒアリングで引き出せなかったこと）
  - 聞き直しが続いた質問や、ユーザーが「分からない」と答えた質問
  - 試験で不合格になった原因のうち、ナレッジが足りなかったもの
  - ユーザーが生成プラグインを直した内容のうち、対話で聞いていれば入ったもの

  見つかったときは、クリエイターのリポジトリ（plugin-creator）に起票する Issue の案（タイトルと本文）を示す。案には、質問の何が足りなかったかだけを書き、ユーザーの仕事の中身（引き出したナレッジや資産の内容）は書かない。ユーザーが案ごとに承認すると、その案が Issue として起票される。
- 根拠：憲章 第14条、第9条1項／ナレッジ「プラグインを作るプラグイン（ハーネスの作り方）」（質問は改善し続ける）。Issue は公開のリポジトリに載ることがあるので、仕事の中身を書かない
- 受け入れ基準：
  - 生成プラグインに入れることになったナレッジのうち、その項目をヒアリングした後にユーザーが自分から話したものか、生成する前の確認で足されたものがあると、生成の後に、それを引き出すヒアリングが足りなかったことを書いた Issue の案が示される。
  - その項目をヒアリングする前にユーザーが自分から話したナレッジ（最初の頼みの中のものなど）だけでは、ヒアリングで引き出せなかったことの Issue の案は示されない。
  - 案に、ユーザーの仕事の中身が書かれていない。
  - 承認した案は、plugin-creator に Issue として作られる。承認していない案は、作られない。
