# 改善・設計変更の要件

ユーザーが手元の既存のプラグインを示して、機能を足したり設計を変えたりするよう頼んだとき、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第11条〜第13条、第17条、第18条）。新しいフォルダに作り直すときの振る舞いは、[作る流れの要件](creation-requirements.md) 6章で定める。ここに書いていないことは、[作る流れの要件](creation-requirements.md) と [試験の要件](test-requirements.md) と同じである。

この文書では、示された既存のプラグインを「元のプラグイン」と呼ぶ。また、クリエイターが作った生成プラグインに入っている、ヒアリングで確かめた決まりの一覧を「決まりの一覧」と呼ぶ。

## 1. 頼む

### REQ-052 改善・設計変更を頼む

- 要件：ユーザーは、チャットで元のプラグインのフォルダを示し、足したい機能や変えたい設計を伝えて、改善・設計変更を頼める。`/plugin-creator:change-plugin` と打っても始められる。
  - 受け付ける元のプラグインは、Copilot CLI で読み込めるプラグイン（Agent Plugins の形式と、Copilot CLI の以前の形式）である。クリエイターが作った生成プラグインでなくてもよい。
  - 受け付ける変更は、次の3つである。
    - スキルと、Web管理画面の設定項目・表示の追加と変更
    - エージェントの組み方の変更（作業エージェントの追加、役割の分け直し）
    - ユーザーが要らないと言った機能を消すこと
  - 次の変更は受け付けず、理由を示す。Web管理画面の表示の頼みでは、用意した部品のうち近いものを示す（REQ-026 と同じ）。
    - 生成プラグインの条項に反する変更（例：検証エージェントをなくす）
    - どの生成プラグインにも共通する部分を、そのプラグインだけ変えること（例：Web管理画面の共通部分の配色）
  - 頼みが、新しいフォルダへの作り直しか、元のフォルダを直す改善・設計変更か分からないとき（例：フォルダを示して「作り直したい」とだけ頼まれた）は、どちらにするかを聞く。

  使うための準備と、答えが来ないときや質問のツールがない起動での振る舞いは、作る対話（REQ-023）と同じである。頼み方は、クリエイターの README に書かれている。
- 根拠：憲章 第4条、第13条1項、第19条
- 受け入れ基準：
  - フォルダを示して「このプラグインに〇〇のスキルを足したい」と頼むと、改善・設計変更の対話が始まる。新しく作る対話と、新しいフォルダへの作り直しの対話は始まらない。
  - `/plugin-creator:change-plugin` と打っても始められる。
  - クリエイターが作っていないプラグインを示しても、改善・設計変更の対話が始まる。
  - 作業エージェントを足す頼みを受け付ける。
  - 検証エージェントをなくす頼みと、Web管理画面の共通部分の配色を変える頼みは受け付けられず、理由が示される。
  - フォルダを示して「作り直したい」とだけ頼むと、元のフォルダを直すか新しいフォルダに作るかを聞かれる。
  - README に、改善・設計変更の頼み方が書かれている。

### REQ-053 始める前の確かめ

- 要件：クリエイターは、対話を始めるときと、直し始める直前に、元のプラグインのフォルダについて次を確かめる。満たさないときは、直し方を示して止まる。止まっても、フォルダの中身は変わらない。
  - Copilot CLI を起動したフォルダの中にある。外にあるときは、元のプラグインのフォルダか、それを含むフォルダで Copilot CLI を起動し直すよう示す。直している途中で、フォルダの許可の確認が何度も出たり、断られて止まったりしないためである。
  - Copilot CLI がインストールやマーケットプレイスのために持っているプラグインの写しではない。写しのときは、元のリポジトリを手元に取ってきて、そのフォルダを示すよう示す。写しを直しても、Copilot CLI がプラグインを更新すると消えるためである。
  - git のリポジトリの中にあり、フォルダのファイルが git で管理されている（.gitignore で外されていない）。
  - フォルダの中に、まだコミットしていない変更（変えたファイル、git add しただけのファイル、git に入れていないファイル）がない。確かめるのはフォルダの中だけで、同じリポジトリのほかのフォルダの変更は確かめない。

  直す前の状態に git で戻せるようにするためである。
- 根拠：憲章 第13条1項／Copilot CLI のフォルダの許可（起動したフォルダの中だけが、確認なしで読み書きできる）
- 受け入れ基準：
  - Copilot CLI を起動したフォルダの外にあるプラグインを示すと、起動し直すやり方が示されて止まる。
  - インストールされたプラグインの写しのフォルダを示すと、元のリポジトリを示すよう示されて止まる。
  - git のリポジトリの外にあるプラグインと、.gitignore で外されたフォルダのプラグインを示すと、直し方が示されて止まる。
  - フォルダの中に、コミットしていない変更か git に入れていないファイルがあると、直し方が示されて止まる。
  - 同じリポジトリのほかのフォルダにだけコミットしていない変更があるときは、止まらずに始まる。
  - 止まったとき、フォルダの中身は変わっていない。

## 2. 今のプラグインを確かめる

### REQ-054 読み取ったことを確かめる

- 要件：クリエイターは、元のプラグインを読み、次を示して確かめる。
  - できていたこと（何を頼むと、何をするか）の一覧。すべて引き継ぐ。機能を消すのは、ユーザーが消したいと頼んだものだけで、機能ごとに要るかどうかは聞かない。
  - 決まり。
    - 元のプラグインがクリエイターの作った生成プラグインのときは、決まりの一覧をまとめて示し、違うものと古くなったものを1回の問いで聞く。違う・古いと答えた決まりは、今はどうかを聞いて直すか、外す。
    - 生成プラグインのファイルに、決まりの一覧にない決まりが書かれているとき（作った後にユーザーが書き足したものなど）は、その決まりを「〜という決まりですか？」と1件ずつ確かめる。正しいと答えられたものは、決まりの一覧に足す。
    - クリエイターが作っていないプラグインのときは、読み取った決まりを「〜という決まりですか？」と1件ずつ確かめ、正しいと答えられたものだけを使う（REQ-017 と同じ）。
- 根拠：憲章 第10条、第13条2項
- 受け入れ基準：
  - できていたことの一覧が示される。機能ごとに要るかどうかは聞かれない。
  - 消したいと頼んだ機能は、直した後のプラグインにない。それ以外は、直した後もできる。
  - クリエイターが作った生成プラグインでは、決まりの一覧が1回の問いで示される。違うと答えた決まりは、答えたとおりに直されるか、外される。
  - 作った後に決まりを書き足した生成プラグインでは、書き足した決まりが1件ずつ確認の質問として示される。正しいと答えた決まりは、直した後のプラグインと決まりの一覧に入っている。違うと答えた決まりは入っていない。
  - クリエイターが作っていないプラグインでは、読み取った決まりが1件ずつ確認の質問として示され、違うと答えた決まりは組み込まれない。

### REQ-055 既存のスキルを取り込む

- 要件：ユーザーが、組み込みたい既存のスキル（例：今使っているクロスコンパイルやデプロイのスキル）の場所を示すと、クリエイターはそれを読み、そこから分かる決まりを「〜という決まりですか？」と確かめる。正しいと答えられた決まりを、プラグインのルールのスキルに書き直して組み込み、その作業をするエージェントがそのスキルに従うようにする。
  - 書き直したスキルは、単体でも使える（[出力の要件](output-requirements.md) REQ-062）。
  - プラグインのスキルの名前は、示されたスキルの名前と重ならないようにする。同じ名前だと、示されたスキルが読み込まれている作業フォルダで、プラグインのスキルが使われないためである。
  - スキルに付いたスクリプトなどのファイルは、ユーザーの資産（REQ-018）として流用する。
  - 示されたスキルのフォルダの中身は変えない。
- 根拠：憲章 第12条2項・4項、第13条2項
- 受け入れ基準：
  - 示したスキルから読み取った決まりが、確認の質問として示される。
  - 正しいと答えた決まりが、直した後のプラグインのルールのスキルに入っている。違うと答えた決まりは入っていない。
  - 直した後のプラグインで作業すると、取り込んだ決まりに沿ってその作業（例：ビルド、デプロイ）が行われる。
  - プラグインのスキルの名前が、示したスキルの名前と違う。
  - 書き直したスキルの仕事を、統括エージェントを始めずにチャットで頼むと、取り込んだ決まりどおりに行われる。
  - 示したスキルのフォルダの中身が、改善・設計変更の前と後で変わっていない。

## 3. 足りないナレッジを聞く

### REQ-056 変えるところだけ聞く

- 要件：クリエイターは、変えるところについてだけ聞く。変えないところは、確かめた決まり（REQ-054）で済ませ、聞き直さない。
  - 変えるところに関わる作業の、最近実際にやった1回を、最初から順に話してもらう（REQ-016 の聞き方）。
  - 項目ごとの質問（REQ-015）は、変えるところに関わる項目のうち、まだ分からないものだけを聞く。
  - 画面で設定したいこと・見たいことの質問（REQ-026）は、Web管理画面の設定項目や表示を変えるときだけ聞く。

  クリエイターが作っていないプラグインのときは、生成プラグインの形にすること自体が変えるところになる。そのため、作業の最初から最後までの実際の1回と、画面の質問を行う。

  クリエイターの画面（REQ-043）では、変えないので聞かない項目を、まだ聞いていない項目と分けて示す。
- 根拠：憲章 第13条2項、第18条／ナレッジ「人からナレッジを引き出す手法」。本人が当たり前だと思っている手順は、実際の1回をたどらないと話されにくい
- 受け入れ基準：
  - 変えないところについて、もう一度質問しない。
  - 変えるところについて、実際の1回をたどる質問がある。
  - Web管理画面を変えない改善・設計変更では、画面の質問がない。
  - クリエイターが作っていないプラグインでは、作業の最初から最後までの実際の1回をたどる質問と、画面の質問がある。
  - クリエイターの画面で、変えないので聞かない項目が、まだ聞いていない項目と分けて示される。

## 4. 確かめてから直す

### REQ-057 直す前の確認

- 要件：直す前に、クリエイターは、生成する前の確認（REQ-020）と同じもの（決まりの一覧、振る舞いの案、EVAL の課題と合否の基準〔REQ-061〕）に加えて、次を示す。これらは、クリエイターの画面でも見られる（REQ-044）。
  - 引き継ぐこと（できていたこと、確かめた決まり、流用する部品）
  - 変わること（足したり変えたりするスキル、設定項目、エージェントの役割、消す機能、足す決まり・直す決まり・外す決まり）
  - クリエイターが作っていないプラグインのときは、生成プラグインの条項を満たすために足したり変えたりすること（REQ-035 と同じ。例：統括・作業・検証のエージェントに分かれる、Web管理画面が付く、憲章・仕様書・設計書・試験が足される）と、形式を移したために読まれなくなり消すファイル
  - 共通の土台（どの生成プラグインにも共通する部分。[生成プラグインの構造](../design/generated-plugin-structure.md) の「土台」）を今の版に上げることと、それで変わること（元のプラグインの土台が今の版と違うとき）
  - 新しい版の案（`plugin.json` の version）

  Web管理画面の設定項目や表示を変えるときは、見本（REQ-027）も示す。ユーザーが直したり足したりして、よいと答えてから直す。版は、ユーザーがよいと答えた版にする。
- 根拠：憲章 第7条、第13条1項、第15条2項、第17条1項、第18条
- 受け入れ基準：
  - 直す前に、上のものがすべて示され、クリエイターの画面でも見られる。
  - ユーザーがよいと答えるまで、元のプラグインのフォルダの中で git が管理するファイルは変わらない（作業用の一時フォルダは除く。REQ-059）。
  - 引き継ぐと示した部品は、確認で示した変更のほかは変わっていない。
  - 直した後のプラグインの version が、ユーザーがよいと答えた版になっている。

### REQ-058 決まりの番号

- 要件：改善・設計変更の後も、引き継いだ決まりの番号は変わらない。プラグインの中で番号を指している箇所が、別の決まりを指さないようにするためである。
  - 足した決まり（REQ-054 で一覧に足したものを含む）には、これまでに使ったどの番号（前の改善・設計変更で外した番号を含む）よりも後の番号が付く。
  - 中身を直した決まりは、元の番号を外し、新しい番号を付ける。古い番号を指したままの箇所が、構造の検査で見つかるようにするためである。
  - 外した番号は、ほかの決まりに使わない。
- 根拠：憲章 第6条3項、第17条1項
- 受け入れ基準：
  - 引き継いだ決まりの番号が、直す前と同じである。
  - 足した決まりと中身を直した決まりの番号が、直す前の番号とも、前の改善・設計変更で外した番号とも重ならない。
  - 外した番号や、中身を直す前の番号を指したままの箇所があると、構造の検査が不合格になる。

## 5. 受け取る

### REQ-059 直す場所とコミット

- 要件：クリエイターは、元のプラグインのフォルダを直接直す。直した後のプラグインは、生成プラグインの条項を満たす（[出力の要件](output-requirements.md)）。共通の土台は今の版に上げ、プラグインの憲章・仕様書・設計書は、変えた内容に合わせて直す（ないときは作る）。
  - 試験と直しが終わったら（合格しても、上限の回数で止めても、試験をしなかったときも）、作るとき（REQ-039）と同じく、直した内容を元のプラグインのリポジトリにコミットする。コミットには、元のプラグインのフォルダの中のファイルだけを入れる。
  - 元のプラグインのフォルダの外のファイルは、作ったり変えたりしない。ただし、ヒアリングの途中経過の記録（REQ-021）、試験の道具（REQ-048）、作業用の一時フォルダ（Copilot CLI を起動したフォルダの `.plugin-creator-work/`。直す内容の下書きを置き、終わったら消す。コミットには入れない）は除く。
  - push など、手元の外に出る操作はしない。ユーザーが承認した質問の改善案の起票（REQ-049）だけは、クリエイターが行う。
- 根拠：憲章 第11条、第13条1項、第15条2項、第17条1項、第24条2項
- 受け入れ基準：
  - 新しいフォルダは作られず、元のプラグインのフォルダが直されている。
  - 直した後のプラグインが、出力の要件の受け入れ基準を満たす。
  - 直した後のプラグインの仕様書の要件から、設計書の箇所・実装資産・テストをたどれる（REQ-003）。
  - 直した内容がコミットされている。そのコミットを戻すと、直す前と同じ中身になる。
  - そのコミットに、元のプラグインのフォルダの外のファイルが入っていない。ほかのフォルダで git add してあった変更も入っていない。
  - 元のプラグインのフォルダの外で、ヒアリングの記録と試験の道具のほかに、作られたり変わったりしたファイルがない。作業用の一時フォルダは、終わった後に残っていない。
  - リモートのリポジトリに push されていない。

### REQ-060 直したことの説明

- 要件：直し終わると、クリエイターは次を示す。
  - 変わったこと
  - 足した決まり、直した決まり、外した決まり
  - 流用した資産。公開のプラグインを使うときは、そのプラグインの入れ方
  - 構造の検査と部品の試験の結果（REQ-039）。試験をしなかったときは、そのこと
  - コミットと、直す前に戻すやり方
  - 試験のしかた（REQ-022 と同じ）
  - 直したプラグインを Copilot CLI に読ませるやり方（入れ方ごとに。例：手元のフォルダのマーケットプレイスから入れたときは Copilot CLI を起動し直す。GitHub から入れたときは、ユーザーが push してから入れ直す）
  - マーケットプレイスの一覧にこのプラグインを載せているときは、一覧の版や説明を手で直す必要があること
  - 直した後のプラグインがまだ自分のリポジトリに Issue を起票できないときは、起票できるようにする手順（REQ-022 と同じ。[出力の要件](output-requirements.md) REQ-014）
  - クリエイターが作っていないプラグインに元からあったテストは残したことと、クリエイターの試験では動かしていないこと（元からあったとき）
- 根拠：憲章 第9条1項、第12条、第13条1項、第17条、第24条2項
- 受け入れ基準：
  - 直した後に、上のものが示される（「〜ときは」と書いたものは、そのときだけ）。

## 6. 試験

### REQ-061 変えたところの試験

- 要件：直した後、クリエイターは、作ったときと同じく構造の検査と部品の試験を行い、不合格なら直す（REQ-039）。EVAL の課題と合否の基準は、次のとおりにして、直す前の確認（REQ-057）で示し、プラグインのリポジトリに入れる。ユーザーが試験を頼むと（REQ-040）、これらの課題で EVAL が行われる。
  - 元のプラグインの課題と合否の基準は、確かめた決まりに合わせて引き継ぐ。元のプラグインに課題がないときは、作るとき（REQ-038）と同じく、実際の1回（REQ-056）と示したファイルから、作業全体を試す課題を作る。
  - 変えたところを試す課題と合否の基準を、1つ以上足す。取り込んだ決まり（REQ-055）に沿って作業したかを判定する基準を入れる。
  - 変えたところが本物の機器や外部のシステムに頼るとき（例：本物のツールチェーンでのビルド、機器への転送）は、手元のパソコンの中の擬似の機器で試す課題にする。EVAL は課題を何回も動かすので、本物の機器に何回も送らないためである。本物の手順そのものは試せないことを、直す前の確認で示す。
  - エージェントの組み方の変更のように、成果物が変わらない変更では、実行の記録で、決めたエージェントが決めた仕事をしたか（例：足した作業エージェントが動いたか）を見る基準を使う。
- 根拠：憲章 第17条1項・2項／[試験の設計](../design/testing.md) 7章
- 受け入れ基準：
  - 直した後に、構造の検査と部品の試験の合否が示される。
  - プラグインのリポジトリに、変えたところを試す課題と合否の基準が入っている。
  - 課題のなかった元のプラグインでは、作業全体を試す課題と合否の基準も入っている。
  - 変えたところを壊したプラグインで EVAL を行うと、足した課題の基準が不合格になる。
  - 本物の機器に頼る変更では、EVAL で本物の機器に何も送られない。そのことが直す前の確認で示されている。
