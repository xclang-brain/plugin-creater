# 改善・設計変更の要件

ユーザーが手元の既存のプラグインを示して、機能を足したり設計を変えたりするよう頼んだとき、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第11条〜第13条、第17条）。新しいフォルダに作り直すときの振る舞いは、[作る流れの要件](creation-requirements.md) 6章で定める。ここに書いていないことは、[作る流れの要件](creation-requirements.md) と [試験の要件](test-requirements.md) と同じである。

この文書では、示された既存のプラグインを「元のプラグイン」と呼ぶ。

## 1. 頼む

### REQ-052 改善・設計変更を頼む

- 要件：ユーザーは、チャットで元のプラグインのフォルダを示し、足したい機能や変えたい設計を伝えて、改善・設計変更を頼める。改善・設計変更は、作る対話とは別のスキル（`/plugin-creator:improve-plugin`）で行う。
  - 受け付ける元のプラグインは、Copilot CLI で読み込めるプラグイン（Agent Plugins の形式と、Copilot CLI の以前の形式）である。クリエイターが作った生成プラグインでなくてもよい。
  - 受け付ける変更は、スキルの追加と変更、Web管理画面の設定項目と表示の追加と変更、作業エージェントの追加や役割の分け直しなどの設計の変更である。
  - 生成プラグインの条項に反する変更（例：検証エージェントをなくす）は受け付けず、反する理由を示す。
  - 頼みが、新しいフォルダへの作り直しか、元のフォルダを直す改善・設計変更か分からないときは、クリエイターがどちらにするかを聞く。

  使うための準備と、答えが来ないときや質問のツールがない起動での振る舞いは、作る対話（REQ-023）と同じである。頼み方は、クリエイターの README に書かれている。
- 根拠：憲章 第4条、第13条1項、第19条／ナレッジ「スキル」（スキルが呼ばれるかは description で決まる）
- 受け入れ基準：
  - フォルダを示して「このプラグインに〇〇のスキルを足したい」と頼むと、改善・設計変更の対話が始まる。新しく作る対話と作り直しの対話は始まらない。
  - `/plugin-creator:improve-plugin` と打っても始められる。
  - クリエイターが作っていないプラグインを示しても、改善・設計変更の対話が始まる。
  - 作業エージェントを足す頼みを受け付ける。
  - 検証エージェントをなくす頼みは受け付けられず、理由が示される。
  - 作り直しか改善・設計変更か分からない頼みでは、どちらにするかを聞かれる。
  - README に、改善・設計変更の頼み方が書かれている。

### REQ-053 直す前の git の確かめ

- 要件：クリエイターは、対話を始めるときと、直し始める直前に、元のプラグインのフォルダが git のリポジトリの中にあり、まだコミットしていない変更がないことを確かめる。満たさないときは、直し方（git のリポジトリにしてコミットする、変更をコミットする）を示して止まる。直す前の状態に git で戻せるようにするためである。
- 根拠：憲章 第13条1項
- 受け入れ基準：
  - git のリポジトリの外にあるプラグインを示すと、直し方が示されて止まり、フォルダの中身は変わらない。
  - コミットしていない変更があるプラグインを示すと、直し方が示されて止まり、フォルダの中身は変わらない。

## 2. 今のプラグインを確かめる

### REQ-054 読み取ったことを確かめる

- 要件：クリエイターは、元のプラグインを読み、次を示して確かめる。
  - できていたこと（何を頼むと、何をするか）の一覧。最初はすべて引き継ぐことにしておき、ユーザーが要らないと答えたものだけを外す。
  - 決まり。
    - 元のプラグインがクリエイターの作った生成プラグインのときは、入っている決まりの一覧をまとめて示し、違うものと古くなったものを1回の問いで聞く。違う・古いと答えた決まりは、今はどうかを聞いて直すか、外す。
    - それ以外のプラグインのときは、読み取った決まりを「〜という決まりですか？」と1件ずつ確かめ、正しいと答えられたものだけを使う（REQ-017 と同じ）。
- 根拠：憲章 第10条、第13条2項
- 受け入れ基準：
  - できていたことの一覧が示される。要らないと答えたものは、直した後のプラグインにない。それ以外は、直した後もできる。
  - クリエイターが作った生成プラグインでは、決まりの一覧が1回の問いで示される。違うと答えた決まりは、答えたとおりに直されるか、外される。
  - それ以外のプラグインでは、読み取った決まりが1件ずつ確認の質問として示され、違うと答えた決まりは組み込まれない。

### REQ-055 既存のスキルを取り込む

- 要件：ユーザーが、組み込みたい既存のスキル（例：今使っているクロスコンパイルやデプロイのスキル）の場所を示すと、クリエイターはそれを読み、そこから分かる決まりを「〜という決まりですか？」と確かめる。正しいと答えられた決まりを、プラグインのスキルに書き直して組み込む。スキルに付いたスクリプトなどのファイルは、ユーザーの資産（REQ-018）として流用する。示されたスキルのフォルダの中身は変えない。
- 根拠：憲章 第12条2項・4項、第13条2項
- 受け入れ基準：
  - 示したスキルから読み取った決まりが、確認の質問として示される。
  - 正しいと答えた決まりが、直した後のプラグインのスキルに入っている。違うと答えた決まりは入っていない。
  - 示したスキルのフォルダの中身が、改善・設計変更の前と後で変わっていない。

## 3. 足りないナレッジを聞く

### REQ-056 変えるところだけ聞く

- 要件：クリエイターは、変えるところについてだけ聞く。変えないところは、確かめた決まり（REQ-054）で済ませ、聞き直さない。
  - 変えるところに関わる作業の、最近実際にやった1回を、最初から順に話してもらう（REQ-016 の聞き方）。
  - 項目ごとの質問（REQ-015）は、変えるところに関わる項目のうち、まだ分からないものだけを聞く。
  - 画面で設定したいこと・見たいことの質問（REQ-026）は、Web管理画面の設定項目や表示を変えるときだけ聞く。

  元のプラグインがクリエイターの作った生成プラグインでないときは、生成プラグインの形にすること自体が変えるところになるので、作り直し（REQ-034）と同じく、実際の1回と画面の質問を行う。
- 根拠：憲章 第13条2項／ナレッジ「人からナレッジを引き出す手法」。本人が当たり前だと思っている手順は、実際の1回をたどらないと話されにくい
- 受け入れ基準：
  - 変えないところについて、もう一度質問しない。
  - 変えるところについて、実際の1回をたどる質問がある。
  - Web管理画面を変えない改善・設計変更では、画面の質問がない。
  - クリエイターが作っていないプラグインでは、実際の1回をたどる質問と、画面の質問がある。

## 4. 確かめてから直す

### REQ-057 直す前の確認

- 要件：直す前に、クリエイターは、生成する前の確認（REQ-020）と同じもの（決まりの一覧、振る舞いの案、EVAL の課題と合否の基準）に加えて、次を示す。
  - 引き継ぐこと（できていたこと、確かめた決まり、流用する部品）
  - 変わること（足したり変えたりするスキル、設定項目、エージェントの役割、足す決まりと外す決まり）
  - 共通の土台（Web管理画面とその仕組み）を今の版に上げることと、それで変わること（元のプラグインの土台が今の版と違うとき）
  - 変えたところを試す EVAL の課題と合否の基準（1つ以上）
  - 新しい版の案（`plugin.json` の version）

  Web管理画面の設定項目や表示を変えるときは、見本（REQ-027）も示す。ユーザーが直したり足したりして、よいと答えてから直す。版は、ユーザーがよいと答えた版にする。
- 根拠：憲章 第7条、第13条1項、第15条2項、第17条1項
- 受け入れ基準：
  - 直す前に、上のものがすべて示される。
  - ユーザーがよいと答えるまで、元のプラグインのフォルダは変わらない。
  - 直した後のプラグインの version が、ユーザーがよいと答えた版になっている。

### REQ-058 決まりの番号

- 要件：改善・設計変更の後も、引き継いだ決まりの番号は変わらない。足した決まりには、今ある番号の続きの番号が付く。外した決まりの番号は、ほかの決まりに使わない。プラグインの中で番号を指している箇所が、別の決まりを指さないようにするためである。
- 根拠：憲章 第6条3項
- 受け入れ基準：
  - 引き継いだ決まりの番号が、直す前と同じである。
  - 足した決まりの番号が、直す前のどの番号とも重ならない。

## 5. 受け取る

### REQ-059 直す場所とコミット

- 要件：クリエイターは、元のプラグインのフォルダを直接直す。直した後のプラグインは、生成プラグインの条項を満たす（[出力の要件](output-requirements.md)）。共通の土台は今の版に上げ、プラグインの憲章・仕様書・設計書も、変えた内容に合わせて直す。
  - 構造の検査と部品の試験に合格すると、クリエイターは、直した内容を元のプラグインのリポジトリにコミットする。上限の回数まで直しても合格しないときは、コミットせずに止め、残った不合格の試験とその理由と、直す前に戻すやり方を示す。
  - 元のプラグインのフォルダの外のファイルは変えない。push など、手元の外に出る操作はしない。
- 根拠：憲章 第11条、第13条1項、第15条2項、第17条1項
- 受け入れ基準：
  - 新しいフォルダは作られず、元のプラグインのフォルダが直されている。
  - 直した後のプラグインが、出力の要件の受け入れ基準を満たす。
  - 直した後のプラグインの仕様書の要件から、設計書の箇所・実装資産・テストをたどれる（REQ-003）。
  - 試験に合格すると、直した内容がコミットされている。そのコミットの前に戻すと、直す前と同じ中身になる。
  - 元のプラグインのフォルダの外のファイルが変わっていない。リモートのリポジトリに push されていない。

### REQ-060 直したことの説明

- 要件：直し終わると、クリエイターは次を示す。
  - 変わったこと
  - 足した決まり、直した決まり、外した決まり
  - 流用した資産
  - 構造の検査と部品の試験の結果（REQ-039）
  - コミットと、直す前に戻すやり方
  - 試験のしかた（REQ-022 と同じ）
- 根拠：憲章 第9条1項、第13条1項、第17条
- 受け入れ基準：
  - 直した後に、上の6つが示される。

## 6. 試験

### REQ-061 変えたところの試験

- 要件：直した後、クリエイターは、作ったときと同じく構造の検査と部品の試験を行い、不合格なら直す（REQ-039）。EVAL の課題と合否の基準は、元のプラグインのものを確かめた決まりに合わせて引き継ぎ、変えたところを試す課題（REQ-057）を足して、プラグインのリポジトリに入れる。ユーザーが試験を頼むと（REQ-040）、引き継いだ課題と足した課題で EVAL が行われる。
- 根拠：憲章 第17条1項・2項／[試験の設計](../design/testing.md) 7章
- 受け入れ基準：
  - 直した後に、構造の検査と部品の試験の合否が示される。
  - プラグインのリポジトリに、変えたところを試す課題と合否の基準が入っている。
  - 変えたところを壊したプラグインで EVAL を行うと、足した課題の基準が不合格になる。
