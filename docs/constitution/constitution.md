# クリエイター憲章

- 版：0.26.0（ドラフト）

> 最大の目的：ユーザーとの対話を通じてユーザーのナレッジを引き出し、それを組み込んだ、公式仕様に準拠した Agent Plugin を生成する。

## 第1章 総則

### 第1条 目的

本憲章は、クリエイターが守る最上位ルールであり、クリエイターが生成する生成プラグインが守るルールも定める。

### 第2条 構成

| 章 | 適用対象 |
| --- | --- |
| 第2章 共通条項 | クリエイターと生成プラグイン |
| 第3章 クリエイターの条項 | クリエイター |
| 第4章 生成プラグインの条項 | 生成プラグイン |
| 第5章 アイデア創出の条項 | クリエイターのアイデア創出スキル |

### 第3条 用語

| 用語 | 定義 |
| --- | --- |
| クリエイター | リポジトリ plugin-creator 自身。Agent Plugin を生成するプラグインである |
| 生成プラグイン | クリエイターが生成した Agent Plugin |
| 統括エージェント | 作業全体の指揮とタスク分担を行う |
| 作業エージェント | 割り当てられた作業を実行する |
| 検証エージェント | 作業成果物を検証する |
| Web管理画面 | ローカルWebサーバーが提供する、設定・監視・確認のためのブラウザ画面 |
| PDSサイクル | Plan（計画）– Do（実行）– Study（評価・学習）の反復 |
| アイデア創出スキル | クリエイターのスキルの1つ。ユーザーが決めた制限の中でアイデアを作り、その良さが伝わる説明を書く |
| 6つの柱 | アイデア創出スキルの中心の手順（第25条） |

### 第4条 クリエイターのインプットとアウトプット

| 区分 | 内容 |
| --- | --- |
| インプット | ユーザーからのプロンプトと、対話で引き出したユーザーのナレッジ。作り直すときは、既存のプラグイン。アイデアを作るときは、ユーザーが決めた制限 |
| アウトプット | 生成プラグイン。アイデアを作るときは、アイデアとその説明 |

## 第2章 共通条項

### 第5条 準拠仕様

1. Agent Plugins 1.0.0 と GitHub Copilot CLI の公式プラグイン仕様に従う。
2. 両仕様が両立しない場合は Agent Plugins 1.0.0 を優先する。
3. 技術的な判断は、その時点の最新の公式の情報（公式の仕様、公式ドキュメント、更新履歴、最新の版での実測）にもとづいて行う。古い版や古いモデルの情報を使うときは、版と時点を書き、最新の情報で確かめ直す。

### 第6条 リポジトリの構成

1. リポジトリは、次の4種類の成果物を基本とする。

   | 成果物 | 内容 |
   | --- | --- |
   | 憲章 | プロジェクトが必ず守る最上位ルール |
   | 仕様書 | 実現する機能や振る舞いの要件 |
   | 設計書 | 仕様を実現するための構造・方式 |
   | 実装資産 | プログラムのソースコードとテストコードに加え、`SKILL.md` などのエージェント用定義ファイルを含む |

2. 優先順位は 憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 とし、下位は上位に矛盾しない。
3. 仕様書の要件は、設計書・実装資産・テストまで追跡できるようにする。

### 第7条 開発の進め方

ユーザーと対話しながら、憲章 → 仕様書 → 設計書 → 実装資産 の順に開発・保守する。

### 第8条 SWEBOK

[SWEBOK](https://www.computer.org/education/bodies-of-knowledge/software-engineering) の知識体系・考え方を踏まえて開発する。一律の手順とはせず、対象に適した実践方法を選ぶ。

### 第9条 分かりやすさ

1. 人間に伝える内容と人間が読む成果物は、分かりやすさを何より重視し、簡潔に、伝わる用語で書く。
2. 人間の指摘は、文言をそのまま残さず、目的に沿って直す。

### 第10条 KISS

1. 必要なものだけを、できるだけ単純に作る（KISS：Keep It Simple, Stupid）。
2. リポジトリを肥大化させない。

## 第3章 クリエイターの条項

### 第11条 生成プラグインの要件

生成プラグインは、第2章と第4章を満たす。

### 第12条 既存資産の流用

1. 生成プラグインは、必ずしも一から作らない。ユーザーは、生成プラグインに組み込む資産をすでに持っていることがある。
2. ユーザーとの対話を通じて、既存の資産がないかを確認し、引き出す。
3. Copilot CLI の標準機能や、公開されているプラグインで済むものがないかも調べ、ユーザーに示す。
4. 使える既存の資産があるものは流用し、ないものだけを新たに作る。

### 第13条 既存プラグインの作り直し

1. ユーザーが既存のプラグインを示したときは、それを元に、第4章を満たす生成プラグインに作り直す。
2. 既存のプラグインから読み取ったナレッジは、ユーザーに確かめてから使う。足りないナレッジは、対話で引き出す。

### 第14条 ナレッジを引き出す質問の改善

1. ユーザーからナレッジを引き出す質問（何を、どう聞くか）は、クリエイターの性能に直結する。
2. 質問は一度決めて終わりにせず、実装や試験の結果、ユーザーが実際に使った結果をもとに、改善し続ける。

### 第15条 Web管理画面の作成の支援

1. Web管理画面の見た目、機能、Copilot CLI との連携は、AI に一から作らせると失敗しやすい。性能の低いモデルを使っても、毎回同じ品質で作れるようにする。
2. どの生成プラグインにも共通する土台は、クリエイターが設計して用意する。
3. 生成プラグインごとに違う部分は土台の上に作る。そのとき、デザインの仕方、機能の作り込み方、Copilot CLI との連携の仕方を示して支援する。

### 第16条 推論の重さに合わせた分担

1. クリエイターが行う推論を、高い推論力が要るものと、そうでないものに分ける。
2. 高い推論力が要るもの（対話で仕様を決めることなど）は、思考力の高いモデルで行えるようにする。そうでないもの（決まった内容に沿ってファイルを書くことなど）は、費用の低いモデルで行う。

### 第17条 生成プラグインの試験

1. クリエイターは、生成プラグインを、構造の検査、部品の試験、EVAL（実際のモデルで課題を実行して採点する試験）の3段階で試験できるようにし、結果をユーザーに示す。
2. 生成の後だけでなく、ユーザーが生成プラグインを直した後も試験できるようにする。

### 第18条 クリエイターの画面

1. クリエイターは、ローカルWebサーバーの画面で、生成プラグインを作る対話で決まったことの一覧と、生成プラグインの試験の結果を見せる。

## 第4章 生成プラグインの条項

### 第19条 マルチエージェント構成

1. 統括エージェント1体、作業エージェント1体以上、検証エージェント1体で構成する。
2. 作業エージェントは自らの成果物を判定しない。検証エージェントは成果物を修正せず、指摘を統括エージェントに返す。

### 第20条 Web管理画面

1. ローカルWebサーバーを起動し、Web管理画面で各種設定を行えるようにする。
2. 既定ではローカルホストからの接続だけを受け付ける。

### 第21条 監視

Web管理画面で、各エージェントの状態・担当タスク・PDS のフェーズを監視でき、実行を停止できるようにする。

### 第22条 結果確認

Web管理画面で、各エージェントの実行結果と検証結果を確認できるようにする。

### 第23条 PDSサイクル

PDS サイクルで成果物と作業の進め方を改善する。

- Plan：統括エージェントが実施内容と評価基準を決める。
- Do：作業エージェントが計画に沿って試行する。
- Study：検証エージェントが結果を分析し、統括エージェントが次の試行に反映する。

### 第24条 自己改善

1. 実行中にログを残し、実行後にログを振り返って課題を洗い出す。
2. 自身の改善につながる課題を見つけたら、自身の GitHub リポジトリに Issue を起票する。
3. 起票は毎回ユーザーの承認を得てから行う。

## 第5章 アイデア創出の条項

### 第25条 6つの柱

1. アイデア創出スキルは、次の6つの柱でアイデアを作る。
   1. 制限の決定
   2. 徹底的な事前調査
   3. 本質の見極め（なぜなぜ分析）
   4. 本質の掛け合わせによるアイデア創出（壁打ち）
   5. アイデアの説明（第三者目線）
   6. 知識・経験の蓄積
2. 6つの柱の中身は、仕様書に書く。
3. 6つの柱の名前・順番・中身は、ユーザーの承認なしに変えない。変えたほうがよいと考えたときは、変えずに案を示し、承認を得たときだけ変える。

### 第26条 パラメーター

6つの柱の中の数は、すべてパラメーターにし、ユーザーがファイルで変えられるようにする。

### 第27条 機能の分離

アイデア創出スキルは、クリエイターのほかの機能（生成プラグインを作る、試験する）と、機能ブロックとして分ける。
