# 試験の設計

クリエイターと生成プラグインを、どう試験するかを定める。

## 1. 前提

試験には次の2つがある。2章と11章は両方に共通で、3〜9章は開発の試験、10章はユーザーの試験について書く。

| 試験 | 目的 | 行う人と環境 |
| --- | --- | --- |
| 開発の試験 | クリエイターを開発する。クリエイターと、クリエイターが作った生成プラグインを試験し、クリエイターを採点する | AI が Claude Code で自律的に行い、人は結果を見る |
| ユーザーの試験 | ユーザーが、受け取った生成プラグインを試験する（[試験の要件](../specs/test-requirements.md)） | ユーザーが頼むと、クリエイターがユーザーの手元の Copilot CLI で行う |

- クリエイターと生成プラグインは Copilot CLI 向けだが、開発の試験は Claude Code だけで行う。開発のクラウド環境では、Copilot CLI を動かす試験は行わない。Copilot CLI での確かめは、最終確認で、人が手元の Copilot CLI で行う（9章）。

## 2. 試験の段階

| 段階 | 確かめること | やり方 |
| --- | --- | --- |
| 1 構造の検査 | 設定ファイル、ファイルの置き場所、フロントマターが正しいか | 公式のスキーマと公式ドキュメントの決まりで検査する |
| 2 部品の試験 | スクリプト、フック、MCP サーバーなどが正しく動くか | 部品を直接動かし、正常な入力と異常な入力で確かめる |
| 3 EVAL | 必要な場面で呼ばれ、期待する成果物を作れるか | 実際のモデルで課題を実行して採点する。プラグインあり・なしで同じ課題を繰り返し実行し、スコアを比べる |

- 開発の試験とユーザーの試験は、同じ3段階で行う。1・2段目は、同じ仕組みを使う（10.2）。
- 1・2段目はモデルを使わないので、費用がかからず、結果も毎回同じになる。
- 1段目では、Agent Plugins の公式スキーマを手元に写して使う。カスタムエージェントの項目は、Copilot CLI のコマンドリファレンスとカスタムエージェントの設定リファレンスとで一部違うので、両方を認める（`model` は1つでも優先する順のリストでも認める。[クリエイターの構造](creator-structure.md) 3.3）。
- 公式のスキーマで検査するだけでは足りない。相対パスの閉じ込め、`mcp.json` と `plugin.json` の版の一致、URL と `command` の決まりは、スキーマで検査できない。スキル・エージェントのフロントマター、`hooks.json`、`marketplace.json` のスキーマは、仕様リポジトリにも Copilot CLI のパッケージにもない。これらは、公式ドキュメントの決まりを1段目の Python の検査に足して確かめる。
- 生成プラグインの1段目では、作業の定義が決まりの形に合うか、EVAL の課題の基準の写しが作業の定義と同じか、生成前の確認でよいと答えたナレッジがすべて入っているかも確かめる（10.1、10.3）。eval.json の採点のしかた（確かめ方の種類とその項目、設定の値の型、設定の `key` が作業の定義にあること、必須の設定の値が課題にあること）まで、EVAL の採点と同じ決まりで確かめる。採点の正規表現が読めるかは、node があるときに確かめる（採点は JavaScript の正規表現で行うため）。1段目は Python、採点は Node.js で書くので、両者の決まりのずれは、見張りの試験で見張る。エージェントの定義では、作業・検証の `tools` に `skill` がなく、統括に `tools` がないことも確かめる（[生成プラグインの構造](generated-plugin-structure.md) 4.7）。土台のファイルがひな形と同じかは、生成プラグインの1段目では確かめず、クリエイターが組み立ての後に確かめる（[クリエイターの構造](creator-structure.md) 4.1）。クリエイター自身の1段目では、会話例の版も確かめる（6.6）。土台について1・2段目で確かめることの一覧は、[生成プラグインの構造](generated-plugin-structure.md) 10章にある。
- 2段目では、たとえば次のように部品を動かす。
  - フック：標準入力に JSON を渡し、標準出力の JSON と終了コードを確かめる。入力の形は Copilot CLI と Claude Code で違う（例：エージェント名が `agentName` と `agent_type`）ので、両方の形で確かめる。
  - MCP サーバー：単体で起動し、MCP のクライアント（MCP 公式の Inspector の CLI モードなど）からツールを呼ぶ。
  - Web管理画面：エクステンションの中心の処理と画面を、偽物のつなぎ口（テストのフォルダに置く）につないで動かし、ブラウザーを操作するプログラム（Playwright）で、人と同じ操作をして確かめる。エージェントの状態は、本物のエージェントを動かさず、偽物のつなぎ口から用意したイベントを流して確かめる。開始や止めるの操作が、つなぎ口への正しい呼び出しになるかも確かめる。確認の待ちのイベント（許可の求め、返事の待ち、利用の上限の待ち）も偽物のつなぎ口から流し、この実行のエージェントの確認の待ちが「チャットで確認を待っています」と、何の確認か（許可の求めならコマンドの全文や注意）つきで画面に出ること、待ちの終わりで画面の待ちが消えること、チャットでのほかの作業の確認とエクステンション自身の権限の求めは画面に出ないこと、画面に確認に答えるボタンがなく、エクステンションが確認に答えないこと（許可の求めは見るためだけに受け、いつも `no-result` を返す）を確かめる（[生成プラグインの構造](generated-plugin-structure.md) 3.2、4.14、6.1、6.3、10章）。つなぎ口そのものは、最終確認で確かめる（9章）。

## 3. 試験は2重になる

クリエイターの出力は生成プラグインである。生成プラグインが正しいかは、その生成プラグインをさらに試験して確かめる。

```text
外側の試験（クリエイターを試す）
  模擬した会話 ──▶ クリエイター ──▶ 生成プラグイン
                                        │
内側の試験（生成プラグインを試す）        ▼
  分野の課題 ─────────────────▶ 生成プラグイン ──▶ 成果物
```

| 段階 | 外側（クリエイター） | 内側（生成プラグイン） |
| --- | --- | --- |
| 1 構造の検査 | クリエイターのファイル（会話例の版を含む） | できた生成プラグインのファイル |
| 2 部品の試験 | クリエイターのスクリプト、クリエイターのエクステンション（画面、記録のツール、状態取得ツール、文書をテキストにするツール、フック、偽物の `gh` での起票）など | 生成プラグインのスクリプト、フック、MCP サーバー、Web管理画面 |
| 3 EVAL | 模擬した会話を入力し、生成プラグインを作らせる | 分野の課題を入力し、成果物を作らせる |

1・2段目の仕組みは、外側と内側で同じものを使う。

試験は次の順に進める。

1. クリエイターに、1・2段目の試験を行う。`python3 tests/creator/run.py` の1つのコマンドで動かす。
2. クリエイターを Claude Code 向けに置き換え、外側の EVAL を行う。生成プラグインができる。
3. できた生成プラグインに、1・2段目の試験を行う。
4. 生成プラグインを Claude Code 向けに置き換え、内側の EVAL を行う。
5. 1〜4の結果から、クリエイターを採点する。

模擬ユーザーやユーザー役を変えたときは、先にユーザー役の試験（6.2）を行う。

## 4. Claude Code 向けの置き換え

3段目は Claude Code で実行するため、プラグインを Claude Code が読み込める形に置き換えてから試す。

| 部品 | Copilot CLI 向けの形 | Claude Code 向けの形 |
| --- | --- | --- |
| マニフェスト | 直下の `plugin.json` | `.claude-plugin/plugin.json` |
| スキル | `skills/<名前>/SKILL.md` | 同じ場所。フロントマターの `allowed-tools` や本文に書いたツール名を、Claude Code の名前にそろえる |
| MCP サーバー | `mcp.json` | `.mcp.json`。サーバー本体は同じで、設定の書き方（`${PLUGIN_ROOT}` を `${CLAUDE_PLUGIN_ROOT}` にするなど）を置き換える |
| カスタムエージェント | `com.github.copilot/agents/` | `agents/` のサブエージェント。`tools` の別名（`read`、`edit`、`execute`、`search` など）と MCP のツール（`サーバー名/ツール名`）を Claude Code の名前（`Read`、`Edit` と `Write`、`Bash`、`Grep` と `Glob`、`mcp__plugin_<プラグイン名>_<サーバー名>__<ツール名>`）にし、モデル名を置き換える。`web` は `WebFetch` と `WebSearch` にする。`model` のないエージェントには、`model: inherit`（メインの会話のモデルを使う）を入れる |
| フック | `com.github.copilot/hooks/hooks.json` | `hooks/hooks.json` の形。イベント名（`subagentStart` → `SubagentStart` など）、コマンドの項目（`bash` → `command`）、`${PLUGIN_ROOT}` を置き換える |
| インストラクション | `com.github.copilot/rules/` | Claude Code では、プラグインの直下に置いた CLAUDE.md は読み込まれない。EVAL の課題の側で、指示として足す |
| エクステンション | `com.github.copilot/extensions/<名前>/`（生成プラグインのものと、クリエイター自身のもの） | Claude Code にはない。置き換えた版から外し、試験の仕組みが Agent SDK 用のつなぎ口を持って、同じ中心の処理と画面、同じ記録のツールを動かす（下） |

- ツール名は、Copilot CLI の公式ドキュメント（フックのリファレンス）にある対応表に従う。例：`bash` → `Bash`、`view` → `Read`、`ask_user` → `AskUserQuestion`、`task` → `Agent`。
- 本文の中のツール名は、バッククォートで囲んだもの（`` `task` `` など）と、`ask_user` のような普通の単語と紛れない名前だけを置き換える。そのため、SKILL.md やエージェントの本文では、ツール名をバッククォートで囲んで書く。
- 統括の `task` の引数も置き換える。Copilot CLI の `agent_type` は Claude Code の `Agent` の `subagent_type`、`mode` の `"sync"`・`"background"` は `run_in_background` の false・true にする（Claude Code の `mode` は別の意味）。Claude Code のサブエージェントは既定で裏で動くので、統括の本文が `run_in_background: false` を指定する。変換スクリプトは、バッククォートで書かれた名前と値を置き換える。
- エクステンションのツール名は、`<エクステンション>_<ツール>` を `mcp__<エクステンション>__<ツール>` にする。サーバー名は、エクステンションのフォルダの名前にする。`skill` は `Skill` にする。この対応は公式の対応表になく、変換スクリプトが補う。
- 変数（`${PLUGIN_ROOT}` など）の置き換えは、設定ファイル（mcp.json、フック、lsp.json）だけで行う。スキルとエージェントの本文では置き換えない。
- 置き換えた版には、トップの `docs/`・`tests/`・`examples/`・`wip/`・`.git`、どこにあっても `heldout` のフォルダ、シンボリックリンクを写さない。見ない模擬ユーザー（6.3）を試されるクリエイターから隠すのは、この仕組みによる。
- 置き換えた版の `.eval/` に、変換レポートと `rules.md` を置く。モデルの対応表は、変換レポートの `model_map` にも出る。
- モデル名は、Claude Code で使える名前にする。Claude 以外のモデルは、Claude Code では使えない。次の決まりで置き換える。
  - カスタムエージェントの `model`（1つ、または優先する順のリスト）は、Claude Code の `model` 1つにする。候補の中に Claude のモデルがあれば、最初のものを Claude Code の ID にする（例：`claude-haiku-5.5` → `claude-haiku-5-5`）。
  - 候補に Claude のモデルがなければ、Copilot の価格表で同じ値段の Claude のモデルにする（例：`gpt-6-luna` → `claude-haiku-5-5`）。この対応は、変換スクリプトに表として持つ。
  - `model-policy` は Claude Code にないので外す。`reasoningEffort` は `effort` にする。
  - Web管理画面で選ぶモデルは Copilot の名前（例：`gpt-6-luna`）で出す。試験の仕組みが、選ばれた名前を、この対応で Claude Code の ID にしてから `model` に入れる。
- メインのエージェントのモデルは、試験の仕組みが決める。Copilot CLI ではプラグインからメインのエージェントのモデルを決められないので、Claude Code のプラグインの `settings.json` の `agent`（プラグインのエージェントをメインにする設定）は使わない。使うと、Copilot CLI にない振る舞いを試すことになる。
- Claude Code では、サブエージェントは質問のツール（`AskUserQuestion`）を使えない。クリエイターは、ユーザーへの質問をメインのエージェントだけで行うので（[クリエイターの構造](creator-structure.md) 3.2）、置き換えてもこの点の振る舞いは変わらない。
- 質問のツール：Claude Code の `AskUserQuestion` は、1回に1〜4問、各問に2〜4個の選択肢が要る（Claude Agent SDK「Handle approvals and user input」）。
  - make-plugin の SKILL.md には「質問のツールが選択肢を必ず求めるときは、自由入力で聞く問いは、文章で1つ聞いて手番を終える」の1文がある（[ヒアリングの設計](hearing.md) 10.4）。そのため、Claude Code では、自由入力で聞く問い（聞き出すヒアリングと理解の確かめ）は文章で出る。選択肢で聞く問い（決める質問、決まりの確かめ、生成前の承認）は `AskUserQuestion` で出る。
  - 試験の仕組みは、ツールの問いと文章の問いを、どちらも全文で記録する（6.6）。
  - 質問のツールの記録（`qa.jsonl`）には、問いを `{ message, choices, header }` の形で、答えを Claude Code の `AskUserQuestion` の結果の文 `The user answered: "質問"="答え"` の形で残す。
- 生成プラグインの Web管理画面は、エクステンションの中で動く（[生成プラグインの構造](generated-plugin-structure.md) 4.1）。エクステンションは、Copilot CLI とつなぐ薄いつなぎ口と、Copilot CLI に依らない中心の処理と画面に分かれている（同 3.2）。開発の試験では、試験の仕組みが Agent SDK 用のつなぎ口を持ち、生成プラグインの中心の処理と画面をそのまま動かす。
  - 画面を開くツールと記録のツールは、試験の仕組みが、試すエージェントに MCP のツールとして出す（Agent SDK の同じプロセスの中で動く MCP サーバー）。エージェントの定義の `tools` に書いたエクステンションのツール名と、本文にバッククォートで書いたツール名（例：`weekly-report_plan`）は、Agent SDK の MCP のツール名（`mcp__<サーバー名>__<ツール名>`）に置き換える。MCP のツールは、既定ではツール検索の裏に回るので、`_meta['anthropic/alwaysLoad']` を付けて出す（Copilot CLI の `defer: "never"` に当たる）。
  - クリエイター自身のエクステンションも、置き換えた版から外す。画面を開くツール、決まったことを画面に知らせる記録のツール、状態取得ツール、文書をテキストにするツール、質問の改善案の起票も、同じく MCP のツールとして出す。起票は偽物の `gh` で受けて記録だけ残し、本物の plugin-creator に Issue を作らない。ツールがあるので、スキルが「エクステンションがない」と判断して止まらず、外側の EVAL（3章の手順2）と会話例の作成（6.6）が動く。
  - クリエイターのエクステンションのフックがしている問答の記録（[ヒアリングの設計](hearing.md) 7.4）は、試験の仕組みが自分の会話の記録から同じ形で作る。コンパクションの後の1回の差し込み（同 8章）は再現しない。Claude Code の公式ドキュメントでは、自動コンパクションの後に、呼んだスキルを各先頭5,000トークン（合計25,000トークン、古いものから落とす）まで入れ直す（Claude Code「Skills」）。そのため、同じ手番のコンパクションで SKILL.md の本文が消えない見込みである（確かめていない）。この備えは、2段目と最終確認（9章）で確かめる。
  - 記録のツールを呼んだエージェントは、フックの入力の `tool_use_id`（と `agent_id`）と、MCP のツールの呼び出しに付く `_meta['claudecode/toolUseId']` で結び付けて知る。
  - 開始では、統括のエージェントの定義（指示とモデル）で、Agent SDK の別の実行を始める。統括は `agent: '<プラグイン>:orchestrator'` とし、システムプロンプトを `claude_code` のプリセットにして始める。統括の定義には `tools` がない（[生成プラグインの構造](generated-plugin-structure.md) 4.7）ので、つなぎ口が、使ってよいツールの一覧を Claude Code の名前にして `tools` に書く。作業・検証のモデルは、置き換えたエージェントの定義の `model` を、画面で選んだモデルにしてから始める。
  - 止めるでは、統括の Agent SDK の実行を中断する。メインの実行は中断しない（[生成プラグインの構造](generated-plugin-structure.md) 4.4 と同じ範囲）。
  - 状態は、Agent SDK のフックとメッセージ（サブエージェントの開始と終わり、ツールの使用）から作る。エージェントの終わりが取り消されたものかは取れないので、試験の仕組みが止めたかどうかで決める。
  - 開発の試験では、5章のとおり普段のツールをあらかじめ許可する。確認の待ちを画面に示す流れ（[生成プラグインの構造](generated-plugin-structure.md) 4.14）は、2段目の偽物のつなぎ口と、最終確認で確かめる。
  - つなぎ口が違うので、Copilot CLI とのつなぎ（統括の起動、モデルの上書き、取り消し、イベント（確認の待ちと待ちの終わりを含む）、エクステンションの読み込みのときの確認、`/clear` での読み込み直し）は、開発の試験では確かめられない。最終確認で確かめる（9章）。
- 置き換えは、変換スクリプトで行う。毎回同じ結果になるようにするためである。変換スクリプトも2段目で試験する。
- 置き換えた版は、`claude plugin validate` で Claude Code に読み込めることを確かめてから試す。警告（作者の情報がないなど）は不合格にしない。エージェントとスキルが読み込まれたかは、`claude -p` の始まり（init）の agents・skills でも見られる。
- 置き換えた版を試すので、結果は Copilot CLI での振る舞いと完全には一致しない。特に、スキルが呼ばれる場面や、エージェントへの仕事の割り振りは、ツールが違うと変わりうる。自由入力で聞く問いも、上の質問のツールの項のとおり、Copilot CLI と出し方が変わる。作業エージェントも Claude のモデルで動くので、本来のモデル（GPT-6 Luna など）で書いたときの出来は、この試験では分からない。

## 5. EVAL を実行する仕組み

- ここでは、開発の試験の EVAL の仕組みを書く。ユーザーの試験の EVAL は、Copilot SDK で動かす（10.4、10.5）。
- 外側と内側の EVAL は、Agent SDK（Claude Code をプログラムから動かす公式の部品）を使った、同じ自作の仕組みで実行する。
- Claude Code の `claude plugin eval` は使わない。公式ドキュメントに、ユーザー役が質問に答える仕組みも、実行中にブラウザーを操作する仕組みも見当たらないためである。
- 実行のたびに、まっさらな作業フォルダで始め、試すプラグインだけを読み込む。外側の EVAL では、模擬ユーザーのファイル（6.1）を置いてから始める。プラグインなしで比べるときは、何も読み込まない。
- 試されるエージェントは、次のように隔離する。
  - 環境変数は、必要なもの（パス、プロキシと証明書、モデルの接続先）だけを渡し、実行のたびに一時的なホームフォルダを使う。試験する側のセッションの設定が混ざると振る舞いが変わり、資格情報が混ざると試されるコードから見えてしまうためである。
  - ユーザー設定とプロジェクト設定は読み込ませない。
  - コマンドは OS のサンドボックスで動かし、書き込みを作業フォルダに限る。ファイルの書き込みのツールも、作業フォルダの中だけを許す。サンドボックスがないと、エージェントが自分の判断で作業フォルダの外に作業を移すことがあるためである。
  - コマンドは、毎回、作業フォルダから始める（環境変数 `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`）。Claude Code のサンドボックス（bubblewrap）は、コマンドの中だけ、コマンドの始まりのフォルダにある保護するファイル（`.mcp.json`、`.gitconfig`、`.bashrc`、`.claude/` の中など）を、中身のない装置のファイルで重ねる。生成プラグインのフォルダがコマンドの始まりのフォルダになると、そこに中身のない `.mcp.json` が重なり、生成プラグインの1段目が落ちた。実際の利用（Copilot CLI）では起きない。この直しが効くかは、本物のモデルで EVAL をやり直さないと分からない。
  - 生成プラグインの Web管理画面は、試験の仕組みのつなぎ口の側で動き（4章）、試されるエージェントは画面を起動しない。画面を操作する Playwright も、試験の仕組みが動かす。どちらもサンドボックスの中のコマンドではないので、画面にブラウザーからつながる。
- 普段のツールと、試すプラグインの MCP サーバーのツールは、あらかじめ許可する。許可を求める仕組みに回すのは、ユーザー役が答える質問だけにする。裏で動くサブエージェントの許可の求めは、受け付けられずに失敗することがあるためである。
- 使われたスキル、サブエージェントとそのモデルは、Agent SDK の実行の記録から採点に使う。

## 6. 外側の EVAL

### 6.1 模擬した会話

- 人間との会話は、ユーザー役の AI で模擬する。開発者が自分の題材で試すときだけ、開発者が自分で答える（6.7）。
- ユーザー役には、模擬ユーザーごとに、依頼の内容と、その人が持っているナレッジを渡す。ナレッジごとに、答える条件と、自分から話すかどうかを決める。聞かれないと話さないナレッジ（当たり前すぎて話されにくいこと、すでに持っている資産）は、具体的に聞かれたときだけ答える条件にする。
- 模擬ユーザーには、示すファイル（前回の成果物、いつも使うテンプレート。docx か xlsx を1つ以上含める）も用意する。試験の仕組みはファイルを作業フォルダに置き、ユーザー役はその場所を答える。ファイルには、本当の決まり、例外のある決まり、たまたまそうなっている書き方を1つずつ入れる。決まりの確かめの4つ目の答え「違う」に当たるもの（`wrong`。例：議事録の模擬ユーザーの文体）も入れる。入れないと、「違う」の答えを外側の EVAL で確かめられないためである。ファイルを読む段階、読み取り役、文書をテキストにするツール、決まりの確かめ（[ヒアリングの設計](hearing.md) 3.1、6.1、9章）を動かすためである。
- 答える条件は、人ならどう答えるかを考えて決める。狭く書きすぎると、人なら答える質問にも答えない（6.4）。
- ユーザー役は、クリエイターに聞かれたことだけに答える。ナレッジにないことは「特に決まっていません」と答え、推測で決まりを作らない。
- ユーザー役には、それまでのやり取りも渡す。「その2つ以外は？」のように、前の答えを指す質問に答えるためである。やり取りには、クリエイターが質問の前にチャットに書いた文も含める。渡さないと、ユーザー役は「上のまとめ」のような問いに、中身を見ずに答える。
- ユーザー役への指示には、次も書く。
  - 選択肢は名前だけを使い、「名前（説明）」と丸ごと写さない。
  - 見えないものを指す問い（「上のまとめ」など）には、中身を読んでいないのに「違いはない」と答えず、聞き返す。
  - 同じ意味の言葉を括弧で重ねない。
  - 最初に書いてある自分の立場と仕事は、自分のこととして答える。
  - 決まりの確かめで、足す中身がすでに書いてあるときは「このとおり」を選ぶ。
- ユーザー役は、自分への指示（答える条件など）のことを話さない。人はそう話さないうえ、クリエイターに手がかりを与えるためである。
- クリエイターからの質問には、試験の仕組みが、ユーザー役の答えを返す。クリエイターが質問のツールを使わずに、文章で質問して手番（エージェントが返事をし終えるまでのひと区切り）を終えたときも、ユーザー役の答えを次の発言として返す。

### 6.2 ユーザー役の試験

ユーザー役が、話すべきでないことを話したり、ナレッジにないことを作ったりすると、EVAL の結果が変わる。そのため、模擬ユーザーやユーザー役（モデルや指示）を作ったり変えたりしたときは、外側の EVAL に使う前に、ユーザー役だけを試験する。クリエイターは動かさず、模擬ユーザーごとに決めた質問を、ユーザー役に直接聞く。

| 観点 | 聞くこと | 合格の条件 |
| --- | --- | --- |
| 漏らさない | 「守らないと困ることはありますか？」のような大まかな質問 | 聞かれないと話さないナレッジを話さない |
| 答える | ナレッジごとの具体的な質問 | そのナレッジを答える |
| まとめて答える | いくつかのことを1つにまとめた質問 | 聞かれたことをすべて答える |
| 作らない | ナレッジにないこと | 「特に決まっていません」と答える |
| 前の話を踏まえる | 前の答えを指す質問 | 前の答えに沿って答える |
| 選択肢で済ませない | 選択肢のついた質問 | 選択肢の言葉だけでなく、具体的に答える |
| 決まりの確かめに答える | 示すファイルの決まりについての、決まりの確かめ（4つの答えの選択肢をつけた問い） | ファイルの決まりの種類に合う答え（本当の決まりは「このとおり」、例外のある決まりは「そうしないときもある」、たまたまの書き方は「決まりではなく、たまたま」、違うものは「違う」）を選ぶ |
| 指示のことを話さない | すべての質問 | 答える条件など、自分への指示のことを話さない |

- 同じ質問を何回か聞き、割合で見る。合格の条件は、「漏らさない」と「指示のことを話さない」は0件、ほかの観点は90%以上とする。
- 6.1 のユーザー役への指示を変えたときも、外側の EVAL に使う前に、この試験を本物のモデルでやり直す。
- ユーザー役のモデルと指示は、この試験に通ったものにし、比べる EVAL のあいだで変えない。ユーザー役が変わると、同じクリエイターでも結果が変わるためである。
- プロトタイプでは、Haiku のユーザー役は、大まかな質問に隠すべきナレッジを話し（25回中3回）、ナレッジにない決まりを作り、選択肢の言葉だけで答えた。Sonnet にし、やり取りを渡し、答え方の決まりを足すと、すべての観点に通った。

### 6.3 試験が正しく働くかを確かめる

- 大まかな質問しかしないクリエイター（対照）でも外側の EVAL を行い、聞かれないと話さないナレッジが組み込まれないことを確かめる。試験が、落ちるべきときに落ちるかを見るためである。プロトタイプでは、対照のスコアは2回とも 0.71 で、ユーザー役の答えにも漏れはなかった。
  - 対照のクリエイターは、大まかな質問を3つだけする別の小さなスキルで作り、生成プラグインは本物の組み立てのスクリプトを呼んで作らせる。できる生成プラグインの形を、本物と同じにするためである。
  - 対照で、聞かれないと話さないナレッジが組み込まれたか、ユーザー役が聞かれていないのにそのナレッジを話したときは、試験が落ちるべきときに落ちていないとする（試験を疑う）。
- 模擬ユーザーは、いくつかの分野で用意する。クリエイターを直すときに使った模擬ユーザーとは別の模擬ユーザーでも確かめる。クリエイターの手順を1人の模擬ユーザーに合わせて書くと、その模擬ユーザーでしか通らないためである。見ない模擬ユーザーは、置き換えた版に写さないことで、試されるクリエイターから隠す（4章）。プロトタイプのクリエイターは、手順に「締めくくりの決まり」を挙げていたので週報の模擬ユーザーでは 1.00 だったが、議事録の模擬ユーザーでは、聞かれないと話さないナレッジを2つとも引き出せなかった（2回とも 0.71）。
- 示すファイルがなく、まだやったことのない作業の模擬ユーザーも用意する。想定の1回をたどり、仮のファイルを作る流れ（[ヒアリングの設計](hearing.md) 3.3）を見るためである。
- 話し方（口数が少ない、あいまいに答える、「分からない」と答えがち、「特にない」と答えがち、急いでいるなど）を変えたユーザー役でも行う。答え方が違っても、クリエイターがナレッジを引き出せるかを見るためである。ユーザー役への指示には、答えの長さと言い方は話し方に従い、何を話してよいかは答え方の決まりに従うと書く。プロトタイプでは、これを書かないと話し方が答え方の決まりに負け、あいまいに答える設定でも初めから具体的に答えた。
- 急いでいる話し方の合図は、話し方の指示の1文にせず、試験の仕組みが、決まった回数の答えの後に、答えに足す（`signal`）。急いでいる話し方のユーザー役は、進め方の問いに「残りを手早く聞く」を選ぶ。
- 試験の仕組みは、ナレッジごとに、クリエイターが聞いたか、ユーザー役が答えたか、生成プラグインに組み込まれたかを記録する。スコアが下がったときに、クリエイターが聞かなかったのか、ユーザー役が答えなかったのかを見分けるためである。聞いたかどうかは、ナレッジごとに決めた言葉が質問にあるかで見るので、最後は会話の記録を読んで確かめる。プロトタイプでは、あいまいに答えるユーザー役が、締めくくりを具体的に聞き直されても答えず、スコアが下がったことがあった（2回中1回）。クリエイターではなく、ユーザー役の誤りである。

### 6.4 模擬の限界

- ユーザー役は、人の代わりにはならない。公開の研究でも、ユーザー役のモデルを変えるだけで成功率が変わること、人とは違う話し方の癖が出ることが報告されている。
- プロトタイプのユーザー役には、人より協力的なところも、人より厳しいところもあった。口数が少ない設定でも、長く答えたり、聞かれていないことを自分から話したりした。一方で、例として「決定事項と意見を混ぜない」と挙げた質問には、決定事項の印のことを答えなかった。人なら答えそうな質問である。
- そのため、外側の EVAL の結果は、同じ模擬ユーザーとユーザー役で、クリエイターの版どうしを比べるのに使う。人と話したときの出来は、この結果だけでは分からない。
- 次は、外側の EVAL では効き目を測れない。形どおりに出るかは、6.5 と最終確認（9章）で見る。
  - 決まりの確かめの形（[ヒアリングの設計](hearing.md) 6.1）。ユーザー役が、人のような「はい」への偏りを示すとは限らない。LLM は、英語の はい／いいえ の質問では逆に「いいえ」に偏り、ドイツ語とポーランド語でははっきりした傾向がなかった（Braun 2025）。日本語での傾向と、ユーザー役としての振る舞いは確かめていない。
  - 疲れ・急ぎへの対応（同 5.6）。ユーザー役は疲れない。
- Copilot CLI でしか起きないこと（同じ手番のコンパクション、答えが来ないとき）への備えは、外側の EVAL では試せない。最終確認（9章）で確かめる。

### 6.5 採点

外側の EVAL では、できた生成プラグインを次の観点で採点する。採点の観点は、出力の要件の受け入れ基準に対応づける。

- 1・2段目の試験に通るか
- 模擬ユーザーのナレッジ、特に聞かれないと話さないナレッジが組み込まれているか
- クリエイターが作った EVAL の課題と合否の基準（REQ-038）が、模擬ユーザーのナレッジ、特に聞かれないと話さないナレッジを含むか。ナレッジごとに決めた言葉が、課題と基準のファイルにあるかで見る。良い試験を作れるかも、クリエイターの性能として測るためである
- 内側の EVAL の結果
- 全項目をヒアリングしたか：生成前の確認に進むまでに、未着手の項目がなくなっている。項目ごとに（エクステンションが状態を計算する項目を除く）、未着手から状態を変えたときに添えたユーザーの言葉の抜き書きが、それより前のユーザー役の答え（質問のツールへの答えか、文章の問いの後の発言）の中にある。最初の依頼の文は、抜き書きの出どころに含めない。答えの中にない抜き書きがあれば、不合格にする。
- 承認の前に生成しなかったか：段階を「生成」に進めた記録に添えた抜き書きが、その記録の直前にあるユーザー役の答え（質問のツールへの答え）の中にある。その記録の時刻（[ヒアリングの設計](hearing.md) 6.3）より前に、組み立てのスクリプトが動いておらず、作業エージェントが作業の定義の案のほかにファイルを書いていない。書き込みは、Write・Edit 系のツールの書き込み先で見る（Bash で書いたファイルは見分けられない）。作業の定義の案は、置き場所 `.plugin-creator-work/draft/` で見分ける。
- 急いでいるユーザー役（6.3）では、急ぐ合図の後に、残りの項目と3つの進め方を示す問いがある。どれを選んでも、未着手の項目がなくなってから生成前の確認に進む（REQ-015）。
- まだやったことのない作業の模擬ユーザー（6.3）では、「初めてやるとしたら、最初に何をしますか」に当たる問いがあり、その後に想定の1回をたどってもらっている（REQ-016）。たどってもらったかは、項目「前回の1回」の記録で見る。
- ユーザー役が「違う」か「決まりではなく、たまたま」と答えた決まりが、生成プラグインに組み込まれていない（REQ-017）。
- 課題の入力のファイルが、生成プラグインのリポジトリに入っている（REQ-038）。生成前の確認で一覧で示され、仮のファイルには仮の印がある（[ヒアリングの設計](hearing.md) 6.5）。課題の入力のファイルは、模擬ユーザーが示すファイルのうち role が input のものである。
- メインのエージェントが指定のモデルで動いたか（REQ-045）。作業エージェントが費用の低いモデルで動いたか（REQ-046）。

抜き書きが答えの中にあるかは、次のように決める。抜き書きと答えを NFKC にし、空白とかぎ括弧・句読点を除く。抜き書きを「…」で区切った断片が、すべて同じ1つの答えの中にあればよい。エクステンションの守り（[ヒアリングの設計](hearing.md) 7.2）と同じ決め方である。採点の道具とエクステンションが同じ中身を重ねて持つので、ずれは試験が見張る。

ナレッジが組み込まれたかを見る範囲からは、ナレッジの一覧（`tests/knowledge.json`）を除く。一覧に記録されただけでは、組み込まれた証拠にならないためである。入ってはいけないナレッジが入っていないかを見るときは、一覧も含める。ナレッジに決めた言葉のうち、漏れを見るための言葉（`markers.leak`）は、外側の EVAL の採点には使わない。

「全項目をヒアリングしたか」と「承認の前に生成しなかったか」は、クリエイターが呼んだ記録のツールと、試験の仕組みの会話の記録から、機械的に見る（[ヒアリングの設計](hearing.md) 7章）。あわせて、次の数を記録する。

- 問いの数
- 1回の問いの欄の数
- 保留の項目と AI の判断の数
- 記録のツールが断った回数と、その後に直した回数。断りは、ツールの結果が失敗のものの数で数える。

外側の EVAL は、思考力の高いモデルと、費用の低いモデル（Claude Haiku 5.5）で回す。クリエイターのモデルは、試験の仕組みが決める（4章）。

| モデル | 合格に求めること |
| --- | --- |
| 思考力の高いモデル | 上のすべての採点の観点 |
| Claude Haiku 5.5 | 「1・2段目の試験に通るか」「全項目をヒアリングしたか」「承認の前に生成しなかったか」の3点 |

### 6.6 会話例

会話例（REQ-037）は、外側の EVAL の会話から作る。会話例のために EVAL を足すことはしない。

- 記録：外側の EVAL の記録（形は `outer-record/1` の JSON）に、クリエイターの発言（質問、生成前の確認、できたことの説明）と、ユーザー役の答えの全文を残す。試作は、クリエイターが文章で質問したとき、最後の300文字しか残していなかった。見ない模擬ユーザーの各回の記録は `records-heldout/` に分けて置き、要約では名前を伏せる。
- 作り方：スクリプト「会話例の作成」が、記録から Markdown のファイルを、外側の EVAL を回した模擬ユーザーごとに1つ作る。聞かれないと話さないナレッジを引き出した質問には、6.3 の記録（ナレッジごとに、聞いたか・答えたか）を使って印を付ける。
  - 冒頭に、AI が演じたユーザーとの会話であることと、クリエイターの版（「plugin-creator の版：x.y.z」）と日付を書く。続けて、試験の条件と点数（演じたユーザー、話し方、モデル、点数、採点の観点を1行ずつ）と、聞かれないと話さないことにしていた決まりの一覧（引き出した質問と★の番号つき）を書く。
  - 会話からは、画面の URL のポート番号と合言葉、作業フォルダなどのパス、会話の番号、鍵のような文字を伏せる。伏せ残しがあれば、書き出さずに断る。
  - 引用の改行は、行末に空白2つを足して残す。行頭の `##` は太字にする。HTML コメントは置かない。クリエイターの画面は会話例を text/plain で見せるので、丸見えになるためである。
- 選ぶ条件：記録のうち、クリエイターの版が今の `plugin.json` と同じものを使う。その版の外側の EVAL の会話のうち、次をどちらも満たすものから選ぶ。点数の高さだけでは選ばない。ユーザー役が隠すべきことを漏らすと、点数が上がるためである（ナレッジ「ユーザー役の AI で人を模擬するときの注意」）。
  - 採点の観点（6.5）にすべて合格した。
  - ユーザー役の誤り（聞かれていないのに隠すべきナレッジを話した、ナレッジにない決まりを作った、自分への指示のことを話した）がない。6.3 の記録で機械的に除き、最後は全文を読んで確かめる。
- 版：クリエイターの版を上げるたびに、その版の外側の EVAL の会話から作り直す。作り直し忘れは、クリエイター自身の1段目で、会話例に書いた版と `plugin.json` の版を突き合わせて見つける。違えば不合格にする。
- 置き場所：クリエイターのスキルのフォルダの外に置く。README とクリエイターの画面は、同じファイルを開く。
- クリエイターに読ませない：変換スクリプト（4章）は、置き換えた版から会話例を外す（トップの `examples/` を写さない）。クリエイターが会話例を読むと、例の分野の決まりを別の分野の生成プラグインに持ち込んだり、外側の EVAL で模擬ユーザーが隠しているナレッジを先に知ったりするためである。
- 載せない会話：クリエイターを直すときに見ないことにしている模擬ユーザー（6.3）の会話は、会話例にしない。リポジトリに載せると、このリポジトリで作業する AI が読み、見ていない模擬ユーザーではなくなるためである。開発者が答えた会話（6.7）も、会話例にしない。会話例は、AI が演じたユーザーとの会話と決めているためである（REQ-037）。

### 6.7 開発者が答える外側の EVAL

開発者が自分の題材で生成プラグインを作って試すときは、ユーザー役の AI の代わりに、開発者がクリエイターの問いに答える。ユーザー役の AI で行う外側の EVAL（6.1〜6.6）は、そのまま残す。

**問いと答えの中継**

- 開発者は、試験の仕組みを動かす Claude Code のセッション（以下、統括）と話す。統括が、クリエイターの問いを開発者に渡し、開発者の答えをクリエイターに返す。
- 最初の依頼の文は、開発者が書く。
- 試験の仕組みは、クリエイターが問うたびに、中継のフォルダに問いのファイルを書き、統括が答えのファイルを置くまで待つ。問いのファイルには、問いの文、見出し、選択肢、複数選べるか、問いの前にクリエイターがチャットに書いた文を入れる。質問のツールの問いも、文章で聞いて手番を終えた問いも、同じように中継する。
- 統括は、問いと問いの前の文を、言い換えずにそのまま示す。選択肢のある問いは、同じ見出しと選択肢で、統括の質問のツールで聞き、おすすめは付けない。クリエイターの問い方を試すためである。
- 統括は、開発者の答えを変えずに返す。選択肢を選んだときは、その選択肢の名前を返す。
- 開発者が示すファイルは、統括が中身を受け取って作業フォルダに置き、置いた場所を開発者に示してから、答えに足す。
- 統括は、試験の仕組みを、統括のコマンドの時間の上限（Claude Code の Bash のツールでは最長2時間）に縛られない形で動かす。開発者が答えるまでに時間がかかるためである。中継の状態（待っている問い、試験の仕組みのプロセス）はファイルに残し、統括がコンパクションの後に試験の仕組みを動かし直さないようにする。
- 待ちの長さ：
  - 質問のツールの問いは、クリエイターの手番の途中で、Claude Code のプロセスを動かしたまま待つ。Agent SDK 0.3.310 の型定義では、許可を求める問いの待ちに期限はない。ただし、外の画面（リモートのクライアント）に送った問いは、既定で5分で打ち切ると書かれている。試験の仕組みの問いがこれに当たるかは確かめていないので、期限をなくす `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS=0` を渡す（0 が期限なしであることは、Claude Code 2.1.310 の実装で確かめた）。
  - 文章の問いは、手番を終えた後に待つので、Claude Code のプロセスは動いていない。答えが来たら、同じセッションを続ける（resume）。
  - 答えの間が5分を超えると、プロンプトのキャッシュが切れて費用が増える。キャッシュを1時間保つよう、`ENABLE_PROMPT_CACHING_1H=1` を渡す。
- 開発者の答えには、ユーザー役のような誤り（隠すべきことを話す、指示のことを話す）の確かめをしない。

**採点**

- 模擬ユーザーのナレッジの一覧がないので、ナレッジにもとづく観点は採点しない。ナレッジが組み込まれたか、EVAL の課題と基準がナレッジを含むか、「違う」と答えた決まり、まだやったことのない作業、急ぐ合図、課題の入力のファイルの観点である。ナレッジが入ったかは、開発者が生成プラグインを見て確かめる。
- 採点するのは、生成プラグインが1つできたか、1・2段目の試験に通るか、全項目をヒアリングしたか、承認の前に生成しなかったか、メインのエージェントと作業エージェントのモデルである（6.5）。
- 内側の EVAL は、生成プラグインに入った課題と合否の基準（開発者が生成前の確認でよいと答えたもの）で行う。ユーザーの試験（10.4）と同じく、エージェントの問いには決まった返事を返し、画面の設定は課題に書いた値を入れる。開発者は答えない。プラグインなしのときに、開発者のナレッジが伝わらないようにするためである。
- 内側の EVAL の結果は、クリエイターの点数に入れず、別に示す。クリエイターが作った基準でクリエイターを採点しないためである（7章）。
- 開発者の答え方は毎回違うので、結果を、クリエイターの版どうしの比べ合いには使わない。

## 7. 内側の EVAL

- 内側の EVAL の課題と採点基準は、クリエイターとは別に、試験の資産として模擬ユーザーごとに用意する。生成プラグインに入っている EVAL の課題と合否の基準（REQ-038）はクリエイターが作ったものなので、クリエイターの採点には使わない。自分で作った基準で自分を採点しないためである。これは、開発の試験でクリエイターを採点するための決まりである。ユーザーの試験では、ユーザーが確かめて生成プラグインに入れた課題と基準で採点する（10.4）。
- 試験の仕組みは、人と同じ流れ（設定 → 開始 → 監視 → 結果）でブラウザーを操作して、置き換えた生成プラグインを動かす。画面は、試験の仕組みの Agent SDK 用のつなぎ口につないだ、生成プラグインの中心の処理と画面である（4章）。生成プラグインには、試験のためだけの機能を足さない。
  - Web管理画面の URL が出るのを待ってブラウザーで開き、設定して開始する。
  - 作業ごとの設定の欄は、クリエイターが作るときに決まるので、模擬ユーザーの eval.json の値と鍵が合わない。そのため、ユーザー役が、画面の設定の欄の見出しと説明を読み、模擬ユーザーのナレッジから値を決めて入れる（人と同じ流れ）。模擬ユーザーの `inner/eval.json` の `settings.task` は、鍵が合うときだけ使い、ふつうは書かない。
  - 実行中は、フェーズとエージェントの状態の表示を記録する。
  - 終わったら、結果の表示を読む。
- 生成プラグインがチャットで返事や答えを求めて手番を終えたときは、ユーザー役が人の代わりに返事をする。プラグインなしのときも、同じように返事をする。そのため、ユーザーが自分から話すナレッジ（ファイル名や金額の書き方）は、プラグインがなくても伝わることがある。プロトタイプでは、なしのスコアが実行によって 0〜0.5 と変わった。
- 画面で選んだモデルで作業エージェントが動いたかは、実行の記録で確かめる。
- 採点の基準は、模擬ユーザーのナレッジに書いたとおりにする。ナレッジにない細かさまで求めると、正しい成果物を落とす。プロトタイプでは、金額を「52万」と書いた成果物を、「52万円」を求める基準で落とした。

## 8. 費用と時間

### 8.1 開発の試験

- 外側の EVAL は、1回ごとに生成プラグインを丸ごと作る。さらに、できた生成プラグインを内側の EVAL で繰り返し動かすので、実行の回数がかけ算で増える。
- 1・2段目は費用がかからないので、すべての生成プラグインに行う。内側の EVAL は、生成プラグインの数と実行の回数を絞って行う。
- 同じ条件でも、進め方や結果は実行のたびに変わる。1回の結果だけで判断しない。
- 目安（内側の EVAL とユーザー役の試験は、プロトタイプで測った値。統括は Sonnet、作業エージェントは Haiku。費用は定価での見積もり）：
  - 内側の EVAL：プラグインありで1回 約1分・約 0.13〜0.22 ドル、なしで1回 約10〜25秒・約 0.03〜0.06 ドル
  - 外側の EVAL（実測。クリエイターが Claude Opus 5.5、ユーザー役が Sonnet）：1回 約30分（26〜31分）、手番 約140、問い 約45、Agent SDK の値で約7ドル分（クリエイター 約6ドル、ユーザー役 約0.9ドル）。プロトタイプで測った値（1回 約3分・約 0.4 ドル）の約10倍の時間、約17倍の費用である。
  - ユーザー役の試験：1回 約 0.15 ドル（Sonnet で約75問）
- EVAL は、モデルの利用枠も使う。プロトタイプでは、EVAL を続けて回したところ、試されるエージェントが利用枠の上限に達したというエラーで止まり、示された時刻（約3時間後）まで再開できなかった。回す数は、利用枠も考えて決める。

### 8.2 ユーザーの試験

- 1・2段目はモデルを使わないので、AI クレジットを使わない。
- EVAL は、Copilot の AI クレジットを使う。1クレジットは 0.01 ドルで、使ったモデルとトークンの量で決まる。個人プランの月の枠は、Pro が 1,500、Pro+ が 7,000、Max が 20,000 クレジットである。公式ドキュメントでは、Copilot CLI が数える対象に入っている。Copilot SDK は、Copilot CLI と同じランタイムをユーザーのアカウントで動かし、モデルの呼び出しごとに Copilot の API が返す費用を記録する。そのため、SDK で動かした分も同じく数えられる（Copilot SDK 1.0.22 の説明と型定義で確認）。
- 見込みは、次のかけ算で出し、EVAL を始める前に回数とあわせて示す（REQ-040）。
  - （ありの1回分 ＋ なしの1回分）× 回数 ＋ 採点でモデルを使う分
  - 1回分には、同じ生成プラグインで前に EVAL をしたときの記録（`assistant.usage`）から測った値を使う。初めてのときは、開発の試験で測った目安（1回あたりのトークン数）に、使うモデルの価格（Copilot の価格表）をかけて出す。
- 目安は、開発の試験で測った1回あたりのトークン数に、既定のモデルの Copilot の価格（公式の Models and pricing で確かめる）をかけた、1回あたりの AI クレジット（あり・なし・採点）として、クリエイターの試験のスキル（test-plugin）に持たせる。
- 目安は、まだ測っていない。測るまでは、初めての EVAL で見込みを示せず、REQ-040 の受け入れ基準を満たさない。試作（Claude の定価）では、内側の EVAL がプラグインありで1回 約 0.13〜0.22 ドルだった。同じくらいなら、あり・なしを3回ずつで 50〜80 クレジット程度になる（推定）。回数の既定値は、ユーザーの環境で費用を測ってから決める。
- EVAL の時間は、動かす回数（課題の数×回数×2）と、1回の上限（既定30分）だけを伝える。
- 見込みは上限ではない。使った分は、`assistant.usage` を足し上げて示す（REQ-041）。そこにある費用（`copilotUsage.totalNanoAiu`）は nano-AIU で表され、1 AI クレジットは 10億 nano-AIU である。API の説明が、同じ量を「AI クレジット（小数）」と「nano-AIU（整数）」の2つで返しているので分かる。セッション全体の合計と、その合計がすべての呼び出しを含むか（`aiCreditsStatus`）も、SDK から取れる。

## 9. 最終確認

- 最終確認では、人が手元の Copilot CLI にプラグインをインストールし、使い始められることを確かめる（出力の要件のインストールの受け入れ基準）。
- Copilot CLI での読み込みの不具合や、Copilot CLI でしか起きない不具合は、ここで見つける。
- ユーザーの試験のうち、Copilot CLI を動かす部分（Copilot SDK での EVAL の実行と、試験を頼まれたときの流れ）も、ここで人が手元で確かめる。開発の試験では、Copilot CLI を動かさないためである（1章）。
- 生成プラグインとクリエイターのエクステンションのつなぎ口の確かめは、[生成プラグインの構造](generated-plugin-structure.md) 11章（実機で確かめること）に従う。
- クリエイターの README に、REQ-023 の準備と、答えが来ないときと質問のツールがない起動での振る舞いが書かれているかを、人が読んで確かめる。
- 作り直しの流れ（REQ-032〜REQ-036）を、手元の Copilot CLI で1回確かめる。
- REQ-019・REQ-022・REQ-047 と、REQ-020・REQ-024・REQ-026・REQ-027 のうち自動の試験で見ていない受け入れ基準も、ここで確かめる。
- クリエイターのヒアリングについて、次を確かめる。開発の試験の Claude Code では起きないか、再現できないためである（4章、6.4）。あわせて、[ヒアリングの設計](hearing.md) 14章の項目も確かめる。
  - `/<クリエイターの名前>:make-plugin` で、ヒアリングが始まる。
  - 長いヒアリングの途中で自動コンパクションが起きても、make-plugin を読み直し、状態取得ツールを呼んで、同じ段階から続く。手番の途中で自動コンパクションを起こす手順は未決である。
  - 問いを取り消す（Esc）か、断る（Ctrl+D）か、autopilot で動かすと、聞きたかったことと続け方が示されて止まり、生成されない。
  - `-p` か `--no-ask-user` を付けて起動して頼むと、それらを付けずに対話モードで起動する直し方が示され、ヒアリングが始まらない。
  - `--continue` で起動し直すと、やめたところから続く。
  - 決まりの確かめで、4つの答えが並び、「このとおり」が最初にない。急ぐ合図を出すと、残りの項目と3つの進め方が示される。
  - GPT の族のモデル（例：GPT-6 Luna）でクリエイターを1回動かし、ヒアリングを飛ばさないか。GPT の族のシステムプロンプトには、足りない情報を推し量って進めるよう求める指示があり（[ヒアリングの設計](hearing.md) 2.7）、Claude Code では再現できないためである。

## 10. ユーザーの環境での試験

ユーザーが受け取った生成プラグインを、クリエイターがユーザーの手元で試験するやり方を書く。ユーザーから見た振る舞いは [試験の要件](../specs/test-requirements.md) にある。

### 10.1 置き場所と流れ

| もの | 置き場所 |
| --- | --- |
| 1・2段目のスクリプトと、それを1つのコマンドで動かす入口 | 生成プラグインのリポジトリ（ひな形から入れる） |
| 番号と種類を付けたナレッジの一覧 | 生成プラグインのリポジトリ |
| EVAL の課題（頼むときの言葉、入力のファイル、Web管理画面の設定、基準の番号と文の写し、基準ごとの採点のしかた） | 生成プラグインのリポジトリのテストのフォルダ。合否の基準は作業の定義が元で、課題には番号と文を写す。1段目で、写しが作業の定義と同じかを確かめる（[生成プラグインの構造](generated-plugin-structure.md) 4.9） |
| EVAL を動かす仕組みと採点 | クリエイター |

試験は次の順に進める。

1. クリエイターの画面を開き、URL をチャットに示す（[クリエイターの構造](creator-structure.md) 2章）。1・2段目の道具がそろっているかを確かめる。足りないときは、足りない道具と入れ方を示し、ユーザーがよいと答えたら入れる（REQ-048、11.2）。
2. 生成プラグインのリポジトリの入口で、1・2段目を動かす（10.2）。生成した直後に不合格のときは、作業エージェントに直させてやり直す。直しの上限は3回で、組み立てのスクリプトが断ったときの直しも、この3回に数える。上限の回数まで直しても合格しないときは止めて、残った不合格を示す（REQ-039、[クリエイターの構造](creator-structure.md) 4.1）。
3. ユーザーが試験を頼んだときは、EVAL の回数と AI クレジットの見込み（8.2）を示す。ユーザーが EVAL を始めてよいと答えたら、EVAL の道具がそろっているかを確かめ、足りなければ手順1と同じく示して、よいと答えたら入れる。EVAL の道具を入れないと答えても、1・2段目の結果は示す。道具がそろったら、生成プラグインあり・なしで課題を実行し、採点する（10.4）。
4. 結果を、チャットとクリエイターの画面に示す（REQ-039、REQ-041、REQ-044）。

### 10.2 1・2段目の入口

- クリエイターの1・2段目のスクリプトの写しと、それを1つのコマンドで動かす入口を、ひな形のテストのフォルダに入れる。組み立てのときに、生成プラグインに入る。開発の試験とユーザーの試験で、同じ仕組みを使うためである。
- 入口は、初めに道具がそろっているかを確かめる。足りなければ、足りない道具を示して止まる。クリエイターがなくても、何を入れればよいかが分かるようにするためである。
- 入口は、段階ごとの合否と、不合格の試験とその理由を出す。クリエイターと画面が読めるように、同じ内容をファイルにも書く。終了コードでも合否が分かる。
- クリエイターも、この入口を動かす。ユーザーが自分で動かしたときと、結果が同じになるためである。
- 1・2段目は、Linux・macOS・Windows で動かす。Windows では、偽物の `gh` を使う試験と、終了の合図の試験を飛ばす。
- Node 22 では `node --test <フォルダ>` が動かないので、入口は、テストのファイルを渡す形で node を動かす。

### 10.3 ナレッジの番号の突き合わせ

構造の検査で、生成前の確認でよいと答えたナレッジが、すべて生成プラグインに入っているかを確かめる（REQ-039、[クリエイターの構造](creator-structure.md) 3.5）。

- メインのエージェントは、よいと答えたナレッジに番号（例：`K-01`）と種類（合否の決め方か、それ以外か）を付けて一覧にする。組み立てのときに、一覧を生成プラグインのテストのフォルダに入れる。直した後も、リポジトリだけで突き合わせられるようにするためである（REQ-042）。
- 作業の定義の合否の基準に付けるナレッジの番号は、合否の決め方のナレッジのものだけにする。作業エージェントは、それ以外のナレッジを入れた箇所に、その番号を書く。
- 構造の検査は、一覧の番号ごとに、種類で決まった置き場所を調べる。合否の決め方は作業の定義の中に、それ以外は作業の定義とテストのフォルダを除くファイルの中に、番号があるかを見る（[生成プラグインの構造](generated-plugin-structure.md) 6.4）。ない番号は、そのナレッジの文と一緒に、不合格の理由として示す。
- 番号があっても、ナレッジが正しい意味で入ったとは限らない。意味は EVAL で確かめる。

### 10.4 EVAL

**読み込みと隔離**

- Copilot SDK（Copilot CLI をプログラムから動かす公式の部品）で Copilot CLI を起動し、生成プラグインを `--plugin-dir` で読み込む。プラグインなしのときは、何も読み込まない。
- 環境変数 `COPILOT_PLUGIN_DIR_ONLY=true` で、ユーザーがインストールしているほかのプラグインを読み込ませない。あり・なしの比べ合いに、ほかのプラグインが混ざらないようにするためである。読み込まれたプラグインは、セッションの `rpc.plugins.list()` で確かめる。
- ユーザーの `~/.copilot/extensions/` のエクステンションは、`COPILOT_PLUGIN_DIR_ONLY` では止まらない（プラグインの探索しか止めない）。そのため、`extensionLaunchProvider`（下）で、生成プラグインのもの以外のエクステンションの起動を断って混ぜない。「ほかのエクステンションが混ざった」と示すのは、断れなかったときだけにする。
- 実行のたびに、課題の入力のファイルだけを写した、まっさらな作業フォルダで始める。
- 生成プラグインの Web管理画面はエクステンションの中で動き、エクステンションはサンドボックスの外で動く見込みである（[生成プラグインの構造](generated-plugin-structure.md) 4.12、要確認。同 11章 #3）。外で動くと確かめられたら、EVAL では Copilot CLI のサンドボックスを使い、作業フォルダの外への書き込みを止める。確かめるまでは、作業フォルダの外への書き込みを、許可の求めへの答え（下）で拒む。ただし、シェルのコマンドがどこに書くかまでは、許可の求めでは見分けきれない。
- Copilot SDK でエクステンションを読み込むには、セッションの作成で `requestExtensions: true` を指定するだけでは足りない。セッションの `extensionSdkPath`（SDK のパッケージの `dist/`）と、`CopilotClient` の `extensionLaunchProvider`（実験的な API）が要る。EVAL の仕組みが、Node.js でエクステンションを起動する。この方式では、エクステンションの読み込みのときの確認が許可の求めとして出ない。本物のアカウントでも出ないことは、最終確認で確かめる（[生成プラグインの構造](generated-plugin-structure.md) 11章 #1）。
- `-p` で Copilot CLI を直接動かすときは、`EXTENSIONS` の機能の旗が要る。読み込みの確認に答える人がいないので、`--allow-tool='extension-permission-access'`（または `--allow-all-tools`）も要る。
- `--plugin-dir` で読み込んだプラグインも、マニフェストの `$schema` で形式が決まり、Agent Plugins の形式なら `com.github.copilot/` の中のエージェントやフックが読まれる。確認は Copilot CLI 1.0.98 の実装（パッケージに含まれるプログラム、付属の説明、更新履歴）で行った。Agent Plugins の形式のプラグインを `--plugin-dir` で読み込み、スキルが読まれることは、実際に動かして確かめた。カスタムエージェントが読まれたかは、ログインしないと確かめられないので、EVAL のたびに `subagent.started` の記録で確かめる。
- Copilot SDK は、対応する版の Copilot のランタイムを同梱している（SDK 1.0.25 は Copilot CLI 1.0.102、1.0.22 は 1.0.98）。EVAL は同梱のものを使い、`COPILOT_CLI_PATH` で手元の Copilot CLI に替えない。ユーザーがふだん使う Copilot CLI と版が違うことがあるので、使った版を記録に残す。

**質問と許可の求め**

- 課題の頼むときの言葉には、作業に要る情報をすべて書く。入力のファイルの場所（作業フォルダの `inputs/<名前>`）も含む。
- エージェントの質問（`ask_user`）には、`onUserInputRequest` で、決まった返事（「課題に書いたこと以外は決まっていません。判断して進めてください」）を返す。あり・なしで同じ返事にし、ユーザー役の AI は使わない。AI クレジットを増やさず、プラグインなしのときにナレッジが伝わらないようにするためである（7章）。
- 許可の求めには、`onPermissionRequest` で答える。作業フォルダの外への書き込みは拒み、ほかは許可する。組織の管理設定で人の承認が要る求めは、自動では許可せず、EVAL を止めて理由を示す。受け口の第2引数に `promptRequest` が足されたので、人の承認が要るかは `invocation.promptRequest?.managedApprovalRequired` を先に見る。この印を持つのは、commands・write・read・url・workflow の5種類である。
- エクステンションの読み込みのときの確認（`kind` が `extension-permission-access`。[生成プラグインの構造](generated-plugin-structure.md) 4.1）は、上の読み込みの方式では許可の求めとして出ないので、前もって許可する指定は要らない。
- 生成プラグインありのときも、実行のエージェントの許可の求めに、同じ決めで答えるのは、この `onPermissionRequest` だけである。生成プラグインのエクステンションは、許可の求めを見るためだけに登録し、答えない（`no-result` を返す）。画面に「チャットで確認を待っています」と示すだけで（[生成プラグインの構造](generated-plugin-structure.md) 4.14）、画面の操作でも答えない。答えが出ると待ちの終わり（`permission.completed`）として届き、画面の待ちが消える（チャットで答えたときに届くことは確かめた。同 11章 #21）。
- エクステンションは答えないので、EVAL の `onPermissionRequest` と答えの取り合いにならず、EVAL の答えが効く。
- AI クレジットの予算を使い切ったという求め（`session_limits_exhausted.requested`）には、クレジットを足さずに止める。ユーザーが承認していない費用を使わないためである。
- 裏で動くサブエージェントの許可の求めも、この `onPermissionRequest` に届き、答えると効くかは要確認である（[生成プラグインの構造](generated-plugin-structure.md) 11章 #21）。違ったときの代わりの案は、Copilot CLI を起動するときに、任せるツールを前もって許可する指定（`--allow-tool`）を渡すことである。

**Web管理画面の操作と終わり**

- 7章と同じく、Playwright でブラウザーを操作し、人と同じ流れ（設定 → 開始 → 監視 → 結果）で生成プラグインを動かす。チャットに出た URL（`assistant.message`）を開き、課題に書いた設定を入れて開始する。実行中の確認（許可の求めなど）には、画面では答えない。上の `onPermissionRequest` と `onUserInputRequest` が答える。生成プラグインには、試験のためだけの機能を足さない。
- Copilot SDK の EVAL では Issue を起票しない。そのため、エクステンションの中から `gh` のログインで起票できるか（[生成プラグインの構造](generated-plugin-structure.md) 11章 #11）の影響を受けない。
- 生成プラグインありのときは、画面に終わった理由（REQ-012）が出たら終わりとし、結果の表示を読む。なしのときは、エージェントが手番を終えたら（`session.idle`）終わりとする。
- EVAL のコマンドは数十分かかる。Copilot CLI 1.0.102 のシェルのツール `bash` は、`initial_wait`（30〜600秒）を過ぎても終わらないコマンドは、途中の出力を返して動き続け、終わると知らせが来る。クリエイターのメインのエージェントは、この知らせを待ち、同じコマンドを動かし直さない。

**採点と記録**

- 採点は、生成プラグインの外で行う。生成プラグインの検証エージェントが出した合否は使わない（REQ-041）。
- 基準ごとに、文字や形で決まるもの（ファイルがある、決まった言葉がある、最後の行が決まった文字であるなど）はプログラムで採点し、それ以外はモデルが判定する。モデルが判定する分も、見込みと使った分に入れる。
- 実行ごとに、次のイベントを記録のファイルに残し、採点と結果に使う。

  | イベント | 使い方 |
  | --- | --- |
  | `skill.invoked` | 生成プラグインのスキルが呼ばれたか（`pluginName`） |
  | `subagent.started`、`subagent.completed`、`subagent.failed` | カスタムエージェントが動いたか。どのモデルで動いたか（`model`） |
  | `tool.execution_start`、`tool.execution_complete` | 使ったツール |
  | `user_input.requested`、`permission.requested` | 質問と許可の求め |
  | `assistant.message` | チャットに出た URL と返事 |
  | `assistant.usage` | 呼び出しごとのモデル、トークン、費用 |
  | `session.idle` | 手番の終わり |

- 結果として、実行ごとの基準ごとの合否、あり・なしの点数とその差、使った AI クレジットを示す（REQ-041）。

### 10.5 EVAL の仕組みが2つになること

EVAL を動かす仕組みは、開発の試験（5章）とユーザーの試験で2つになる。

| | 開発の試験 | ユーザーの試験 |
| --- | --- | --- |
| エージェントを動かす部品 | Agent SDK（Claude Code） | Copilot SDK（Copilot CLI） |
| 試す生成プラグイン | Claude Code 向けに置き換えた版（4章） | そのまま |
| 人の代わりの返事 | ユーザー役の AI | 決まった返事 |

- 課題と基準のファイルの形、採点のスクリプト、Web管理画面の操作は、2つで同じものを使い、エージェントを動かす部分だけを分ける。保つものを減らすためである（憲章 第10条）。
- 開発のクラウド環境では Copilot CLI を動かさない（1章）ので、開発の試験は Copilot SDK に寄せない。
- Copilot SDK でエージェントを動かす部分は、最終確認で人が手元で確かめる（9章）。課題と基準のファイルの読み込み、採点、Web管理画面の操作は、2つで同じものを使うので、開発の試験で確かめられる。

## 11. 試験環境に必要なもの

### 11.1 開発の試験

- Agent SDK（Claude Code と同じ版にそろえる。今は 0.3.310 で、Claude Code 2.1.310 に当たる）。peer の `@anthropic-ai/sdk`・`@modelcontextprotocol/sdk`・`zod` も版を固定する。
- bubblewrap と socat（Linux で OS のサンドボックスを動かすため）。クラウド環境には入っていないので、環境の設定のセットアップスクリプトで入れる。
- ブラウザー（Chromium）と、ブラウザーを操作する Playwright。ブラウザーはクラウド環境に入っている。Playwright は、そのブラウザーに合う版（1.56.1）に固定して、試験の仕組みのフォルダに入れる。全体に入っている Playwright は、ESM 形式のスクリプトから読み込めなかったためである。環境のブラウザーは 1.56.1 用で、1.64.1 では起動に失敗した。
- Python と PyYAML・jsonschema（1段目の検査と変換スクリプト）、tiktoken（SKILL.md の本文のトークンの数を数える）、python-docx・openpyxl（模擬ユーザーの docx・xlsx を作る）

### 11.2 ユーザーの試験

| 道具 | 使うところ |
| --- | --- |
| Python と PyYAML・jsonschema | 1段目 |
| Node.js（Copilot SDK は 20.19 以上か 22.12 以上）と npm | 2段目の Web管理画面の試験、EVAL |
| Playwright とブラウザー（手元の Chrome か Edge。どちらもないときは Playwright の Chromium） | 2段目の Web管理画面の試験、EVAL の画面の操作 |
| Copilot SDK（`@github/copilot-sdk` 1.0.25） | EVAL |
| Linux でサンドボックスを使うときは、bubblewrap 0.5.0 以上、slirp4netns、util-linux 2.35 以上（unshare と nsenter）、iptables・ip6tables とその -restore（外への通信を許すかどうかに関係なく、Linux のすべてのサンドボックスで要る） | EVAL |

- 試験の前に、入口とクリエイターが、道具がそろっているかを確かめる。足りないときは、クリエイターが足りない道具と入れ方を示し、ユーザーがよいと答えたら入れる（REQ-048）。
- 1・2段目は、Linux・macOS・Windows で動かす（10.2）。
- Python のパッケージは仮想環境に入れ、ユーザーの環境全体は変えない。Node.js のパッケージも、試験のためのフォルダに入れる。
  - 1・2段目の道具は、生成プラグインの `tests/.venv` と `tests/node_modules` に入れる。git には入れない。生成プラグインのリポジトリだけで1・2段目が動くようにするためである（REQ-042）。
  - EVAL の道具（`@github/copilot-sdk` 1.0.25 と playwright 1.56.1）は、クリエイターのデータの場所 `<COPILOT_HOME>/plugin-data/plugin-creator/tools/` に1つだけ入れる（`npm install --ignore-scripts`。約190MB）。プラグインが実行中に書くデータは、インストール先ではなく `PLUGIN_DATA` に置くという公式の勧めに合わせる。
- ブラウザーは、Playwright の `channel`（`chrome`、`msedge`）で手元の Chrome か Edge を使う。どちらもないときだけ、Playwright の Chromium を、Playwright の既定の場所（ホームフォルダの中の共通の場所）に入れる（REQ-048）。生成プラグインごとに入れ直さないためである。
- 要確認：Python や Node.js そのものがないときの入れ方（OS ごとに違う）。
