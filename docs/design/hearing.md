# ヒアリングの設計

クリエイターのスキル make-plugin と change-plugin が、ユーザーからナレッジを引き出すヒアリングを、どう進めるかを定める。ユーザーから見た振る舞いは [作る流れの要件](../specs/creation-requirements.md)、[改善・設計変更の要件](../specs/improvement-requirements.md)、[試験の要件](../specs/test-requirements.md) にある。

## 1. 範囲と分担

- 範囲は、make-plugin が呼ばれてから、生成前の確認でユーザーがよいと答えるまでのヒアリングである。既存のプラグインの作り直しも含む。今のプラグインをそのフォルダのまま直すとき（改善・設計変更）のヒアリングは、change-plugin が行う（3.4）。
- 生成の後（組み立て、試験、できたことの説明、質問の改善案の起票）と、直す前の確認の後（直す、試験、コミット、直したことの説明）は [クリエイターの構造](creator-structure.md) 3.4・4章にある。改善案の対象の判定だけは、この設計書の 11章に書く。

| 書いてあること | 文書 |
| --- | --- |
| ユーザーから見た振る舞い | 作る流れの要件、改善・設計変更の要件、試験の要件 |
| 部品と、推論の重さによる分担 | [クリエイターの構造](creator-structure.md) |
| クリエイターのエクステンションのツールとフックの一覧 | [生成プラグインの構造](generated-plugin-structure.md) 9章 |
| 試験のやり方 | [試験の設計](testing.md) |
| ヒアリングの流れ、問いの形、確かめ方、記録の中身、コンパクションと再開への備え、SKILL.md の組み立て | この設計書 |

この設計書の用語：

| 用語 | 意味 |
| --- | --- |
| ヒアリング | クリエイターがユーザーからナレッジを引き出すやり取り |
| 問い | ヒアリングの中の1回の問いかけ。`ask_user` の1回の呼び出しに当たる |
| 手番 | ユーザーが打った1回の発言から、エージェントが返事をし終えるまで。`ask_user` の答えでは区切られない |
| 項目 | ヒアリングで漏れなく聞くもの（7.2） |
| 候補 | ファイルや頼みの文から推し量り、まだユーザーが確かめていないナレッジ |
| 記録のツール | ヒアリングの状態とナレッジなどを書く、クリエイターのエクステンションの「知らせる」ツール。一覧は [生成プラグインの構造](generated-plugin-structure.md) 9章 |
| 状態取得ツール | ヒアリングの状態を返す、クリエイターのエクステンションのツール（`<クリエイターの名前>_state`。7.5） |

## 2. 依って立つ Copilot CLI の事実

- この章の事実は、断りがない限り、Copilot CLI 1.0.98 で実測し、1.0.101 でも同じであることを確かめた（オフラインのモードで偽物のモデルにつないで確認、2026-10-22）。1.0.101 で測り直したのは、`ask_user` のフォームと結果の文、Esc と Ctrl+D、autopilot、同じ手番の自動コンパクションでスキルが消えること、フックの差し込みの場所、`@ファイル`・`view`・文書の送られ方、2.7 のシステムプロンプトである。npm の最新の 1.0.102（2026-10-21）でも、2.7 のシステムプロンプトは同じだった。
- 限界：BYOK（自前の API キーとエンドポイントでモデルを使う設定）の経路だけを見た。GitHub にログインして Copilot のモデルを使う経路で同じかと、本物のモデルが指示にどう従うかは確かめていない。Auto を選んだときのシステムプロンプトも確かめていない（14章）。

### 2.1 ask_user

| 事実 | 使う節 |
| --- | --- |
| 対話モードの `ask_user` はフォームの形で、1つのフォームに複数の欄を置ける | 4.1 |
| 選択肢の欄には、自由入力の行（「Other (type your answer)」）が必ず付く | 4.2 |
| `default` を付けた選択肢にカーソルが合う。おすすめの印は画面に出ない | 4.2 |
| `default` がないと、最初の選択肢にカーソルが合い、Enter だけでそれが選ばれる。選択肢の欄が1つだけのフォームは、選ばずに確定できない（閉じるのは Esc か Ctrl+D だけ） | 4.2、6.1 |
| 2つ以上の欄があるフォームでは、Tab で飛ばした欄は、`required` を付けても答えに入らない。答えが1つだけのときは、「User responded: b1」のように項目名なしでモデルに届く | 4.1 |
| 値と表示名を分けた選択肢（`oneOf`）では、表示名ではなく値がモデルに返る | 4.2 |
| 自由入力の欄は Enter で確定する。改行は Ctrl+J や Alt+Enter で入る。10行・約1万字の貼り付けも欠けずに届いた | 4.2 |
| Esc で閉じると「User cancelled the request.」が返る | 5.5 |
| Ctrl+D で断ると「The user is not available to respond and will review your work later. Work autonomously and make good decisions. If the request is genuinely ambiguous or unresolvable, stop and call task_complete …」が返る | 5.5 |
| autopilot では、Ctrl+D と同じ文が、ユーザーに聞かずに返る。`task_complete` ツールが加わり、呼ばずに手番を終えると、続けるよう促す発言が送られる（既定で最大5回、`--max-autopilot-continues`）。その発言は「Do NOT call task_complete if: - You have open questions or ambiguities - make good decisions and keep working」と、あいまいでも進めるよう求める | 5.5、10.2 |
| `task_complete` は、autopilot と plan モードで加わる。説明は「Only call this tool when you are confident the task is fully complete.」である | 5.5 |
| `-p` と `--no-ask-user` では、`ask_user` がない | 3.1 |
| サブエージェントは、`tools` に書いても `ask_user` を持たない | 4.1、9 |
| Copilot CLI のシステムプロンプトは、Copilot CLI で選べる全モデルで同じ `<ask_user>` 節を持ち、文章での質問を禁じ（「Never ask questions via plain text output.」）、おすすめを `default` にするよう指示する。全モデルに「Ask for guidance if uncertain; use the ask_user tool to ask clarifying questions」もある（1.0.101） | 4.1、4.2 |
| Copilot CLI のシステムプロンプトは、関係する好みを1つのフォームにまとめて聞くことも勧める（「You want to collect several related preferences at once rather than asking one at a time」） | 4.1 |

### 2.2 SKILL.md とコンテキストウィンドウ

| 事実 | 使う節 |
| --- | --- |
| システムプロンプトに入るのは、スキルの名前と description だけである | 10.1 |
| `skill` ツールで呼ぶと、SKILL.md の本文が会話の履歴に入る。スキルのフォルダの別のファイルはパスだけが並び（Related files）、中身はモデルが `view` で読む | 10.1 |
| 本文は `<skill-context>` で囲まれ、「Base directory for this skill: <フォルダ>」が添えられる（1.0.98〜1.0.102 で同じ） | 10.1 |
| Related files には、SKILL.md 以外のスキルのフォルダのファイルがすべて、1件ずつ並ぶ。97件のフォルダでも、件数にまとめられずに全部並んだ（1.0.102） | 10.1 |
| プラグインのスキルを `skill` ツールで呼ぶ名前は `make-plugin` である。ユーザーが打つコマンドは、実機では `/<プラグイン>:<スキル>`（クリエイターは `/<クリエイターの名前>:make-plugin`）で、`/make-plugin` は「Unknown command」になる。公式のコマンドリファレンスの `/<プラグイン>/<スキル>` とは食い違う。スキルの名前がプラグインの名前と同じとき（生成プラグインの入口のスキル）は `/<名前>` になる | 10.1 |
| 毎回、システムプロンプト、ツールの定義、履歴のすべてがモデルに送られる | 7.5、9 |
| 自動コンパクションは、コンテキストウィンドウの約80%を使うと始まる（公式ドキュメント「Context management」と実測） | 8 |
| 自動コンパクションの後に原文で残るのは、ユーザーが打った発言、要約、前の手番までに最後に呼んだスキルの本文（それより前に呼んだスキルはパスだけ）、todo である | 8 |
| 自動コンパクションで、`ask_user` の答え、ツールの結果（エクステンションのツールの返り値を含む）、`view` で読んだ中身は消える | 7.1、8 |
| 手番の途中でモデルが `skill` ツールで呼んだスキルは、その手番の中で自動コンパクションが起きると、本文もパスも残らない。次にユーザーが打った手番でも戻らない。ユーザーが `/<クリエイターの名前>:make-plugin` と打って始めた手番で同じことが起きるかは、確かめていない（14章） | 8 |
| コンパクションの後に `skill` ツールで呼び直すと、本文がもう一度入る。参考にとどめる実験1回だけで確かめた（その実験では、上限を超えて履歴が削られ、偽物のモデルが手順を繰り返した） | 8 |
| エクステンションのプロセスはコンパクションをまたいで動き続け、`session.compaction_start` と `session.compaction_complete` のイベントを受け取れる。1.0.101 では、イベントに `compactionAttemptId`、`outcome` などの項目が足された（1.0.98 の項目は残る） | 8 |

### 2.3 再開と /clear

- `--resume=<セッションの番号>` か `--continue`（最後のセッション）で前の会話に戻ると、履歴とセッションのフォルダが戻る。
- `/clear` は新しいセッション（新しいセッションの番号）になる。エクステンションも読み込み直され、メモリの中の値は消える（Copilot CLI 1.0.98 の npm パッケージの `copilot-sdk/docs/extensions.md`）。

### 2.4 ファイルと貼り付け

| 事実 | 使う節 |
| --- | --- |
| テキストのファイルの `@ファイル` は、中身ではなくパスと行数だけを入れる。公式のショートカットの表（中身を入れる）と食い違う | 3.1 |
| `view` は 20KB を超えるファイルを読まない | 9、10.1 |
| `view` は docx・xlsx・pptx・PDF を文字にせず、生のバイトを返す。文書を文字にする組み込みのツールはない | 9 |
| 打った発言の `@` やパスの貼り付けで示した文書は、モデルの API の形式によって、ファイルのまま提供元に送られる（native document）。対象は pdf・doc・docx・xls・xlsx・ppt・pptx・rtf・odt で、拡張子で決まる。OpenAI Responses の形式はこれらすべてを送り、Anthropic の形式は PDF だけを送る。chat completions の形式はどれも送らず、パスだけを入れる。どれを送るかは、モデルの名前ではなく通信の形式で決まる（Claude のモデル名でも Responses の形式なら全部を送り、GPT-6 のモデル名でも Anthropic の形式なら PDF だけを送った。1.0.101）。ログインした経路で、各モデルがどの形式で送られるかは確かめていない（H7） | 3.1 |
| ファイルのまま送ったときは、発言に「The user included native document attachments in this message. Review any attached document directly before responding, and do not call tools just to read an attached document.」の文が加わる | 3.1 |
| ファイルのまま送った文書は、その発言の一部として履歴に残る見込みである（確かめていない） | 3.1、9 |
| 提供元が文書を断ると（400）、その手番はエラーで終わる。履歴の中の文書は、パスに置き換わる | 3.1 |
| 入力欄への貼り付けは、約20KB までは全文がモデルに届く。それより大きいと、セッションのフォルダのファイルに保存され、モデルには `<pasted_content file="…" />` のパスだけが届く | 3.1 |

### 2.5 フックと画面への出方

- `onPreToolUse` と `onPostToolUse` は、`ask_user` でも呼ばれる（Esc と Ctrl+D のときも）。
- `onPostToolUse` の入力には、問い（`toolArgs`）と答え（`toolResult`）がそろう。
- `onUserPromptSubmitted` は、ユーザーが打った発言でだけ呼ばれ、`ask_user` の答えでは呼ばれない。
- 差し込み（`additionalContext`）の入る場所と、ユーザーの画面への出方：

  | フック | 入る場所 | ユーザーの画面 |
  | --- | --- | --- |
  | `onPostToolUse` | ツールの結果の末尾 | `ask_user` の後では「Tool "ask_user" succeeded. Additional guidance from postToolUse hooks:」と一緒に出る。`suppressOutput` を返しても消えない |
  | `onPreToolUse` | そのツールの結果の後ろに、別のユーザーのメッセージとして | 出ない |
  | `onUserPromptSubmitted` | その発言の末尾（`<system_reminder>`） | 出ない |

- コンパクションで、それまでの差し込みはすべて消える。フックはコンパクションの後も呼ばれる。
- 差し込みは 10,240 バイトで、印なく切られる。
- エクステンションのツールの返り値は、ユーザーの画面に1行で出る。

### 2.6 サブエージェント

- サブエージェントが受け取るのは、自分のシステムプロンプトと、渡した prompt だけである。返るのは最後の文だけである。
- 複数のサブエージェントを並列に呼べる。
- サブエージェントのモデルは、呼び出しごとの値、`~/.copilot/settings.json` の subagents の上書き、エージェントの定義の `model`、親のセッションの値の順で決まる（公式のコマンドリファレンス）。
- 組み込みの explore（費用の低いモデル）と research（claude-sonnet-5）は、定義でモデルが決められている（Copilot CLI 1.0.98〜1.0.102 の npm パッケージの `definitions/`）。公式のコマンドリファレンスの表は research を claude-haiku-4.5 としていて、パッケージと食い違う。
- サブエージェントの `tools` には、エクステンションのツールを名前のまま書けて、呼べる（[生成プラグインの構造](generated-plugin-structure.md) 11章 #8）。
- カスタムエージェントが `tools` の別名 `search`・`web` で対応するツールを受け取れるのは、更新履歴では 1.0.100 からである（「Custom agents that declare the documented `search`, `web` or `todo` tool aliases … now receive the matching tools」）。1.0.102 で、`search` で検索のツールが渡ることを確かめた（Claude の族は grep・glob、GPT の族は rg・glob）。`web` は確かめていない（[生成プラグインの構造](generated-plugin-structure.md) 11章 #24）。

### 2.7 モデルごとのシステムプロンプト

- Copilot CLI のシステムプロンプトは、モデルの ID ごとに族に分かれる（1.0.101 で、Copilot CLI で選べる全モデル（33 のモデル名）を測った。1.0.102 でも同じ）。
- 族はモデルの ID の完全一致で決まり、通信の形式では変わらない。知らない ID は「その他」の族になる。

| 族 | モデル（2026-10 に Copilot CLI で選べるもの） | ヒアリングと逆向きの指示 |
| --- | --- | --- |
| GPT | GPT-6.1 Sol、GPT-6 Sol、GPT-6 Luna、GPT-6 Astra、GPT-5.6 Sol・Terra・Luna、GPT-5.3-Codex | 「…then stop—no recap, optional extras, offer to continue, or follow-up question.」「Bias to action: … assume they want tools/code used.」「Make reasonable assumptions for missing details; do not stop at analysis or a partial fix.」 |
| Claude 5 | Claude Haiku 5.5、Sonnet 5.5、Sonnet 5、Opus 5.5、Opus 5、Opus 4.8、Fable 5、Fable 5.1 | 「limit your response to 100 words or less」「Prioritize brevity. Default to the shortest possible response that satisfies the request.」 |
| その他 | Gemini 4 Argon、Gemini 3.8 Flash、Claude Haiku 4.5、Grok、Kimi K3、MAI-Code-1.1-Flash | 「try to limit your response to 100 words or less」 |

- どの族にも、同じ `<ask_user>` 節（2.1）がある。
- GPT の族の「Make reasonable assumptions for missing details」は、推し量りで埋めずに `ask_user` で聞くヒアリングの決まりと、まともにぶつかる（10.2）。
- 既定のモデルは Claude Sonnet 5.5 である（公式ドキュメント「Supported AI models in GitHub Copilot」）。
- Auto を選んだときにどの族になるかは、確かめていない（14章）。

## 3. ヒアリングの流れ

### 3.1 新しく作るとき

| 段階 | 目的 | 終わる条件 |
| --- | --- | --- |
| 始まり | 使える状態かを確かめ、続きか新しいかを決める | 記録ができ、画面の URL を示した |
| 実物を受け取る | 前回の1回のファイルと、いつも使うファイルの場所を受け取る | ファイルの場所を記録したか、「ない」の答えを得た |
| 読む | ファイルから候補を取り出す。ファイルがなければ飛ばす | 返った候補をすべて記録した |
| 前回の1回 | 最近の1回をたどってもらう（REQ-016） | 項目「前回の1回」が未着手でない |
| 決まりの確かめ | ファイルから読み取った決まりを確かめる（REQ-017） | ファイルから読み取った候補が残っていない |
| 項目の点検 | 仕様の10項目の聞き漏らしをなくす（REQ-015） | 10項目に未着手がない |
| 資産と公開のプラグイン | 流用するものを決める（REQ-018、REQ-019） | 資産と、標準機能と公開のプラグインの項目が未着手でない |
| 画面 | Web管理画面で設定したいこと・見たいことを決める（REQ-026） | 画面の3つの項目が未着手でない |
| 生成前の確認 | 一覧と案を確かめてもらう（REQ-020） | ユーザーがよいと答え、段階を「生成」に進めた（6.3） |
| 生成 | 組み立て、試験、できたことの説明、質問の改善案（[クリエイターの構造](creator-structure.md) 4章） | 生成プラグインにタグ `plugin-creator-generated` が付き、できたことの説明と質問の改善案を示した（11章） |

段階の名前は、記録の「今の段階」に入れる（7.1）。段階ごとに、することを次に書く。

**どの段階でも**

貼り付けと文書がそのまま届くことは、どの段階でも起きうる。そのため、次の扱いは段階ごとではなく、SKILL.md の本文に置く（10.1）。

- 答えに `<pasted_content file="…" />` が届いたら、そのファイルが貼り付けられた答えとして扱う（2.4）。
- ユーザーが打った発言で、文書がファイルのままメインのエージェントに届いたとき（2.4）は、メインのエージェントがそのまま読む。届いた後に読み取り役に回しても、メインのエージェントのコンテキストは小さくならないためである。

**始まり**

- `ask_user` と、画面を開くツール（`<クリエイターの名前>_open`）があるかを確かめる。
- ないものがあれば、その直し方をすべて示し、ヒアリングを始めない（REQ-023）。
  - `ask_user` がないとき：`-p` と `--no-ask-user` を付けずに、対話モードで起動し直す（2.1）。
  - 画面を開くツールがないとき：[クリエイターの構造](creator-structure.md) 4.3 の2つの直し方。
- 画面を開くツールを呼び、URL を、最初の問いより前に、文章でチャットに示す（REQ-043）。URL は画面を開くツールの返り値にだけあり、文章で示さないと、ユーザーに見えなかったためである。
  - 画面を開くツールの返り値は、1行目を「plugin-creator の画面：<URL>」にし、2行目で、上の1行だけをほかのツールを呼ぶ前にチャットの文に書くよう、メインのエージェントに求める（「この1行」だと2行目そのものとも読める）。ユーザーに向けた文（「ブラウザーで開いてください」）だけだと、もう示したと取り違えやすい。手順を思い出させるより、直前の返り値の文のほうが守られやすいためでもある。返り値は画面に1行で出る（2.5）ので、1行目はユーザーが見ても分かる URL の行にする。外側の EVAL（改善）の3回目では、画面を開くツールと状態取得ツールを1つの応答で続けて呼び、URL を書く手番がなくなって、URL は確認まで出なかった。
- 状態取得ツールを呼ぶ。このセッションの記録があれば（コンパクションの後に make-plugin を読み直したときなど）、記録の段階から続ける（8章）。
- 記録が段階「生成」まで進んでいれば（同じセッションで生成が終わった後に、別の生成プラグインを頼まれたとき）、`/clear` してから頼み直すよう示して止まる。前のヒアリングの内容がコンテキストに残っていて、新しいヒアリングに混ざるおそれがあるためである。
- 新しく始めるときは、これからの流れを短く、画面の URL を示した後、最初の問いより前に文章で示す。モデルの選び方は示さない（REQ-047）。URL は画面を開くツールの直後に1行で書く（上の手順）ので、「URL と一緒に」と書くと、URL を書いたことで済んだと取り違え、流れを書かないおそれがあるためである。
- 頼みの文から分かること（作業、目的、頼む場面と言い方）を、候補として記録する。

**実物を受け取る**

- 1つの問いで、前回の1回で受け取ったファイルと作ったファイル、いつも使っているファイル（テンプレート、手順書、スクリプトなど）の場所を、まとめて書いてもらう。「ない」とも答えられる。
- 場所（パスか `@`）で受け取る。中身の貼り付けは頼まない。例外は、PDF をファイルのまま届けられず、テキストにしてもらうときである（読む）。
- PDF をファイルのままモデルに渡してもらうやり方は未決である（14章）。`ask_user` の自由入力の欄に書いた `@` で、ファイルのまま届くかを確かめていないためである。
- 示されたファイルは、決まりの候補の元（REQ-017）、資産の候補（REQ-018）、EVAL の課題の入力（REQ-038）になる。

**読む**

- まだ問わない。
- ファイルを読み取り役に読ませる（9章）。ファイルのまま届いた文書は、メインのエージェントが読む（どの段階でも）。
- 返った候補は、すぐ記録する。ツールの結果はコンパクションで消えるためである（2.2）。
- PDF が届かないときは、ユーザーにテキストにしてもらう（PDF の文の貼り付けか、テキストのファイル）。
- 読み取り役が読めなかったファイルは、ユーザーに示す。

**前回の1回**（REQ-016）

- 最近実際にやった1回を、最初から順に話してもらう。途中で口を挟まない。
- 頼みの文に作業の流れが順を追って書かれているときは、最初から話してもらう代わりに、頼みの文から理解した流れを番号付きで問いの文の中に示し（4.3）、最近の1回でしたことのうち、その流れに書かれていないことを聞く。形は聞き出すヒアリング（4.2）のままで、選択肢も答えの例も付けない。
  - 頼みの文に書かれた流れを、もう一度書くよう求めないためである（4.4）。開発者が答えた外側の EVAL（[試験の設計](testing.md) 6.7）では、頼みの文に11段の流れを書いたのに、調べ始めてから終わるまでを順に書くよう聞かれた。開発者は「答えない」と答え、次の問いへの答えで「最初の初期プロンプトであなたに伝えられてませんか？」と、頼みの文をもう一度貼り付けた。
  - 聞くのは、流れに書かれていない、実際にしたことである。本人が当たり前だと思っている手順や決まりは、頼みの文にも書かれにくいためである。この問いの答えは、項目「前回の1回」の抜き書き（7.2）の元になる。頼みの文はユーザーの答えに数えないので（7.4）、示した流れからは抜き書きを取らない。
- 話を番号付きの短い時系列にして返し、違うところと足りないところを聞く。頼みの文の流れを示したときは、答えで足した段と変わった段を入れた時系列にする。足した段も変わった段もなければ、この問いは出さない。示した流れを、そのままもう一度示すことになるためである。
- 時系列の抜けと、判断が要った段だけを、深掘りの型（5.2）で聞く。
- ファイルの候補と食い違うところは、その場で聞く（問いの例：「ファイルでは A、前回は B でした。普段はどちらですか？」）。
- 話に出た手順や決まりのうち、まだ聞いていないものは、その場で聞く。
- 最後に、「初めての人がやると、どこで間違えそうですか？」を1回聞く。
- 根拠：理由を聞くより「何をしたか」を聞くほうが確かな答えになり、時系列の抜けは聞き漏らしの合図になる（Freeman ほか 1991）。最近の1回をなぞる形は、Hoffman 2005 の Recent Case Walkthrough にならう。

**決まりの確かめ**（REQ-017）

- 候補を1つずつ、生成プラグインの振る舞いに効く順に確かめる。形は 6.1。

**項目の点検**（REQ-015）

- 仕様の10項目を順に見る。
- 記録から分かった項目は、分かったことを示し、違うところと足りないところを聞く。仕様 REQ-015 は、この聞き方も「質問した」に数える。示した候補は、答えに合わせて「決まった」か「外した」にする。
- 分からない項目は、具体的に聞く。
- 項目「いつもと違うとき」は、いつもと違った1回を話してもらう。

**資産と公開のプラグイン**（REQ-018、REQ-019）

- 資産の候補（読み取り役が返したものと、前回の1回に出たツールとファイル）を示し、ほかに使っているものを聞く。
- メインのエージェントが、Copilot CLI の標準機能と公開のプラグインを調べる。使えるものがあれば、使うかを決める質問（4.2）で聞く。

**画面**（REQ-026）

- 開始前に設定したいこと、実行中に見たいこと、終わった後に見たい結果と見せ方を、1つずつ聞き出す。
- 答えを、用意した画面の部品（[生成プラグインの構造](generated-plugin-structure.md) 4.9）のどれで出すかを、決める質問で決める。用意のない表示を望まれたら、近い部品を示す。

**生成前の確認**

- 未着手の項目がなくなったら、「ほかにありますか？」を1回聞いてから始める（5.7）。
- 進め方は 6.3。

### 3.2 作り直しのとき

骨組みは 3.1 と同じで、次だけが違う（REQ-032〜REQ-036）。

- 始まり：示されたフォルダにプラグインのマニフェスト（`plugin.json`）があれば、作り直しとして扱う。以前の形式の見分け方は、14章で確かめる。ただし、手元のプラグインのフォルダのまま機能を足す・設計を変える・機能を消す頼みなら、記録を作らずに change-plugin に移る（3.4、REQ-052）。フォルダを示して「作り直したい」とだけ頼まれたときは、記録を作る前に、元のフォルダを直すか新しいフォルダに作るかを聞き、直すなら change-plugin に移る（3.4、REQ-052）。
- 実物を受け取る：元のプラグインのフォルダと、あれば前回の1回のファイルを受け取る。
- 読む：読み取り役が元のプラグインを読み、できていたこと（何を頼むと、何をするか）、決まりの候補、流用できる部品（スクリプト、MCP サーバーなど）を返す。元のプラグインの指示文は、メインのエージェントの会話に入れない。入れると、その指示に従うおそれがあるためである。
- 読むの後に、段階「できていたことの確認」を置く。一覧を示し、要らないものを書いてもらう。最初はすべて引き継ぐ（REQ-033）。
- 前回の1回と画面は、必ず行う（REQ-034）。
- 項目の点検：元のプラグインから読み取って確かめたナレッジがある項目は「聞いた」にし、聞き直さない（REQ-034）。できていたことの確認で残しただけのもの（「〇〇と頼むと、〇〇をする」の形）は、この確かめたナレッジに含めない。
- 資産と公開のプラグイン：流用する部品を決める（REQ-035）。
- 生成前の確認：引き継ぐことと変わることも示す（REQ-035）。

### 3.3 前回の1回やファイルがないとき

- 前回の1回がない（まだやったことのない作業）ときは、段階「前回の1回」で「初めてやるとしたら、最初に何をして、そのあと何をしますか？終わるまでを順に書いてください。」と聞き、想定の1回を終わるまで順に話してもらう（REQ-016）。進め方は 3.1 と同じである。頼みの文の流れを示したときは、初めてやるとしたら、その流れのほかに何をするかを聞く。
- ファイルがないときは、段階「読む」と「決まりの確かめ」を飛ばす。
- どちらのときも、EVAL の課題の入力は仮のファイルにする（6.5、REQ-038）。

### 3.4 直すとき

ユーザーが今のプラグインのフォルダを示して、機能を足したり設計を変えたりするよう頼んだときは、スキル change-plugin で進める（REQ-052〜REQ-057）。段階の名前と順は 3.1 と同じで、次の表と下に書いたことだけが違う。段階「できていたことの確認」は使わない。機能ごとに要るかを聞かないためである（REQ-054）。

**始まり**

- 直すフォルダが頼みから分からなければ聞く。
- フォルダを示して「作り直したい」とだけ頼まれたときは、元のフォルダを直すか、新しいフォルダに作るかを、決める質問で聞く（REQ-052）。記録を作る前に聞く。作る流れの記録ができると、直す流れの記録を作れないためである（7.5）。make-plugin が呼ばれたときも、始まりの初めに同じ問いを置く。
- 受け付けない頼み（生成プラグインの条項に反するもの、どの生成プラグインにも共通する部分をそのプラグインだけ変えるもの）は、理由を示す。画面の表示の頼みでは、用意した部品のうち近いものを示す。すべてが受け付けられないときは止まる（REQ-052）。
- `change-check` が断ったときは、返った直し方（起動し直す、元のリポジトリを手元に取ってくる、コミットするなどの実際のコマンド）をそのまま示して止まり、記録を作らない。止まっても、フォルダは変わらない（REQ-053）。
- 同じセッションに作る流れの記録があるときは、`/clear` してから頼み直すよう示して止まる。
- 画面の URL は、画面を開くツールだけを呼んだ直後に、ほかのツールを呼ぶ前に、返り値から写して1行でチャットの文に書く（REQ-043）。返り値は画面に1行で出るだけで（2.5）、チャットの文で示さないとユーザーに届かなかったためである（3.1）。画面を開くツールは、ほかのツールと同じ応答で呼ばない。外側の EVAL（改善）の1回目では、ツールは呼んだが URL をチャットに書かず、確認まで URL が出なかった。3回目では、始まりの手番が、画面を開くツールと状態取得ツールを続けて呼んでから URL と流れを同じ文に書く形で、流れに「直すと決まってから」の条件があったため、文の全体が後回しになり、最初の問いより前に URL が出なかった。
- これからの流れ（段階を words.md の言葉で並べたもの）の文は、直す流れの記録を作るツールの返り値の1か所にだけ置く（7.5）。返り値は、画面を開くツールの返り値と同じ並びにする。1行目に流れの文そのもの、2行目に「上の1行（これから、次の順に…）だけを、ほかのツールを呼ぶ前に、そのままチャットの文に書いて、ユーザーに示してください。」、記録の知らせ（7.5）はその後に置く。change-start.md の7は、返り値に流れの文があれば、ほかのツールを呼ぶ前に、そのまま書く、という条件のない手順である。URL と結び付けないのは、流れの条件（新しく作る頼みや「作り直したい」とだけの頼みでは、直すと決まってから書く）が、URL まで遅らせたためである。外側の EVAL（改善）の1〜4回目では、流れは一度も書かれなかった（2回目は「URL をまだ書いていなければ一緒に書く」で済んだと扱い、3回目は「3で書いている」と済んだこととして書いた7で思い出す手がかりがなかった）。4回とも、記録を作るツールの直後に作業用の一時フォルダの残りを確かめ、その結果を受けて次の手順が流れを書くことになった時点でも、書かずに、段階を進めるツールか、次の段階のファイルを読むツールを呼んだ（3回目は、その確かめと段階を進めるツールを同じ手番で呼んだ）。4回目は、返り値の「次のツールを呼ぶ前に書いて」があっても書かなかった。一方、画面の URL は、書く1行そのものを返り値に入れたら書けた（上）。手順でも返り値でも「流れを書いて」と言うだけでは、文を自分で組み立てる手間があり、飛ばされたので、返り値に書く文そのものを入れる。5回目は、記録の知らせ、頼み、書く文（最後の行）の順に返したが、返り値を受けた直後に、文を書かずに段階を進めるツールを呼んだ。URL の返り値は、書く行が1行目で、頼みが「上の1行」を指す形で書けたので、同じ並びにする。
  - 流れの文は、エクステンションが、生成プラグインか（7.1 の `change` の `generated`）で2つに書き分ける。作っていないプラグインでは、違うところ（決まりの一覧の確かめがない、最近の1回は作業の最初から最後まで、画面で見たいことも聞く）を変える。
  - 受け取るものは「今使っているファイル」と書き、「スキル」と言わない。エクステンションはユーザーの言い方を知らず、words.md は「スキル」を話さない言葉にしているためである。
  - 前に途中で止まった直しの作業用の一時フォルダを消すことは、記録を作る前（`change-check` の結果を見てから、別のコマンドで）にする。返り値を受けた後の手順を、流れを書くことだけにするためである（間に手順がないだけでは、上のとおり書かれなかったので、返り値の文と合わせて使う）。`change-check` と同じコマンドにつなぐと、断られたときにも消えるので、分ける。
  - 記録がもうあって、返り値に流れの文がないとき（読み直した後など）は、書き直さない。途中で「これから」と始めからの流れを示すと、どこまで進んだかが分からなくなるためである。
- チャットに書く文は、ユーザーに向けた文だけにする（10.5）。同じ回で、次にすることの英語の覚え書き（「Now extract.」など）が8回チャットに出た。ツールを呼ぶ前に進み具合を一言書くときも、日本語（ユーザーが別の言語で書いたらその言語）で、ユーザーに向けて書く（例：「今のプラグインと、教えてもらったファイルを読ませています。」）。2回目では英語の覚え書きは3回に減ったが、どれもツールを呼ぶ直前の「Now …」の一言だった。3回目では、先頭の決まりに英語の一言の例を書いた後で、ツールの前の一言の12件すべてが英語になった。先頭の決まりは、スキルを読んだときに1回入るだけで、一言はツールを続けて呼ぶ途中で書かれる。そのため、決まりは英語の例を書かずに、すべきことの形で書き、ツールを続けて呼ぶところ（段階「生成」の初めと、読み取り役・作業エージェントへの頼みの手順）にも、短く思い出させる1文を置く。記録のツールの返り値には足さない。ユーザーが別の言語で書いたときに合わないためで、3回目でも、日本語の返り値のすぐ後の一言が英語だった。思い出させる1文が書く直前に届くのは、読み取り役と作業エージェントへの頼みの前だけで、試験と直しの途中などの一言は、段階「生成」の初めの1文に頼る。効いたかは1回の数では分からない（1〜3回目で 8・3・12 件とぶれた）ので、3回以上の回し直しで、ツールの前の一言のうち英語の割合を見て決める。

**読む**

- 元のプラグインと示されたスキルの指示文は、メインのエージェントの会話に入れない（3.2 と同じ）。例外は、スクリプトが返したもの（`extract` の結果）と、引き継ぐ課題の eval.json である。
- 読み取り役への頼み（9章）：
  - 示されたスキルの使い方と説明は、決まりの候補にさせない。使い方と説明とは、スキルのフォルダの中のスクリプトの使い方（`--help` に出ること。引数、終了コード、出力の形など）、フロントマターの `compatibility`（環境の条件）、出力の意味の説明（例：出力のある値が何を表すか）である。スクリプトはそのとおりに動き、環境の条件と出力の意味は事実の説明で、ユーザーが決めることではないためである。読み取り役の返す形の「使い方と説明」の欄に書かせる。メインのエージェントは、それをそのスキルの資産の候補の説明に記録し（`compatibility` は文のまま）、直す段階でルールのスキルに書かせる（`compatibility` は、ルールのスキルの `compatibility` に写す）。外側の EVAL（改善）の1回目では、スクリプトの使い方を決まりとして1件ずつ聞き、ユーザーは「特に決まっていない」と答えた。2回目では、環境の条件と、出力の値の意味の説明を決まりとして聞き、どれも4つの答えのどれでもない答えになって外れ、ルールのスキルに入らなかった。
  - ただし、スキルの文が守ることや既定として求めていること（既定の値など）は、`--help` に出ていても、スクリプトがそうしていても、決まりの候補にする。`SKILL.md` の本文に書かれた、スキルのフォルダの外の道具（機器の道具など）の打ち方（コマンドの形）も、決まりの候補にする。今もそうしているか（既定の値が古くないかなど）は、ユーザーにしか分からないためである。使い方を「スクリプトの既定の値」まで広げると、確かめていない値がルールのスキルに入る（REQ-055 の受け入れ基準）。2回目では、使い方の枠がメーカーの道具のコマンドの形まで吸い込み、決まりとして確かめなかった。
  - 決まりの候補にする文の種類は、頼みに並べない。並べた種類が1つの模擬ユーザーのナレッジと1つずつ重なると、その模擬ユーザーでしか通らない手順になるためである（[試験の設計](testing.md) 6.3）。読み取り役は、自分の定義のとおり、ファイルに表れている決まりをすべて返す。
  - 生成プラグインでは、決まりの候補にさせるのは、ルールのスキル（入口のほかのスキル）とエージェントの定義の作業ごとの指示の文のうち、決まりの番号（`K-01` の形）が付いておらず、作った後に足されたと見える文だけにする。作業エージェントは、決まりから書いた文に番号を添える（[クリエイターの構造](creator-structure.md) 3.5）ので、番号のない文は、作った後に書き足された文か、クリエイターが書いた文（手順の骨組み、プラグインの部品の使い方、スクリプトの使い方など）である。クリエイターが書いた文をユーザーの決まりかと聞いても、ユーザーには答えられないためである（REQ-054）。
    - 印のタグ（[クリエイターの構造](creator-structure.md) 4.1）があれば、メインのエージェントが、タグからの差分（`git -C <フォルダ> diff <タグ> HEAD -- .`）をファイルに書き、読み取り役に渡す。読み取り役は、その差分で足された行の文だけを候補にする。印のタグは、クリエイターが最後に作るか直したときの状態なので、その後の差分がユーザーの直しである。メインのエージェントは差分の中身を読まない（元のプラグインの指示文を会話に入れないため。3.2）。読み取り役は git を使えないので、差分はファイルで渡す。
    - 印のタグがないとき（手でマーケットプレイスに写したプラグインなど。軽いタグは push で送られない）は、ユーザーの仕事や環境に固有の名前・値・やり方が入った文（例：使う道具や機器の名前、コマンドの形、書類の宛先、決まった値）だけを候補にさせ、プラグイン自身の部品（プラグインのフォルダのスクリプト、`<名前>_show` などのツール、作業フォルダの中の置き場所）を使う文は除かせる。外側の EVAL（改善）の2回目までは「機器や道具に固有の文」で分けていたが、それでは週報のような分野でユーザーが書き足した決まり（宛先、締め切りなど）が落ち、題材の作業ごとの指示にある、クリエイターが書いた道具の名前とコマンドの形の文（差分のスクリプト、表示のツール）が候補に入る。
    - どちらのときも、ルールのスキルの使い方と説明（スクリプトの呼び方・引数・終了コード、`--help` で確かめられること、`compatibility`、出力の意味の説明）は候補にさせない。直したときに作業エージェントがルールのスキルに番号なしで書く（上の、示されたスキルの使い方と説明）ので、同じプラグインをもう一度直すと、スクリプトの使い方を決まりかと聞くことになるためである。2回目の直しの結果のルールのスキルには、終了コードの表や、コンパイラとフラグの説明が番号なしで入った。
    - 仕様書、設計書、README、作業の定義、作業の画面の振る舞い（表示、図、差分の出し方、保存の場所など）と、ルールのスキルと作業ごとの指示のうち上で候補にしなかった文は、前に作ったときにお話から書いた「できていたこと」なので、候補にさせず、できていたことと構成として返させる。範囲の確かめで確かめ済みだからである。外側の EVAL（改善）の2回目では、仕様書の要件（図の色、差分の形）、作業の定義の表示、ルールのスキルの「決まった場所に保存」を決まりかと聞き、ユーザーは中身が分からないと答えた。直す前の確認では「外す決まり」に並び、機能を消すように読めた。
    - 一覧の決まりを言い換えた文と、一覧の決まりから出てくる文（例：役割を分ける決まりから来る、ある役がしないこと）も候補にさせない。外側の EVAL（改善）の1回目では、役割の分け方から来る文を、ユーザーの決まりかと聞いた。
    - 1回目の直しで入れた、ひな形のフォルダを検索させてひな形の文をはじく手順は、やめた。候補にさせる範囲（ルールのスキルと作業ごとの指示）は作業エージェントが書いたもので、ひな形の文がないためである。
    - タグがないときに見分けきれずに聞いた文は、決まりの確かめの聞き直し（下）で扱う。
- 読み取った決まりの候補（元のプラグインと示されたスキルの両方。書き足した決まりなど）は、ほかの問いの答え（範囲の確かめ、決まりの一覧の確かめなど）に同じ中身が出ても、外したり「決まった」にしたりせず、決まりの確かめで「〜という決まりですか？」と1件ずつ確かめる。一覧の決まりと同じ中身の候補も同じである。REQ-054 の受け入れ基準が、書き足した決まりを1件ずつ確かめの問いで示すことを求めるためである。外側の EVAL（改善）の1回目は、範囲の確かめの答えで、書き足した決まりの候補を確かめの問いなしに「決まった」にした。4回目は、決まりの一覧の確かめの答えで、同じ中身を引き継いだ決まりの今のやり方として言われ、その番号を直した後、候補を「同じ中身なので重ねない」と外した。どの問いの答えに出るかは回ごとに違うので、問いごとに書かず、候補の扱いとして change-read.md の2の1か所に置く。本文（SKILL.md）の決まりの確かめの「一覧の決まりは段階『読む』で確かめ終えている」も、同じ中身の候補を確かめずに済ませる理由に読めるので、同じ中身の候補も1件ずつ確かめると添える。
- 範囲の確かめ（理解の確かめ。1つの問い）：できていたこと（「〇〇と頼むと、〇〇をする」の一覧）と、今回変えるところ・消すところを示し、ほかは引き継いで聞き直さないことを添えて、違うところと足りないところを聞く。機能ごとに要るかは聞かない。消すのは、ユーザーが消したいと頼んだ機能だけである（REQ-054）。この答えを「変えないので聞かない」の抜き書きにする。頼みの文はユーザーの答えに数えない（7.4）ので、抜き書きに使えないためである。
  - 問いには、頼みと読み取りから分かる変えるところだけを書き、変えるかもしれないこと（画面の設定、ほかのルールなど）を例として書き足さない。頼みにない変更を誘うためである。
- 決まりの一覧の確かめ（生成プラグインのときだけ。理解の確かめ。1つの問い）：取り込んだ決まり（7.3）のすべての番号と文を1つの問いの文の中に入れ、今と違うものと古くなったものの番号を聞く（REQ-054）。
  - 範囲の確かめの答えで、番号や「ほかはそのとおり」と言われても、この問いは省かない。ユーザーは一覧の文をまだ見ていないので、その答えは一覧を確かめたことにならない。外側の EVAL（改善）の1回目では、この問いを飛ばし、一覧を見ていないユーザーの1文で16件を「決まった」にした。記録のツールも、この飛ばしを断る（7.2）。
  - 挙げられなかった決まりは「決まった」にする。抜き書きは、この答えである。
  - 挙げられた決まりは、1件ずつ、番号と文を示して、今はどうしているかを聞き出す。範囲の確かめの答えに今のやり方がもう書かれていれば、聞き直さない。今のやり方を答えたら、その答えのとおりに直す（新しい番号になる。7.3）。決まりでなくなった、決まっていないと答えたら、外す。代わりの案は作らない（5.4）。
  - 「ない」と答えても、決まりを足したことにはならない。

**決まりの確かめ**

- 4つの答え（6.1）のどれでもない答え（「特に決まっていない」など）は、メインのエージェントがどれかに決めて記録せず、その答えの言葉を添えて、同じ4つのどれに当たるかを1回だけ聞き直す。外側の EVAL（改善）の1回目では、このような答えを「外した」として記録した。
  - この聞き直しは、5.4 の「決まっていない」の行（その点は聞き直さない）より先にする。4つの答えの問いでの「決まっていない」は、「決まりではなく、たまたま」とも「このとおり」とも読めるためである。
  - 聞き直しても4つのどれでもなければ、正しいと答えていないので入れない（状態「外した」、抜き書きはその答え）。直す前の確認の1つ目で、確かめても決まらなかったので入れない決まりとして文を示し、入れたいと答えたら、その番号を「決まった」にする（抜き書きはその答え）。候補のまま残さないのは、確かめていない候補が残ると、項目「候補の確かめ」が未着手のままになり、確認のツールが受け付けないためである（7.2）。
- 元のプラグインから読んだ候補に「違う」と答えたら、外す記録の抜き書きは、読み取った場所（ファイル名と箇所と引用）のままにする。答えの言葉は、本当のやり方の新しいナレッジの抜き書きに残る。その場所の文は、直す前の確認で消すと示して、直す段階で消す（6.3）。違うと答えた決まりを、直した後のプラグインに残さないためである（REQ-054 の受け入れ基準）。外側の EVAL（改善）の2回目では、外す記録の抜き書きを答えの言葉にしたので、読み取った場所が記録に残らなかった。

**作っていないプラグイン**

- 生成プラグインの形にすること自体が、変えるところになる（REQ-056）。そのため、「変えないので聞かない」を使わず、作業の最初から最後までの1回と、画面の3つの問いを行う。読み取った決まりは、決まりの確かめで1件ずつ確かめる（REQ-054）。

## 4. 問いの形と書き方

### 4.1 手段と数

- 問いはすべて、メインのエージェントが `ask_user` で出す。サブエージェントは `ask_user` を持たないためである（2.1）。
- 1回の `ask_user` には、問いを1つ、欄を1つだけ置く。
  - 1通で3つ聞くと2つしか答えなかった例がある（Zhang ほか 2026）。
  - 2つ以上の欄があると、Tab で飛ばした欄は答えに入らず、答えは項目名なしで届くことがある（2.1）。
- 文章で問いを出して手番を終えない。Copilot CLI のシステムプロンプトが禁じていて（2.1）、autopilot ではユーザーに届かないためである。例外は、答えが来ないときに止まるとき（5.5）と、Claude Code 向けの置き換え（10.4）である。
- Copilot CLI のシステムプロンプトは、関係する好みを1つのフォームにまとめて聞くことも勧める（2.1）。この節の「1回に1つ」はそれと逆なので、守られるかを外側の EVAL で記録から見る（[試験の設計](testing.md) 6.5）。

### 4.2 問いの種類

| 種類 | 当てはまるもの | 形 |
| --- | --- | --- |
| 聞き出すヒアリング | 仕事のやり方、決まり、例外、前回の1回、資産、画面で設定したいこと・見たいこと、決まりの確かめの後の「どんなときか」「本当はどうか」（6.1） | 自由入力の欄を1つ。選択肢も答えの例も付けない |
| 理解の確かめ | 記録から分かった項目（3.1）、段階の区切りの要約（6.2）、生成前の確認の直し（6.3）、候補の多い一覧（4.5） | 分かったことや一覧を示し、違うところと足りないところを聞く。自由入力の欄を1つ。選択肢を付けない |
| 決める質問 | 公開のプラグインを使うか、画面の部品、疲れ・急ぎのときの進め方（5.6） | 選択肢を2〜4個。おすすめを先頭に置き、`default` にする。おすすめの印は画面に出ないので（2.1）、選択肢の文にも「（おすすめ）」と書く。理由を1文添える |
| 決まりの確かめ | ファイルから読み取った決まり | 4つの答えから選ぶ（6.1）。おすすめも `default` も付けない |
| 承認 | 生成前の承認（この内容で作ってよいか）、試験の道具を入れてよいか、EVAL を始めてよいか、Issue を起票してよいか | おすすめも `default` も付けない。よいと答える選択肢を最初に置かない |

- 聞き出すヒアリングと理解の確かめを、自由入力で聞く問いと呼ぶ。決める質問、決まりの確かめ、承認を、選択肢で聞く問いと呼ぶ。
- 質問のツールが選択肢を必ず求めるとき（Claude Code。10.4）は、自由入力で聞く問いに選択肢を作らず、文章で1つ聞いて手番を終える。外側の EVAL の2回目の会話例では、自由入力で聞く問いの30問が、すべて選択肢つきで出た。
- 聞き出すヒアリングに選択肢や例を付けないのは、人は示された選択肢の中から答えを選び、書かれていない答えを自分から書きにくいためである（Krosnick 1999）。
- 決まりの確かめと承認におすすめを付けないのは、確かめの問いへの答えが「はい」に偏るためである（Barari ほか 2026、Krosnick 1999）。
- 決まりの確かめと承認で、「このとおり」や「作る」を最初に置かないのは、`default` がなくても Enter だけで最初の選択肢が選ばれるためである（2.1）。
- 選択肢の文は、ユーザーの言語のまま読める文にし、値と表示名を分けない（2.1）。

### 4.3 問いの文

- 問いは、「なぜ聞くかの1文」と「それだけで答えられる完全な疑問文」で書く。
- なぜ聞くかは、AI がそれを知らないと何を間違えるかで書く。
- 理解の確かめの問いでは、示す一覧や要約も、問いの文の中に入れる。「上のまとめ」「上の受け取るもの」のように、問いの外を指さない。会話例では、問いが指す中身が問いの中になかった所が5か所あった。
- 項目の名前、番号、ラベルだけで聞かず、何を知りたいかを言葉で書く。ラベルだけの問いは答えられないとして、GitHub Spec Kit は完全な疑問文と理由の1文を必須にした（プルリクエスト #3745）。
- クリエイターの内部の言葉（スキル、エージェント、フック、MCP、EVAL、ナレッジなど）は、置き換えの表で、ふだんの言葉にする（REQ-024）。表は references に置く。表の中身は未決である（14章）。
- ユーザーが使った言葉は、言い換えずにそのまま使う。聞き取りを繰り返すうちに、聞き手と話し手のあいだで意味を詰めた言葉で話すようになるという報告がある（Freeman ほか 1991）。
- なぜ聞くかの1文は、Copilot CLI のシステムプロンプトの「100 words or less」などの指示（2.7）があっても省かない。

### 4.4 調べて分かることは聞かない

- 問う前に、頼みの文、記録、ファイルの候補を見る。
- 調べて分かることは聞かず、候補として記録する。調べて分かることを聞いても価値が低いと報告されている（Vijayvargiya ほか 2026、Zhang ほか 2026）。
- ただし、目的、合否の決め方、守らないと困ること、いつもと違うとき、好みは、推し量れても聞く。文書に書かれた決まりと、実際のやり方は違うことが多いためである（Hoffman 2005、Sherlock & Rugg 2003）。

### 4.5 候補の多い一覧

- 候補が4つを超える一覧（基準の案、できていたこと、公開のプラグインの候補など）は、一覧を文章で示し、外したいものや選ぶものを自由入力で書いてもらう。
- Copilot CLI と Claude Code の両方で同じ形で動くようにするためである（[試験の設計](testing.md) 4章）。

## 5. 深掘りと、聞き終えるまで

### 5.1 あいまいさの合図

次の7つを合図に、聞き直す。

1. 基準のない形容詞・副詞（「見やすく」「ちゃんと」「適切に」「早めに」）
2. 「普通」「いつもどおり」「適当に」
3. 一般論・仮定（「普通は〜」「〜だと思う」「場合による」）
4. 範囲のぼかし（「など」「いろいろ」）
5. 本人だけの言葉（略語、社内用語、固有名）
6. 矛盾（前の答えや、示されたファイルと食い違う）
7. 判定できない合否（「良ければ合格」）

- ナレッジを記録する前に、「作業を知らない AI が、この1文だけで作業や判定ができるか」を点検する。できなければ聞き直す。
  - 作業エージェントと、生成プラグインのエージェントは会話を見ないので、この1文がそのまま使われるためである（[クリエイターの構造](creator-structure.md) 3.3）。
- 同じ点検で、聞き直しを止める。作業や判定ができる細かさになったら止め、それ以上は求めない（[試験の設計](testing.md) 7章）。
- 根拠：要求を聞くインタビューの失敗で最も多いのは、あいまいな問いである（Bano ほか 2019）。あいまいさは、本人にしか分からないナレッジを引き出す手がかりになる（Ferrari ほか 2016）。

### 5.2 合図ごとの型

| 合図 | 型 | 問いの例 |
| --- | --- | --- |
| 基準のない形容詞 | 見分け方を聞く。数、有無、見本に落ちたら止める | 「見やすいかどうかは、どこを見れば分かりますか？」 |
| 普通・いつもどおり | 実際の1回を聞くか、初めての人がつまずく所を聞く | 「最近の1回では、どう書きましたか？」 |
| 一般論・仮定 | 実際にあった1件に戻す。「何を見て、何をしたか」を聞く | 「最後にそれをしたときは、何を見て決めましたか？」 |
| 範囲のぼかし | ないと言われるまで、ほかを聞く | 「ほかにはありますか？」 |
| 本人だけの言葉 | 意味を聞く | 「〇〇とは、何のことですか？」 |
| 矛盾 | 両方を並べて聞く | 「先ほどは A、ファイルでは B でした。どちらですか？」 |
| 判定できない合否 | 合格の例と、やり直しになった例を、1つずつ別の問いで聞く | 「合格だった例を1つ教えてください」の後に「やり直しになった例を1つ教えてください」 |
| 言い切りの決まり | 例外を聞く | 「それに当てはまらなかったときはありましたか？」 |

- 1つの問いで聞く点は1つにする。1つの問いで2つのことを聞くと、答えを解釈しにくくなる（Pew Research Center）。
- 「なぜ」は目的を聞くときだけ使う。自分の行動の理由を聞くと、後から作った説明になりやすいためである（Freeman ほか 1991 が引く Ericsson & Simon 1980）。
- 推し量ったことを示すときは、「こう理解しました。違うところと足りないところを教えてください」と聞く。
- 根拠：基準のない言葉は「どうやって見分けるか」をたどると、測れる基準になる（Sherlock & Rugg 2003）。初めての人の誤りを聞く問いは、Critical Decision Method の最後のなぞりの問いである（Freeman ほか 1991）。

### 5.3 聞き直しの上限

- 同じ点への聞き直しは2回までにする。
- 問いの意味が伝わらなかったときの言い直しは、回数に数えない。
- 2回聞いてもあいまいなら、ユーザーの言葉のまま、その項目を保留にして先へ進む（7.2）。保留は、生成前の確認で示す（6.3）。
- 問いの総数には上限を置かない。仕様 REQ-015 の項目をすべて聞くためである。
- 根拠：似た問いの繰り返しが、利用者の不満として報告されている（Roudiere & Lento 2026）。

### 5.4 「分からない」などへの対応

| ユーザーの答え | 扱い |
| --- | --- |
| 問いの意味が分からない | なぜ聞くかと、どの細かさの答えがほしいかを足して、1回言い直す。聞き直しの回数に数えない |
| 決まっていない | その点は聞き直さない。項目全体に決まりがなければ、項目を「決まりなし」にする |
| 知らない・思い出せない | 項目を保留にし、だれが知っているか、どの資料にあるかを記録する |
| おまかせ | 理由つきの案を1つ示し、出どころを「AI の判断」として記録する |

- 直すとき（3.4）の決まりの確かめで、4つの答え（6.1）の問いに「決まっていない」と答えたときは、この表より 3.4 の聞き直しを先にする。
- 「決まっていない」と答えたこと（状態「決まりなし」の項目）と、決まりの確かめで「決まりではなく、たまたま」と答えた候補（6.1）には、AI の案を作って示さない。おまかせと言われていないのに案を作ると、ユーザーが決まりではないと答えたやり方が、生成プラグインに入るためである。外側の EVAL の1回目では、決まりではないと答えた題名の日付の書き方を、AI の案として足し直して「決まった」で記録し、作業エージェントの定義に入った。
- 保留と AI の判断の示し方は、6.3 にある。
- 「分からない」と答えた問いは、問答の記録に残る（7.4）。質問の改善案の材料になる（11章）。

### 5.5 答えが来ないとき

- `ask_user` の結果が「User cancelled the request.」か「The user is not available …」（2.1）のときは、答えが来なかったとして扱う。エクステンションも、結果の文の頭で、問答の記録の結果（答えた、取り消した、断った）を見分ける（7.4）。Copilot CLI がこの文を変えると、答えたとして記録される。
- 推測で埋めず、記録を変えない。答えが来なかったことは、問答の記録に残る（7.4）。
- 何を聞きたかったかと、続け方（チャットに答えを書く、autopilot を切る）を短く示して止まる。autopilot は、Shift+Tab で標準・計画・autopilot のモードを切り替えて切る（公式のコマンドリファレンス）。
- `task_complete` がツールにあれば（autopilot と plan モードで加わる）、それを呼んで止まる。autopilot で呼ばずに手番を終えると、続けるよう促す発言が送られるためである（2.1）。
- 続けるよう促されても、ユーザーの答えなしに次の段階へ進まない。
- ここまでは、ヒアリングの問い（生成前の承認まで）の扱いである。先頭の決まり1（10.2）の「答えを受け取るまで先へ進まない」も、この範囲に当てはまる。
- 生成の後の承認（試験の道具を入れる、Issue を起票する）に答えが来なかったときは、止まらず、入れない・出さないと答えたときと同じに進める（[クリエイターの構造](creator-structure.md) 4.1、4.5）。
- `ask_user` がない起動（`-p`、`--no-ask-user`）では、始まりで止まる（3.1）。
- 仕様 REQ-023。

### 5.6 疲れ・急ぎ

- 合図は、「早く」「まだ？」などの発言と、答えが短くなることである。
- 合図を見たら、残りの項目を示し、次の3つから選んでもらう（決める質問）。
  - ここでやめて後で続ける（おすすめ。後で落ち着いて答えると、仕事の決まりが生成プラグインに正しく入りやすいため）
  - 残りを手早く聞く（1項目に1問、聞き直しは1回まで）
  - このまま続ける
- ユーザーがはっきり「質問しないで作って」と頼んだときも、推し量って埋めて作らない。聞かないと仕事の決まりが生成プラグインに入らないことを1文で伝えてから、同じ3つから選んでもらう（REQ-015）。
- やめるときは、続きから聞く戻り方を2つ示して止まる（8章）。
  - すぐに再開するなら `copilot --continue`（最後のセッションに戻る）
  - 間に別の会話をしたなら `copilot --resume=<このセッションの番号>`（番号はエクステンションが記録から示す。14章 H3）
- どれを選んでも、残りの項目は飛ばさない。
- 根拠：文字のチャットでのインタビューは、対面の約2倍の時間がかかり、集中が落ちる。勧めは回を分けることである（Opdenakker 2006）。疲れると「はい」と答えやすくなる（Krosnick 1999）。仕様 REQ-015。

### 5.7 聞き終える条件

1. 未着手の項目がなくなる。
2. 「ほかにありますか？」を1回聞く。
3. 生成前の確認（6.3）に進む。

- 未着手の項目が残っていれば、エクステンションが生成前の確認を受け付けない（[生成プラグインの構造](generated-plugin-structure.md) 9章）。
- 根拠：
  - 聞き終える判断は、モデルによって大きく違う（Jin ほか 2026）。そのため、モデルの判断に任せず、項目の一覧で決める。
  - 1人への聞き取りで聞き終える判断の研究は見つからない。項目の一覧との照合と、「ほかに」への答えが出なくなることが物差しになる（Wiegers 2013）。

## 6. 確かめ方

### 6.1 ファイルから読み取った決まり

- 問いは「〜という決まりですか？」のままにし、読み取った場所（ファイル名と箇所）を添える（REQ-017、作り直しは REQ-033、直すときは REQ-054・REQ-055）。
- 答えは次の4つから選んでもらう。おすすめも `default` も付けない。

  | 答え（並べる順） | 記録 |
  | --- | --- |
  | そうしないときもある（どんなときか） | 候補を「決まった」にし、どんなときかを例外の欄に書く。種類が「合否の決め方」なら、文も、例外のときに何なら合格かを書いた形に直す |
  | 違う（本当はどうか） | 候補を「外した」にし、本当はどうかを新しいナレッジとして記録する |
  | 決まりではなく、たまたま | 候補を「外した」にする |
  | このとおり | 候補を「決まった」にする |

- 並べる順は表のとおりで、「このとおり」を最後に置く（4.2）。
- 「どんなときか」と「本当はどうか」は、選ばれた後の次の問いで、自由入力で聞く。
- 「合否の決め方」の文を例外のときも合格が分かる形に直すのは、合格の条件（作業の定義の基準、`tests/knowledge.json`）には文だけが渡り、例外の欄が渡らないためである（[クリエイターの構造](creator-structure.md) 3.5）。直すときの取り込みも、番号・種類・項目・文だけを引き継ぐ（7.3）。例外の欄も残す。確かめた後で種類を「合否の決め方」に変えるとき（生成前の確認の基準の案、6.3 のある場合だけの決まり）も、同じく文を直す。種類を変えるときは、この段階の手順を読んでいないので、記録のツールの返り値で促す（7.5）。外側の EVAL（改善）の3回目では、確かめのときは「それ以外」だった例外のある決まりを、確認の前に「合否の決め方」に変えて「<場合> のときは〜」の形にしたとき、文から例外が落ち、例外のないまま合格の条件に入った。例外どおりの成果物が不合格になりうる形である。
- 根拠：チャットボットが答えを分類し、その分類が合っているかを回答者本人に確かめた研究がある（Barari ほか 2026）。本人の確認を正解にすると、適合率は平均 94.6% だった。第三者の判断を正解にすると、平均 75.2% だった。本人の確認は「はい」に偏っていた。

### 6.2 段階の区切りの要約

- 段階「前回の1回」と「項目の点検」の終わりに、記録した内容を短く要約して示し、違うところと足りないところを自由入力で聞く。
- 推し量ったことは、推し量ったと示す。
- 1回の発言の中で同じことを繰り返さない（REQ-024）。
- 直すとき（3.4）の項目の点検の終わりの要約では、その段階の問いで示して確かめたことをもう一度並べず、まだ示していないこと（AI が決めたこと、推し量ったこと、保留、入れないもの）だけを示す。示すことがなければ、ほかに示すことはないと1文で書き、足りないところだけを聞く。直すときは、項目の点検の問いが、読み取ったことを示して違うところを聞く形になり、同じ決まりを何度も示すためである。外側の EVAL（改善）の1回目と2回目では、終わりの要約が、それまでの要約をもう一度すべて並べた。
- 根拠：インタビューの後に要約しなかった失敗が多く（Bano ほか 2019、28組中19組）、要約がさらに聞き直しを生む（同）。

### 6.3 生成前の確認

- 5.7 の条件を満たしてから始める。
- 次の3つに分けて示す（REQ-020、REQ-027、REQ-038）。
  1. ナレッジの一覧と、生成プラグインの振る舞いの案。保留の項目と AI の判断は、本人の決まりと分けて示す。
  2. EVAL の課題と合否の基準。基準の案は 6.4、入力のファイルは 6.5。
  3. Web管理画面の見本（[生成プラグインの構造](generated-plugin-structure.md) 9章）。
- 同じものを、クリエイターの画面にも出す（REQ-044）。
- 作り直しでは、引き継ぐことと変わることも示す（REQ-035）。
- 毎回、違うところと足りないところを自由入力で聞く。直したら、指摘の文言をそのまま残さず、目的に沿って直して示し直す（REQ-020）。
- 確認で足されたナレッジは、出どころを「生成前の確認で足した」として記録する。足したナレッジにするのは、ユーザーが答えの中で自分の言葉で述べた決まりだけである。「違うところはない」のような答えは、示したものを確かめただけで、決まりを足したことにならない。
- 振る舞いの案の中でメインのエージェントが自分で決めたやり方は、ナレッジの一覧に入れず、振る舞いの案の中に書く。部品の分け方でも、よいと答えた振る舞いの案にない振る舞いを足さない（[クリエイターの構造](creator-structure.md) 4.1）。
- 最後に「この内容で作ってよいか」を聞く。形は 4.2 の承認である。
- よいと答えたら、記録のツールで段階を「生成」に進める。ユーザーの答えの抜き書きを添える。記録のツールは、生成前の確認を受け付けた後でないと、この記録を受け付けない。エクステンションは、この記録の時刻を承認の時刻として残す（7.1）。
- 確認で示した後に、ナレッジが変わったとき（足した、直した、決まったものでなくなった）と、作業の定義の案の中身が変わったときは、確認で示し直すまで、記録のツールが段階を「生成」に進める記録を断る。ユーザーがよいと答えた中身と、生成に使う中身を食い違わせないためである。
- よいと答えるまで、組み立てのスクリプトを動かさず、作業エージェントに生成プラグインのファイルを書かせない。画面の見本のための作業の定義の案だけは、[生成プラグインの構造](generated-plugin-structure.md) 9章のとおり、確認の中で作業エージェントが書く。

**直す前の確認**（REQ-057、REQ-061）

直すとき（3.4）は、生成前の確認を「直す前の確認」と呼び、上と同じものに次を足して示す。

- 引き継ぐこと（できていたこと、確かめた決まり、流用する部品）と、変わること（足したり変えたりするスキル・設定項目・エージェントの役割、消す機能、足す・直す・外す決まり）。生成前の確認で示すものを知らせるツールに、必ず渡す（7.5）。
- 決まりは、番号の範囲だけにせず、1件ずつ番号と文で示す。直したことの説明でも同じにする。画面を開けないユーザーも、何を引き継ぎ、何が変わるかを分かって答えられるようにするためである。外側の EVAL（改善）の1回目では、引き継ぐ決まりを「K-01〜K-14、K-16、K-17」とだけ示した。
  - 分け方：引き継ぐ、足す、直す（元の番号 → 新しい番号）、外す、入れない（確かめた結果）。
  - 外す決まりは、元のプラグインの決まりの一覧（`tests/knowledge.json`）にあったものだけにする。読み取った候補を確かめて入れなかったものは、入れない決まりとして分け、「違う」と答えたもの（代わりに足す決まりの番号も）、決まりではないと答えたもの、確かめても決まらなかったもの（3.4）を分けて示す。外側の EVAL（改善）の2回目では、仕様書と画面の振る舞いから読んだ候補が「外す決まり」に並び、機能を消すように読めた。
  - 作業エージェントに文も番号も残さないよう渡すのは、一覧にあった外す決まり（記録の状態のツールの「外した決まり」。中身を直して付け直した元の番号は入らない）だけにする。
  - 元のプラグインから読んだ候補で「違う」と答えたもの（3.4 の決まりの確かめ）は、消す文と消す場所（抜き書きの場所を、どのスキルか、どの AI への指示かで）を、変わることに1件ずつ示し、直す段階で、作業エージェントに文とファイルと箇所だけを渡して、その場所のその文だけを消させる。消すのは、ユーザーが承認した変更でなければならないためである（REQ-057）。外側の EVAL（改善）の2回目の直しでは、外した候補をすべて消させる指示にしていたが、確認には出ていなかった。
  - 決まりではない・確かめても決まらなかった候補は、プラグインの文を今のまま残し、そのことを示す。ユーザーは違うとは答えていないので、引き継ぐ部品を変えないためである。ほかの候補は作業エージェントに渡さない。候補の文を渡すと、似た文の機能の説明まで消すおそれがあるためである（[クリエイターの構造](creator-structure.md) 3.4）。
- 確認を部分に分けて番号（「1/2」など）を書くときは、実際に示す数で書く。見本を示さないときは2つである。外側の EVAL（改善）の2回目では、見本を示さないのに「（1/3）」「（2/3）」と書いた。
- 確認の前に、決まったナレッジの文を見直す。作り手への頼みやどこに書くかが文に入っていれば（7.3）、作業する AI が従う決まりの形に直して記録する。段階「生成」に進むと記録は変えられず、作業エージェントは文を言い換えずに書くので、確認の前に直す。
- 決まりの文が、Web管理画面の設定と同じものの値を固定で決めているとき（例：送り先を決まった値にする）は、決まりの文を「頼みや画面に〇〇がなければ（決まりの値）」の形に直して記録し、振る舞いの案にも同じ使い方を書いて確かめる。決めないと、画面に別の値を入れたときに、生成プラグインの AI がどちらを使うかが決まらないためである。決まりの文はそのままルールのスキルと合否の基準に入る（7.3、6.4）ので、案だけを直すと、画面に別の値を入れた実行で、基準と案が食い違う。外側の EVAL（改善）の2回目では、決まりの値がルールのスキルのコマンドに固定で入り、作業役の AI への指示は画面の値を読むままだった。
- 組み立ての `extract` の結果：今の版に上げると上書きされる土台のファイル、1段目で落ちるところとその直し、消すファイル、取り込んだスキルとの名前の重なり（[クリエイターの構造](creator-structure.md) 3.4）。作っていないプラグインでは、生成プラグインの条項を満たすために足したり変えたりすることも示す。
- 土台を上げると元の機能と重なるとき（例：元のプラグインの決まりと、土台のエージェントごとの思考の深さ）は、元の機能を消さずに残し、重なることを示す。消すのは、ユーザーが頼んだ機能だけだからである（REQ-054）。
- 1段目で落ちる古い書き方（例：エージェントの本文の `${PLUGIN_ROOT}`。[生成プラグインの構造](generated-plugin-structure.md) 4.7）は、直す変更として示してから直す。確認で示した変更のほかは変えないためである。
- 土台を上げることと1段目の直しは、ファイルの名前やパス、`${PLUGIN_ROOT}` を出さず、何が変わるかを置き換えの表（4.3）の言葉で示す（例：AI への指示で、部品の場所を、プラグインのフォルダから読む書き方にする。上書きされるものは、プラグインの説明書、AI への指示、作業の画面、仕様書・設計書、試験の道具のように、何のためのものかで示す）（REQ-024）。消すファイル（`extract` の結果）だけは、何が消えるかをユーザーが確かめられるよう、名前で示す。直したことの説明でも同じにする。
- 新しい版の案（`plugin.json` の version）。スキル・設定・エージェントを足す・変える・消すときは2つ目の数を、決まりの文だけを直すときは3つ目の数を上げた案にし、ユーザーがよいと答えた版にする。今の版がないときは 0.1.0 を案にする。今の版より大きくないと、確認のツールが断る（今の版がないときは、形だけを確かめる）。版を下げたり同じにしたりすると、入れたプラグインと新しい版を見分けられないためである。
- EVAL の課題と合否の基準（REQ-061）：
  - 元の課題は、元の頼むときの言葉・設定・基準のまま引き継ぐ。入力は、プラグインの中の場所を、仮の印をつけて示す。確かめた決まりと食い違う課題（例：入力のルールのファイルが、取り込んだスキルと違う）は、直す案を示す。外すのは、ユーザーが自分から頼んだときだけである。
  - 引き継ぐ課題のうち、外した決まり（付け直していないもの）を除くと基準が1つも残らない課題（確認の直しの中でそうなったときも）は、外さない。合格かを決められないことを示し、その課題の合格の条件を1つの問い（聞き出す問い。自由入力）で聞く。答えは 6.4 と同じく「合否の決め方」のナレッジにし（出どころは、確認を示す前なら「ヒアリングの答え」、確認の直しの中なら「生成前の確認で足した」。項目「合否の決め方」が「変えないので聞かない」でも「聞いた」にする）、その課題の基準にする。基準のない課題は組み立てが断り、課題を外すのはユーザーが自分から頼んだときだけだからである。
  - 変えたところを試す課題を1つ以上足す。引き継いだ課題と頼むときの言葉が違う課題がないと、確認のツールが断る。基準には、取り込んだ決まりに沿って作業したかを判定できる「合否の決め方」のナレッジを入れる。引き継いだものでもよい。言っていない合否の決め方を作らせないためである。
  - エージェントの組み方を変えるときは、決めたエージェントが動いたかを実行の記録で見る基準を入れる（[試験の設計](testing.md) 10.4 の `agent_ran`）。
  - 元のプラグインに課題がないときは、作業全体を試す課題も、変えたところを試す課題とは別に1つ以上作る（6.4、6.5 と同じ作り方）。
  - 変えたところが機器に頼るときは、擬似の機器で試す課題にし（[試験の設計](testing.md) 10.4）、本物の手順そのものは試せないことを示す。決まりが機器の道具を絶対パスで呼ぶときは、擬似の機器に差し替えられないので、機器に送る手順を課題に入れない。
  - 擬似の機器の記録（呼ばれたときの引数と順）で守ったかが分かる決まりは、すべて変えたところを試す課題の基準の案にし、採点のしかたをプログラム（擬似の機器の記録を見る）にする。外側の EVAL（改善）の1回目では、変えた決まりのうち、手順の順、目印、アドレス、やり直しが基準になかった。
  - ある場合（機器、相手、書類の種類など）だけに当てはまる決まりを「合否の決め方」にする（基準の案にする）ときは、文を「<場合> のときは〜。ほかの場合は当てはまらないので合格とする」の形に直して記録する。例外があれば、例外のときに何なら合格かも「〜」に書く（6.1）。合否の決め方は作業の定義の合否の基準になり、どの課題の、どの実行でも、統括と検証のエージェントに渡り、検証のエージェントは確かめられない基準を合格にしない（ひな形の `com.github.copilot/agents/verifier.agent.md` の手順1）ためである。当てはまらない場合の扱いを文に書かないと、ほかの場合の実行で合否が決まらない。確認の1つ目で、これらがすべての実行の合格の条件になることを示す。引き継ぐ課題がほかの機器の課題で、これらと食い違うときは、上の食い違う課題と同じく直す案を示す。作業の定義と基準の形は変えない（KISS）。外側の EVAL（改善）の2回目では、ある機器の決まりを「合否の決め方」にしたので、ほかの機器の引き継いだ課題を動かしても、その機器の条件が評価基準に入る形になった（動かしては確かめていない）。
  - 基準にする決まりの文が、示されたスキルの名前やフォルダを指すときは、確認の前に、直した後のルールのスキルの名前で書いた文に直して記録する。基準の文はナレッジの文をそのまま使う（6.4）ので、元のスキルを指したまま課題に入るためである。
- 示されたスキルの決まりを入れるルールのスキル（足すか、今あるものを直すか）と、足すルールのスキルの名前と description は、メインのエージェントが決めて、ここで示す。作業エージェントには、よいと答えた名前と description を、言い換えずにそのまま渡す（[生成プラグインの構造](generated-plugin-structure.md) 4.9）。示すものが記録（`confirmation`）に残るので、コンパクションの後も写せる。今あるルールのスキルを示されたスキルの決まりで書き直すときも、必ず description の案を示す（何をするか、いつ使うか、機器や道具の名前。誰が読むかは書かない）。今の description を案にしてよいのは、それがこの書き方をすべて満たす（誰が読むかを書いていない、機器や道具の名前があれば入っている、など）ときだけである。仕事と使う場面が変わらないことは、今の description のままにする理由にならない。外側の EVAL（改善）の1回目では、書き直したルールのスキルの description が前のまま（機器の名前がなく、誰が読むかが書いてある）で、チャットで頼むと、同じ作業フォルダのユーザーのスキルが選ばれやすかった（REQ-055、REQ-062）。
- 足すルールのスキルの名前は、示されたスキルの名前と違うものにする（REQ-055）。取り込んだスキルと名前が重なる元のプラグインのスキルも、新しい名前を決め、元の名前 → 新しい名前を示す（[クリエイターの構造](creator-structure.md) 3.4）。
- Web管理画面の見本は、画面の設定や表示を変えるときと、作っていないプラグインのときだけ示す（REQ-027）。
- `extract` の結果と、試せない本物の手順は、「変わること」の文にも必ず入れる。クリエイターの画面にも出すためである（REQ-044）。
- 承認の問いは「この内容で直してよいですか？」にする（形は 4.2 の承認）。聞く前に、取り出した後に元のフォルダが変わっていないかを確かめ、変わっていれば取り出し直して示し直す。段階が「生成」に進むと記録のツールが確認を受け付けないので、承認の後に分かると、`/clear` してから始めからやり直すことになるためである（[クリエイターの構造](creator-structure.md) 3.4 の「取り出した後の変更」）。
- よいと答えるまで、元のプラグインのフォルダは変えない。`extract` は承認の前に動かすが、書くのは作業用の一時フォルダの中だけである（REQ-057）。作業の定義の案などを誰が書くかは、[クリエイターの構造](creator-structure.md) 3.4 にある。

### 6.4 合否の基準の案

- 項目「合否の決め方」の答えは、種類「合否の決め方」のナレッジにする。
- 項目「決まった書き方やルール」と「守らないと困ること」のナレッジのうち、成果物を見て守られたかが分かるものを、「基準の案」として示す。
- 基準の案にするナレッジは、確認で示す前に、種類を「合否の決め方」にする。ユーザーに外したいものを書いてもらい（4.5）、外されたものの種類を「それ以外」に戻す（REQ-038）。
- 「合否の決め方」のナレッジも基準の案もないときは、生成前の確認に進む前に、合格の条件を1つ以上、自由入力で聞き、「合否の決め方」のナレッジにする。出どころは「ヒアリングの答え」である。
- 確認の中で基準の案がすべて外されて0件になったときも、合格の条件を聞いて「合否の決め方」のナレッジにする。出どころは「生成前の確認で足した」である。
- 基準の文は、ナレッジの文をそのまま使い、1件を1つの基準にする。言い換えると、ユーザーが確かめていない細かさが入り、正しい成果物を落とすためである（[試験の設計](testing.md) 7章）。
- 組み立てのスクリプトが、ナレッジの一覧から作業の定義の基準を書き込むかは、未決である（14章）。

### 6.5 課題の入力のファイル

- 入力のファイルは、ユーザーが示したファイルのうち、作業で受け取るもの（前回の1回で受け取ったファイルなど）である。
- 実物のファイルがあれば写す。生成前の確認で、「生成プラグインのリポジトリに入るファイル」として一覧で示す。ユーザーは差し替えられる。
- 一覧で示すのは、生成プラグインのリポジトリを公開すると、これらのファイルも公開されるためである（REQ-022）。
- 実物のファイルは、組み立てのスクリプトが、manifest.json の `eval_inputs` の一覧から写す（[クリエイターの構造](creator-structure.md) 2章）。写すのはファイルごとで、フォルダは写せない。そのため、生成前の確認では、実物はファイルの絶対パスで1つずつ示す。フォルダの中のファイルが要るときは、使うファイルを1つずつ示す。
- 生成前の確認で示すものを知らせるツールは、実物の入力のファイルが、あるファイルの絶対パスでなければ断る（7.5）。承認の後の組み立てで初めて断られると、確認をやり直せず、生成プラグインを作れないためである。
- 実物のファイルがあるときは、仮のファイルを足さず、課題も実物で作る。架空の中身で作った課題は、ユーザーが確かめた1回ではないためである。
- 実物がなければ、前回の1回（未経験の作業では想定の1回）をもとに仮のファイルを作り、「仮」と示して確かめてもらう（REQ-038）。
- 仮のファイルの中身は、メインのエージェントが作る。前回の1回の話を見ているのはメインのエージェントだけだからである。中身は生成前の確認で示し、承認の後に、メインのエージェントが `.plugin-creator-work/parts/files/` の下に書く。承認の後に書くので、6.3 の関門に例外は要らない。
- 限界：仮のファイルの中身は記録に残らない。承認の後、書く前にコンパクションが起きると、確かめた中身のとおりには戻せない。

## 7. 記録

### 7.1 ただ1つの元と置き場所

- ヒアリングの状態のただ1つの元は、クリエイターのエクステンションの記録（JSON）である。
- クリエイターの画面の一覧（REQ-043）、生成前の確認の一覧（REQ-020）、組み立てと構造の検査に渡すナレッジの一覧（[試験の設計](testing.md) 10.3）は、すべてこの記録から作る。
- モデルは、記録のツールでだけ状態を変える。ツールの一覧は [生成プラグインの構造](generated-plugin-structure.md) 9章にある。
- 会話の外に置くのは、`ask_user` の答えとツールの結果が、自動コンパクションで消えるためである（2.2）。長い会話では途中の情報が落ちやすく、前の情報を見せ直すと一部戻るという研究もある（Laban ほか 2025）。
- 置き場所の例：`<COPILOT_HOME>/plugin-data/<クリエイターの名前>/hearings/<セッションの番号>/`
  - 上の階層は、生成プラグインの記録（[生成プラグインの構造](generated-plugin-structure.md) 6.5）と同じである。
  - クリエイターの記録は、セッションごとに分ける。続きから進めるのは同じセッションに戻ったときだけなので（8章）、セッションの番号で分ければ足りるためである。
  - `state.json`：今の段階、項目ごとの状態（7.2）、ナレッジ（7.3）、流用する資産、標準機能と公開のプラグインの選んだ結果、生成前の確認で示したもの、承認の時刻（6.3）。エクステンションだけが書く。一時ファイルに書いてから名前を変えて置く。欄の名前は下の表のとおりで、組み立てのスクリプトが読む。
  - `qa.jsonl`：問答の記録。追記だけをする（7.4）。
  - 記録は自動では消さない。前の会話に戻れば続きから進めるので（8章）、古いかどうかでは決められないためである。置き場所と消し方は、クリエイターの README に書く。
- 記録（`state.json`）を作るのは、状態を変えるツール（段階と項目の状態を知らせる、決まったことを知らせる、生成前の確認で示すものを知らせる、直す流れの記録を作る）の、最初に成功した呼び出しである。画面を開く、状態取得、試験の結果を知らせる、文書をテキストにする、Issue を起票するツールは、記録を作らない。

| 欄 | 中身 |
| --- | --- |
| `schemaVersion` | 記録の形の版 |
| `sessionId`、`createdAt`、`updatedAt` | セッションの番号、作った時刻、最後に変えた時刻 |
| `stage` | 今の段階（3.1） |
| `rebuild` | 作り直しか |
| `change` | 直すとき（3.4）だけ。直すフォルダの実パス、見つけたマニフェストの場所、名前、今の版、生成プラグインか（[クリエイターの構造](creator-structure.md) 3.4 の見分け方）、取り込んだ決まりの番号と外した番号（`tests/knowledge-removed.json`）、その最大、元の合否の基準の番号とナレッジの番号の対応、元の課題の頼むときの言葉、変えたいこと |
| `items` | 項目ごとの状態と抜き書き（7.2） |
| `knowledge`、`knowledgeCounter` | ナレッジ（7.3）と、番号を付けた数 |
| `assets` | 流用する資産 |
| `ossChoices` | 標準機能と公開のプラグインの選んだ結果 |
| `confirmation` | 生成前の確認で示したもの（6.3）。示した時刻（`at`）、ナレッジの番号（`knowledgeIds`）と中身の写し（`knowledge`）、振る舞いの案（`behavior`）、作業の定義の案のパス（`taskPath`）と中身の印（`taskHash`）、設定の見出し（`settingLabels`）、EVAL の課題（`evalTasks`：頼むときの言葉、入力のファイル、基準にするナレッジの番号、設定の値〔繰り返しの上限と作業ごとの設定〕）、作り直しと直すときに引き継ぐことと変わること（`rebuild`）、合否の基準の番号とナレッジの番号の組（`criteria`。7.3）、直すときの新しい版（`version`） |
| `approvedAt`、`approvalQuote` | 承認の時刻と、承認の答えの抜き書き |
| `url` | 画面の URL |

- EVAL の課題の作業ごとの設定の値は、名前を作業の定義の案の設定の `key` から取る。必須で初めの値のない設定には、値を入れる。入れないと、画面で開始できないためである。
- 記録には、ユーザーの仕事の中身が入る。手元にだけ置き、外へ送らない。
- 仕様 REQ-021 の「作業フォルダの外には何も作られない」の対象は生成プラグインのファイルで、この記録は含まない。

### 7.2 項目と状態

項目は、エクステンションが決まった一覧として持つ。

- 仕様 REQ-015 の10項目
- 前回の1回（REQ-016）
- 候補の確かめ（REQ-017。候補があるときだけ）
- 資産（REQ-018）
- 標準機能と公開のプラグイン（REQ-019）
- 画面の3つ：開始前に設定したいこと、実行中に見たいこと、終わった後に見たい結果と見せ方（REQ-026）
- 作り直しでは、できていたことの確認（REQ-033）。直すときは使わず、エクステンションが断る（3.4）

| 状態 | 意味 |
| --- | --- |
| 未着手 | まだ聞いていないか、聞いたが答えが来ていない |
| 聞いた | 聞いて、答えを得た |
| 決まりなし | 聞いて、決まりがないと答えた |
| 保留 | 聞いたが、答えが出ていない点がある（本人が知らない・思い出せない、聞き直しの上限を超えた） |
| 変えないので聞かない | 直すときに、変えるところに関わらないので聞かない（REQ-056） |

- 「変えないので聞かない」は、生成プラグインを直すときだけ、未着手からだけ使える。「前回の1回」には使えない。作っていないプラグインでは、どの項目にも使えない。生成プラグインの形にすること自体が変えるところになるためである（REQ-056）。抜き書きの確かめ（下）は、ほかの状態と同じく行う。
- 状態を変えるときは、ユーザーの言葉の抜き書きを添える。添えないと、記録のツールが断る。モデルが自分の判断で項目を済ませないためである。問いを1つもせずに「あいまいさなし」と終えた事故が報告されている（Spec Kit の issue #1717）。
- 抜き書きは、1つの答えの言葉をそのまま写したものにする。要約や、いくつかの答えのつなぎ合わせにしない。間を省くときは「…」を使う。外側の EVAL の採点（[試験の設計](testing.md) 6.5）と同じ決め方である。外側の EVAL の1回目では、前回の1回の答えを「→」でつないだ要約と、括弧を印なしに省いたものが、抜き書きとして記録された。
- 記録のツールは、抜き書きを次のとおり確かめる（エクステンションの守り）。
  - 項目の状態を未着手から変えるとき、抜き書きが、それより前のユーザーの答え（`ask_user` への答えと、打った発言）のどれか1つの中になければ断る。比べるときは、NFKC にし、空白とかぎ括弧・句読点を除き、「…」で区切った断片がすべて同じ答えの中にあればよいとする。
  - 出どころが「生成前の確認で足した」の新しいナレッジ（7.3）で、抜き書きが、ユーザーが選んだ選択肢の文だけなら断る（6.3）。
  - 生成プラグインを直すとき（3.4）、引き継いだ決まりを中身を変えずに「決まった」にする記録で、抜き書きが、その番号を示した `ask_user` の問いへの答えの中になければ断る。決まりの一覧の問いを飛ばして、一覧を見ていないユーザーの言葉で決まったにしないためである（REQ-054）。
    - 番号を示したかは、問いの引数の中のすべての文字（見出し、問いの文、選択肢の文）に、前後が英数字でない形で番号があるかで見る（`K-01` は `K-010`・`K-01a`・`AK-01` に当たらない）。
    - 答えは、答えが来た問いの答えと、答えが来なかった問い（取り消した、答えられなかった）のすぐ次に打った発言である。答えが来ないときは、チャットに答えを書くよう示して止まる（5.5）ので、その発言がその問いへの答えになるためである。チャットの文だけで聞いた問い（`ask_user` を使わない問い）への答えは数えない。問いの文が問答の記録に残らないためである。
    - 決まりの文が問いにあるかは見ない。モデルが長い文を縮めて示したときに、断り続けて止まらないためである。番号だけを並べた問いは通るので、文を示すことはスキルの文（change-read.md の4）に任せる。
    - 確かめないもの：もう「決まった」の行の記録し直し（一度この確かめを通っているので、断ると一覧の問いをもう一度させてしまう）、中身の直し（付け直し。7.3）、外す記録。問答の記録に `ask_user` が1件もないときは、上の1つ目と同じ理由で確かめずに通す。
  - 問答の記録にユーザーの言葉が1件もないときは、確かめずに通す。問答の記録のフックの形が、実機で確かめられていないためである。
- この守りは、意味までは確かめられない（選択肢の言い換え、選択肢と自分の言葉の混ざったものは見分けられない）。また、選択肢を選んで決まりを足した正しい記録も同じ形なので断られる。その場合は、ユーザーの言葉を写し直せば通る。
- 保留のうち、本人が知らない・思い出せないときは、だれが知っているかも書く。
- 項目「候補の確かめ」の状態は、エクステンションが計算する。確かめていない候補（ファイルや頼みの文から推し量ったもの）が残っていれば未着手、なければ聞いた、である。
- クリエイターの画面の「まだ聞いていないこと」の一覧（REQ-043）は、仕様 REQ-015 の10項目のうち、未着手のものである。「変えないので聞かない」の項目は、聞いたこととも、まだ聞いていないこととも分けて、別の欄に示す（REQ-056）。

### 7.3 ナレッジの欄

| 欄 | 中身 |
| --- | --- |
| 番号 | `K-01` の形。エクステンションが記録の順に付け、使い回さない。直すときは、元の番号の続きから付ける（下） |
| 種類 | 合否の決め方、またはそれ以外（[クリエイターの構造](creator-structure.md) 3.5） |
| 項目 | 仕様 REQ-015 の10項目のどれか |
| 文 | ナレッジ。書き方は下 |
| 出どころ | ヒアリングの答え、ユーザーが自分から話した、生成前の確認で足した、ファイルから読んで確かめた、既存のプラグインから読んで確かめた、AI の判断（ユーザーが任せた） |
| ユーザーの言葉 | 短い抜き書き。ファイルからは、ファイル名と箇所 |
| 例 | あれば |
| 例外 | あれば |
| 状態 | 候補、決まった、外した |

- エクステンションは、記録した時刻と、記録したときにその項目が未着手でなかったか（聞いた、決まりなし、保留）を、自動で付ける（11章）。
- 出どころの決め方：
  - 聞いた問いへの答えは「ヒアリングの答え」にする。
  - 聞いた問いとは別の項目のことを話したとき（前に聞いた項目でも、まだ聞いていない項目でも）と、「ほかにありますか？」（5.7）の答えは、「ユーザーが自分から話した」にする。
  - 項目が未着手のまま出た「ユーザーが自分から話した」話は、エクステンションが質問の改善案の対象から外す（11章）。
  - 直すときは、出どころ「生成前の確認で足した」を、画面と返り値では「直す前の確認で足した」と示す。
- 直すときの決まりの番号（REQ-058）：
  - 元の決まりの一覧（`tests/knowledge.json`）は、直す流れの記録を作るときに、番号・種類・項目・文のまま「候補」で取り込む。出どころは「既存のプラグインから読んで確かめた」で、取り込んだ印（`carried`）と、元の項目の名前を付ける。組み立てが、元の一覧と同じ中身かを項目の名前で比べるためである。項目が10項目の名前と同じ文字でないとき（記号の名前など）と、項目や文の初めか終わりに空白か改行があるときは、理由を示して断り、記録を作らない。組み立ては文字のまま比べるので、承認の後でなく、初めに止めるためである。
  - 新しい番号は、元の `tests/knowledge.json` と `tests/knowledge-removed.json` の番号の最大の次から付ける。外した番号を使い回さないためである。プラグインの本文に出てくる番号は数えない。ひな形の試験の例のような、決まりでない番号も拾うためである。
  - 取り込んだ決まりの中身（種類、項目、文、例、例外）を直す記録が来たら、エクステンションは元の行を「外した」にし、新しい番号の行（元の番号を `replaces` に持つ）を「決まった」で足す。古い番号を指したままの箇所を、構造の検査で見つけられるようにするためである。中身を直す記録の状態が「決まった」でない（候補、外した）ときは断る。付け直すのは、ユーザーが今の中身を答えたときだけだからである。この会話で足した行の直しは、まだプラグインに入っていないので、番号を変えない。付け直した元の行を「決まった」に戻したり直したりする記録は断る。
  - 外した決まりは、直した後のプラグインの `tests/knowledge-removed.json` に移る（[生成プラグインの構造](generated-plugin-structure.md) 7章、[クリエイターの構造](creator-structure.md) 3.4）。
- 合否の基準の番号（`C-01` の形）は、確認を受け付けたときに、エクステンションが「合否の決め方」のナレッジに付けて記録する。直すときは、元の作業の定義で同じナレッジに付いていた番号を引き継ぎ、新しい基準には元の番号の最大の続きを付ける。作るときは `C-01` から付ける。組み立ては、この番号を確かめて使う。引き継いだ課題の eval.json が基準を番号で指すので、確認で示した番号とできあがりの番号をそろえるためである。
- 画面の3つの項目の答え（REQ-026）と、そこで決めた設定と表示の部品、資産には、ナレッジの欄がない。これらは、作業の定義の案と、資産の記録に入る。コンパクションの後は、問答の記録（7.4）から拾う。
- 文の書き方：
  - 1件に1つの決まりを書く。
  - 固有の言葉、数、書式、名前は、ユーザーの言葉のまま書く。言っていない単位や書式を足さない（[試験の設計](testing.md) 7章）。
  - 合否の決め方は、成果物の何を見て、何なら合格かまで書く。
  - 直すとき（3.4）は、作業する AI が従う決まりの形で書く。どこに書くか（スキルか画面か）や、作り手への頼み（「〜と書いてください」「既定ではなく決まりとして」など）は文に入れない。置き場所は直す前の確認の「変わること」で示し、ユーザーの言葉は抜き書きに残る。作業エージェントは文を言い換えずに書くので、頼みの形のまま生成プラグインに入るためである。外側の EVAL（改善）の2回目では、ユーザーの「既定ではなく決まりとして〜と書いてください」をそのまま文にし、ルールのスキル、ナレッジの一覧、合否の基準に、作り手への頼みが入った。change-plugin の本文（始まりの手番で make-plugin の「記録のしかた」に足す）と、直す前の確認の前の見直し（6.3）で行う。

### 7.4 問答の自動記録

- エクステンションは、ヒアリングの最中だけ、次をフックで `qa.jsonl` に追記する。
  - `onPostToolUse`（ツールが `ask_user` のとき）：問い（`message` と欄の定義）と答え（結果の文。取り消しと断りを含む）、答えの結果（答えた、取り消した、断った）
  - `onUserPromptSubmitted`：ユーザーが打った発言
- どちらのフックも、差し込みを返さない。`onPostToolUse` の差し込みは画面に出るためである（2.5）。
- ヒアリングの最中とは、このセッションの記録があり、段階が「生成」に進む前の間である（6.3）。
- 答えの結果は、結果の文の頭で見分ける。「User cancelled the request.」で始まれば取り消した、「The user is not available to respond」を含めば断った、それ以外は答えたである（2.1）。Copilot CLI がこれらの文を変えると、答えたとして記録される。
- 最初の頼みの文も残す。
  - 記録（7.1）ができるのは、状態を変えるツールの最初の成功の呼び出しなので、その前に打たれた発言（make-plugin を呼ぶもとになった頼みの文）は、ヒアリングの最中の発言として追記されない。
  - そのため、エクステンションは、記録がまだないあいだも、このセッションで打たれた発言を `onUserPromptSubmitted` でメモリーに覚えておく。記録を作るときに、覚えておいた発言を、頼みの文として `qa.jsonl` の初めに追記する。記録ができた後は、覚えない。
  - 頼みの文は、打った発言とは別の種類として残す。抜き書きの確かめ（7.2）では、ユーザーの答えに数えない。外側の EVAL の採点が、抜き書きの出どころに最初の依頼の文を含めないため（[試験の設計](testing.md) 6.5）、両者をそろえる。
  - 頼みの文は、質問の改善案の振り返り（11章）の材料に入る。
- 段階が「生成」に進むと、問答の記録も、コンパクションの後の差し込みも止まる。生成の手番の中のコンパクションへの影響は、8章にある。
- モデルは答えを書き写さない。記録のツールで渡すのは、ナレッジと短い抜き書きだけである。
- 使い道：
  - コンパクションの後に、記録しそこねた答えを拾う（状態取得ツールが最後の数件を返す）。
  - 質問の改善案の振り返り（11章）。頼みの文も含む。

### 7.5 記録のツールと状態取得ツールの返り値

- 記録のツールの返り値は、ユーザーの画面に出る（2.5）。そのため、平易な日本語の短い文にする（例：「記録しました。まだ聞いていないこと：成果物、合否の決め方」）。
- 決まったことを知らせるツールは、種類か例外を渡して、例外のある「合否の決め方」になった決まりがあれば、返り値の同じ行の終わりに、その番号と、文に例外のときに何なら合格かが書かれていなければ文を直して記録し直すよう、促す文を足す（6.1）。種類を後で変える手順（生成前の確認の基準の案など）は、例外に触れていないためである。文だけを直す記録では促さない。
- 項目は、画面に出る名前（10項目の言葉）で書き、内部の記号を使わない。誤りのときも、使える値を同じ言葉で返す。
- 段階と項目の状態を知らせるツールと、決まったことを知らせるツールは、7.2 の抜き書きの確かめに合わないときも断る。
- 生成前の確認で示すものを知らせるツール：
  - 引数は、ナレッジの番号の一覧、振る舞いの案、作業の定義の案のパス（`.plugin-creator-work/draft/task.json`）、EVAL の課題（頼むときの言葉、入力のファイル、基準にするナレッジの番号、設定の値）、作り直しと直すときは引き継ぐことと変わること、直すときは新しい版の案、である。
  - 次の順に確かめ、最初に合わなかったところで断る。
    1. 未着手の項目が残っている（残りを返す。5.7）
    2. 引数が欠けている、形が違う（課題の頼むときの言葉、入力のファイルの場所、設定の値の形を含む）。仮でない入力のファイルの場所が、あるファイルの絶対パスでない（フォルダ、ないファイル、相対パス）
    3. 作業の定義の案が、決まった置き場所にない
    4. 作り直しなのに、引き継ぐことと変わることがない。直すときに、引き継ぐことと変わること（変わることは1件以上）か、新しい版の案（`x.y.z` の形で、今の版より大きい。今の版がないときは形だけ）がない。作るときに版を渡した
    5. ナレッジの番号が見つからない、外したもの、決まったものでない
    6. 課題の基準にしたナレッジが、示す一覧にないか、種類が「合否の決め方」でない
    7. 決まったナレッジのうち、示す一覧に入っていないものがある
    8. 直すときに、引き継いだ課題と頼むときの言葉が違う課題がない（変えたところを試す課題がない。6.3）
    9. 作業の定義の案を読めない、「合否の決め方」のナレッジが1件もない、案が決まりに合わない
    10. 課題の設定の値が、作業の定義の案の設定に合わない（名前、型、選択肢、必須で初めの値のない設定の値がない）
- 直す流れの記録を作るツール（`<クリエイターの名前>_change`。3.4）：
  - 引数は、直すフォルダ（作業フォルダからの相対か絶対）と、変えたいこと（1件以上）である。
  - 元のプラグインのマニフェスト（直下、`.plugin/`、`.github/plugin/`、`.claude-plugin/` の順に探す）、決まりの一覧、外した番号の一覧、作業の定義、課題を読み、段階「始まり」の新しい記録を作って、決まりの一覧を取り込む（7.1、7.3）。あるのに読めないファイルがあれば、理由を示して断る。
  - 同じフォルダでもう一度呼ぶと、変えたいことだけを置き換え、取り込み直さない。違うフォルダのときと、作る流れの記録があるときは断る。
  - 返り値には、名前と今の版、取り込んだ決まりの数と番号の範囲、次に付く番号を書く。作っていないプラグインのときは、そのことと、読み取った決まりを1件ずつ確かめることを書く。新しく記録を作ったときは、画面を開くツールの返り値と同じ並びで、1行目に、これからの流れの文そのもの（生成プラグインかで2つに書き分ける）を、2行目に、上の1行だけをほかのツールを呼ぶ前にそのままチャットに書く頼みを置き、ここまでの知らせは3行目から書く（3.4）。
- 状態取得ツールは、今の段階、項目ごとの状態、確かめていない候補、保留の項目と AI の判断、画面の URL、セッションの番号（やめるときの案内に使う。5.6）を返す。直すときは、直すプラグイン、変えたいこと、引き継いだ決まりの数、足した・直した・外した決まりも返す。
- 引数で、最後の数件の問答か、振り返りの材料（ヒアリングで引き出せなかったナレッジ〔11章〕の番号と、問答の記録のすべて）も返す。
- 状態取得ツールの返り値には、「SKILL.md の本文がコンテキストになければ、`skill` ツールで make-plugin を読み直す」旨を入れる。直すときは、読み直すスキルを change-plugin にする。
- 返り値は、振り返りの材料を返すときを除き、数 KB 以内にする。
- 状態取得ツールの説明（description）には、「コンパクションの後、再開の後、段階の始めにまず呼ぶ」と書く。ツールの定義は毎回モデルに送られるためである（2.2）。

## 8. コンパクションと再開への備え

`ask_user` でつなぐヒアリングは、1つの手番が長くなる。その手番の中で自動コンパクションが起きると、`ask_user` の答えが消え、SKILL.md の本文も残らないことがある（2.2）。備えは次の4つである。

1. 状態を会話の外の記録に置く（7.1）。
2. 状態取得ツールを置き、SKILL.md の先頭の決まりにも同じことを書く（7.5、10.2）。
3. コンパクションの後に、1回だけ差し込む。
   - エクステンションは、ヒアリングの最中に `session.compaction_complete` を受けたら、次のメインのエージェントの `onPreToolUse` の `additionalContext` で、1回だけ次の旨を差し込む。「`skill` ツールで make-plugin を読み直し、状態取得ツールを呼んでから続ける」。直す流れの記録（7.1 の `change`）があるときは、読み直すスキルを change-plugin にする。
   - 差し込みは 1KB 未満にする。
   - `onPreToolUse` を使うのは、`ask_user` の後でも画面に出ないためである（2.5）。
   - サブエージェントのツールの呼び出しには差し込まない。フックの入力のエージェントの番号で見分ける（[生成プラグインの構造](generated-plugin-structure.md) 11章 #13）。
   - 1回だけにする理由：毎回差し込むと、差し込みがコンパクションまで履歴にたまる。ツールの結果の後の頻繁な注意書きは、プロンプトインジェクションと疑われうる（Anthropic のプロンプトの手引き、Claude Sonnet 5.5）。
   - 限界：差し込みは、そのツールの結果の後ろに入る（2.5）。そのため、コンパクションの後の最初のツールの呼び出しは、SKILL.md の本文がないまま行われることがある。
4. 読み取り役に大きいファイルを読ませ、メインのエージェントのコンテキストの使用量を抑える（9章）。

生成の段階：

- 段階が「生成」に進むと、問答の記録と差し込みのフックは止まる（7.4）。そのため、生成の手番の中でコンパクションが起きても差し込みはなく、SKILL.md の本文が残らないと、`references/generate.md` を読み直す手がかりがない。差し込みの範囲は広げず、このままにする。
- 生成の続け方は、記録ではなく作業フォルダで決める。`.plugin-creator-work/` があれば組み立ての前で、`parts/manifest.json` の有無で、部品の分け方を終えたかを見分ける。`.plugin-creator-work/` がなければ組み立ては終わっていて、生成プラグインにタグ `plugin-creator-generated` があるかで、試験と直しを終えたかを見分ける（[クリエイターの構造](creator-structure.md) 4.1）。
- 生成の段階の終わる条件は、生成プラグインにタグ `plugin-creator-generated` が付き、できたことの説明と質問の改善案を示したことである（3.1）。
- 直すとき（3.4）も、続け方は作業用の一時フォルダと元のプラグインで決める。一時フォルダに、`change` が残す変わったファイルの一覧がなく、`extract` の結果があれば、部品を直すところから続ける。変わったファイルの一覧があれば、試験から続ける（直しの回数が分からなければ、残りを1回とする）。一時フォルダがなく、HEAD に印のタグがあれば、直したことの説明から続ける。タグもないが、HEAD のコミットの説明が「plugin-creator: <名前> を直した」で始まれば、タグを付けられなかったとき（[クリエイターの構造](creator-structure.md) 4.1）として、説明から続ける。

再開：

- `--continue`／`--resume` で前の会話に戻ったときだけ、続きから進める（2.3）。
- 戻ったときは、`skill` ツールで make-plugin（直すときは change-plugin）を読み直し、始まりの手番から進める（10.2 の5）。
- エクステンションは、同じセッションの番号の記録を読む。
- 画面のサーバーは止まっているので、状態取得ツールが起動し直して URL を返す。メインのエージェントは、URL が変わったかどうかによらず、画面の URL をいつもチャットに示し直す。
- `/clear` や新しい会話は新しいセッションなので、最初から始める。前の記録は残る（自動では消さない。7.1）。

開発の試験の Claude Code では、同じ手番のコンパクションで SKILL.md の本文が消えない見込みなので、この備えは試せない（[試験の設計](testing.md) 4章）。2段目と最終確認で確かめる（12章）。

## 9. 仕事の分け方とモデル

| 担当 | モデル | すること |
| --- | --- | --- |
| メインのエージェント | ユーザーが選んだモデル（REQ-045） | ヒアリングのすべての問い、候補の確かめ、深掘りの判断、記録、資産と公開のプラグインの見極め、生成前の確認、部品の分け方 |
| 読み取り役（カスタムエージェント） | `model` を書かない | ユーザーのファイルとスキル、作り直す・直す元のプラグインを読み、候補を返す |
| 作業エージェント | 費用の低いモデル（[クリエイターの構造](creator-structure.md) 3.3） | 生成プラグインのファイルを書く |
| 文書をテキストにするツール（クリエイターのエクステンション） | モデルを使わない | docx・xlsx・pptx の中の文字を返す |

読み取り役：

- `com.github.copilot/agents/` に置く。メインのエージェントが `task` で頼む。
- `model` を書かない。公式の順（2.6）では、呼び出しで `model` を渡さず、ユーザーが subagents の上書きを設定していなければ、親のセッションのモデル（ユーザーが選んだモデル）になる見込みである（14章 H6）。ファイルから決まりを推し量るのは高い推論力が要る仕事だからである（REQ-045、[クリエイターの構造](creator-structure.md) 3.1）。組み込みの explore と research は、定義でモデルが決められているので使わない（2.6）。
- `tools` は、読む（`read`）、探す（`search`）、Web（`web`）と、文書をテキストにするツールだけにする。スキルを呼ばせないためである。`tools` に書かなければ `skill` は載らないことを、1.0.102 で確かめた（ナレッジ「カスタムエージェント」、[生成プラグインの構造](generated-plugin-structure.md) 11章 #16）。
- `web` は、ファイルが指している Web のページを読むときだけ使う。
- 別名 `search` で検索のツールが渡ることは、1.0.102 で確かめた。`web` は確かめていない（2.6、[生成プラグインの構造](generated-plugin-structure.md) 11章 #24）。
- 渡した prompt しか見えないので、ファイルの場所、分かっている作業と目的、探すものを渡す（2.6）。
- 返すのは、決まりの候補、前回の1回の手がかり、資産の候補である。どれにも出どころ（ファイル名と箇所、短い引用）を付ける。作り直しでは、元のプラグインのできていたことも返す（REQ-033）。読めなかったファイルは、その旨を返す。
- 1つのファイルが同じ決まりを2か所に書いているとき（手順と、気をつけることや理由など）は、1つの候補にまとめ、両方の箇所と引用を出どころに書かせる。片方が何なら合格かを書いていれば、まとめた候補の項目を「合否の決め方」にさせる。手順書は、手順を「気をつけること」の節でもう一度書くことが多く、分けて返すと、同じ決まりを2回確かめ、2つの番号でルールのスキルに2回入るためである。外側の EVAL（改善）の3回目では、示されたスキルの手順と気をつけることから、同じ決まりが3組、別の番号になった。
- 直すとき（3.4）は、元のプラグインと、示されたスキルとファイルの、2つの頼みに分けて並べて頼む。
  - 元のプラグイン：できていたことに加え、構成（スキル、エージェント、スクリプト、MCP サーバー、画面の設定と表示の項目、試験の課題）と、人に聞く場面を返す。生成プラグインのときは、取り込んだ決まりの一覧を頼みに書き、一覧のどれにも当たらない決まりだけを候補として返させる（REQ-054）。読むところは、作業ごとに違う部分に絞らせる。どの生成プラグインにも共通する文を、書き足された決まりと取り違えないためである。
  - 示されたスキル：スキルごとに、`SKILL.md` のあるフォルダの絶対パス、`name` と `description`、決まりの候補（ファイルと節つき）、資産の候補（絶対パスつき）、人に聞く場面を返す（REQ-055）。メインのエージェントは、スキルのフォルダを流用する資産として記録する。組み立てが、この記録で名前の重なりを確かめるためである（[クリエイターの構造](creator-structure.md) 3.4）。
  - 人に聞く場面は、決まりの候補として確かめ、正しいと答えたものだけを、振る舞いの案で人に聞く場面にする。作業エージェントは人に聞けない（`ask_user` を持たない）ためである。
- 20KB を超えるファイルは、範囲を指定するか検索して読む（2.4）。
- 複数のファイルは、並列に頼める（2.6）。
- ユーザーには問わない。`ask_user` を持たないためである（2.1）。
- 読み取り役を分けるのは、読んだ中身がメインの会話に残ると、以後の往復のたびに送り直され（2.2）、コンテキストウィンドウが早く埋まるためである。埋まると、同じ手番の自動コンパクション（8章）が起きやすくなる。

文書をテキストにするツール：

- クリエイターのエクステンションのツールである（例：`<クリエイターの名前>_doc_text`）。docx・xlsx・pptx の場所を受け、中の文字を返す。
- `view` は文書を文字にせず、組み込みの変換のツールもない（2.4）。ユーザーのパソコンに変換のコマンドがあるとは限らないので、エクステンションの中で変換する。
- 読み取り役が呼ぶ。サブエージェントの `tools` に書けて、呼べる（2.6）。
- 許可の確認を省く設定（`skipPermission`）にする。作業フォルダの外の文書も、確認なしで読める。
- 変換は、外部のパッケージを使わずに、エクステンションの中で自前で行う。
  - docx：本文。ヘッダー、フッター、脚注、コメントも返す。
  - xlsx：シートごとのセルの文字
  - pptx：スライドごとの文字
  - PDF、古い形式（doc・xls・ppt）、パスワード付きの文書には対応しない。
  - 返す文字は、先頭の16,000文字までにする。

聞き漏らしやあいまいさを点検するサブエージェントは置かない。外側の EVAL で必要と分かったら足す（憲章 第10条、第14条）。

## 10. SKILL.md の組み立て

### 10.1 本文と references

- 本文と references は、日本語で書く。
  - 指示の言語だけを変えて比べた研究は、小型の公開モデルのものしかない。そこでは英語の指示のほうが出力形式の制約を守りやすかったが、課題の性能で英語が圧倒的に有利なわけではなかった（Enomoto ほか 2025）。
  - 商用のモデルで、日本語の指示と英語の指示を比べた研究は見つからなかった。
- 本文は500行・5,000トークン以内にする（Agent Skills の仕様、Anthropic「Skill authoring best practices」）。
- 本文に置くもの（上から）：
  1. 先頭の決まり（10.2）
  2. 始まりの手番（3.1）
  3. 段階の一覧。段階ごとに、目的を1行、その段階の始めに読む references のファイル、記録で確かめられる終わる条件を書く。段階「生成」も入れる（3.1、8章）。
  4. 問いの形（4章）。すべての段階で使い、コンパクションの後も本文と一緒に残すためである。どの段階でも起きる貼り付けと文書の扱い（3.1）と、Claude Code 向けの1文（10.4）も、ここに置く。
  5. 記録のしかた（7章）
  6. 赤信号の表（10.3）
  7. 疲れ・急ぎのときと、「質問しないで作って」と頼まれたとき（5.6）
  8. `ask_user` がないときと、答えが来ないとき（5.5）
- フロントマターは、Agent Skills の仕様の項目（`name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools`）だけにする。`user-invocable`・`disable-model-invocation`・`argument-hint` は、Agent Plugins 1.0.0 では飛ばされるおそれがあり、参照の実装では誤りになる。`name` は英小文字・数字・ハイフンで、フォルダの名前と同じにする。
- references：
  - 段階ごとに1つ置く。中身は、その段階の問いの型、深掘りの型、例である。
  - 各ファイルは 20KB 未満にする。`view` が 20KB を超えるファイルを読まないためである（2.4）。
  - 本文から1段で参照する。
  - 本文で「この段階の始めに `references/<ファイル>` を読む」と名指しする。Related files にはパスしか並ばないためである（2.2）。
  - 中身はコンパクションで消えるので、コンパクションの後は今の段階のファイルを読み直す。
- 生成プラグインのひな形は、クリエイターの直下の `template/` にある（[生成プラグインの構造](generated-plugin-structure.md) 9章）。スキルのフォルダの外なので、Related files に並ばない（2.2）。スキルのフォルダの中に置いたときは、ひな形のファイルがすべて Related files に並んだ。外へ移して、97件から16件になった。本文では、ひな形の場所（スキルのフォルダの2つ上の `template/`）と、メインのエージェントがひな形を読まないことを書く。
- スキルのフォルダのスクリプトとひな形は、スキルを呼んだときに添えられる「Base directory for this skill」のフォルダ（2.2）から作った絶対パスで扱う。作業フォルダはスキルのフォルダではないためである。
- ツール名はバッククォートで囲む（[試験の設計](testing.md) 4章の置き換えのため）。
- `ask_user` の引数の名前（`requestedSchema`、`default` など）は書かず、「自由入力の欄」「選択肢」「おすすめ」と書く。形はホストのツールの定義に任せる。Claude Code の質問のツールは形が違うためである。
- description は、何ができあがるかを手順でない短い1句で書き、続けて、呼ばれる場面と、呼ばれてはいけない似た頼みを書く。手順の要約は書かない。日本語で書き、ユーザーが頼むときの言い方を入れる。クリエイターのスキルと、クリエイターのメインのエージェントが書く生成プラグインの入口のスキルの両方に当てはまる。ルールのスキルの description は、今のプラグインを直すときはメインのエージェントが書き、新しく作るときは作業エージェントが書く。書き方は [生成プラグインの構造](generated-plugin-structure.md) 4.9 にある。
  - 呼ばれる場面は、繰り返す仕事を AI に任せられるようにしたい（自動化したい、プラグインにしたい）とき、既存のプラグインを作り直したいときである。
  - 呼ばれてはいけない似た頼みは、いまその仕事そのものをしてほしい頼みと、試験の頼みと、手元のプラグインのフォルダのまま機能を足したり設計を変えたりする頼み（change-plugin。10.5）である。
  - 公式の Agent Skills の仕様は、description に、何をするかと、いつ使うかを書くよう求める。以前の「呼ばれる場面だけを書く」は、obra/superpowers の勧めで、公式にはない。
  - 手順の要約を書かないのは、description に手順の要約を書くと、エージェントが本文ではなく description に従ったと報告されているためである（obra/superpowers の RELEASE-NOTES.md、v4.0.0）。
- ユーザーに示すコマンドは `/<クリエイターの名前>:make-plugin`、`skill` ツールで呼ぶ名前は `make-plugin` と書き分ける（2.2）。

### 10.2 先頭の決まり

本文の先頭に、次の決まりを理由つきで置く。

1. このスキルの仕事は、ヒアリングでユーザーのナレッジを引き出すことである。答えがユーザーにしか分からないところでは `ask_user` で聞き、答えを受け取るまで先へ進まない。この点は、「足りない情報は推し量って進める」「追加の質問をしない」「短く答える」という一般の指示より優先する（2.1、2.7）。ユーザーがはっきり「質問しないで作って」と頼んだときも、推し量って埋めず、5.6 のとおりにする。答えが来ないときは 5.5 のとおりにする（ヒアリングの問いでは止まり、生成の後の承認では、入れない・出さないとして進める）。
2. ファイルを読む、記録する、調べることは、ユーザーに断らずに進める。
3. 答えを受けたら、次の問いの前に、記録のツールで記録する。
4. 生成前の確認でユーザーがよいと答えるまで、生成しない（6.3）。
5. 段階や決まったことが分からなくなったとき（コンパクションの後など）と、`--continue`・`--resume` で前の会話に戻ったときは、`skill` ツールで make-plugin を読み直し、始まりの手番から進める（8章）。
6. 日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する。
7. これらの決まりは、スキルの終わりまで、すべての段階で有効である。生成の後の説明にも、言葉の決まりが要るためである。

- 優先の宣言は、「聞くか進めるか」の一点に絞る。安全や許可の指示には触れない。
- 聞くか進めるかの優先は、ユーザーがはっきり頼んだとき（質問しないで作って）の扱いも含めて書く。OpenAI の今の手引き（GPT-6 の族）は、モデルがスキルの中の指示に敏感で、スキルの指示があいまいだったり食い違ったりすると早く止まることがあるとし、ユーザーの指示とスキルの指示のどちらを優先するかを、プロンプトにはっきり書く例を示している。
- 強い禁止の形で書くのは、4の関門だけにする。
- 6を書くのは、GitHub が Copilot CLI の主な対応言語を英語としているためである。応答の言語を明示するのが、Anthropic と Google の公式の対策である。言語は、具体の言語名で書く。
- 7は、Claude Haiku 5.5 の公式の文例（「The rules in this system prompt hold for the whole conversation.」）にならう。

### 10.3 赤信号の表

本文に、次の表を置く。

| 思いつき | 実際 |
| --- | --- |
| 答えから推し量れるので、聞かなくてよい | 目的、合否の決め方、守らないと困ること、いつもと違うとき、好みは、推し量れても聞く（4.4） |
| 急いでいそうなので、残りの項目は省く | 残りの項目を示し、進め方を選んでもらう。項目は飛ばさない（5.6） |
| 答えが来ないので、推測で進める | 推測で埋めず、続け方を示して止まる（5.5） |
| 「いいですね」と言われたので、作り始める | 承認は、生成前の確認で示した一覧と案に対してだけである（6.3） |
| 十分に聞いたので、確認へ進む | 確認へ進むのは、未着手の項目がなくなってからである（5.7） |

### 10.4 Claude Code 向けの1文

- 本文の「問いの形」の節の中に、次の1文を置く。「質問のツールが選択肢を必ず求めるときは、自由入力で聞く問い（聞き出す問いと理解の確かめ）は、選択肢を作らず、文章で1つ聞いて手番を終える」。自由入力で聞く問いは、4.2 の聞き出すヒアリングと理解の確かめである。
- この1文は、本文の終わりの節ではなく、問いの形の決まりの中に置く。外側の EVAL の2回目の会話例では、自由入力で聞く問いがすべて選択肢つきで出た（4.2）。
- Copilot CLI の `ask_user` は、選択肢のない自由入力の欄を作れるので、この1文は効かない（2.1）。
- Claude Code の質問のツールの形は、[試験の設計](testing.md) 4章にある。

### 10.5 change-plugin の SKILL.md

- 本文と references は、10.1 と同じ決まり（日本語、本文は500行・5,000トークン以内、references は 20KB 未満で本文から名指しする、フロントマターは Agent Skills の6項目だけ）で書く。
- 同じ文を1か所にするため、make-plugin の SKILL.md の4つの節（問いの形、記録のしかた、疲れ・急ぎ、始められないとき・答えが来ないとき）と、make-plugin の references（words.md と各段階のファイル）を読んで使う。読み替え（make-plugin は change-plugin、生成前の確認は直す前の確認）と、make-plugin の始まりの手番と段階の一覧を使わないことを、本文に書く。make-plugin の本文は 5,000 トークンの上限に近く、直す流れの分かれ道を足せないためでもある。
- 隣の make-plugin のフォルダは、スキルを呼んだときの「Base directory for this skill」の1つ上から作った絶対パスで読む（test-plugin と同じ）。Related files には自分のフォルダのファイルしか並ばないためである（2.2）。本物の Copilot CLI で確認なしに読めるかは、14章で確かめる。
- 直す流れだけの手順は、名前が `change-` で始まる4つの references（始まり、読む、直す前の確認、直す）に置き、「`change-` で始まるものだけがこのスキルのもので、ほかは make-plugin のもの」と本文に書く。共有するファイルの中の `references/<ファイル>` が、どちらのフォルダかを分けるためである。共有するファイルの「次へ」と作り直しのための文は使わず、進む先は change-plugin の段階の表で決める。
- 先頭の決まりには、1回の `ask_user` に問いを1つ・欄を1つだけ置くことと、推し量って埋めないことを短く書く。コンパクションの後、4つの節を読み直すまでの間を埋めるためである。ほかに、承認の前に元のフォルダを書かない、元のフォルダの外を書かない（記録、試験の道具、作業用の一時フォルダを除く）、示されたスキルのフォルダを変えない、push しない、読み直すのは change-plugin、言葉は words.md に従う、チャットにはユーザーに向けた文だけを書く（自分のための覚え書きを書かない。ツールの前の進み具合の一言も、日本語〔ユーザーが別の言語で書いたらその言語〕でユーザーに向けて書く。英語の一言を例に挙げて禁じる形にはしない〔3.4〕）、決まりは番号と文で示す、を置く。
- 始まりの手番には、make-plugin の「記録のしかた」に足すナレッジの文の書き方（7.3）を置く。画面を開くツールは1つだけで呼び、ほかのツールを呼ぶ前に URL を1行でチャットに書く（3.4）。これからの流れの文は、URL と結び付けず、記録を作るツールの返り値の1か所に置き、change-start.md の7で、その返り値の直後にそのまま書く（3.4）。外側の EVAL（改善）の3回目では、流れの例を始まりの手番に置き、URL と同じ文に書く形にしたが、URL まで遅れ、流れも書かれなかった。
- 項目の点検の終わりの要約の示し方（6.2）は、「各段階での違い」に置く。make-plugin の items.md を変えずに、直すときだけ変えるためである。
- 赤信号の表は、直す流れのもの（URL を書いたので流れの説明を省く、変えないところもついでに聞く、仕様書や画面の振る舞いもユーザーの決まりかを聞く、機能ごとに要るかを聞く、ついでに古い書き方を直す、範囲の確かめで「ほかはそのとおり」と言われたので一覧の問いを省く、一覧に「ない」と答えたので決まりを足したことにする、スクリプトの引数や終了コード・環境の条件も決まりかを確かめる、スクリプトがそうしているので既定の値・守ること・ほかの道具の打ち方も使い方にする、示されたスキルの決まりをそのまま入れる、試験に通すため引き継いだファイルも直させる、など）を置く。
- 外側の EVAL で共有が崩れたとき（4つの節を読まない、make-plugin の流れを始める）は、4つの節を本文に写す。
- description の呼ばれる場面は、手元のプラグインに機能を足したい、設計を変えたい、作業役を分けたい、機能を消したい、今使っているスキルを組み込みたい、と頼まれたときである。呼ばれてはいけない似た頼みは、新しく作る、新しいフォルダに作り直す、試験、そのプラグインの仕事そのもの、である。「作り直したい」とだけの頼みは make-plugin に残し、どちらが呼ばれても、直すか新しいフォルダに作るかを聞く（3.4）。両方の description が同じ言葉を持つと、どちらが選ばれるかが定まらないためである。test-plugin の description の使わない頼みにも、今あるプラグインに機能を足したり設計を変えたりする頼みを書く。
- ユーザーに示すコマンドは `/<クリエイターの名前>:change-plugin`、`skill` ツールで呼ぶ名前は `change-plugin` と書き分ける（10.1 と同じ）。

## 11. 質問の改善案の判定（REQ-049）

- 1つ目の観点は、エクステンションが記録から機械的に判定し、状態取得ツールが対象のナレッジの番号を返す（7.5）。対象は次の2つである。
  - 出どころが「ユーザーが自分から話した」で、記録したときにその項目が未着手でなかったナレッジ（その項目をヒアリングしたのに出ず、後から出てきたもの）
  - 出どころが「生成前の確認で足した」ナレッジ
- 2つ目の観点（聞き直しが続いた問い、「分からない」と答えた問い）は、メインのエージェントが、状態取得ツールで問答の記録のすべて（最初の頼みの文を含む）を受け取って読み、見つける（7.4、7.5）。
- 試験で不合格になった原因のうちナレッジが足りなかったものと、ユーザーが生成プラグインを直した内容のうちヒアリングで聞いていれば入ったものは、試験の結果、ナレッジの一覧、生成したときの状態からの差分で見る。頼まれた試験の後は、これだけで振り返る。
- 生成したときの状態：生成の後の試験と直しを終えたら、その直しをコミットし、軽いタグ `plugin-creator-generated` を付ける（[クリエイターの構造](creator-structure.md) 4.1）。作業エージェントの直しとユーザーの直しを見分けるためである。直したとき（3.4）も付け直す。タグの名前と、差分をプラグインのフォルダに絞ることは、[クリエイターの構造](creator-structure.md) 4.5 にある。
- 直した後（3.4）も、生成の後と同じく振り返る（REQ-049）。「変えないので聞かない」の項目は、未着手と同じく「その項目をヒアリングした」に数えない。聞いていない項目で出たナレッジを、聞き漏らしとしないためである。
- Issue の案は、決まった言葉だけで書く。
  - 書くもの：段階と項目の名前、起きたことの種類、数、問いの形（選択肢か自由入力か）、plugin-creator の版、対話のモデル
  - 書かないもの：問いの文、答え、ナレッジの文、ファイル名。問いの文にも、仕事の分野の言葉が入りうるためである。
- Issue の案は、1件に1つの項目にし、重要な順に示す。「項目ごとに1件にまとめ」と書くと、2つの項目を1件にまとめてよいと読めたためである。
- 起票のしかたは [クリエイターの構造](creator-structure.md) 4.5 にある。

## 12. 試験

**1段目 構造の検査**（クリエイター自身）

- どのスキル（make-plugin、test-plugin、change-plugin）も、SKILL.md の本文が500行以内で、5,000トークン以内である（トークンの数え方は未決。14章）。
- references の各ファイルが 20KB 未満である。

**2段目 部品の試験**（クリエイターのエクステンション。偽物のつなぎ口からイベントを流す）

- 記録のツールが、項目の名前、状態の移り方、ユーザーの言葉の抜き書きの有無、ナレッジの欄を確かめ、誤りには使える値を平易な日本語で返す。
- 未着手の項目が残っていると、生成前の確認で示すものを受け付けず、残りの項目を返す。
- 生成前の確認を受け付ける前は、段階を「生成」に進める記録を受け付けない。受け付けた後は、抜き書きを添えた記録で段階が「生成」に進み、承認の時刻が残る。その後は、問答を記録せず、差し込みも返さない。
- 確かめていない候補が残っていると、項目「候補の確かめ」が未着手になる。
- `ask_user` の前後のイベント（確定、取り消し、断り）と打った発言を流すと、問答が `qa.jsonl` に記録され、差し込みは返らない。ヒアリングの最中でないときは、記録しない。
- 記録ができる前に打たれた発言は、記録を作ったときに、頼みの文として `qa.jsonl` の初めに追記される。頼みの文は、抜き書きの確かめで、ユーザーの答えに数えられない（7.4）。
- `session.compaction_complete` の後、次のメインのエージェントの `onPreToolUse` でだけ、1回、1KB 未満の差し込みが返る。サブエージェントのツールの呼び出しと、ヒアリングの最中でないときは、差し込まない。
- 状態取得ツールが、段階、項目の状態、URL、最後の数件の問答、振り返りの材料を返し、止まっている画面のサーバーを起動し直す。
- 1つ目の観点の対象（11章）：項目が未着手のときに出どころ「ユーザーが自分から話した」で記録したナレッジは、対象にならない。項目が未着手でないときに記録したものと、「生成前の確認で足した」ものは、対象になる。
- 同じセッションの番号でエクステンションを起動し直すと、記録が読まれる。新しいセッションの番号では、前の記録を読まず、最初から始まる。
- 記録は `COPILOT_HOME` の下のクリエイターのフォルダにだけ作られ、作業フォルダには何も作られない（REQ-021）。
- 文書をテキストにするツールが、見本の docx・xlsx・pptx の中の文字を返す。
- 直すとき（3.4。REQ-052、REQ-054〜REQ-058、REQ-060、REQ-061）：
  - 直す流れの記録を作るツールが、元のプラグインの決まりの一覧を取り込み、生成プラグインかを見分ける（2つのファイルがあるとき、片方だけのとき、ないとき）。同じフォルダの呼び直しでは取り込み直さず、違うフォルダと作る流れの記録では断る。
  - 「変えないので聞かない」が、7.2 の条件のときだけ受け付けられ、画面で別の欄に出る。
  - 取り込んだ決まりの中身（例と例外を含む）を直すと新しい番号になり、新しい番号は外した番号を含む最大の続きから付く。
  - 取り込んだ決まりを中身を変えずに「決まった」にする記録は、その番号を示した問いへの答えの抜き書きでだけ受け付け、番号を示していない問いの答え（答えに番号の範囲があっても）では断って何も変えない（7.2）。答えが来なかった一覧の問いのすぐ次に打った答えは受け付け、間にほかの問いがあれば受け付けない。番号のすぐ後が英字なら、番号を示したことにならない。もう「決まった」の行の記録し直し、中身の直し、外す記録、足した決まりは確かめない。
  - 確認のツールが、変わること・新しい版・変えたところを試す課題のどれかがないと断り、合否の基準の番号を引き継ぐ。課題のない作っていないプラグインでは、作業全体を試す課題と変えたところを試す課題の2つで受け付ける。
  - 状態取得の返り値と、コンパクションの後の差し込みの文が、直すときの中身と change-plugin を示す。
  - 直すときも、記録は `COPILOT_HOME` の下にだけ作られ、直すフォルダは変わらない。

**呼ばれ方の試験**
