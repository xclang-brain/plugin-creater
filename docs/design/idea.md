# アイデア創出の設計

アイデア創出スキル（`make-idea`）が、[アイデア創出の要件](../specs/idea-requirements.md) をどう実現するかを示す。6つの柱の中身は、要件の1章にある（憲章 第26条）。

## 1. 部品

| 部品 | 置き場所 | 役割 | 対応する要件 |
| --- | --- | --- | --- |
| スキル make-idea | `skills/make-idea/SKILL.md` | メインのエージェントが使う。先頭の決まり、始まりの手番、柱の一覧、問いの形、赤信号、止まるとき | REQ-063〜REQ-076 |
| 柱ごとの手順 | `skills/make-idea/references/` | `start.md`（始まり・続き）、`restriction.md`、`research.md`、`essence.md`、`combine.md`、`explain.md`、`accumulate.md`。その柱を始めるときに読む | REQ-065〜REQ-072、REQ-074、REQ-075 |
| 既定のパラメーター | `skills/make-idea/assets/params.json` | 初めて使うときに、データの置き場所へ写す元 | REQ-073 |
| 調査のエージェント | `com.github.copilot/agents/idea-researcher.agent.md` | Web で作品を集め、掘り下げ、似たものを探す。引用つきで書き写す。`tools`：`web`、`read`、`edit`、`search`。モデルは費用の低いもののリスト | REQ-066、REQ-070 |
| 検討のエージェント | `com.github.copilot/agents/idea-thinker.agent.md` | なぜなぜ分析、本質の集約、案を作る、壁打ちの相手、説明を書く、振り返り。役は頼みの文で決まる。`tools`：`read`、`edit`、`search`。`model` を書かず、ユーザーが選んだモデルを継ぐ | REQ-067〜REQ-071 |
| 読み手のエージェント | `com.github.copilot/agents/idea-reader.agent.md` | 説明の文だけを読む第三者。ファイルの場所を渡されず、探すツールを持たない（`tools`：`read` だけ） | REQ-070 |
| 試験 | `tests/creator/make-idea/`、`tests/dev-eval/runner/idea*.mjs` | 7章 | 全体 |

- 3つのエージェントに分けるのは、持つツールが違うからである（調査だけが Web、読み手だけがファイルを読めない）。役ごとにエージェントを増やさない（憲章 第10条）。
- 読み手の `tools` を空にしないのは、Claude Code 向けの置き換え（`convert.py`）が、空の `tools` を「すべてのツール」にするためである。`todo` だけにすると、置き換えた `TodoWrite` が Claude Code（Agent SDK 0.3.310 が同梱する版）になく、「ツールが1つもないエージェント」として起動を断られた（流れの試験で実測）。そこで、`read` だけにする。読み手には、ファイルの場所を渡さず（REQ-070）、探すツール（`search`）も渡さないので、作る過程のファイルにたどり着けない。読み手がファイルを読んでいないことは、流れの試験で確かめる（7.1）。
- スクリプトを使わない。業務の Windows の PC に Python や Node.js があるかが分からないためである。パラメーターの確かめも、メインのエージェントが行う。

## 2. データの置き場所と形

置き場所は `<ホームフォルダ>/.plugin-creator/make-idea/` である（REQ-074）。ホームフォルダの絶対パスは、メインのエージェントがシェルで `$HOME` を見て決める（bash と PowerShell のどちらでも使える）。

```text
<ホーム>/.plugin-creator/make-idea/
  params.json                 パラメーター（初回に assets/params.json から写す。ユーザーが書き換える）
  knowledge/                  知識・経験（柱ごとに1つ）
    1-restriction.md  2-research.md  3-essence.md  4-combine.md  5-explain.md  6-accumulate.md
  runs/<年月日-時分>/          1回の実行（以下、回のフォルダ）
    state.md                  状態ファイル（今の柱、次にすること、状態：途中か終わり）
    knowledge-used.md         柱ごとに、使った知識・経験の番号と、それで変えた判断（REQ-072）
    restriction.md            制限
    research/collect-<n>.md   集めた作品（エージェントごと）
    research/index.md         作品の一覧（番号、名前、URL、1行の説明、評価の手がかり、掘り下げるか）
    research/deep-<n>.md      掘り下げた作品（束ごと）
    essence/analysis-<a>.md   なぜなぜ分析（エージェントごと）
    essence/opinion-<a>-r<k>.md  ほかの分析への意見
    essence/final-<a>.md      出し直した本質
    essence/index.md          本質の一覧（番号、目的、仕組み、裏づけの作品）
    combine/c<nn>/ideas-r<k>.md   組の案（k は直した回数）
    combine/c<nn>/judge-<p>-r<k>.md 壁打ちの相手の判定
    combine/log.md            組ごとの本質、数、通った案の数
    combine/passed.md         通った案の一覧
    selection.md              ユーザーが選んだアイデアと理由
    explain/<n>/similar.md    似た既存のもの
    explain/<n>/draft-<k>.md  説明の版
    explain/<n>/reading-<r>-<k>.md 読み手の読み方
    explain/<n>.md            できた説明
    reflect/reflection-<a>.md 振り返り（エージェントごと）
    reflect/candidates.md     知識・経験の候補
```

- エージェントが読むファイルは、1つ 20,000 バイト未満にする。Copilot CLI のファイルを読むツールが、それより大きいファイルを読まないためである（[ヒアリングの設計](hearing.md) の実測）。大きくなるものは、束ごとのファイルに分ける。
- メインのエージェントは、作品や分析の本文を読まず、索引と、エージェントが返す短い要約だけを見る。コンテキストを小さく保ち、会話の自動の要約（コンパクション）を減らすためである。例外は、壁打ちの判定（短い）と、説明の文（読み手に渡すため）である。
- サブエージェントには、読むファイルと書くファイルの絶対パスを渡す。サブエージェントは渡された文しか見えないためである（ナレッジ「カスタムエージェント」）。

### 2.1 知識・経験の項目の形

```markdown
## K<柱の番号>-<通し番号> <本質の1文>
- 例：<裏づけの具体例1件>
- 出典：runs/<回>/<ファイル>
- 制限：分野を問わない | <得た制限の短い名前>
- 得た日：<年-月-日>
- 確かさ：ユーザーが確かめた | エージェントの判定だけ
```

- 項目の単位で足し・直し・消す。全体を書き直さない。書き直しで細部が消える（ACE の context collapse）ためである。
- 具体例と出典を必ず添える。短くしすぎると、分野の細かいことが落ちる（ACE の brevity bias）ためである。
- 柱を始めるとき、メインのエージェントは、その柱のファイルだけを読み、「制限」が「分野を問わない」か、今の制限に合う項目を使う。別の分野の経験は、合わないときに誤らせる（Xiong ら 2025、ExpeL の比較）。
- 使った項目の番号と、それで変えた判断を、`knowledge-used.md` に柱ごとに書く（REQ-072）。

## 3. 進め方

### 3.1 始まり（`references/start.md`）

この会話で既に回を始めていて、コンパクションの後などに読み直したときは、下の手順をせず、その回の `state.md` の次にすることから続ける（REQ-075。聞き直さない）。

1. 質問のツールがあるかを確かめる。なければ止まる（REQ-064）。
2. 同じ会話で make-plugin・change-plugin・test-plugin のどれかを使っていたら、`/clear` を勧めて止まる（REQ-064、REQ-076）。エクステンションの頼みの文の記録に、アイデア創出の発言が混ざるのを防ぐためである（[ヒアリングの設計](hearing.md) 7.4、`hooks.mjs`）。
3. ホームフォルダを確かめ、`params.json` がなければ既定を写す。読んで確かめる（4章）。
4. 知識・経験の件数を数える（各ファイルの `## K` の見出しを探す）。
5. 使うパラメーターの値、知識・経験の件数、データの置き場所を示す（REQ-063）。続きの回でも示す。
6. `runs/*/state.md` で状態が「途中」の回があれば、続けるか新しく始めるかを聞く（REQ-075）。続けるときは、今の柱と次にすることを示し、文章で「続けて」を待って手番を終える（3.2）。新しく始めるなら、回のフォルダと `state.md` を作る。

### 3.2 手番の区切りと続き

- 制限の決定が終わったら、事前調査の承認を文章で示して手番を終える（REQ-066）。Copilot CLI では、手番の途中でコンパクションが起きると、その手番で呼んだスキルの本文が消える。前の手番までに呼んだスキルの本文は残る（[ヒアリングの設計](hearing.md) の実測、1.0.98〜1.0.102）。最初の手番を早く区切ると、長い柱の途中のコンパクションでも、SKILL.md の本文が残る。
- 新しい会話で途中の回を続けるときも、同じ理由で、続ける承認を文章で聞いて手番を区切る（次にすることが柱1の中か、事前調査の承認を待つところなら区切らない）。
- 区切りの後は、ユーザーの承認や選択のほかは止まらずに進める。
- 各手順を終えるたびに `state.md` を書き直す。手順が分からなくなったら（コンパクションの後など）、`skill` で make-idea を読み直し、`state.md` から続ける。

### 3.3 制限の決定（`references/restriction.md`）

- 頼みの文と前の回の `restriction.md` から分かることを、候補として先に書き出す。
- 足りない項目（目的、範囲、必須の条件、望ましい条件、良さを決める観点）だけを、1問ずつ自由入力で聞く。頼みの文に全部あれば、問いは確かめの1問になる。
- 決めた制限を一覧にして、違うところと足りないところを聞く（理解の確かめ）。ユーザーが直さなくなったら、`restriction.md` に書く。
- 知識・経験：`1-restriction.md` の項目（例：範囲が広すぎて案がぼやけた）を、候補の書き出しと問いに使う。

### 3.4 徹底的な事前調査（`references/research.md`）

1. 承認：集める作品の数、掘り下げる作品の数、同時に調べるエージェントの数、起動の数の見込み（5章）を示し、続けるかを文章で聞いて手番を終える。
2. 集める：調査のエージェントを「同時に調べるエージェントの数」だけ、1つの応答で同時に起動する。1体の目標は、集める数をエージェントの数で割って切り上げた数である。メインのエージェントは、制限から調べる切り口を決め、エージェントごとに違う切り口を渡す（例：公開のプラグインとスキル、分野の道具と製品、技術記事と事例、研究と手法、遠い分野の作品）。遠い分野も入れるのは、珍しい組み合わせが新しさを生む（Uzzi ら 2013）ためである。
3. 一覧：検討のエージェント1体が、`collect-*.md` を読み、URL で重なりを除き、`index.md` を作る。評価の手がかり（スター数、採用例、受賞、レビュー）を見て、掘り下げる作品を選び、理由を書く。`index.md` の行は、番号、名前、URL、評価の手がかり、掘り下げの理由だけにし、説明は `collect-*.md` に残す（2章の大きさの上限に収めるため）。数が足りなければ、メインのエージェントが足りない数だけ集め直す（「集め直しの回数の上限」まで）。それでも足りなければ、もう一度集めるか、今の数で進むかを聞く（REQ-066）。
4. 掘り下げ：選んだ作品を「1体が掘り下げる作品の数」ずつの束に分け、調査のエージェントを束ごとに起動する（同時の数は上の数まで）。作品ごとに、何をするか、誰の何に効くか、評価の証拠を、引用と URL つきで書く。
- 作品は、Web で URL を確かめたものだけを数える。モデルの記憶だけの作品は数えない。
- 同時に起動できる数の上限で断られたら、終わるのを待って次を起動する（Copilot CLI はプランで上限が違う）。
- 知識・経験：`2-research.md` の項目（役に立った情報源、調べ方）を、調査のエージェントへの頼みに入れる。

### 3.5 本質の見極め（`references/essence.md`）

1. 独立の分析：検討のエージェントを「なぜなぜ分析をするエージェントの数」だけ、同時に起動する。エージェントごとに違う観点を渡す（例：使う人の困りごと、仕組み、広まり方）。各エージェントは、掘り下げた作品をすべて読み、作品ごとに「なぜ評価されているのか」「なぜこの形なのか」を、段の上限まで重ねる。本質を、目的と仕組みで書き、裏づけの作品と引用を付ける。1体で「本質の数」以上を出す。
2. 意見の出し合い：各エージェントに、ほかのエージェントの分析のファイルを渡し、相手の主張をいちばん強い形で言い直してから、反論と補いを書かせる（`opinion-*.md`）。
3. 出し直し：各エージェントに、自分あての意見を渡し、互いの結論を見ずに本質を出し直させる（`final-*.md`）。出し合いの往復の数だけ 2〜3 を繰り返す。
4. 集約：検討のエージェント1体が、`final-*.md` を集め、言い換えを1つにまとめ、支持したエージェントの数を記録し、`index.md` を作る。目的と仕組みで書けないものは、印を付けて残す。
- 最後の合意ではなく、各エージェントが出し直した判断を集めるのは、議論の中で同調や迎合が起きる（Weng ら 2025、Sharma ら 2023）ためである。
- 本質の数が足りなければ、REQ-067 のとおり聞く。
- 知識・経験：`3-essence.md` の過去の本質を、今回の作品で裏づけられなくても候補にし、印「過去の本質」と出典（K の番号）を付けて一覧に入れてよい。発明家は事前調査の外の経験からもアイデアを作る、という開発者の考え（ナレッジ「アイデア創出」）のためである。役に立った問い方を、分析の頼みに入れる。

### 3.6 本質の掛け合わせによるアイデア創出（`references/combine.md`）

1. 組を選ぶ：メインのエージェントが、`essence/index.md` から、制限に効きそうで互いに似ていない本質を、今の数だけ選ぶ。前に試した組と同じ組は選ばない。
2. 案を作る：検討のエージェント（案を作る役）が、組から「1つの組から作る案の数」の案を、決まった型（名前、誰が、どの場面で、何をする、掛け合わせた本質がどう効くか）で作る。いちばん新しい版を `ideas.md` にも書き、壁打ちの相手にはこれだけを読ませる（どの版かを伏せるため）。
3. 壁打ち：検討のエージェント（壁打ちの相手）を「壁打ちの相手のエージェントの数」だけ、同時に起動する。相手は、互いを見ずに、案ごとに「通す・通さない」と理由を書く。観点は、制限の必須の条件、良さを決める観点、作品の一覧と比べて既にあるものではないか。返事の最後に、通した案の番号だけを1行で返す。
4. 直す：案を作る役が、相手の判定を読んで案を直す（`ideas-r<k>.md`）。相手がもう一度判定する。壁打ちの往復の数だけ繰り返す。
5. 判定：最後の判定で、相手の過半数が通した案を、通った案とする。メインのエージェントが、相手の返事の番号の行から数える。
6. だめなとき：組の案が1つも通らなければ、その組はだめとする。同じ数で別の組を選ぶ。同じ数で「同じ数で試す組の数」だけ続けてだめなら、「掛け合わせる数を変える順」の次の数にする。通った組が出たら、続けてだめな数を0に戻し、その数のまま続ける。順の最後の数でもだめなら、それまでの結果を示し、順の最初の数から組を選び直すか、止めて後で続けるか、（通った案が1つ以上あれば）説明に進むかを聞く。
7. 止める：壁打ちした案の数が「壁打ちする案の総数」に届き、通った案が1つ以上あれば止める。通った案が0なら止めずに組を選び直す。説明する案がないと柱5を行えず、柱を飛ばすことになるためである。`combine/log.md` と `combine/passed.md` を書き、通った案の一覧を示す。
8. 記録の形：`combine/log.md` は、組ごとに `- c01｜数 3｜E2、E7、E15｜作った案 10｜通った案：1、4、7`（なければ「通った案：なし」）の1行を書く。流れの試験が、数の移り方を採点するためである（7.1）。
- 案を作る役と相手を別のエージェントにするのは、柱の中身（別のエージェントに案をぶつける）であり、自分の出力をひいきする偏り（Panickssery ら 2024）も避けるためである。
- 相手に、どのエージェントが作ったかと、直した案かどうかを伏せるのは、審査の偏り（Zheng ら 2023）を減らすためである。
- 組は順に試す（1つずつ）。次の組の数が、前の組の結果で決まるためである。組の中の相手は同時に起動する。
- 知識・経験：`4-combine.md` の項目（だめだった組の傾向、効いた組み方）を、組を選ぶときと案を作る頼みに使う。

### 3.7 説明するアイデアを選ぶ

- 通った案の一覧（番号、名前、1行）を示し、説明するアイデアの番号（上限まで）と選んだ理由を聞く。自由入力で聞く（REQ-069）。`selection.md` に書く。

### 3.8 アイデアの説明（`references/explain.md`）

1. 似たもの：選んだアイデアごとに、調査のエージェントが、似た既存のものを Web で探し、`similar.md` に書く（同時に起動）。
2. 書く：検討のエージェント（説明を書く役）が、アイデア、制限、組の本質、似たものを読み、説明を書く。型は、題、ひとことで、誰がどの場面で何に困っているか、このアイデアで何が良くなるか、どう動くか、似たものとの違い、よくある質問（Amazon の PR/FAQ の形）。長さの上限を守る。
3. 読む：メインのエージェントが説明の文を読み、読み手のエージェントを「説明を読む第三者のエージェントの数」だけ、同時に起動する。頼みの文には、説明の全文と、読み手の立場（例：同じ業務の開発者、AI に詳しくない上司）だけを入れる。作る過程は入れない。作る過程を知る読み手は、足りないところを自分の知識で補ってしまう（知識の呪い。Camerer ら 1989）ためである。
4. 直す：メインのエージェントが読み手の返事を `reading-*.md` に書き、説明を書く役に渡す。役は、意図と読み方を比べ、合っていれば終わり、違えば直す。直したら新しい読み手で 3 からやり直す。直す回数の上限まで直したときは、最後の版を新しい読み手に読ませ、返事を記録して終える（最後の版を第三者が読まないまま終えないため）。
5. 終わり：できた説明を `explain/<n>.md` に写し、場所と、読み手の指摘で直したことを示す。

### 3.9 知識・経験の蓄積（`references/accumulate.md`）

1. 振り返り：検討のエージェントを「振り返りのエージェントの数」だけ、同時に起動する。回のフォルダの索引と記録（制限、作品の一覧、本質の一覧、組の記録、通った案、ユーザーの選択と理由、読み手の読み方）と、今の知識・経験を読み、互いを見ずに「なぜうまくいったか」「なぜだめだったか」「次に何を変えるか」を問い、本質を見極める。
2. 候補：検討のエージェント1体が、振り返りを集め、今の項目と比べて、足す・直す・消すの候補を `reflect/candidates.md` に、見出し「## 候補<番号> <操作> 柱<番号>」つきで書く。項目は 2.1 の形にする。社名・製品名・数値などの具体は、一般的な言い方に直す。ユーザーの選択で裏づけた候補の確かさは「ユーザーが確かめた」にする。
3. 確かめ：候補の一覧（番号、操作、柱、1文）を示し、外す番号を自由入力で聞く（REQ-071）。
4. 保存：外さなかった候補を、柱ごとのファイルに項目の単位で反映する。ファイルが大きさの上限の「まとめ始める大きさの割合（%）」を超えたら、まとめる・消す候補を示して聞く。
5. 終わり：保存した件数と場所、作ったアイデアでプラグインを作るときは `/clear` してから make-plugin に頼むことを示す。`state.md` を「終わり」にする。

## 4. パラメーター

- 形式は JSON である。キーは日本語の名前で、ユーザーが読んで書き換えられるようにする。ファイルの頭の `説明` に、範囲と止まる値を書く。
- 確かめ（メインのエージェント。REQ-073 の値の扱い）：
  - 要件の表のすべての項目があり、知らない項目がない。
  - 整数で1以上。範囲は `最小`・`最大` を持ち、最小が2以上で、最小≦最大。変える順のどの数も範囲の中。
  - エージェントの数（なぜなぜ分析、壁打ちの相手、読み手、振り返り）が2以上。
  - 本質の数が、掛け合わせる数の最大以上。
  - 1体が掘り下げる作品の数が20以下、まとめ始める大きさの割合が100以下。
  - JSON として読めない、柱の名前の値が表でないときも止まる。
- 既定の値の根拠：

| パラメーター | 既定 | 根拠 |
| --- | --- | --- |
| 集める作品の数 | 100 | 開発者の指示 |
| 同時に調べるエージェントの数 | 4 | 開発者が AI に任せた。Copilot CLI の Pro・Pro+ の同時の上限が4（公式。Free は2、Business は16）で、上のプランでも当たらない。Copilot CLI の組み込みの調査も1回に3〜5個を並列に出す |
| 掘り下げる作品の数 | 30 | 本質の数（30）と同じにし、1つの作品から少なくとも1つの本質を裏づけられるようにする。10件ずつ3つの束になり、同時の上限（4）に収まる |
| 1体が掘り下げる作品の数 | 10 | 1作品の記録を約1,500バイトとして、1体が書くファイルが 20,000 バイト未満に収まる数。上限は20 |
| 集め直しの回数の上限 | 2 | 1回目の集めで重なりが多くても、切り口を変えて2回足せば届く見込み。足りなければユーザーに聞く |
| 本質の数 | 30 | 開発者の指示 |
| なぜなぜ分析をするエージェントの数 | 2 | 開発者の指示 |
| なぜを重ねる段の上限 | 5 | なぜなぜ分析の元のやり方（大野耐一）が5回 |
| 意見を出し合う往復の数 | 1 | 往復を重ねると同調が進む（Weng ら 2025）。まず1回で試し、知識・経験で見直す |
| 一度に掛け合わせる本質の数 | 2〜4 | 開発者の指示 |
| 掛け合わせる数を変える順 | 3 → 4 → 2 | 開発者の例（3つ、だめなら4つ、2つ） |
| 同じ数で試す組の数 | 3 | 開発者の例（別の3つを3回） |
| 壁打ちの相手のエージェントの数 | 2 | 開発者の指示 |
| 1つの組から作る案の数 | 10 | 総数100を10の組で試せる。1つの組で多く作ると、後の案ほど似る（Si ら 2024：4000案のうち重ならないのは約5%） |
| 壁打ちする案の総数 | 100 | 元の手順の「100個でも1000個でも」の少ないほう。費用を見てから増やせる |
| 壁打ちの往復の数 | 2 | 判定 → 直し → 判定。繰り返すほど案が一点に寄るので、少なく始める |
| 説明を読む第三者のエージェントの数 | 2 | 開発者の指示 |
| 説明するアイデアの数の上限 | 3 | 説明は1件に約10回の起動を使うので、ユーザーが良いと思う案に絞る |
| 説明を直す回数の上限 | 2 | 初めの説明と、直した2つの版を読み手に確かめられる |
| 説明の長さの上限（文字） | 4000 | PR/FAQ の1ページと数問の質問の分。読み手の LLM は長い文を高く見る（Zheng ら 2023）ので、長くしない |
| 振り返りのエージェントの数 | 2 | 振り返りにも本質の見極めが要る。本質の見極めは2者以上という開発者の指示から |
| 知識・経験のファイル1つの大きさの上限（バイト） | 16000 | エージェントが読む上限（20,000 バイト未満）より小さくし、まとめる余地を残す |
| まとめ始める大きさの割合（%） | 80 | 上限を超える前に、まとめる・消すを確かめる余地を残す |

## 5. 起動の数の見込み

事前調査の承認で示す数は、パラメーターから次のように数える（P は壁打ちの相手の数、R は読み手の数、N は往復の数）。

| 柱 | 起動の数 | 既定の値で |
| --- | --- | --- |
| 徹底的な事前調査 | 同時の数 ＋ 一覧の1 ＋ 掘り下げの束の数（掘り下げる数 ÷ 1体が掘り下げる作品の数 の切り上げ） | 4 ＋ 1 ＋ 3 ＝ 8 |
| 本質の見極め | 分析の数 ×（1 ＋ 2 × 往復）＋ 集約の1 | 2 × 3 ＋ 1 ＝ 7 |
| 本質の掛け合わせ | 組の数（総数 ÷ 1組の案の数）×（1 ＋ P ＋（N − 1）×（1 ＋ P）） | 10 × 6 ＝ 60 |
| アイデアの説明 | 説明の数 ×（2 ＋ R ×（1 ＋ F）＋ F）。似たもの1と書く役1、読み手は版ごと、直す役は直した回数。F は直す回数の上限 | 3 × 10 ＝ 30 |
| 知識・経験の蓄積 | 振り返りの数 ＋ 候補の1 | 3 |

- 既定の値で合わせて約108回である。組がだめで選び直すと、掛け合わせの数が増える。
- 1回の起動の費用は、モデルとプランで変わるので、AI クレジットの見込みは示さない。起動の数を示し、ユーザーが値を下げてから始められるようにする。Copilot CLI の `/usage` と `/limits` を案内する。

## 6. 問いの形

- 問いは、メインのエージェントだけが出す。サブエージェントは質問のツールを持たない（Copilot CLI 1.0.98・1.0.102 の実測、Claude Code の公式）。
- 1回の問いには、問いを1つだけ置く。問いの文は、なぜ聞くかの1文と、それだけで答えられる疑問文で書く。
- 決める問い（続けるか、どの回を続けるか）は選択肢で聞き、おすすめを先頭に置いて「（おすすめ）」と書き、理由を1文添える。
- 聞き出す問い（制限の項目、選ぶ番号と理由、外す番号）は自由入力で聞く。質問のツールが選択肢を必ず求めるとき（Claude Code）は、文章で1つ聞いて手番を終える。make-plugin と同じ決まりである。
- 事前調査の承認は、文章で聞いて手番を終える（3.2）。

## 7. 試験

| 段階 | 試験 | 置き場所 | 見ること |
| --- | --- | --- | --- |
| 1段目 | 構造の検査 | `tests/creator/check_creator.py`（ひな形の構造の検査を使う） | スキルとエージェントの形。make-idea の SKILL.md の本文が500行・5,000トークン以内 |
| 2段目 | 形の試験 | `tests/creator/make-idea/test_make_idea.py` | 既定のパラメーターが要件の表と同じか。README にデータの置き場所と消し方があるか（REQ-074）。references がすべて名指しされ、20,000 バイト未満か。エージェントの `tools`（読み手がファイルを読めない、`skill` がない）。make-idea の本文が `plugin-creator_` のツールと reader・worker を使うよう書いていないか。6つの柱の名前が、憲章と仕様書と SKILL.md で同じか |
| 2段目 | 入口の部品の試験 | `tests/dev-eval/runner/idea-*.test.mjs` | 採点の部品を、作ったデータで確かめる（モデルを使わない） |
| 3段目 | 流れの試験 | `tests/dev-eval/runner/idea.mjs` | 本物のモデルで、置き換えた版の make-idea を最後まで動かし、8章の項目を採点する |

- 3段目は、外側の EVAL と同じ部品（置き換え、隔離、ユーザー役、記録）を使う。ユーザー役には、制限を知っている人の説明と、選び方の方針だけを渡す。
- 許可：Web の検索と取得、データの置き場所（一時的なホームの下）への書き込みを、あらかじめ許可する。外側の EVAL の隔離の部品は変えず、入口で足す。
- パラメーターは、試験の入口が一時的なホームに `params.json` を置いて決める。小さな値（流れの試験）と既定の値（規模の試験）を選べる。

### 7.1 流れの試験の採点

- 柱ごとの出力があり、数がパラメーターに合う：作品の一覧の URL の数、本質の数、意見のファイルの数、組の数と本質の数、壁打ちした案の数、説明の数、知識・経験の項目。
- 組の記録（`combine/log.md`）が 3.6 の形で、掛け合わせる数の移り方が、続けてだめな数と変える順の決まりに合う（REQ-068）。
- ユーザーが外した候補が、知識・経験に保存されていない（REQ-071。流れの試験のユーザー役は、候補の1番を外す）。
- メインとサブエージェントが書いたファイルが、すべてデータの置き場所の中にある（REQ-074）。
- 役ごとの起動の数：調査、検討、読み手のエージェントの起動が、パラメーターの数以上。集めるエージェントが1つの応答で同時に起動された。
- 読み手が、ファイルを読むツールを呼んでいない。
- `plugin-creator_` のツールが呼ばれず、ヒアリングの記録ができていない（REQ-076）。
- 知識・経験の項目が 2.1 の形で、ファイルが大きさの上限より小さい。
- `state.md` が「終わり」。
- 2回目の実行（知識・経験がある状態）では、`knowledge-used.md` に、柱ごとの使った項目がある（REQ-072）。
- 続きの試験：柱の途中で会話を止め（`--stop-at-pillar`）、新しい会話でデータを写して頼む（`--data-from`）。続けるかが聞かれ、新しい回のフォルダができずに、止まった回が「終わり」になる（REQ-075。`--expect-resume`）。

## 8. 既存の機能との分離

| 結合点 | 分け方 |
| --- | --- |
| エクステンションのフック（頼みの文の記録、コンパクションの後の差し込み） | make-plugin・change-plugin・test-plugin を使った会話では始めない（`/clear` を勧める）。終わりに、make-plugin は `/clear` してから頼むよう示す。エクステンションは変えない |
| `plugin-creator_` のツール | SKILL.md に使わないと書く。試験で呼ばれていないことを見る |
| クリエイターの画面 | 使わない（憲章 第18条は、生成プラグインを作る対話に限る） |
| reader・worker・words.md・examples/ | 使わない。アイデア創出の言葉は SKILL.md に書く |
| make-plugin・change-plugin・test-plugin の description | 変えない。make-idea の description に、プラグインを作る頼み、直す頼み、試験の頼みを除外として書く。呼ばれ方の試験（[試験の設計](testing.md) 6.9）に、アイデアの頼みを足す |
| エージェントの一覧 | 3つの description に「make-idea の手順の中で、メインのエージェントが呼ぶ」と書く |
| 会話例と版 | クリエイターの版を変えない。版を上げると、会話例を作り直す外側の EVAL が要るためである。版は、次に make-plugin の会話例を作り直すときに上げる |
| 構造の検査 | `check_creator.py` のスキルの大きさの検査（skills/ のすべての SKILL.md を測る）が、make-idea の SKILL.md も測る。make-idea のための検査は足さない |
