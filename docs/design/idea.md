# アイデア創出の設計

アイデア創出スキル（`make-idea`）が、[アイデア創出の要件](../specs/idea-requirements.md) をどう実現するかを示す。6つの柱の中身は、要件の1章にある（憲章 第26条）。

## 1. 部品

| 部品 | 置き場所 | 役割 | 対応する要件 |
| --- | --- | --- | --- |
| スキル make-idea | `skills/make-idea/SKILL.md` | メインのエージェントが使う。先頭の決まり、始まりの手番、柱の一覧、問いの形、赤信号、止まるとき | REQ-063〜REQ-076 |
| 柱ごとの手順 | `skills/make-idea/references/` | `start.md`（始まり・続き）、`restriction.md`、`research.md`、`essence.md`、`combine.md`、`explain.md`、`accumulate.md`。その柱を始めるときに読む | REQ-065〜REQ-072、REQ-074、REQ-075 |
| 既定のパラメーター | `skills/make-idea/assets/params.json` | 初めて使うときに、データの置き場所へ写す元 | REQ-073 |
| 調査のエージェント | `com.github.copilot/agents/idea-researcher.agent.md` | Web で作品を集め、評価を確かめ、掘り下げ、先行例と似たものを探す。元のページを読み、引用つきで書き写す。`tools`：`web`、`read`、`edit`、`search`。`model` を書かず、ユーザーが選んだモデルを継ぐ | REQ-066、REQ-068、REQ-070 |
| 検討のエージェント | `com.github.copilot/agents/idea-thinker.agent.md` | 調べる計画、一覧、調査のまとめ、なぜなぜ分析、本質の集約、案を作る、壁打ちの相手、通った案を比べる、説明を書く、振り返り。役は頼みの文で決まる。`tools`：`read`、`edit`、`search`。`model` を書かず、ユーザーが選んだモデルを継ぐ | REQ-066〜REQ-071 |
| 読み手のエージェント | `com.github.copilot/agents/idea-reader.agent.md` | 説明の文だけを読む第三者。ファイルの場所を渡されず、探すツールを持たない（`tools`：`read` だけ） | REQ-070 |
| 試験 | `tests/creator/make-idea/`、`tests/dev-eval/runner/idea*.mjs` | 7章 | 全体 |

- 3つのエージェントに分けるのは、持つツールが違うからである（調査だけが Web、読み手だけがファイルを読めない）。役ごとにエージェントを増やさない（憲章 第10条）。
- 読み手の `tools` を空にしないのは、Claude Code 向けの置き換え（`convert.py`）が、空の `tools` を「すべてのツール」にするためである。`todo` だけにすると、置き換えた `TodoWrite` が Claude Code（Agent SDK 0.3.310 が同梱する版）になく、「ツールが1つもないエージェント」として起動を断られた（流れの試験で実測）。そこで、`read` だけにする。読み手には、ファイルの場所を渡さず（REQ-070）、探すツール（`search`）も渡さないので、作る過程のファイルにたどり着けない。読み手がファイルを読んでいないことは、流れの試験で確かめる（7.1）。
- スクリプトを使わない。業務の Windows の PC に Python や Node.js があるかが分からないためである。パラメーターの確かめも、メインのエージェントが行う。

## 2. データの置き場所と形

置き場所は `<ホームフォルダ>/.plugin-creator/make-idea/` である（REQ-074）。ホームフォルダの絶対パスは、メインのエージェントがシェルで `$HOME` を見て決める（bash と PowerShell のどちらでも使える）。

```text
<ホーム>/.plugin-creator/make-idea/
  params.json                 パラメーター（初回に assets/params.json から写す。ユーザーが書き換える）
  knowledge/                  知識・経験（柱ごとに1つ）
    1-restriction.md  2-research.md  3-essence.md  4-combine.md  5-explain.md  6-accumulate.md
  runs/<年月日-時分>/          1回の実行（以下、回のフォルダ）
    state.md                  状態ファイル（今の柱、次にすること、状態：途中か終わり）
    knowledge-used.md         柱ごとに、使った知識・経験の番号と、それで変えた判断（REQ-072）
    restriction.md            制限
    research/plan.md          調べる計画（問い、切り口、検索語、評価の基準）
    research/collect-<n>-r<k>.md 集めた作品（切り口ごと。k は 0 が1回目、1から調べ直し）
    research/gaps-r<k>.md     足りないところと新しい切り口（調べ直しごと）
    research/index.md         作品の一覧（番号、名前、URL、種類、評価：あり・未確認・なし、評価の手がかり）
    research/eval-<n>.md      評価の確かめ（未確認の作品の束ごと）
    research/deep-<n>.md      掘り下げた作品（束ごと。評価ありの作品すべて）
    research/overview.md      調査のまとめ（問いごと、引用つき）
    essence/chunks.md         分析のまとまり（まとまりごとの掘り下げの束の番号）
    essence/whys-<c>-<a>.md   なぜなぜ分析（まとまりと観点ごと。エージェント自身が書く）
    essence/opinion-<c>-<a>-r<k>.md  ほかの分析への意見
    essence/final-<c>-<a>.md  出し直した本質
    essence/part-<g>.md       集約の1段目（組ごと）
    essence/index.md          本質の一覧（番号、目的、仕組み、なぜの連なり、裏づけの作品）
    combine/c<nn>/ideas-r<k>.md   組の案（k は直した回数）
    combine/c<nn>/prior-r<k>.md   先行例（k は何回目の判定の前か）
    combine/c<nn>/judge-<p>-r<k>.md 壁打ちの相手の判定
    combine/log.md            組ごとの本質、数、選んだ理由、通った案
    combine/passed.md         通った案の一覧
    combine/ranked.md         通った案を3つの観点で比べた順の一覧
    selection.md              ユーザーが選んだアイデアと理由
    explain/<n>/similar.md    似た既存のもの
    explain/<n>/draft-<k>.md  説明の版
    explain/<n>/reading-<r>-<k>.md 読み手の読み方
    explain/<n>.md            できた説明
    reflect/reflection-<a>.md 振り返り（エージェントごと）
    reflect/candidates.md     知識・経験の候補
```

- エージェントが読むファイルは、1つ 20,000 バイト未満にする。Copilot CLI のファイルを読むツールが、それより大きいファイルを読まないためである（[ヒアリングの設計](hearing.md) の実測）。大きくなるものは、束ごとのファイルに分ける。
- サブエージェントに書かせるファイルの名前は、ANALYSIS・REPORT・SUMMARY・FINDINGS で始めない（3.5）。
- メインのエージェントは、作品や分析の本文を読まず、索引と、エージェントが返す短い要約だけを見る。コンテキストを小さく保ち、会話の自動の要約（コンパクション）を減らすためである。例外は、壁打ちの判定（短い）と、説明の文（読み手に渡すため）である。
- サブエージェントには、読むファイルと書くファイルの絶対パスを渡す。サブエージェントは渡された文しか見えないためである（ナレッジ「カスタムエージェント」）。

### 2.1 知識・経験の項目の形

```markdown
## K<柱の番号>-<通し番号> <本質の1文>
- 例：<裏づけの具体例1件>
- 出典：runs/<回>/<ファイル>
- 制限：分野を問わない | <得た制限の短い名前>
- 得た日：<年-月-日>
- 確かさ：ユーザーが確かめた | エージェントの判定だけ
```

- 項目の単位で足し・直し・消す。全体を書き直さない。書き直しで細部が消える（ACE の context collapse）ためである。
- 具体例と出典を必ず添える。短くしすぎると、分野の細かいことが落ちる（ACE の brevity bias）ためである。
- 柱を始めるとき、メインのエージェントは、その柱のファイルだけを読み、「制限」が「分野を問わない」か、今の制限に合う項目を使う。別の分野の経験は、合わないときに誤らせる（Xiong ら 2025、ExpeL の比較）。
- 使った項目の番号と、それで変えた判断を、`knowledge-used.md` に柱ごとに書く（REQ-072）。

## 3. 進め方

### 3.1 始まり（`references/start.md`）

この会話で既に回を始めていて、コンパクションの後などに読み直したときは、下の手順をせず、その回の `state.md` の次にすることから続ける（REQ-075。聞き直さない）。

1. 質問のツールがあるかを確かめる。なければ止まる（REQ-064）。
2. 同じ会話で make-plugin・change-plugin・test-plugin のどれかを使っていたら、`/clear` を勧めて止まる（REQ-064、REQ-076）。エクステンションの頼みの文の記録に、アイデア創出の発言が混ざるのを防ぐためである（[ヒアリングの設計](hearing.md) 7.4、`hooks.mjs`）。
3. ホームフォルダを確かめ、`params.json` がなければ既定を写す。読んで確かめる（4章）。
4. 知識・経験の件数を数える（各ファイルの `## K` の見出しを探す）。
5. 使うパラメーターの値、知識・経験の件数、データの置き場所を示す（REQ-063）。続きの回でも示す。
6. `runs/*/state.md` で状態が「途中」の回があれば、続けるか新しく始めるかを聞く（REQ-075）。続けるときは、今の柱と次にすることを示し、文章で「続けて」を待って手番を終える（3.2）。新しく始めるなら、回のフォルダと `state.md` を作る。

### 3.2 手番の区切りと続き

- 制限の決定が終わったら、事前調査の承認を文章で示して手番を終える（REQ-066）。Copilot CLI では、手番の途中でコンパクションが起きると、その手番で呼んだスキルの本文が消える。前の手番までに呼んだスキルの本文は残る（[ヒアリングの設計](hearing.md) の実測、1.0.98〜1.0.102）。最初の手番を早く区切ると、長い柱の途中のコンパクションでも、SKILL.md の本文が残る。
- 新しい会話で途中の回を続けるときも、同じ理由で、続ける承認を文章で聞いて手番を区切る（次にすることが柱1の中か、事前調査の承認を待つところなら区切らない）。
- 区切りの後は、ユーザーの承認や選択のほかは止まらずに進める。
- 各手順を終えるたびに `state.md` を書き直す。手順が分からなくなったら（コンパクションの後など）、`skill` で make-idea を読み直し、`state.md` から続ける。

### 3.3 制限の決定（`references/restriction.md`）

- 頼みの文と前の回の `restriction.md` から分かることを、候補として先に書き出す。
- 足りない項目（目的、範囲）だけを、1問ずつ自由入力で聞く。頼みの文に全部あれば、問いは確かめの1問になる。必須の条件、望ましい条件、良さを決める観点は聞かない。良さは要件の1章の3つ（新しさ、役立つか、価値）で判定し、制限は事前調査の範囲を決めるためだけに使うためである（開発者の考え）。前の版では、これらを壁打ちの観点に使い、案が制限の中に押し込められた。
- 決めた制限を一覧にして、違うところと足りないところを聞く（理解の確かめ）。ユーザーが直さなくなったら、`restriction.md` に書く。
- 知識・経験：`1-restriction.md` の項目（例：範囲が広すぎて案がぼやけた）を、候補の書き出しと問いに使う。
- 柱3から後のエージェントには、`restriction.md` の場所も中身も渡さない（REQ-065）。流れの試験で、柱3から後の起動が `restriction.md` を読んでいないことを見る（7.1）。

### 3.4 徹底的な事前調査（`references/research.md`）

ディープリサーチの形で調べる（REQ-066）。開発者が示したのは、各社の AI のディープリサーチの機能である。

- CLI のディープリサーチの機能は、スキルから呼べない。Copilot CLI の `/research`（v0.0.417 から。調べるのは専用の research エージェント）も、Claude Code の `/deep-research`（同梱の workflow。v2.1.218 から、ユーザーが手で呼んだときだけ起動する）も、ユーザーが打つコマンドで、スキルやカスタムエージェントから呼ぶ方法は公式に書かれていない（2026-10-28 に公式のドキュメントで確かめた）。Copilot CLI の `task` に `agent_type: "research"` を渡せることは、公式には書かれていない。
- そこで、make-idea の手順の中で、同じ形の調べ方を組む。Copilot CLI の `/research` も、本体が調査のエージェントに作業を何度も振る形である。
  1. 承認：集める作品の数、調べ直しの回数、1件に読む情報源の数、同時に調べるエージェントの数、起動の数の見込み（5章）を示し、続けるかを文章で聞いて手番を終える。
  2. 計画：検討のエージェント1体が、制限から、答えたい問い、切り口（近い分野と、同じ困りごとを別の分野でどう解いているかなどの遠い分野）、切り口ごとの検索語と情報源、作品の種類ごとの「評価を受けている」の基準を `plan.md` に書く。遠い分野も入れるのは、珍しい組み合わせが新しさを生む（Uzzi ら 2013）ためである。
  3. 集める：調査のエージェントを切り口ごとに同時に起動する。作品ごとに元のページを開き、何をするかと評価の手がかりを確かめて書く（`collect-<n>-r0.md`）。前の版では、検索結果の要約だけで書いた行が多かった。
  4. 調べ直す：検討のエージェント1体が、計画の問いのうち答えが薄いもの、近い分野への偏り、評価の手がかりが取れていない種類を見つけ、新しい切り口を書く（`gaps-r<k>.md`）。調査のエージェントがそれを集める（`collect-<n>-r<k>.md`）。調べ直しの回数だけ繰り返す。
  5. 一覧と評価の確かめ：検討のエージェント1体が、重なりを除いて `index.md` を作り、作品ごとに評価を「あり・未確認・なし」にする。「未確認」は、調査のエージェントが別の情報源で確かめ（`eval-<n>.md`）、一覧を直す。数が足りなければ、もう一度調べ直すか、今の数で進むかを聞く（REQ-066）。
  6. 掘り下げ：評価が「あり」の作品をすべて、「1体が掘り下げる作品の数」ずつの束に分けて掘り下げる（同時の数は上の数まで）。件数を決めて選ばない。前の版は、一覧の短いメモだけを見て30件を選んでいた。作品ごとに、決めた数以上の情報源（公式の説明、利用者の評判、第三者の評価）を読み、なぜ評価されているかの材料と、利用者の困りごとを引用で集める（`deep-<n>.md`）。
  7. まとめ：検討のエージェント1体が、問いごとに分かったことを引用つきでまとめる（`overview.md`）。ディープリサーチの最後の、引用つきのまとめに当たる。名前を `report.md` にしないのは、3.5 の Claude Code の名前の決まりのためである。
  8. 終わり：集めた数、評価ありの数、掘り下げた数、読んだページの数（調査のエージェントがファイルの最後の行と返事に書く数の合計）、かかった時間を示す。
- 調査のエージェントのモデルは、メインのエージェントと同じにする（`model` を書かない）。評価の確かめと掘り下げは、何が評価の根拠かを読み分ける、高い推論力が要る仕事である（憲章 第16条）。前の版は費用の低いモデルのリストにしていたが、掘り下げの浅さにつながった。
- 作品は、Web で元のページを確かめたものだけを数える。モデルの記憶だけの作品は数えない。ページが取得できないとき（403 など）は、別の情報源で同じ事実を確かめる。
- 同時に起動できる数の上限で断られたら、終わるのを待って次を起動する（Copilot CLI はプランで上限が違う。Free 2、Pro 4、Max 8、Business 16、Enterprise 32）。
- Claude Code の WebSearch は、対話のセッション1つにつき200回まで（サブエージェントの分も合わせる。`-p` ではターンごと）で、環境変数 `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` で上げられる（公式のドキュメント、2026-10-28）。ディープリサーチと先行例の調べでは、200回を超えうる。超えて検索が断られたら、調査のエージェントはそのことを返事に書き、メインのエージェントは止まって、上限の上げ方を示す。流れの試験は、入口でこの環境変数を上げる（7章）。
- 知識・経験：`2-research.md` の項目（役に立った情報源、調べ方）を、計画と調査のエージェントへの頼みに入れる。

### 3.5 本質の見極め（`references/essence.md`）

0. 分ける：掘り下げの束を、1つのまとまりが「1体が分析する作品の数」を超えないように分け（`chunks.md`）、まとまりごとに 1〜3 を行う。前の版は1体がすべての掘り下げを読む形だったが、評価ありをすべて掘り下げると、1体では読みきれない量になった。ファイルの名前は `whys-<まとまり>-<観点>.md`、`opinion-<まとまり>-<観点>-r<k>.md`、`final-<まとまり>-<観点>.md`（例：`whys-c01-a1.md`）である。
1. 独立の分析：まとまりごとに、検討のエージェントを「なぜなぜ分析をするエージェントの数」だけ、同時に起動する。エージェントごとに違う観点を渡す（例：使う人の困りごと、仕組みの原理、広まり方と使われ方）。各エージェントは、掘り下げの記録（`deep-*.md`）と調査のまとめ（`overview.md`）を読み、作品ごとに「なぜ評価されているのか」から始め、「なぜこの形なのか」など、できる限り多くの疑問を投げかける。答えは、掘り下げで集めた評価の材料の引用にもとづいて書く。「それはなぜか」を、人の困りごとか仕組みの原理に届くまで重ねる（段の上限まで）。各段は前の段の問いの答えにし、根拠（引用か作品の番号）を付ける。機能の言い換えの段で止めない。本質を、目的と仕組みと「なぜ」の連なりで書き、裏づけの作品と引用を付ける。1体で「本質の数」以上を出す。制限のファイルは読ませない。
   - 分析のファイルは、分析したエージェントが自分で書く。名前は `whys-<a>.md`（大きいときは `whys-<a>-2.md`…）にする。Claude Code は、サブエージェントが名前の頭が ANALYSIS・REPORT・SUMMARY・FINDINGS の `.md` を書くのを断る（Agent SDK 0.3.310 が同梱する版の Write の確かめ。大文字小文字を区別しない）。前の版は `analysis-<a>.md` に書かせたため断られ、メインのエージェントが返事を縮めて書き写し、「なぜ」の段が削られた。サブエージェントに書かせるファイルの名前は、どれもこの4つの言葉で始めない。メインのエージェントは、分析の本文を書き写さない。
2. 意見の出し合い：各エージェントに、ほかのエージェントの分析のファイルを渡し、相手の主張をいちばん強い形で言い直してから、根拠の弱さ、言い換え、見落とし、抽象的すぎる本質、なぜの浅さ（機能の言い換えで止まっている段、前の段の答えになっていない段）を書かせる（`opinion-*.md`）。制限との関係は見ない。
3. 出し直し：各エージェントに、自分あての意見を渡し、互いの結論を見ずに本質を出し直させる（`final-*.md`）。出し合いの往復の数だけ 2〜3 を繰り返す。
4. 集約：2段で行う。1段目は、`final-*.md` を「1体が集約する出し直しのファイルの数」ずつの組に分け、組ごとに検討のエージェント1体が、言い換えを1つにまとめ、支持したエージェントの数を記録して `part-<組>.md` を作る。2段目は、検討のエージェント1体が `part-*.md` だけを読み、組をまたいだ言い換えをまとめて `index.md` を作る。本質ごとに、たどり着いた「なぜ」の連なり（短く）を残す。目的と仕組みで書けないものは、印を付けて残す。
5. 終わり：本質の数、場所、柱3にかかった時間、本質の例2つ（「なぜ」の連なりつき）を示す（REQ-067）。
- 最後の合意ではなく、各エージェントが出し直した判断を集めるのは、議論の中で同調や迎合が起きる（Weng ら 2025、Sharma ら 2023）ためである。
- 本質の数が足りなければ、REQ-067 のとおり聞く。
- 知識・経験：`3-essence.md` の過去の本質を、今回の作品で裏づけられなくても候補にし、印「過去の本質」と出典（K の番号）を付けて一覧に入れてよい。発明家は事前調査の外の経験からもアイデアを作る、という開発者の考え（ナレッジ「アイデア創出」）のためである。役に立った問い方を、分析の頼みに入れる。

### 3.6 本質の掛け合わせによるアイデア創出（`references/combine.md`）

1. 組を選ぶ：メインのエージェントが、`essence/index.md` から、新しさと価値につながるように、今の数だけ選ぶ。例えば、根拠のある困りごとにたどり着いた本質と、別の分野の仕組みの原理の本質を組む。互いに似ていないものにし、前に試した組と同じ組は選ばない。選んだ理由を、案を作る前に `combine/log.md` の組の行の下に書く（前の版では、理由を判定の後に書いていた）。制限は使わない。
2. 案を作る：検討のエージェント（案を作る役）が、組から「1つの組から作る案の数」の案を、決まった型（名前、誰のどんな困りごとか（出典。なければ「仮説」の印）、どの場面で、何をするか、掛け合わせた本質がどう効くか）で作る。制限と場面の例は渡さない（前の版では、制限と「今日から試せる案を多めに」と場面の例を渡し、例の場面がそのまま案になった）。いちばん新しい版を `ideas.md` にも書き、壁打ちの相手にはこれだけを読ませる（どの版かを伏せるため）。
3. 先行例を探す：調査のエージェント1体（先行例を探す役）が、組の案ごとに、いちばん近い既存のもの（製品、OSS、論文、特許）を Web で探し、`combine/<組>/prior-r<k>.md` に書く。案の仕組みを一般的な言葉に直した言い方、困りごとの言い方など、複数の言い方で探し、使った検索語と見たページを残す。見つからなかったときも、検索語の一覧を書く。見つけることが役目なので、案の良し悪しは書かない。案を直した回は、直した案だけを探し直す。前の版では、評価役が Web を持たず、集めた一覧100件と比べただけで、選んだ後の調べでほぼ同じ研究が見つかった。浅い調べのまま「新しい」と判定する失敗は、LLM の研究の案でも報告されている（Beel ら 2025、Gupta・Pruthi 2025）。
4. 壁打ち：検討のエージェント（壁打ちの相手）を「壁打ちの相手のエージェントの数」だけ、同時に起動する。相手は、`ideas.md` と `prior-r<k>.md` を読み、互いを見ずに、案ごとに3つの観点（新しさ：いちばん近い既存のものとの違いが価値の中心か。役立つか：根拠のある困りごとに効くか。価値：その人や世の中にとっての大きさに根拠があるか）で判定し、「通す・通さない」と理由と直し方を書く。3つともそろった案だけを通す。相手の1番は、その案がだめな理由をいちばん強く示す役にする。制限のファイルは読ませない。返事の最後に、通した案の番号だけを1行で返す。
5. 直す：案を作る役が、相手の判定と先行例を読んで案を直す（`ideas-r<k>.md`）。先行例を探し直し（3）、相手がもう一度判定する（4）。どの相手の判定にも直す指摘がなくなるか、壁打ちの往復の上限に届くまで繰り返す。
6. 判定：最後の判定で、相手の過半数が通した案を、通った案とする。メインのエージェントが、相手の返事の番号の行から数える。
7. だめなとき：組の案が1つも通らなければ、その組はだめとする。同じ数で別の組を選ぶ。同じ数で「同じ数で試す組の数」だけ続けてだめなら、「掛け合わせる数を変える順」の次の数にする。通った組が出たら、続けてだめな数を0に戻し、その数のまま続ける。順の最後の数でもだめなら、それまでの結果を示し、順の最初の数から組を選び直すか、止めて後で続けるか、（通った案が1つ以上あれば）説明に進むかを聞く。
8. 止める：壁打ちした案の数が「壁打ちする案の総数」に届き、通った案が1つ以上あれば止める。通った案が0なら止めずに組を選び直す。説明する案がないと柱5を行えず、柱を飛ばすことになるためである。`combine/log.md` と `combine/passed.md` を書き、通った案の一覧を示す。
9. 記録の形：`combine/log.md` は、組ごとに `- c01｜数 3｜E2、E7、E15｜作った案 10｜通った案：1、4、7`（なければ「通った案：なし」）の1行を書く。流れの試験が、数の移り方を採点するためである（7.1）。
- 案を作る役と相手を別のエージェントにするのは、柱の中身（別のエージェントに案をぶつける）であり、自分の出力をひいきする偏り（Panickssery ら 2024）も避けるためである。
- 相手に、どのエージェントが作ったかと、直した案かどうかを伏せるのは、審査の偏り（Zheng ら 2023）を減らすためである。
- 組は順に試す（1つずつ）。次の組の数が、前の組の結果で決まるためである。組の中の相手は同時に起動する。
- 相手の1人に、だめな理由をいちばん強く示す役を持たせるのは、LLM が自分や同じモデルの出力を甘く見る偏り（Panickssery ら 2024）を減らすためである。
- 壁打ちの相手に、案を作る役と別のモデルは指定しない。Copilot CLI はセッションのモデルが Auto のとき、エージェントの `model` を無視する。Claude Code のエージェントは他社のモデルを選べず、同じ会社の別のモデルは判定の力が下がりうる（どちらも 2026-10-28 に公式のドキュメントで確かめた）。代わりに、先行例を別の役が探し、相手の1人をだめな理由を示す役にして、偏りを減らす。別のモデルでの判定は、流れの試験の良さの判定（7.2）で行う。
- 知識・経験：`4-combine.md` の項目（だめだった組の傾向、効いた組み方）を、組を選ぶときと案を作る頼みに使う。良さの判定を3つの観点のほかにする項目は使わない（REQ-071）。

### 3.7 説明するアイデアを選ぶ

- 比べる：検討のエージェント1体が、`combine/passed.md` と、通った案の最後の判定・先行例のファイルを読み、組をまたいで重なる案をまとめ、3つの観点で比べた順に並べて `combine/ranked.md` に書く。上位（「選ぶ一覧で詳しく示す案の数」まで）は、3つの観点の評価の要点と、いちばん近い既存のものを1行ずつ付ける。
- 聞く：`ranked.md` の一覧を問いの文に書き、説明するアイデアの番号（上限まで）と選んだ理由を自由入力で聞く（REQ-069）。`selection.md` に書く。前の版では、49案の名前（一部だけ1行の説明つき）しか示さず、選ぶ材料がなかった。

### 3.8 アイデアの説明（`references/explain.md`）

1. 似たもの：選んだアイデアごとに、調査のエージェントが、柱4の先行例（`prior-r<k>.md` のその案の行）を受け取り、それに足して似た既存のものを Web で探し、`similar.md` に書く（同時に起動）。
2. 書く：検討のエージェント（説明を書く役）が、アイデア、最後の判定、組の本質、似たものを読み、説明を書く。制限は渡さない（REQ-065）。型は、題、ひとことで、誰がどの場面で何に困っているか、このアイデアで何が良くなるか、どう動くか、似たものとの違い、よくある質問（Amazon の PR/FAQ の形）。長さの上限を守る。
3. 読む：メインのエージェントが説明の文を読み、読み手のエージェントを「説明を読む第三者のエージェントの数」だけ、同時に起動する。頼みの文には、説明の全文と、読み手の立場（例：アイデアを使う人と同じ立場の人、AI に詳しくない上司）だけを入れる。作る過程は入れない。作る過程を知る読み手は、足りないところを自分の知識で補ってしまう（知識の呪い。Camerer ら 1989）ためである。
4. 直す：メインのエージェントが読み手の返事を `reading-*.md` に書き、説明を書く役に渡す。役は、意図と読み方を比べ、合っていれば終わり、違えば直す。直したら新しい読み手で 3 からやり直す。直す回数の上限まで直したときは、最後の版を新しい読み手に読ませ、返事を記録して終える（最後の版を第三者が読まないまま終えないため）。
5. 終わり：できた説明を `explain/<n>.md` に写し、場所と、読み手の指摘で直したことを示す。

### 3.9 知識・経験の蓄積（`references/accumulate.md`）

1. 振り返り：検討のエージェントを「振り返りのエージェントの数」だけ、同時に起動する。回のフォルダの索引と記録（調べる計画、作品の一覧、調査のまとめ、本質の一覧、組の記録、比べた案の一覧、ユーザーの選択と理由、読み手の読み方）と、今の知識・経験を読み、互いを見ずに「なぜうまくいったか」「なぜだめだったか」「次に何を変えるか」を問い、本質を見極める。
2. 候補：検討のエージェント1体が、振り返りを集め、今の項目と比べて、足す・直す・消すの候補を `reflect/candidates.md` に、見出し「## 候補<番号> <操作> 柱<番号>」つきで書く。項目は 2.1 の形にする。社名・製品名・数値などの具体は、一般的な言い方に直す。ユーザーの選択で裏づけた候補の確かさは「ユーザーが確かめた」にする。良さの判定を要件の1章の3つのほかにする項目（例：制限に合うものが良い、手元ですぐ試せるものが良い）は、候補にしない（REQ-071）。前の版では、ユーザー役の選び方から「ユーザーは環境に合うか、手元ですぐ試せるかで選ぶ」という項目ができ、次の回の案作りと壁打ちの観点に使われた。
3. 確かめ：候補の一覧（番号、操作、柱、1文）を示し、外す番号を自由入力で聞く（REQ-071）。
4. 保存：外さなかった候補を、柱ごとのファイルに項目の単位で反映する。ファイルが大きさの上限の「まとめ始める大きさの割合（%）」を超えたら、まとめる・消す候補を示して聞く。
5. 終わり：保存した件数と場所、作ったアイデアでプラグインを作るときや今あるプラグインに足すときは `/clear` してから make-plugin・change-plugin に頼むことを示す。`state.md` を「終わり」にする。

## 4. パラメーター

- 形式は JSON である。キーは日本語の名前で、ユーザーが読んで書き換えられるようにする。ファイルの頭の `説明` に、範囲と止まる値を書く。
- 確かめ（メインのエージェント。REQ-073 の値の扱い）：
  - 要件の表のすべての項目があり、知らない項目がない。
  - 整数で1以上。範囲は `最小`・`最大` を持ち、最小が2以上で、最小≦最大。変える順のどの数も範囲の中。
  - エージェントの数（なぜなぜ分析、壁打ちの相手、読み手、振り返り）が2以上。
  - 本質の数が、掛け合わせる数の最大以上。
  - 1体が掘り下げる作品の数が20以下、まとめ始める大きさの割合が100以下。
  - 選ぶ一覧で詳しく示す案の数が、説明するアイデアの数の上限以上。
  - JSON として読めない、柱の名前の値が表でないときも止まる。
- 既定の値の根拠：

## 5. 起動の数の見込み

事前調査の承認で示す数は、パラメーターから次のように数える（C は同時に調べるエージェントの数、K は調べ直しの回数、D は1体が掘り下げる作品の数、P は壁打ちの相手の数、R は読み手の数、N は壁打ちの往復の上限、F は説明を直す回数の上限）。

| 柱 | 起動の数 | 既定の値で |
| --- | --- | --- |
| 徹底的な事前調査 | 計画1 ＋ 集める C ×（1 ＋ K）＋ 足りないところ K ＋ 一覧と一覧の直し2 ＋ 評価の確かめ（未確認の数 ÷ 2D）＋ 掘り下げ（評価ありの数 ÷ D）＋ まとめ1 | 1 ＋ 12 ＋ 2 ＋ 2 ＋ 10まで ＋ 20まで ＋ 1 ＝ 48まで |
| 本質の見極め | まとまりの数（掘り下げた数 ÷ 1体が分析する作品の数）× 分析の数 ×（1 ＋ 2 × 往復）＋ 集約（出し直しの数 ÷ 1体が集約するファイルの数 ＋ 1） | 掘り下げが300件なら 10 × 2 × 3 ＋ 3 ＋ 1 ＝ 64 |
| 本質の掛け合わせ | 組の数（総数 ÷ 1組の案の数）×（2 ＋ P ＋（N − 1）×（2 ＋ P））まで ＋ 比べる1。2は案を作る役と先行例を探す役 | 10 × 12 ＋ 1 ＝ 121まで |
| アイデアの説明 | 説明の数 ×（2 ＋ R ×（1 ＋ F）＋ F）。似たもの1と書く役1、読み手は版ごと、直す役は直した回数 | 3 × 10 ＝ 30 |
| 知識・経験の蓄積 | 振り返りの数 ＋ 候補の1 | 3 |

- 既定の値で、多くて約209回である。組がだめで選び直すと、掛け合わせの数が増える。前の版（約108回）より多いのは、事前調査をディープリサーチの形にし、壁打ちに先行例の調べを足したためである。
- 1回の起動の費用は、モデルとプランで変わるので、AI クレジットの見込みは示さない。起動の数を示し、ユーザーが値を下げてから始められるようにする。Copilot CLI の `/usage` と `/limits` を案内する。

## 6. 問いの形

- 問いは、メインのエージェントだけが出す。サブエージェントは質問のツールを持たない（Copilot CLI 1.0.98・1.0.102 の実測、Claude Code の公式）。
- 1回の問いには、問いを1つだけ置く。問いの文は、なぜ聞くかの1文と、それだけで答えられる疑問文で書く。
- 決める問い（続けるか、どの回を続けるか）は選択肢で聞き、おすすめを先頭に置いて「（おすすめ）」と書き、理由を1文添える。
- 聞き出す問い（制限の項目、選ぶ番号と理由、外す番号）は自由入力で聞く。質問のツールが選択肢を必ず求めるとき（Claude Code）は、文章で1つ聞いて手番を終える。make-plugin と同じ決まりである。
- 事前調査の承認は、文章で聞いて手番を終える（3.2）。

## 7. 試験

試験では、柱で示したプロセスどおりにアイデアが作られたかと、できたアイデアが素晴らしいかを確かめる（REQ-077。開発者の指示）。

| 段階 | 試験 | 置き場所 | 見ること |
| --- | --- | --- | --- |
| 1段目 | 構造の検査 | `tests/creator/check_creator.py`（ひな形の構造の検査を使う） | スキルとエージェントの形。make-idea の SKILL.md の本文が500行・5,000トークン以内 |
| 2段目 | 形の試験 | `tests/creator/make-idea/test_make_idea.py` | 既定のパラメーターが要件の表と同じか。README にデータの置き場所と消し方があるか（REQ-074）。references がすべて名指しされ、20,000 バイト未満か。エージェントの `tools`（読み手がファイルを読めない、`skill` がない）と、調査のエージェントが `model` を書いていないか。make-idea の本文が `plugin-creator_` のツールと reader・worker を使うよう書いていないか。6つの柱の名前が、憲章と仕様書と SKILL.md で同じか。SKILL.md の6つの柱の中身が、仕様書の表の文と一字一句同じか。制限の項目が目的と範囲だけか。サブエージェントに書かせるファイルの名前が、ANALYSIS・REPORT・SUMMARY・FINDINGS で始まらないか（3.5） |
| 2段目 | 入口の部品の試験 | `tests/dev-eval/runner/idea-*.test.mjs` | 採点と判定の部品を、作ったデータで確かめる（モデルを使わない） |
| 3段目 | 流れの試験 | `tests/dev-eval/runner/idea.mjs` | 本物のモデルで、置き換えた版の make-idea を最後まで動かし、7.1 の項目を採点する |
| 3段目 | 中身と良さの判定 | `tests/dev-eval/runner/idea-review.mjs` | 流れの試験の回のフォルダを、別のセッションの AI が読み、7.2 の項目を判定する |

- 3段目は、外側の EVAL と同じ部品（置き換え、隔離、ユーザー役、記録）を使う。ユーザー役には、制限を知っている人の説明と、選び方の方針だけを渡す。
- ユーザー役の選び方の方針は、「新しさがあり、誰かにとても役立ち、世の中にとって価値が大きいものを選ぶ」である（REQ-069）。前の版の「上の制限にいちばん合うもの」は、制限を良さの判定に使い、その選び方から知識・経験ができた。
- 許可：Web の検索と取得、データの置き場所（一時的なホームの下）への書き込み、時刻を出すためのシェルを、あらかじめ許可する。外側の EVAL の隔離の部品は変えず、入口で足す。WebSearch の上限（3.4）は、入口が環境変数 `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` を 5000 にして上げる。
- パラメーターは、試験の入口が一時的なホームに `params.json` を置いて決める。小さな値（流れの試験）と既定の値（規模の試験）を選べる。既定の値で動かすときは、`--params skills/make-idea/assets/params.json` とファイルを渡す（`--params default` は、`--data-from` で写した前の回の値をそのまま使う）。
- 知識・経験は、空で始める（`--data-from` を渡さない）。前の版の知識・経験は、ユーザー役の選び方からできていて、良さの判定を制限に寄せるためである。

### 7.1 流れの試験の採点（プロセスどおりか）

数と形に加えて、記録から機械で確かめられる中身を見る。

- 柱1：`restriction.md` の見出しが「目的」と「範囲」だけで、「必ず満たす条件」「あれば望ましい条件」「良さを決める観点」がない（REQ-065）。
- 柱2：`plan.md` がある。`gaps-r<k>.md` と、その回の `collect-*-r<k>.md` が、調べ直しの回数だけある。作品の一覧の URL の数がパラメーター以上。集めるエージェントが1つの応答で同時に起動された。一覧で評価が「あり」の作品が、すべて `deep-*.md` にある（番号で照らす）。掘り下げた作品ごとに、違う URL がパラメーターの数以上ある。`overview.md` がある。`state.md` に柱2の始めと終わりの時刻と、読んだページの数がある（REQ-066）。
- 柱3：`whys-*.md` を、なぜなぜ分析のエージェントが書いている（Write の持ち主がサブエージェントで、メインのエージェントが `whys-*.md` と `final-*.md` を書いていない）。`whys-*.md` の作品の節のすべてに「なぜ評価されているのか」がある。`essence/index.md` の本質のすべてに、「→」を2つ以上含む「なぜ」の行がある。本質の数、エージェントの数、意見のファイルの数、互いを読んでいないこと（前の版と同じ）（REQ-067）。
- 柱3から後で制限を使っていない：柱3から後の役（なぜなぜ分析、意見、出し直し、集約、案を作る・直す、先行例を探す、壁打ちの相手、通った案を比べる、説明を書く・直す、読み手、似たものを探す、振り返り、候補）の頼みの文に `restriction.md` がなく、その役のサブエージェントが `restriction.md` を読んでいない（REQ-065）。
- 柱4：組ごとに、`combine/log.md` に「選んだ理由」の行があり、判定の前に書かれた（log.md を書いた記録に「（判定の前）」がある）。組ごとに `prior-r1.md` があり、検索語の記録がある。組ごとに、判定の回 k のそれぞれに、相手の数だけ `judge-*-r<k>.md` があり、k は往復の上限以下。判定のファイルのすべてに「新しさ」「役立つ」「価値」がある。案を作る役、先行例を探す役、壁打ちの相手が別の起動。`combine/ranked.md` がある。組の記録の形と、掛け合わせる数の移り方（前の版と同じ）（REQ-068、REQ-069）。
- 柱5・柱6・分離・データの置き場所・続き：前の版と同じ（説明の数、読み手の数、読み手がファイルを読んでいない、選択の記録、振り返りの数、知識・経験の形と大きさ、外した候補、`plugin-creator_` のツール、ヒアリングの記録、書き込みの場所、`state.md` が「終わり」）。
- 入口は、`combine/log.md` と `state.md` を書いた記録だけは、中身を縮めずに残す（判定の前に理由を書いたか、柱ごとの時刻を書いたかを見るため）。

### 7.2 中身と良さの判定（`idea-review.mjs`）

流れの試験の後に、別のセッションの AI が判定する。判定する AI は、作る過程の判定（壁打ちの判定、読み手の評価）を良さの判定には使わない。

1. プロセスの中身：1つのセッションが、回のフォルダの `whys-*.md`、`opinion-*.md`、`essence/index.md`、組ごとの `judge-*.md` と `prior-*.md`、`research/plan.md`・`index.md`・`deep-*.md` の一部を読み、次を項目ごとに「満たす・満たさない」と根拠（ファイルと引用）で返す。
   - なぜの各段が前の段の問いの答えになっていて、根拠がある。機能の言い換えで止まっていない。人の困りごとか仕組みの原理に届いている。
   - 掘り下げに、なぜ評価されているかの材料（利用者の声、レビュー、第三者の評価）が引用で集まっている。
   - 壁打ちの判定が、3つの観点で根拠つきで書かれ、制限を判定に使っていない。だめな理由を示す役が働いている。
   - 先行例の調べが、複数の言い方で、製品・OSS・論文・特許を当たっている。
2. アイデアの良さ：説明したアイデア（`explain/<n>.md`）ごとに、別々のセッションが、説明の文だけを読む。WebSearch と WebFetch で、いちばん近い既存のもの（製品、OSS、論文、特許）を、少なくとも3つの言い方で探し、新しさ・役立つか・価値を判定する。ほぼ同じ既存のものが見つかった、困りごとに根拠がない、価値の大きさに根拠がない、のどれかなら不合格にする。合否、いちばん近い既存のもの（名前と URL）、3つの観点の判定と根拠、使った検索語を返す。
- 判定の AI のモデルは選べる（`--review-model`。既定は流れの試験のメインと同じ `claude-opus-5-5`）。別のセッションで、作る過程の判定を見せずに、自分で既存のものを探させることで、作った側の判定に引きずられないようにする。
- 結果は、流れの試験の結果のフォルダに `review.json` として書く。最後の判断は開発者が行う（REQ-077）。

## 8. 既存の機能との分離

| 結合点 | 分け方 |
| --- | --- |
| エクステンションのフック（頼みの文の記録、コンパクションの後の差し込み） | make-plugin・change-plugin・test-plugin を使った会話では始めない（`/clear` を勧める）。終わりに、make-plugin・change-plugin は `/clear` してから頼むよう示す。エクステンションは変えない |
| `plugin-creator_` のツール | SKILL.md に使わないと書く。試験で呼ばれていないことを見る |
| クリエイターの画面 | 使わない（憲章 第18条は、生成プラグインを作る対話と既存のプラグインを直す対話に限る） |
| reader・worker・words.md・examples/ | 使わない。アイデア創出の言葉は SKILL.md に書く |
| make-plugin・change-plugin・test-plugin の description | 変えない。make-idea の description に、プラグインを作る頼み、直す頼み、試験の頼みを除外として書く。呼ばれ方の試験（[試験の設計](testing.md) 6.9）に、アイデアの頼みを足す。Copilot CLI での呼ばれ方は、最終確認（[ヒアリングの設計](hearing.md) 14章 H27）で見る |
| クリエイターの `plugin.json` の description | アイデアを作れることを1文足す。版は変えない（下の「会話例と版」のとおり） |
| エージェントの一覧 | 3つの description に「make-idea の手順の中で、メインのエージェントが呼ぶ」と書く |
| 会話例と版 | クリエイターの版を変えない。版を上げると、会話例を作り直す外側の EVAL が要るためである。版は、次に make-plugin の会話例を作り直すときに上げる |
| 構造の検査 | `check_creator.py` のスキルの大きさの検査（skills/ のすべての SKILL.md を測る）が、make-idea の SKILL.md も測る。make-idea のための検査は足さない |
