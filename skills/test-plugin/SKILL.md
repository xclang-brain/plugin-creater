# test-plugin

このスキルの仕事は、plugin-creator で作ったプラグイン（生成プラグイン）を、ファイルの形の検査、動きの試験、試しに動かして採点する試験（EVAL）の3段階で試験し、結果を示すことである。

## 決まり

次の決まりは、このスキルの終わりまで有効である。

1. 道具を入れる前と、EVAL を始める前には、`ask_user` でユーザーの承認を得る。答えを受け取るまで、入れない・始めない。道具はユーザーのパソコンを変え、EVAL は AI クレジットを使うためである。
2. 承認の問いは、おすすめを付けず、よいと答える選択肢を最初に置かない。Enter だけで先頭の選択肢が選ばれるためである。問いの文は、なぜ聞くかの1文と、それだけで答えられる疑問文で書く。
3. 日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する。
4. ユーザーに話す言葉は、`<スキルのフォルダ>/../make-plugin/references/words.md` の表に従う。説明のない内部の言葉は、ユーザーに伝わらないためである。
5. `<スキルのフォルダ>` は、このスキルを呼んだときに示される「Base directory for this skill」のフォルダの絶対パスである。スクリプトは、ここからの絶対パスで動かす。作業フォルダは、スキルのフォルダではないためである。
6. 試験の合否は、スクリプトの結果で決める。自分では合否を決めない。
7. 生成プラグインのファイルを直さない。直すかはユーザーが決める。手順9の振り返りが、生成したときの印からの差分を、ユーザーの直しとして読むためである。
8. コンパクションの後は、`<生成プラグインのフォルダ>/tests/results/` を見て、どこまで済んだかを決める。EVAL を始める承認の答えが会話になければ、もう一度聞く。ただし、`eval-<日時>/result.json` の `status` が `running` なら、その EVAL は動いているので、動かし直さずに終わりの知らせを待つ。Copilot CLI を起動し直した後などで、動いているコマンドがないのに `running` のままなら、その EVAL は途中で止まったとして示す。

## 手順

1. `ask_user` と `plugin-creator_open` があるかを確かめる（ツールを探すツールがあれば、それでも探す）。ないものがあれば、「始められないとき・答えが来ないとき」のとおりにして止まる。
2. `plugin-creator_open` を呼び、返った URL を「plugin-creator の画面」としてチャットに示す。試験の結果は、この画面でも見られる。
3. 試験する生成プラグインのフォルダを決める。頼みや会話から分からなければ、自由入力の欄で聞く（問いの例：「どのプラグインを試験するかが分からないと、始められません。試験するプラグインのフォルダの場所を書いてください。」）。
4. ファイルの形の検査と動きの試験の道具を確かめる：`python3 <スキルのフォルダ>/scripts/check_tools.py --plugin <生成プラグインのフォルダ> --scope stage12`。試しに動かして採点する試験の道具は、6で始めてよいと答えた後に確かめる。始めるかを決める前に入れるかを聞かないためである。
   - 足りない道具があれば、その道具と、何に使うか（例：Playwright は、できたプラグインの作業の画面を自動で操作して確かめるのに使う）と、入れ方と、入れる場所を示し、入れてよいかを聞く。問いの例：「試験には、次の道具をこのパソコンに入れる必要があります。（道具と、何に使うかと、入れる場所）入れてよいですか？」選択肢は「入れない」「入れてよい」の順にする。
   - よいと答えたら、同じコマンドに `--install` を付けて動かす。入れないと答えたら、ファイルの形の検査と動きの試験ができないことを示して止まる。
   - Python や Node.js そのものがないときは、入れ方を示して止まる。
5. ファイルの形の検査と動きの試験：`python3 <生成プラグインのフォルダ>/tests/run.py`。段階ごとの合否と、不合格の試験とその理由を示す。理由は、試験の名前だけで示さず、何が合わなかったかを words.md の言葉で短く言い直す。
6. EVAL の見込み：`node <スキルのフォルダ>/scripts/eval.mjs estimate --plugin <生成プラグインのフォルダ> --runs 3` で、実行の回数と、使う AI クレジットの見込みを出す。
   - 同じ作業を、できたプラグインを入れたときと入れないときで、同じ回数ずつ動かして比べることを1文で伝える。回数と見込みを示し、始めてよいかを聞く。見込みは上限ではないこと、課題の数×回数×2回を動かすので長くかかること（1回の上限は既定で30分）、試験の間はできたプラグインの実行の記録が一時的にでき、ふだんの作業の記録がすでに多いと古いものから消えることがあることも伝える。
   - 返り値の `credits.estimate` が null のときは、見込みを推し量らず、返り値の `message` のとおりに伝える。推し量った数を見込みとして示すと、ユーザーがその数を信じて承認するためである。
   - 問いの例：「始めると、見込みの分の AI クレジットを使います。この回数で、試しに動かして採点する試験を始めてよいですか？」選択肢は「試しに動かす試験をしない」「回数を変える」「この回数と見込みで始める」の順にする。見込みがないときは、問いの文から「見込みの分の」を除き、3つ目を「この回数で始める」にする。
   - 回数を変えると答えたら、回数を自由入力の欄で聞き、見込みを出し直して、もう一度聞く。
   - しないと答えたら、7を飛ばして8に進む。
   - 始めると答えたら、試しに動かして採点する試験の道具を `check_tools.py` の `--scope eval` で確かめる。足りなければ、4と同じ形で示して入れてよいかを聞き、よいと答えたら `--install` を付けて動かす。入れないと答えたら、7を飛ばして8に進む。
7. EVAL：`node <スキルのフォルダ>/scripts/eval.mjs run --plugin <生成プラグインのフォルダ> --runs <回数>`。
   - 終わるまで長くかかる。コマンドが終わる前に途中の出力が返っても、終わりの知らせが来るまで待ち、同じ EVAL をもう一度動かさない。二重に動かすと、AI クレジットを二重に使うためである。
   - 結果は `<生成プラグインのフォルダ>/tests/results/eval-<日時>/result.json` に、実行のたびに書き直される。`status` が `running` の間は、まだ終わっていない。
   - 途中で止まったときは、返った理由を示す。
   - 試験の間にできたプラグインが残した実行の記録（`<COPILOT_HOME>/plugin-data/<生成プラグインの名前>/runs/` のうち、試験の実行でできたもの）は、`eval.mjs` が実行のたびに消す。ふだんの作業の記録、生成プラグインのフォルダ、`tests/results/` の結果は消さない。結果の注意（`warnings`）に、消せなかった記録や確かめられなかった記録が出たら、そのまま示す。
8. 結果を示す：5の段階ごとの合否と、EVAL をしたときは、実行ごとの合格の条件ごとの合否、プラグインを入れたとき・入れないときの点数とその差、使った AI クレジット。`plugin-creator_results` に、結果のファイルの絶対パス（`<生成プラグインのフォルダ>/tests/results/latest.json` と、EVAL をしたときは `eval.mjs run` の出力の `resultFile`）を渡し、plugin-creator の画面に出す。相対パスは、作業フォルダから探されるためである。
9. 質問の改善案：`<スキルのフォルダ>/../make-plugin/references/improve.md` を読み、「頼まれた試験の後」のとおりに示す。

## 始められないとき・答えが来ないとき

- `ask_user` がないとき（`-p` や `--no-ask-user` で起動したとき）：`-p` と `--no-ask-user` を付けずに、対話モードで起動し直すよう文章で示して止まる。承認を得られないためである。
- `plugin-creator_open` がないとき：`<スキルのフォルダ>/../make-plugin/references/setup.md` を読み、そこにある直し方をすべて示して止まる。
- `ask_user` の結果が「User cancelled the request.」か「The user is not available to respond」で始まる文のときは、答えが来なかったとして扱う。
  - 承認がなかったとして、道具を入れず、EVAL を始めない。
  - 何を聞きたかったかと、続け方（チャットに答えを書く。autopilot で動かしているなら、Shift+Tab でモードを切り替えて autopilot を切る）を短く示して止まる。
  - `task_complete` があれば、それを呼んで止まる。呼ばずに手番を終えると、続けるよう促す発言が届くためである。この場面では、`task_complete` の説明の「終わったときだけ呼ぶ」より、この決まりを優先する。続けるよう促されても、承認なしに進めない。
- 手順9の改善の要望を出すかの問いに答えが来なかったときは、止まらずに、その案を出さずに improve.md のとおり進める。
