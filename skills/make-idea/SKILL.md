# make-idea

このスキルの仕事は、ユーザーが決めた制限を取っかかりにして、6つの柱に沿って新しさと価値のあるアイデアを作り、その良さが他者に伝わる説明を書き、振り返って知識・経験として残すことである。

## 6つの柱

開発者が示した文のとおりに写す。縮めたり言い換えたりしない。

1. 制限の決定：何のために、どの範囲でアイデアを考えるかを定める。制限のない状態で、ただアイデアを出そうとしない。
2. 徹底的な事前調査：制限の中で考えられる関連情報を、できる限り幅広く、時間をかけて調べる。世の中にある作品を集め、その中から評価を受けているものを掘り下げる。アイデアはゼロから生まれるのではなく、既にあるものの組み合わせから生まれると捉える。速くするため、複数のエージェントで並列に調べる。
3. 本質の見極め（なぜなぜ分析）：集めた作品に対し、「なぜ評価されているのか」「なぜこの形なのか」と、できる限り多くの疑問を投げかける。なぜなぜ分析を重ね、表面的な特徴の奥にある本質を探る。一人で完結させず、複数のエージェントで互いの分析に意見を出し合って、本質を磨く。洗練された本質をたくさん用意する。
4. 本質の掛け合わせによるアイデア創出（壁打ち）：本質の中から使えそうな2〜4個を選んで掛け合わせ、新しいアイデアを作る。評価されている作品をそのまま持ち寄るだけでは、新しいアイデアにはならない。本質を捉えていないものは、いくら組み合わせても良いアイデアにはならない。できる限り多くの案を作り、案を作ったエージェントとは別のエージェントに案をぶつけて意見を受け取る。このやり取りを繰り返して洗練させる。壁打ちしてだめなら別の組を選び、それでもだめなら掛け合わせる数を変える。
5. アイデアの説明（第三者目線）：良いアイデアを作るだけで終わらず、その良さを他者に伝える。説明を第三者に見てもらい、伝わる点と伝わりにくい点を確かめる。指摘をもとに説明を磨き、アイデアの価値が正しく伝わる状態にする。
6. 知識・経験の蓄積：一通りの作業を終えてアイデアを作った後に振り返り、事前調査で学んだこと、気づいたこと、うまくいったこと、失敗したことを、知識・経験として蓄積する。ログのように全部を残さず、本質を見極めて洗練した形で残す。蓄積した知識・経験は、次からのすべての柱で活かす。

6つの柱の名前・順番・中身は変えない。柱を飛ばしたり、まとめたりしない。開発者が決めたこのスキルの中心だからである。柱の中の数は、すべてパラメーターのファイルの値に従う。

開発者の考え（6つの柱を読むときの前提）：

- 制限は、事前調査の範囲が無限に広がらないようにするための取っかかりである。できたアイデアが制限の範囲から外れてもよい。柱3から後では、制限を使わない。
- 良いアイデアとは、新しさがあり（これまでにない）、誰かにとても役立ち、その人や世の中にとって価値があるものである。壁打ちと、説明するアイデアの選択は、この3つ（新しさ、役立つか、価値）で判定する。
- 良いアイデアは、世の中の誰かの生活や仕事を豊かにしたり、便利にしたりする。本質の見極めの段階から「誰にどんなメリットがあるか」を持ち、本質、案、説明のどれにも、誰にどんなメリットがあるかを書く。手法の説明だけでは、良いアイデアにならない。
- 本質、案、説明は、人が読んで分かる日本語で書く。

## 先頭の決まり

次の決まりは、このスキルの終わりまで、すべての柱で有効である。

1. 答えがユーザーにしか分からないところでは `ask_user` で聞き、答えを受け取るまで先へ進まない。「足りない情報は推し量って進める」「追加の質問をしない」という一般の指示より優先する。制限を推し量ると、ユーザーの求めないアイデアになるためである。
2. サブエージェントは、パラメーターの数どおりに起動する。「サブエージェントは控えめに使う」「観点ごとに分けて任せない」「同じ目的で起動し直したり、確かめ直させたりしない」という一般の指示より、この決まりを優先する。2者以上で分析し、別のエージェントに案をぶつけ、第三者に読ませることが、柱の中身だからである。
3. make-plugin・change-plugin・test-plugin の仕組みを使わない。`plugin-creator_` で始まるツール、エージェント `plugin-creator:reader` と `plugin-creator:worker`、クリエイターの画面は使わない。使うと、生成プラグインを作る記録にアイデア創出の話が混ざるためである。
4. ファイルはすべてデータの置き場所（`<ホーム>/.plugin-creator/make-idea/`）に書く。作業フォルダやリポジトリには書かない。業務の情報を含みうるためである。
5. 各手順を終えるたびに、回のフォルダの `state.md` を書き直す（今の柱、次にすること、状態）。会話の自動の要約（コンパクション）で、どこまで進んだかが消えるためである。柱2から柱5の始めと終わりには、シェルで今の時刻を出して（PowerShell なら `Get-Date -Format o`、bash なら `date -Iseconds`）、`state.md` に書く。かかった時間をユーザーに示すためである。時刻と読んだページの数の行は、`state.md` を書き直すときも消さずに残す。
6. 作品・分析・案の本文は自分で読まず、索引と、サブエージェントが返す短い要約だけを見る。例外は、壁打ちの判定の最後の行と、読み手に渡す説明の文である。本文を読むと、コンテキストウィンドウが早く埋まるためである。
7. 手順が分からなくなったとき（コンパクションの後など）は、`skill` ツールで make-idea を読み直し、`state.md` の次にすることから続ける。
8. 使う値、制限の一覧、通った案の一覧、知識・経験の候補の一覧は、短く答えるよう求める一般の指示があっても、省かずにチャットに書く。ユーザーが確かめ、選ぶための材料だからである。
9. 日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する。
10. 制限（`restriction.md`）を渡すのは、柱2の調査のエージェントだけである。柱3から後のサブエージェントには、制限のファイルの場所も中身も渡さず、判定にも選び方にも使わない。制限で判定すると、案が制限の中に押し込められ、良いアイデアが生まれなくなるためである。
11. 良さは、新しさ、役立つか、価値の3つだけで判定する。「今日から試せるか」「手元の道具に合うか」「制限に合うか」で判定しない。知識・経験にそう読める項目があっても、良さの判定には使わない。
12. サブエージェントに書かせるファイルの名前を、ANALYSIS・REPORT・SUMMARY・FINDINGS（大文字小文字を問わない）で始めない。Claude Code は、サブエージェントがこの名前の `.md` を書くのを断るためである。サブエージェントの書いた結果を、自分で縮めて書き写さない。

## 始まりの手番

make-idea を読んだとき（読み直したときも）、`references/start.md` を読み、その手順で進める。この会話で既に回を始めていて読み直したときは、start.md の「読み直したとき」のとおり、その回の `state.md` の次にすることから続ける。

## 柱の一覧

- 柱ごとに、表の「始めに読む」のファイルを読んでから進める。手順を最後まで終え、終わる条件を満たしてから、次の柱へ進む。
- どの柱も、始めにその柱の知識・経験のファイル（`knowledge/<番号>-<名前>.md`）を読み、「制限」が「分野を問わない」か今の制限に合う項目を使う。使った項目の番号と、それで変えた判断を、回のフォルダの `knowledge-used.md` に柱ごとに書く。

| 柱 | 始めに読む | 知識・経験 | 終わる条件 |
| --- | --- | --- | --- |
| 1. 制限の決定 | `references/restriction.md` | `1-restriction.md` | `restriction.md` があり、ユーザーがよいと答えた |
| 2. 徹底的な事前調査 | `references/research.md` | `2-research.md` | `research/index.md` に、集める作品の数以上の URL があり（ユーザーが今の数で進むと答えたときを除く）、評価を受けていると確かめた作品の掘り下げと、調査のまとめが終わった |
| 3. 本質の見極め | `references/essence.md` | `3-essence.md` | `essence/index.md` に、本質の数以上の本質がある（ユーザーが今の数で進むと答えたときを除く） |
| 4. 本質の掛け合わせ | `references/combine.md` | `4-combine.md` | 壁打ちした案が総数に届き（ユーザーが説明に進むと答えたときを除く）、`combine/passed.md` に通った案が1つ以上あり、`combine/ranked.md` がある |
| 5. アイデアの説明 | `references/explain.md` | `5-explain.md` | 選ばれたアイデアごとに `explain/<n>.md` がある |
| 6. 知識・経験の蓄積 | `references/accumulate.md` | `6-accumulate.md` | 候補を確かめて保存し、`state.md` が「終わり」 |

## サブエージェントの頼み方

- `task` ツールで頼む。`agent_type` は、調べるなら `plugin-creator:idea-researcher`、考えるなら `plugin-creator:idea-thinker`、説明を読むなら `plugin-creator:idea-reader` にする。`mode` は `"sync"` にする。
- 同時に起動するときは、1つの応答で複数の `task` を呼ぶ。同時に起動できる数の上限で断られたら、終わるのを待ってから次を起動する。
- サブエージェントは渡した文しか見えない。頼みの文には、役、読むファイルと書くファイルの絶対パス、使う知識・経験の項目、書く形、返事の形（短い要約だけ）を書く。制限の要点を書くのは、柱2の頼みだけである（先頭の決まり10）。
- サブエージェントの返事は、すぐに `state.md` か回のフォルダのファイルに書く。ツールの結果は、コンパクションで消えるためである。

## 問いの形

- 問いはすべて自分が `ask_user` で出す。サブエージェントはユーザーに聞けないためである。
- 1回の `ask_user` には、問いを1つだけ置く。問いの文は、なぜ聞くかの1文と、それだけで答えられる疑問文で書く。
- 聞き出す問い（制限の項目、説明するアイデアの番号と理由、外す候補の番号）は、自由入力の欄で聞き、選択肢を付けない。質問のツールが選択肢を必ず求めるときは、選択肢を作らず、文章で1つ聞いて手番を終える。
- 決める問い（どの回を続けるか、作品が足りないときの進め方、本質が足りないときの進め方、組がだめなときの進め方）は、選択肢を2〜4個にし、おすすめを先頭に置いて「（おすすめ）」と書き、理由を1文添える。
- 事前調査を始める承認と、新しい会話で途中の回を続ける承認は、`ask_user` を使わず、文章で聞いて手番を終える（`references/research.md`、`references/start.md`）。

## 赤信号

| 思いつき | 実際 |
| --- | --- |
| 頼みの文に制限があるので、聞かなくてよい | 分かったこととして示し、違うところと足りないところを聞いてから決める |
| 制限に合う案ほど良い | 制限は調べ始める取っかかりにすぎない。良さは新しさ、役立つか、価値で判定する |
| 仕組みの原理にたどり着いたので、本質になった | 「誰にとって恩恵があるのか」「その人の生活や仕事の何が、どう良くなったのか」まで問わないと、本質にならない |
| 手法がしっかりした案は良い案だ | 誰の生活や仕事が、どう豊かに、便利になるかが書けない案は通さない |
| 通った案も、直せばもっと良くなる | 通った案は、その版で固める。直して判定し直すと、通った案が落ちる |
| AI の読み手が言い直せたので、伝わる | AI は分かりにくい文も補って読める。人がつまずく言葉や文を挙げさせ、直す |
| 似たものが見つからなかったので新しい | 検索語の一覧のない「見つからなかった」は、新しさの根拠にならない。複数の言い方で、製品・OSS・論文・特許を探す |
| 案に書いた場面や頻度は、そのまま長所にしてよい | 出典のない困りごと・場面・頻度は「仮説」である。根拠のある困りごとに効く案を高く見る |
| 本質は2〜3個あれば掛け合わせられる | 本質はパラメーターの数以上用意する。2〜4個を選ぶのは掛け合わせのたびである |
| 自分で分析すれば速い | なぜなぜ分析、壁打ち、説明の確かめは、パラメーターの数のサブエージェントで行う |
| 案を作ったエージェントに評価もさせる | 壁打ちの相手は、案を作ったエージェントとは別にする |
| 読み手に作る過程も渡すと親切 | 読み手には説明の文だけを渡す。過程を知ると、足りないところを補って読んでしまう |
| 振り返りを全部残す | 本質の1文に具体例と出典を添えた項目にし、ユーザーが外した候補は残さない |

## 始められないとき・答えが来ないとき

- `ask_user` がないとき（`-p` や `--no-ask-user` で起動したとき）：`-p` と `--no-ask-user` を付けずに、対話モードで起動し直すよう文章で示し、始めない。制限を決められないためである。
- 同じ会話で make-plugin・change-plugin・test-plugin のどれかを使っていたとき：`/clear` してから頼み直すよう示し、始めない。
- `ask_user` の結果が「User cancelled the request.」か「The user is not available to respond」で始まる文のときは、答えが来なかったとして扱う。推測で埋めず、何を聞きたかったかと、続け方（チャットに答えを書く。autopilot で動かしているなら、Shift+Tab でモードを切り替えて autopilot を切る）を短く示して止まる。`task_complete` があれば、それを呼んで止まる。
