# 段階「生成」（直すとき）

目的：よいと答えた内容で `<P>` を直し、試験し、コミットし、直したことを説明し、質問の改善案を示す。

- `<P>` の外に書くのは、`<W>` と試験の道具だけである。push はしない。
- 作業エージェントに `<P>` の中を書かせるのは、4の試験で落ちたところの直しだけである。それより前は `<W>/parts/` に書かせる。
- よいと答えた内容が会話にないとき（コンパクションの後など）は、会話の要約から書き起こさず、`<state.json>` のナレッジと、直す前の確認で示したもの（`confirmation`）から写す。

## 0. 続きの決め方（コンパクションの後など）

`<W>` と `<P>` を見て、どこから続けるかを決める。印のタグの名前は、`<P>` が git のリポジトリの直下（`git -C <P> rev-parse --show-prefix` が空）なら `plugin-creator-generated`、そうでなければ `plugin-creator-generated-<プラグインの名前>` である。

- `<W>/changed.json` があれば、`<P>` はもう直してある。4から続ける。直しの回数が会話から分からなければ、残りを1回とする。
- `<W>/changed.json` がなく、`<W>/extract.json` があれば、まだ直していない。1から続ける。
- `<W>` がなく、HEAD に印のタグがあれば（`git -C <P> tag --points-at HEAD`）、コミットまで済んでいる。6から続ける。すでに示した説明と、出した Issue の案は繰り返さない。
- `<W>` がなく、印のタグもないが、HEAD のコミットの説明（`git -C <P> log -1 --format=%s`）が `plugin-creator: <プラグインの名前> を直した` で始まれば、タグを付けられなかったときである。6から続ける。

## 1. 部品を用意する

シェルで次をする。作業エージェントは、ファイルを写せないためである。

1. `<W>/draft/task.json` があれば、`<W>/parts/task.json` に写す。
2. 流用すると決めた、示されたスキルのスクリプトなどを、その決まりを入れるルールのスキルのフォルダ `<W>/parts/files/skills/<ルールのスキルの名前>/scripts/` に写す。スキルが使うファイルをそのスキルのフォルダに置くと、ルールのスキルが単体でも動くためである。示されたスキルのフォルダの中は変えない。
3. 消すと決めた機能のファイルを、`<W>/parts/files/` から消す。
4. 名前を変えると決めた `<P>` のスキル（`<W>/extract.json` の `name_conflicts` の `plugin_skill`）のフォルダを、`<W>/parts/files/<plugin_skill>/` から `<W>/parts/files/skills/<新しい名前>/` に移す（`mv`）。移す先がもうあれば、移し終えている。どちらもないときは入口のスキルなので、6で `entry_skill.name` を新しい名前にする。スキルの `name` と、そのスキルを指すところは、2で作業エージェントに直させる。
5. 足す課題の仮の入力のファイルを、直す前の確認で示した中身のまま、`<W>/parts/files/tests/eval/<課題の番号>/inputs/<名前>` に書く。
   - `<W>/parts/files/tests/eval/` にもうあるファイル（引き継ぐ課題の元の入力）は、書かず、読まない。直す案を示した入力は、2で作業エージェントに直させる。
   - 擬似の機器のスクリプトは、2で作業エージェントが書くので、ここでは書かない。
6. `<W>/parts/manifest.json`：
   - plugin-creator が作ったプラグインでは、`extract` が元から作っている。作業役の AI を足すときは、`workers` に `{ "agent", "label", "extra_tools": [] }` を足す。課題の実物の入力のファイルがあれば、`eval_inputs` に足す（`<make-plugin>/references/generate.md` の1の3と同じ決まり）。入口のスキルの名前を変えるときは、`entry_skill.name` を新しい名前にする。ほかは変えない。
   - 作っていないプラグインでは、generate.md の「1. 部品の分け方を決める」と、1の3の形のとおりに、1から書く。入口のスキルの名前は、`<W>/parts/files/skills/` にもうある名前にしない。`workers` は作業の定義の案と同じ名前にする（確認で、`<W>/parts/files/com.github.copilot/agents/` と重ならない名前にしてある）。元のプラグインのスキルとエージェントの定義と重なると、組み立てが断るためである。
   - どちらでも、`plugin_name` は元のプラグインの名前のままにする。違うと、組み立てのスクリプトが断る。

## 2. 作業エージェントに書かせる

`task` ツールで `plugin-creator:worker` に頼む。頼みの初めに「直すプラグインの部品」の仕事だと書く。作業エージェントは会話を見ていないので、次をすべて渡す。

- `<W>/parts/`、ひな形（`<スキルのフォルダ>/../../template/`）、`<P>` の、`..` を畳んだ絶対パス
- 変える差し込み口（`<W>/parts/slots/<名前>.md`）とファイル（`<W>/parts/files/` の下）の一覧と、それぞれ何を変えるか。変えた内容に合わせて、README（`readme-what`・`readme-how`）、仕様書（`task-requirements`）、設計書（`task-design`）、要件のたどり方（`task-trace`）の差し込み口も入れる。仕様書の要件から、設計書・実装・試験をたどれるようにするためである。`extract` で `missing` だった差し込み口も、今の版で書き直すものとして入れる。作っていないプラグインでは、generate.md の2と同じく、すべての差し込み口を書かせる
- 変えない差し込み口とファイルの一覧（書き換えない）
- よいと答えたナレッジの一覧（番号、種類、項目、文、例、例外）と、付け直した番号（元の番号 → 新しい番号）と、外した決まり（`plugin-creator_state` の「外した決まり」の番号と、`<state.json>` の `knowledge` のその番号の文）。差し込み口とファイルにある元の番号は、すべて新しい番号に書き換え、外した決まりの文と番号を残さない
- 名前を変えたスキル（元の名前 → 新しい名前）があれば、その `SKILL.md` の `name` と、差し込み口とファイルの中でそのスキルを指すところを、すべて新しい名前にすること。変える差し込み口とファイルの一覧には、`grep -rlF -- '<元の名前>' <W>/parts/slots <W>/parts/files` で出たものを入れる（ファイルの名前だけを見て、中身は読まない）
- 決まりを入れるルールのスキル（足すものと、今あるものを直すもの）：名前、入れる決まり（番号と文）、1の2で写したスクリプトの場所。足すものは、直す前の確認で決めた description も、言い換えずに渡す（作業エージェントはそのまま書く）。決まりの文はルールのスキルにだけ書き、作業・検証のエージェントの作業ごとの指示には、スキルの場所と番号だけを書く（例：「`<プラグインのフォルダ>/skills/cross-compile-rules/SKILL.md` を読み、その手順でビルドする（K-18）」）。統括エージェントの作業ごとの指示には、スキルの場所を書かない。プラグインのフォルダは `<プラグインのフォルダ>` と書き、`${PLUGIN_ROOT}` や相対パスで書かない
- 振る舞いの案と、変わること（直す前の確認の `rebuild.change`）。`extract` の `stage1` に出た落ちるところと、その直し。エージェントの定義の `${PLUGIN_ROOT}` や相対パス（`skills/<名前>/SKILL.md` など）が出たら、その差し込み口（`orchestrator-task`・`worker-task.<agent>`・`verifier-task`）も変える一覧に入れ、上と同じ書き方に直させる：作業・検証のエージェントの作業ごとの指示では `<プラグインのフォルダ>/…`（例：`<プラグインのフォルダ>/skills/<名前>/SKILL.md`）と書き、統括エージェントの作業ごとの指示からはスキルの場所を消す（それを使う作業・検証のエージェントの作業ごとの指示になければ、そこに足す）。統括エージェントはルールのスキルを読まないためである
- 試験の課題（generate.md の2の「試験の課題」と同じもの）。引き継ぐ課題で直すのは、次の3つだけである。
  - 直す案を示したところ。入力のファイルなら、そのファイル（`files/tests/eval/<課題の番号>/inputs/<名前>`）と、よいと答えた直し方
  - eval.json の基準のうち、付け直した決まりか外した決まりを指すもの。付け直した決まりの基準は `id` と `text` を消して `knowledge` に新しい番号を書き、外した決まりの基準は消す。直す前の確認で示した基準の組と同じにするためである
  - 基準が残らないので、直す前の確認で合格の条件を聞いた課題：その決まりの番号と採点のしかたで、基準を足すこと（同じ理由）
- 擬似の機器を使う課題は、`bin`、擬似の機器のスクリプト（何をまね、何を記録するか）、そのスクリプトの動きの試験（受け付ける形で記録に1行足すこと、受け付けない形を断って0でない終了コードで終わること）。作業役の AI の基準は `agent_ran`
- 流用する資産と、写した場所（書き換えない。合わないときは「足りなかったこと」に書いて返す）
- ファイルを消さないこと（消すのは自分がする）

generate.md の2の終わりの3つ（記録から写す、量が多いときは分けて頼む、足りないことを返されたときの補い方）も守る。

## 3. 直す

1. 次を動かす：`python3 <S> change --hearing <state.json> --work <W> --plugin <P>`
   - 直す直前のフォルダの確かめをやり直し、決まりと合格の条件の番号を確かめてから、`<P>` のファイルを、`<W>` の中で描いたものに入れ替える。コミットはしない。
2. 断られたら（`"ok": false`）、返った `problems` を見て直し、もう一度動かす。
   - フォルダの確かめで断られたとき（コミットしていない変更がある、など）は、返った文を示して止まる。`<P>` は変わっていない。直したら、続けるよう頼んでもらう。
   - 「取り出した後に、…コミットがありました」と断られたとき（`<P>` は変わっていない）：
     1. そのコミットで変わったファイルを、名前だけ見る：`git -C <P> diff --name-only <返った文の「取り出したとき」の番号> HEAD -- .`。どれかが、確認で引き継ぐと示した部品（変えないスキルやスクリプトなど）の外にあるか、確認で示した中身のもと（`plugin.json`、作業の定義〔`com.github.copilot/extensions/<プラグインの名前>/task.json`〕、`tests/knowledge.json`、`tests/eval/`）なら、4に進む。
     2. よいと答えた作業の定義の案を残して取り出し直す（会話の自動の要約で案を失わないよう、1つのコマンドで）：`cp <W>/parts/task.json <W>/confirmed-task.json && python3 <S> extract --plugin <P> --work <W> --hearing <state.json> && mkdir -p <W>/draft && cp <W>/confirmed-task.json <W>/draft/task.json`。断られたら、`references/change-confirm.md` の1の2のとおりにする。
     3. 取り出し直した `<W>/extract.json` の `base`・`stage1`・`delete`・`name_conflicts`・`slots` が、確認で示したもの（`<state.json>` の `confirmation.rebuild`）と変わらなければ、よいと答えた内容のまま直せる。`<W>/parts/` が作り直されたので、1から（作業エージェントへの頼みも）もう一度する。変わっていれば、4に進む。
     4. よいと答えた内容と食い違う。お話を聞くことは終わっていて（段階「生成」）、このセッションでは確認をやり直せない。変わったことと、確認からやり直すことになることを示し、`/clear` してから同じ頼みをし直すよう伝えて止まる。これまでのお話は引き継がれず、始めから聞き直す。
   - 「…から取り出したものではありません」か「…見分けが違います」と断られたとき：取り出した後に何が変わったかを確かめられないので、上の4のとおりにする。
   - 「決まりの一覧（`tests/knowledge.json`）が、直す流れを始めて取り込んだときから変わっています」と断られたとき（`<P>` は変わっていない）：確かめた決まりで直すと、その後の決まりの変更を消してしまう。このセッションでは取り込み直せない（同じフォルダの記録は取り込み直さず、お話を聞くことも終わっている）ので、そのことを示し、`/clear` してから同じ頼みをし直すよう伝えて止まる。新しいセッションでは今の一覧から取り込み直し、残った `<W>` は記録を作るときに消す。
   - 作っていないプラグインで「…に別の名前を付けてください」と断られたとき：入口のスキルなら、`parts/manifest.json` の `entry_skill.name` を `<W>/parts/files/skills/` にない名前に変える。作業エージェントなら、`<W>/draft/task.json` の `workers` の `agent` を `<W>/parts/files/com.github.copilot/agents/` にない名前に変えて `<W>/parts/task.json` に写し直し、`parts/manifest.json` の `workers` と、差し込み口のファイルの名前（`parts/slots/worker-task.<元の名前>.md`。`mv`）も合わせる。その AI を名前で指すところ（`<プラグインの名前>:<元の名前>`、`agent_ran` の `agent`）は、`grep -rlF -e ':<元の名前>' -e '"<元の名前>"' <W>/parts/slots <W>/parts/files/tests/eval` で出たファイルを渡して、作業エージェントに直させる。それから、もう一度動かす。
   - manifest.json、写したファイル、足す課題の仮の入力のファイル、記録のことなら、自分で直す。
   - 作業エージェントが書いた `parts/slots/` か `parts/files/` のことなら、頼みの初めに「直すプラグインの部品」と書き、返った理由と、直す差し込み口とファイルを渡して直させる。この直しも、4の直しの回数に数える。
3. 返った `version` と `knowledge`（決まりの変わり方）は、7の説明で使う。

## 4. 試験と直し

`<make-plugin>/references/generate.md` の「4. 試験と直し」の1〜6のとおりにする。`<生成プラグインのフォルダ>` は `<P>`、`<スキルのフォルダ>/scripts/scaffold.py` は `<S>` と読み、generate.md の「7に進む」は、このファイルの5に進むと読む。違いは次のとおり。

- 3の「試験で落ちたところの直し」の頼みには、変えてよいファイル（`<W>/changed.json` の `files`）と、変えないファイル（それ以外。引き継いだ部品と流用したファイル）を書く。
- 4の `check-base --out <P>` の後に、`python3 <S> change-guard --plugin <P> --work <W>` を動かす。返った `unexpected` にファイルがあれば、`--restore` を付けて動かし、直す前の中身に戻す。そのファイルを変えずに直すよう、作業エージェントに伝える。
- 道具が足りないときは、generate.md の4の2のとおりにする（`--plugin <P>`）。入れないと答えたときと、答えが来なかったときは、試験をせずに5に進む。

## 5. コミット

合格しても、上限で止めても、試験をしなかったときも、次を動かす。

`python3 <S> commit --plugin <P> --work <W> --message "plugin-creator: <プラグインの名前> を直した（<今の版> → <新しい版>）"`

- `<P>` の中だけをコミットし、印のタグを付け直し、`<W>` を消す。push はしない。
- 返った `commit`、`tag`、`revert`（直す前に戻すコマンド）を、7の説明で使う。`tag` が null のときは、コミットは済んでいる。`warnings` の理由を控え、タグがないまま進む。
- 断られたら、返った文を示して止まる。

## 6. 試験の結果を画面に出す

`<P>/tests/results/latest.json` があれば、その絶対パスを `plugin-creator_results` に渡し、plugin-creator の画面に出す。

## 7. 直したことの説明

次を示す。言葉は words.md に従い、見出しも内部の言葉で書かない。`plugin-creator_state` の「直すプラグイン」から始まる4行も使う。「〜とき」と書いたものは、そのときだけ示す。

1. 変わったこと（直す前の確認で示した、変わること）
2. 足した決まり、直した決まり（元の番号 → 新しい番号）、外した決まり
3. 流用した資産。公開のプラグインを使うときは、その入れ方（`copilot plugin install <プラグイン>@<マーケットプレイス>`）
4. ファイルの形の検査と動きの試験の結果（generate.md の5の5と同じ示し方）。試験をしなかったときは、そのことと理由
5. コミット（番号の先頭7文字）と、直す前に戻すやり方（返った `revert` のコマンド）。印のタグを付けられなかったときは、そのことと理由
6. 試験のしかた（generate.md の5の6と同じ）
7. 直したプラグインを Copilot CLI に読ませるやり方（入れ方ごとに）
   - 手元のフォルダのマーケットプレイスから入れたとき：Copilot CLI で `/restart` と打つか、新しいセッションを始める（Copilot CLI は、直したフォルダをそのまま読むため）。
   - GitHub から入れたとき：直したコミットを GitHub に push してから、`copilot plugin uninstall <プラグインの名前>` の後に `copilot plugin install <プラグインの名前>@<マーケットプレイスの名前>` で入れ直し、Copilot CLI を起動し直す。push は、ユーザーがする。
8. `<P>` の外のマーケットプレイスの一覧（`marketplace.json`）にこのプラグインの版や説明を書いているときは、その一覧を手で直す必要があること（plugin-creator は、プラグインのフォルダの外を直さないため）
9. 直した後の `<P>/plugin.json` に `repository` がないときは、直したプラグインが見つけた課題を GitHub の Issue に出せるようにする手順（generate.md の5の4と同じ）
10. 作っていないプラグインに元からあったテスト（段階「読む」で返った構成にあったもの）は、残したことと、plugin-creator の試験では動かしていないこと
