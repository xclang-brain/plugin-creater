# 段階「読む」（直すとき）

目的：元のプラグインと、ユーザーが示したスキルやファイルを読み取り役に読ませ、返ったものを記録する。そのうえで、plugin-creator が作ったプラグインでは今の決まりの一覧を（初めに、今回変えることと、ほかは引き継ぐことを置いて）、作っていないプラグインでは引き継ぐことと変えるところ（範囲）を確かめる。

`<make-plugin>/references/read.md` の「読ませ方」と「返ったものの記録」を使い、このファイルの手順を足す。read.md の「次へ」と、作り直しのための文は使わない。

## 1. 読み取り役に頼む

`task` ツールで `plugin-creator:reader` に、次の2つを並べて頼む（示されたスキルやファイルがなければ、1つ目だけ）。頼む前のチャットの一言も、先頭の決まり8のとおり、ユーザーの言語（ふつうは日本語）で書く（例：「今のプラグインと、教えてもらったファイルを読ませています。」）。頼みの初めに、1つ目は「今のプラグインを直すときの読み取り」、2つ目は「組み込みたいスキルとファイルの読み取り」と書く。読み取り役は渡した文しか見えないので、次をすべて書く。

元のプラグインの頼み：

- `<P>` の絶対パスと、変えたいこと（記録の「変えたいこと」）
- 探すもの：
  - できていたこと（「〇〇と頼むと、〇〇をする」の形で、1つずつ）
  - 構成：スキル、エージェント、スクリプト、MCP サーバー、作業の画面の設定と表示の項目、試験の課題（`tests/eval/` の課題と、元からあるほかのテスト）
  - 決まりの候補（項目つき）と、人に聞く場面（AI が人に確かめたり、人の判断を待ったりするところ）
  - 流用できる部品と、読めなかったファイル
- plugin-creator が作ったプラグインのとき：決まりの一覧（下の4の一覧と同じ、番号と文）を頼みに書き、この一覧のどれにも当たらない決まりだけを、決まりの候補として返すよう書く。読むところは、作業ごとに違う部分（エージェントの定義の「作業ごとの指示」、入口のスキルの作業の節、README の「できること」と「使い方」、仕様書の作業ごとの要件、設計書の作業ごとの設計、ほかのスキル、スクリプト、作業の定義の task.json）に絞らせる。あわせて次を書く。plugin-creator が前に作ったときに書いた文をユーザーの決まりかと聞いても、ユーザーには答えられないためである。
  - 決まりの候補にするのは、ルールのスキル（入口のほかの `skills/*/SKILL.md`）とエージェントの定義の「作業ごとの指示」の文のうち、K の番号が付いておらず、作った後に足されたと見える文だけである。
    - 印のタグ（`python3 <S> change-check --plugin <P> --cwd <作業フォルダ>` の返り値の `tag`）が `<P>` のリポジトリにあれば（`git -C <P> rev-parse -q --verify refs/tags/<タグ>` の終了コードが 0）、`mkdir -p <W> && git -C <P> diff <タグ> HEAD -- . > <W>/since-mark.diff` で差分をファイルに書き（中身は自分で読まない）、その絶対パスを頼みに書いて、この差分で足された行の文だけにする。
    - タグがなければ、ユーザーの仕事や環境に固有の名前・値・やり方が入った文だけにする。プラグイン自身の部品（プラグインのフォルダのスクリプト、`<プラグインの名前>_show` などのツール、作業フォルダの中の置き場所）を使う文は除く
  - どちらのときも、一覧の決まりを言い換えた文、一覧の決まりから出てくる文（例：役割を分ける決まりから来る、ある役がしないこと）、ルールのスキルの使い方と説明（スクリプトの呼び方・引数・終了コード、`--help` で確かめられること、`compatibility`、出力の意味の説明）は、候補にしない
  - 人に聞く場面も、決まりの候補と同じ絞り込み（上の2つの箇条）を通った文から来るものだけを返させる。K の番号の付いた決まりや、plugin-creator が書いた文から来る場面は、決まりの一覧で確かめ終えるか、ユーザーには答えられないためである
  - 仕様書、設計書、README、作業の定義（task.json）、作業の画面の振る舞い（表示、図、差分の出し方、保存の場所など）と、ルールのスキルと作業ごとの指示のうち上で候補にしなかった文（そこから来る人に聞く場面も）は、決まりの候補にせず、できていたことと構成として返す
- plugin-creator が作っていないプラグインのとき：構成に、作業を頼むときに渡すものや選ぶもの（引数、入力のファイル、選べる値など）と、作業の結果として出すものも入れさせる。画面の設定と表示は聞かず、これから作業の画面の案を作るためである（`references/change-hearing.md` の「画面」）。使い方と説明は、示されたスキルと同じく、候補にさせない。

示されたスキルとファイルの頼み：

- 示されたフォルダとファイルの絶対パスと、変えたいこと
- 探すもの：
  - スキルごとに、`SKILL.md` のあるフォルダの絶対パスと、`name` と `description`
  - 決まりの候補（項目つき。出どころには、ファイルと節を書く）と、人に聞く場面
  - 資産の候補（スクリプトなど。絶対パスつき）と、前回の1回の手がかり
  - 使い方と説明：スキルのフォルダの中のスクリプトの使い方（`--help` に出ること。引数、終了コード、出力の形など）、フロントマターの `compatibility`（環境の条件）、出力の意味の説明（例：出力のある値が何を表すか）。返す形の「使い方と説明」に書かせ、決まりの候補にはさせない。スクリプトはそのとおりに動き、環境の条件と出力の意味は事実の説明で、ユーザーが決めることではないためである
  - ただし、スキルの文が守ることや既定として求めていることは、`--help` に出ていても、スクリプトがそうしていても、決まりの候補にさせる。`SKILL.md` の本文に書かれた、スキルのフォルダの外の道具（機器の道具など）の打ち方（コマンドの形）も、決まりの候補にさせる。今もそうしているかは、ユーザーにしか分からないためである
  - 読めなかったファイル

## 2. 返ったものの記録

read.md の表のとおりに記録し、次を足す。

| 返ったもの | 記録のしかた |
| --- | --- |
| 元のプラグインの決まりの候補 | 出どころは「既存のプラグインから読んで確かめた」、状態は「候補」。1で候補にしないとした文（仕様書や画面の振る舞い、K の番号の付いた文、印のタグの後に足されていない文、プラグイン自身の部品を使う文、使い方と説明、一覧の決まりから来る文など）が返っても、記録せず、できていたことと構成として扱う（1） |
| 示されたスキルとファイルの決まりの候補 | 出どころは「ファイルから読んで確かめた」、状態は「候補」 |
| 人に聞く場面 | 決まりの候補にする（文は「〇〇のときは、人に確かめてから進める」の形）。plugin-creator が作ったプラグインから返ったものは、1行目と同じく、1で返さないとした文から来るものを記録しない。確かめで正しいと答えたものだけを、直す前の確認の振る舞いの案で、人に聞く場面にする |
| 示されたスキル | スキルごとに、`SKILL.md` のあるフォルダ（返った `SKILL.md` の絶対パスのフォルダ）の絶対パスを、`plugin-creator_record` の流用する資産の候補（名前はスキルの `name`）として記録する。スクリプトなどのファイルだけを記録しない。組み立てのスクリプトが、この記録で、示されたスキルと直した後のプラグインのスキルの名前が重ならないかを確かめるためである |
| 使い方と説明 | 読み取り役が決まりの候補として返しても、決まりの候補にしない。そのスキルの資産の候補の説明に、要点を書く（`compatibility` は文のまま）。直す段階で、ルールのスキルに書かせる。スキルの文が守ることや既定として求めていることと、スキルのフォルダの外の道具の打ち方は、決まりの候補にする（1） |
| できていたことと構成 | ナレッジにしない（決まりの一覧に入れないため）。直す前の確認で使う。作っていないプラグインでは、3の範囲の確かめの問いでも使う |

- 記録した決まりの候補は、出どころで扱いを分ける。どの問いの答えに同じ中身が出るかは回ごとに違うので、どの段階でも、この扱いにする。
  - plugin-creator が作ったプラグインから読んだ候補（`carried` がない行。作った後に書き足された行から来た決まりと人に聞く場面）：ほかの答え（頼みの文、4の一覧の確かめなど）に同じ中身が出ても、外したり「決まった」にしたりせず、段階「決まりの確かめ」で「〜という決まりですか？」と1件ずつ確かめる。書き足した決まりは、1件ずつ確かめの問いで示すためである。「このとおり」か「そうしないときもある」と答えたとき、頼みの文から記録した決まりに同じ中身のものがあれば、頼みの文から記録したほうを、抜き書きを変えずに「外した」にする（入れない決まりには並べない）。同じ決まりを2つの番号にしないためである。頼みの文の決まりと違う中身なのに「このとおり」と答えたら、deepen.md の矛盾の型で、どちらが今のやり方かを1回聞く。
  - 示されたスキルと、作っていないプラグインから読んだ候補：ユーザーが頼みの文や答えで決まりとして述べたものは、聞き直さない。決まりとして述べたとは、候補の決め手（名前、値、コマンド、条件）がすべて、ユーザー自身の言葉で、ふだんのやり方として今の形で（「〜する」「〜している」「いつも・毎回・毎週〜」「必ず」「しないと動かない」など）述べられていることである。ユーザーが自分の言葉で述べた決まりは、選択肢で「このとおり」を選ぶより確かなためである。
    - 返ったときに、候補の決め手がすべて、頼みの文やそれまでの答えから記録した決まり（`references/change-start.md` の8）に入っていれば、記録しない。その決まりで確かめたものとする。同じ決まりを2つの番号にしないためである。入っていない決め手が1つでもあれば記録し、下の「一部だけを述べた」の扱いにする。
    - 段階「決まりの確かめ」の始めに、記録した候補を、頼みの文とそれまでの答えと比べて、次のとおりにする。
      - 同じ中身を決まりとして述べた：聞かずに、候補の番号を渡して「決まった」にする。文とユーザーの言葉の欄は、ファイルの言葉を残さず、述べたユーザーの言葉にする（出どころは、本文の「記録のしかた」の決め方）。
      - 同じことについて、違う今のやり方を述べた：聞かずに、述べたやり方を「決まった」の決まりにし（もう記録してあれば、記録し直さない）、候補は「外した」にする。外す記録の抜き書きは、決まりの確かめの「違う」と同じく、読み取った場所のままにする。直す前の確認と直す段階では、「違う」と答えた候補と同じに扱う。
      - 一部だけを述べた：述べたところを、ユーザーの言葉で「決まった」の決まりにする（もう記録してあれば、記録し直さない）。候補は、文を述べていないところだけに直し（番号を渡して直す）、4つの答えで聞く。
      - 前の1回にしたこととして話しただけ（「前回は〜した」「この前は〜した」、前回の1回をたどる中でだけ話した手順）：4つの答えで聞く。たまたまのやり方を、決まりとして入れないためである。
      - 同じ中身かどうか迷えば、4つの答えで聞く。
  - 候補は、読み取り役がまとめて返したもののほかは、まとめない。
- コンパクションの後に、できていたことが要るときは、作っていないプラグインでは、`plugin-creator_state` を「振り返りの材料」つきで呼び、3の問いの文を問答の記録から拾う。plugin-creator が作ったプラグインでは、読み取り役に、1の元のプラグインの頼みで、できていたことだけを読ませ直す。

## 3. 変えるところの確かめ

この段階の終わりに、変えるところを示す問いを1つだけ出す。plugin-creator が作ったプラグインでは4の決まりの一覧の確かめ、作っていないプラグインでは下の範囲の確かめである。

- 問いには、頼みと読み取りから分かる変えるところだけを、頼みの言葉を使って書く。変えるかもしれないこと（画面の設定、ほかのルールなど）を、例として書き足さない。頼みにない変更を誘うためである。
- 答えで変えたいことが変わったら、`plugin-creator_change` を同じフォルダで呼び直し、変えたいことを置き換える（決まりは取り込み直されない）。
- 頼みの文と、この問いの答えは、段階「項目の点検」で、「変えないので聞かない」にする項目の抜き書きに使う。

範囲の確かめ（plugin-creator が作っていないプラグインのときだけ）：できていたことと、今回変えるところを示し、違うところと足りないところを聞く（理解の確かめ）。機能ごとに要るかは聞かない。消すのは、ユーザーが消したいと頼んだ機能だけである。作っていないプラグインには決まりの一覧の問いがなく、引き継ぐことを早く示す場がほかにないためである。plugin-creator が作ったプラグインでは、この問いを出さず、4の問いの初めの2行にする。

- 問いの例：「直した後のプラグインは、今できていることをすべて引き継ぎます。引き継ぐことと変えるところが違っていると、要らないところまで直したり、直すべきところが抜けたりします。今のプラグインは、次のことができます。1. 〇〇と頼むと、〇〇をする 2. … 今回は、〇〇を足します（変える・消すものがあれば、それも書く）。ほかは今のまま引き継ぎます。違うところと足りないところを書いてください。なければ「ない」と書いてください。」

## 4. 決まりの一覧の確かめ（plugin-creator が作ったプラグインのときだけ。1つの問い）

- 一覧は、`<state.json>` の `knowledge` のうち、`carried` が true の行すべての番号と文である。`plugin-creator_state` の一覧は長い文と20件より後を切るので、使わない。
- 問いの初めに、次の2行を置く。できていたことの一覧は、ここでは並べない。
  - 「今回変えること：<頼みの言葉を使った、変えることの1行>」
  - 「ほかは、今できていることをすべて引き継ぎます（できていることの一覧は、直す前の確認で示します）。」
- 続けて、一覧のすべての番号と文を1つの問いの文の中に入れ（問いの前のチャットの文だけに書かない）、今と違うものと、古くなったものを聞く（理解の確かめ）。今回変えることが違っていれば、同じ答えに書いてもらう（3）。分けて聞かない。
- 頼みの文や前の答えに、番号や「決まりは今のまま」「ほかはそのとおり」とあっても、この問いは省かない。ユーザーは一覧の文をまだ見ていないので、その言葉は一覧を確かめたことにならない。記録のツールも、一覧の番号を示した問いへの答えでないと、引き継いだ決まりを「決まった」にする記録を断る。
- 問いの例：「今回変えること：〇〇。ほかは、今できていることをすべて引き継ぎます（できていることの一覧は、直す前の確認で示します）。今と違う決まりや古くなった決まりが残っていると、AI が古いやり方で作業します。今のプラグインの決まりは次のとおりです。K-01 〇〇 K-02 〇〇 … K-17 〇〇。今回変えることが違っていれば、それも書いてください。決まりは、今と違うものと古くなったものの番号を書いてください。なければ「ない」と書いてください。」
- 記録：
  - 違う・古いと答えなかった決まりは、`plugin-creator_record` で、番号を渡して状態を「決まった」にする。抜き書きは、この答えの言葉にする。まとめて1回で渡してよい。
  - 違う・古いと答えた決まりは、1件ずつ、今はどうかを聞く（聞き出す問い。例：「今のやり方が分からないと、AI は古い決まりのまま作業します。『K-05 〇〇』は、今はどうしていますか？決まりでなくなったなら、そう書いてください。」）。頼みの文か、この問いの答えに今のやり方がもう書かれていれば、聞き直さず、その言葉で記録する。
    - 今のやり方が分かったら、その番号を渡し、文（要れば項目・例・例外も）を今のやり方のとおりに直して、状態を「決まった」にする。出どころは、本文の「記録のしかた」の決め方にする（聞いた問いの答えなら「ヒアリングの答え」、頼みの文なら「ユーザーが自分から話した」）。記録のツールが元の番号を外し、新しい番号を付ける（返り値に出る）。
    - 決まりでなくなった、決まっていないと答えたら、状態を「外した」にする。代わりの決まりの案を作らない。
  - 「ない」と答えても、決まりを足したことにはならない。
