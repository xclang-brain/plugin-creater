# 段階「生成前の確認」（直すとき。ユーザーには「直す前の確認」と言う）

目的：直す内容を確かめてもらい、直してよいかの答えを得る。`<make-plugin>/references/confirm.md` の1〜3を使い、このファイルの手順を足す。confirm.md の「作る」は「直す」と読み替える。confirm.md の4（作ってよいかを聞く）と「次へ」（generate.md を読む）は使わず、このファイルの4にする。

この段階で書いてよいのは `<W>` の中だけである。`<P>` は変えない。

## 1. 下見を作る（confirm.md の1の後）

1. `<W>/extract.json` がまだなければ、次を動かす：`python3 <S> extract --plugin <P> --work <W> --hearing <state.json>`
   - `<W>` の中だけに、元のプラグインから取り出した部品（`<W>/parts/`）、作業の定義の案（`<W>/draft/task.json`）、今のひな形で描き直した下見と、結果（`<W>/extract.json`）を作る。
   - コンパクションの後などで `<W>/extract.json` がもうあれば、動かし直さずに、その結果を使う。動かし直すと、`<W>` の中の部品と作業の定義の案が作り直されるためである。例外は、3の終わりの、確認の中で組み込むスキルが足されたときだけである。
2. 断られたら（`"ok": false`）、返った `problems` を見る。
   - 記録で直せること（例：示されたスキルのフォルダが資産に記録されていない）は、`references/change-read.md` の2のとおりに記録を直して、動かし直す。
   - ユーザーにしか決められないこと（例：示されたスキルのフォルダが `<P>` の中にある）は、返った文と、選べる直し方を示して聞く（決める問い）。
   - ほかは、返った文を示して止まる。
3. `<W>/extract.json` で次を見る。このファイルの2で案に入れ、3で示す。
   - `base`：共通の土台を今の版に上げると、足される・消える・変わるファイル（`added`・`removed`・`changed`）
   - `stage1`：今のひな形で描き直すと、ファイルの形の検査に落ちるところ
   - `delete`：形式を移すと読まれなくなるので、消すファイル（作っていないプラグインのとき）
   - `name_conflicts`：示されたスキルと同じ名前の、`<P>` のスキル
   - `slots`：取り出せなかった部分（`missing`）。作業エージェントが今の版で書き直す
   - `warnings`

## 2. 示すものを用意する（confirm.md の2に足す）

### 引き継ぐことと変わること

`plugin-creator_confirm` の `rebuild` に、引き継ぐこと（`keep`）と変わること（`change`）を、1件に1つずつ書く。画面にも同じものが出るので、文は words.md の言葉で書く（ユーザーが「スキル」と言っていなければ、「プラグインの中の部品（スキル）」と言う）。

- 引き継ぐこと：段階「読む」の範囲の確かめで確かめた、できていたこと。確かめた決まり。流用する部品（引き継ぐスキル、スクリプトなど）。
- 変わること（1件以上）：
  - 足す・変えるスキル、作業の画面の設定と表示、AI の役割。消す機能。足す決まり・直す決まり（元の番号 → 新しい番号）・外す決まり。
  - 作っていないプラグインのとき：プラグインの形を変えるために足したり変えたりすること（例：まとめ役・作業役・確認役の AI に分かれる、作業の画面が付く、憲章・仕様書・設計書・試験が足される）と、`delete` のファイル（消すこと）。
  - `base` があるとき：共通の土台を今の版に上げることと、上書きされるファイルの一覧。プラグインのフォルダで土台のファイルを直していたなら、その直しは今の版で上書きされること。
  - 土台を上げると、元のプラグインの機能と重なるとき（例：元の作業の画面の設定にある思考の深さと、土台の AI ごとの思考の深さ）：元の機能は消さずに残すことと、重なること。
  - `stage1` があるとき：落ちるところと、その直し（例：エージェントの定義に書かれた `${PLUGIN_ROOT}` を、プラグインのフォルダの絶対パスで読む書き方に直す）。
  - 示されたスキルの決まりを入れるルールのスキル（足すか、今あるルールのスキルを直すか）と、その名前。名前は、示されたスキルの名前と違うものにする（例：示されたスキルが `cross-compile` なら `cross-compile-rules`）。同じ名前だと、示されたスキルが読み込まれている作業フォルダで、直した後のプラグインのスキルが使われないためである。`name_conflicts` に出た `<P>` のスキルも、新しい名前（示されたスキルの名前と違うもの）を決め、元の名前 → 新しい名前を示す。
  - 変えるところが本物の機器や外部のシステムに頼るとき：試しに動かして採点する試験では、本物の機器に送らず、手元のパソコンの中の擬似の機器で試すこと。本物の手順そのもの（例：本物の機器への転送）は試せないこと。
- 新しい版の案（`version`）：今の版（記録の「直すプラグイン」の行）から、スキル・作業の画面の設定と表示・AI の役割を足す・変える・消すときは2つ目の数を上げて3つ目を0にし（0.1.0 → 0.2.0）、決まりの文だけを直すときは3つ目を上げる（0.1.0 → 0.1.1）。今の版がないときは 0.1.0 にする。

### 作業の定義の案

- plugin-creator が作ったプラグインでは、`extract` が元の作業の定義から `<W>/draft/task.json` を作っている。作業エージェントに直させるのは、作業の画面の設定や表示を変えるとき、作業役の AI を足すか分け直すとき、`stage1` に作業の定義が決まりに合わないと出たときだけである。頼みの初めに「作業の定義の案」と書き、confirm.md の2の渡すものに加えて、今の案の場所、変えるところ、ほかの `key` は変えないことを書く。
- 作っていないプラグインでは、`extract` は案を作らない。confirm.md の2の「作業の定義の案」のとおりに、1から書かせる。

### 試験の課題（confirm.md の2の課題の作り方に足す）

- 引き継ぐ課題：`<W>/parts/files/tests/eval/<課題の番号>/eval.json` を読み、頼むときの言葉（`prompt`）と設定の値（`settings`）をそのまま使う。
  - 基準は、eval.json の基準の番号（`C-01` など）を、`<state.json>` の `change.criteriaIds`（決まりの番号から基準の番号への対応）で、決まりの番号に戻して渡す。中身を直した決まりは、新しい番号にする。外した決まりは入れない。
  - 入力は、プラグインの中の置き場所 `tests/eval/<課題の番号>/<inputs に書かれた場所>` を、仮（`provisional` が true）として渡す。示すときは、場所だけを「元のまま引き継ぐ入力のファイル」として示し、中身は示さない。元のプラグインのファイルで、自分で作った中身ではなく、自分では読まないためである。confirm.md の3の2の「作った中身をそのまま示す」は、足す課題の仮のファイルにだけ使う。
  - 確かめた決まりと食い違う課題（例：入力のファイルが、取り込んだスキルの決まりと違う書き方）は、直す案（どのファイルの、どこを、どう直すか）を示す。直すのは、直す段階の作業エージェントである。課題を外すのは、ユーザーが自分から頼んだときだけである。
- 変えたところを試す課題を、1つ以上足す。課題の番号は、引き継ぐ課題の番号の続きにする（例：T-01 と T-02 を引き継ぐなら T-03）。頼むときの言葉は、引き継いだ課題と違うものにする（同じだと、確認のツールが断る）。基準には、取り込んだ決まりに沿って作業したかを判定できる「合否の決め方」の決まりを入れる（引き継いだ決まりでもよい）。
- 元のプラグインに課題がないとき：変えたところを試す課題とは別に、作業全体を試す課題を1つ以上作る（confirm.md の課題の作り方。前回の1回と示したファイルから）。示すときは、「作業全体を試す課題」と分けて示す。
- 作業役の AI を足すか分け直すとき：成果物は変わらないので、その役の仕事の決まり（例：「ビルドは作業役の AI の worker-b が受け持つ」）を基準にし、採点はその AI が動いたかを実行の記録で見る（作業エージェントへの頼みでは `{"type": "agent_ran", "agent": "<エージェントの名前>"}`）。
- 本物の機器に頼る課題（擬似の機器）：
  - 課題の eval.json に `"bin": "inputs/bin"` を書き、`inputs/bin/<道具の名前>` に、機器の道具と同じ名前の差し替えのスクリプト（擬似の機器）を置く。試験のときは、このフォルダが PATH の先頭に入り、本物の道具の代わりに動く。
  - 擬似の機器は、確かめた決まりにある機器の振る舞い（受け付けない形を断る、終わりの目印を出すなど）をまね、呼ばれるたびに、作業フォルダの `device-history.log` に1行足す。基準は、このファイルを見る。
  - 確かめた決まりが、機器の道具を絶対パスで呼ぶときは、差し替えが効かないので、機器に送る手順を課題に入れない（ビルドまでなど、機器に送らない範囲にする）。機器の手順を試せないことも示す。
  - 擬似の機器のスクリプトは、直す段階で作業エージェントが書く。確認では、仮の入力（`tests/eval/<課題の番号>/inputs/bin/<道具の名前>`）として、何をまね、何を記録するかを示す。
- 見本（confirm.md の3の3つ目）は、作業の画面の設定や表示を変えるときと、作っていないプラグインのときだけ示す。

## 3. 示して確かめる（confirm.md の3に足す）

- `plugin-creator_confirm` に、confirm.md の渡すものに加えて、`rebuild`（`keep` と `change`）と `version` を渡す。断られたら、返った理由のとおりに直して呼び直す（例：変えたところを試す課題がない、版が今の版より大きくない）。
- 1つ目には、引き継ぐことと変わること、新しい版の案（今の版 → 案）も示す。ユーザーが版を変えたいと答えたら、その版にして呼び直す。
- 2つ目には、引き継ぐ課題（直す案があれば、その案）、変えたところを試す課題、作業全体を試す課題を分けて示す。擬似の機器で試すときは、そのことと、本物の手順は試せないことも示す。
- 3つ目（見本）は、2の終わりのときだけ示す。
- 確認の直しの中で、ユーザーが組み込むスキルを足したときは、`references/change-read.md` の1と2、`<make-plugin>/references/rules.md` のとおりに読ませて確かめてから、`<W>/extract.json` があっても、1の `extract` を動かし直す（名前の重なりを確かめ直すため）。作業の定義の案は、元のものに戻るか、作っていないプラグインでは消えるので、作業エージェントに書かせていたら、書かせ直す。

## 4. 直してよいかを聞く

3つとも直すところがなくなったら、この内容で直してよいかを聞く（承認の問い）。

- 問いの例：「よいと答えると、元のプラグインのフォルダのファイルを直し始めます。この内容で直してよいですか？」
- 選択肢（この順）：「まだ直したいところがある」「この内容で直してよい」。おすすめを付けない。
- 直したいと答えたら、どこかを聞き、3に戻る。
- よいと答えたら、`plugin-creator_progress` で段階を「生成」に進め、答えの抜き書きを添える。続けて `references/change-apply.md` を読む。
