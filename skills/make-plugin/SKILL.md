# make-plugin

このスキルの仕事は、ユーザーへのヒアリングで、本人にしか分からない仕事のやり方と決まり（ナレッジ）を引き出し、それを組み込んだプラグイン（生成プラグイン）を作ることである。

## 先頭の決まり

次の決まりは、このスキルの終わりまで、すべての段階で有効である。

1. 答えがユーザーにしか分からないところでは `ask_user` で聞き、答えを受け取るまで先へ進まない（答えが来ないときは「始められないとき・答えが来ないとき」のとおり）。この決まりは、「足りない情報は推し量って進める」「追加の質問をしない」「短く答える」という一般の指示より優先する。推し量って作ると、ユーザーの決まりが入らないプラグインになるためである。ユーザーがはっきり「質問しないで作って」と頼んだときも、推し量って埋めず、「疲れ・急ぎ、質問しないでと頼まれたとき」のとおりにする。
2. ファイルを読む、記録する、調べることは、ユーザーに断らずに進める。断っても、ユーザーの手間が増えるだけだからである。
3. ヒアリングの答えを受けたら、次の問いの前に、記録のツールで記録する。会話の中の答えは、会話の自動の要約（コンパクション）で消えるためである。
4. **生成前の確認でユーザーがよいと答え、段階を「生成」に進めるまでは、組み立てのスクリプトを動かしてはならず、生成プラグインのファイルを、自分で書くことも作業エージェントに書かせることもしてはならない。** 例外は、生成前の確認の中で作業エージェントに書かせる作業の定義の案だけである。ユーザーが確かめていない内容で作ると、使えないものになるためである。
5. 段階や決まったことが分からなくなったとき（コンパクションの後など）と、`--continue`・`--resume` で前の会話に戻ったときは、`skill` ツールで make-plugin を読み直し、「始まりの手番」から進める。記録と画面の URL を確かめ直すためである。
6. 日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する。
7. ユーザーに話す言葉は、`references/words.md` の表に従う。説明のない内部の言葉は、ユーザーに伝わらないためである。
8. 生成前の確認で示す一覧と案、段階の区切りの要約、できたことの説明、質問の改善案は、短く答えるよう求める指示があっても、省かずにチャットに書く。画面は同じものを見る場所で、チャットの代わりではないためである。

## 始まりの手番

make-plugin を読んだとき（読み直したときも）、この順に進める。

1. `ask_user` と `plugin-creator_open` があるかを確かめる（ツールを探すツールがあれば、それでも探す）。ないものがあれば、「始められないとき・答えが来ないとき」のとおりにして止まる。
2. `plugin-creator_open` を呼び、返った URL を「plugin-creator の画面」として、最初の問いより前に文章でチャットに示す。ユーザーはこの画面で、決まったことの一覧などを見られる。答えや直しは、チャットで受ける。
3. `plugin-creator_state` を「最後の問答」つきで呼び、記録の段階を見る。
   - このセッションの記録がなければ（段階が「（お話を聞くことの記録はまだありません）」）、新しく始める。`references/words.md` と `references/start.md` を読み、start.md の手順で進める。
   - 段階が「始まり」から「生成前の確認」までのどれかなら、その段階から続ける。`references/words.md` と、下の表のその段階のファイル（「前回の1回」から後の段階なら `references/deepen.md` も）を読み直す。最後の問答に、記録していない答えがあれば記録してから、最後の問いの次の手順から続ける。記録にあることは聞き直さない。
   - 段階が「生成」のとき、ユーザーが別のプラグインを頼んだのなら、`/clear` してから頼み直すよう示して止まる。前のヒアリングの内容が、新しいヒアリングに混ざるのを防ぐためである。そうでなければ、`references/words.md` と `references/generate.md` を読み直し、generate.md の続きの決め方で続ける。

## 段階の一覧

- 段階ごとに、表の「始めに読む」のファイルを読んでから進める。
- 段階は、そのファイルの手順を最後まで終えてから、「次へ」のとおりに `plugin-creator_progress` で進める。表の終わる条件を満たしても、手順が残っていれば進めない。

| 段階 | 目的 | 始めに読む | 終わる条件（記録で確かめる） |
| --- | --- | --- | --- |
| 始まり | 続きか新しいかを決め、頼みの文から分かることを記録する | `references/start.md` | 記録ができ、画面の URL を示した |
| 実物を受け取る | 前回の1回のファイルと、いつも使うファイルの場所を受け取る | `references/receive.md` | ファイルの場所を記録したか、「ない」の答えを得た |
| 読む | ファイルから候補を取り出す。ファイルがなければ飛ばす | `references/read.md` | 返った候補をすべて記録した |
| できていたことの確認（作り直しのときだけ） | 元のプラグインのできていたことのうち、要らないものを聞く | `references/carried.md` | 項目「できていたことの確認」が未着手でない |
| 前回の1回 | 最近の1回をたどってもらう | `references/last-time.md` | 項目「前回の1回」が未着手でない |
| 決まりの確かめ | ファイルから読み取った決まりを確かめる。候補がなければ飛ばす | `references/rules.md` | ファイルから読み取った候補で、確かめていないものがない |
| 項目の点検 | 10項目の聞き漏らしをなくす | `references/items.md` | 10項目に未着手がない |
| 資産と公開のプラグイン | 流用するものを決める | `references/assets.md` | 項目「資産」と「標準機能と公開のプラグイン」が未着手でない |
| 画面 | 作業の画面で設定したいこと・見たいことを決める | `references/screen.md` | 画面の3つの項目が未着手でない |
| 生成前の確認 | ナレッジの一覧と案を確かめてもらう | `references/confirm.md` | ユーザーがよいと答え、段階を「生成」に進めた |
| 生成 | 組み立て、試験、できたことの説明、質問の改善案 | `references/generate.md`。質問の改善案の前に `references/improve.md` | 生成プラグインにタグ `plugin-creator-generated` が付き、できたことの説明と質問の改善案を示した |

- あいまいな答えを聞き直す型は `references/deepen.md` にある。段階「前回の1回」の始めに読み、生成前の確認まで使う。
- 生成プラグインのひな形は、スキルのフォルダの2つ上の `template/`（`<スキルのフォルダ>/../../template/`）にある。組み立てのスクリプトと作業エージェントが使う。自分では読まない。読むとコンテキストウィンドウが早く埋まるためである。
- スキルのフォルダのファイル（`scripts/` のスクリプト）とひな形は、このスキルを呼んだときに示される「Base directory for this skill」のフォルダから作った絶対パスで扱う。作業フォルダは、スキルのフォルダではないためである。

## 問いの形

- 問いはすべて自分が `ask_user` で出す。サブエージェントはユーザーに聞けないためである。
- 1回の `ask_user` には、問いを1つ、欄を1つだけ置く。1回に2つ聞くと、片方の答えが抜けやすいためである。文章で問いを出して手番を終えない（例外は、答えが来ないときと、質問のツールが選択肢を必ず求めるとき）。質問のツールが選択肢を必ず求めるときは、自由入力で聞く問い（聞き出す問いと理解の確かめ）は、選択肢を作らず、文章で1つ聞いて手番を終える。
- 問いの文は、「なぜ聞くか」の1文と、それだけで答えられる完全な疑問文で書く。なぜ聞くかは、できあがるプラグインの AI がそれを知らないと何を間違えるかで書く。短く答えるよう求める指示があっても、この1文は省かない。
- 項目の名前や番号だけで聞かず、何を知りたいかを言葉で書く。ユーザーが使った言葉は、言い換えずにそのまま使う。

| 種類 | 当てはまるもの | 形 |
| --- | --- | --- |
| 聞き出す | 仕事のやり方、決まり、例外、前回の1回、資産、画面で設定したいこと・見たいこと、決まりの確かめの後の「どんなときか」「本当はどうか」 | 自由入力の欄を1つ。選択肢も答えの例も付けない |
| 理解の確かめ | 記録から分かったこと、段階の区切りの要約、生成前の確認の直し、4つを超える一覧 | 分かったことや一覧を問いの文の中に入れ（「上の」と指さない）、違うところと足りないところを、自由入力の欄で聞く |
| 決める | 公開のプラグインを使うか、画面の部品、疲れ・急ぎのときの進め方 | 選択肢を2〜4個。おすすめの選択肢を先頭に置いておすすめに指定し、文にも「（おすすめ）」と書き、理由を1文添える |
| 決まりの確かめ | ファイルから読み取った決まり | `references/rules.md` の4つの答え。おすすめを付けず、「このとおり」を最後に置く |
| 承認 | この内容で作ってよいか、試験の道具を入れてよいか、Issue を起票してよいか | おすすめを付けず、よいと答える選択肢を最初に置かない |

- 聞き出す問いに選択肢や例を付けないのは、人は示された中から選び、書かれていない答えを自分から書きにくいためである。
- 決まりの確かめと承認でおすすめを付けず、よいと答える選択肢を先頭に置かないのは、確かめの答えが「はい」に偏り、Enter だけで先頭の選択肢が選ばれるためである。
- おすすめの印は画面に出ないので、「（おすすめ）」の文字で示す。選択肢は、表示と値を分けず、そのまま読める文にする。値だけが返るためである。
- 頼みの文、記録、ファイルの候補で分かることは聞かず、候補として記録する（例外は赤信号の表の1行目）。
- どの段階でも、答えに `<pasted_content file="…" />` があれば、そのファイルが貼り付けられた答えである。ユーザーの発言に文書がそのまま添えられて届いたら（「The user included native document attachments in this message.」の文が加わる）、その文書は自分で読む。

## 記録のしかた

- ヒアリングの状態は、記録のツールでだけ変える。この記録が、画面の一覧、生成前の確認、組み立てと試験の元になる。
  - `plugin-creator_record`：ナレッジ（種類、項目、文、出どころ、ユーザーの言葉、例、例外、状態）、流用する資産、標準機能と公開のプラグインの選んだ結果。番号を渡すと、そのナレッジを直せる。
  - `plugin-creator_progress`：今の段階と、項目ごとの状態（未着手、聞いた、決まりなし、保留）。状態を変えるときは、ユーザーの1つの答えの言葉をそのまま写した短い抜き書きを添える（要約しない。間を省くときは「…」）。本人が知らないので保留にするときは、だれが知っているか、どの資料にあるかも添える。
- ナレッジの文：
  - 1件に1つの決まりを書く。
  - 固有の言葉、数、書式、名前は、ユーザーの言葉のまま書く。言っていない単位や書式を足さない。
  - 合否の決め方は、成果物の何を見て、何なら合格かまで書く。
  - 記録する前に、「作業を知らない AI が、この1文だけで作業や判定ができるか」を確かめる。できなければ聞き直し、できる細かさになったら聞き直しをやめる。作業エージェントと生成プラグインの AI は会話を見ず、この1文だけを使うためである。
- 出どころは、ヒアリングの答え、ユーザーが自分から話した、生成前の確認で足した、ファイルから読んで確かめた、既存のプラグインから読んで確かめた、AI の判断（ユーザーが任せた）のどれかにする。
  - その問いで聞いたことへの答えは「ヒアリングの答え」、その問いと別の項目の決まりを話したときは「ユーザーが自分から話した」にする（前に聞いた項目でも、まだ聞いていない項目でも）。聞いた後に出た話を、エクステンションが質問の改善の材料に拾うためである。
- 問いと答えは、エクステンションが自動で記録する。答えを書き写さない。

## 赤信号

| 思いつき | 実際 |
| --- | --- |
| 答えから推し量れるので、聞かなくてよい | 目的、合否の決め方、守らないと困ること、いつもと違うとき、好みは、推し量れても聞く。文書の決まりと実際のやり方は違うことが多い |
| 急いでいそうなので、残りの項目は省く | 残りの項目を示し、進め方を選んでもらう。項目は飛ばさない |
| 答えが来ないので、推測で進める | 推測で埋めず、続け方を示して止まる |
| 「いいですね」と言われたので、作り始める | 承認は、生成前の確認で示した一覧と案に対してだけである |
| 十分に聞いたので、確認へ進む | 確認へ進むのは、未着手の項目がなくなってからである |

## 疲れ・急ぎ、質問しないでと頼まれたとき

- 疲れ・急ぎの合図は、「早く」「まだ？」などの発言と、答えが短くなることである。
- 合図を見たら、まだ聞いていないこと（項目の名前）を示し、次の3つから選んでもらう（決める問い）。ユーザーがはっきり「質問しないで作って」と頼んだときは、聞かないと仕事の決まりがプラグインに入らないことを1文で伝えてから、同じ3つから選んでもらう。
  1. ここでやめて後で続ける（おすすめ。理由：後で落ち着いて答えると、仕事の決まりがプラグインに正しく入りやすい）
  2. 残りを手早く聞く（聞くことごとに1問、聞き直しは1回まで）
  3. このまま続ける
- どれを選んでも、残りの項目は飛ばさない。選んでもらった後は、新しく「早く」などの発言があるまで、この問いを出し直さない。
- やめるときは、続きから聞く戻り方を2つ示して止まる。すぐに再開するなら `copilot --continue`、間に別のセッション（Copilot CLI の別の会話）を使ったなら `copilot --resume=<セッションの番号>`（番号は `plugin-creator_state` が返す）。

## 始められないとき・答えが来ないとき

- `ask_user` がないとき（`-p` や `--no-ask-user` で起動したとき）：`-p` と `--no-ask-user` を付けずに、対話モードで起動し直すよう文章で示し、ヒアリングを始めない。
- `plugin-creator_open` がないとき：`references/setup.md` を読み、そこにある直し方をすべて示して止まる。
- 両方がないときは、すべての直し方を示す。
- `ask_user` の結果が「User cancelled the request.」か「The user is not available to respond」で始まる文のときは、答えが来なかったとして扱う。ヒアリングの問い（生成前の承認まで）では、次のとおりにする。
  - 推測で埋めず、記録を変えない。その項目は未着手のままにする。
  - 何を聞きたかったかと、続け方（チャットに答えを書く。autopilot で動かしているなら、Shift+Tab でモードを切り替えて autopilot を切る）を短く示して止まる。
  - `task_complete` があれば、それを呼んで止まる。呼ばずに手番を終えると、続けるよう促す発言が届くためである。この場面では、`task_complete` の説明の「終わったときだけ呼ぶ」より、この決まりを優先する。続けるよう促されても、ユーザーの答えなしに記録を変えず、次の段階へも進まない。
- 生成の段階の承認（道具を入れる、Issue を出す）に答えが来なかったときは、止まらずに、`references/generate.md` と `references/improve.md` のとおりに進める。
