# 段階「生成」

目的：よいと答えた内容で生成プラグインを作り、試験し、できたことを説明し、質問の改善案を示す。

- 以下の `<スキルのフォルダ>` は、「Base directory for this skill」のフォルダの絶対パスである。`<作業フォルダ>` は、ユーザーが Copilot CLI を動かしているフォルダの絶対パスである。
- コンパクションの後は、作業フォルダを見て続きを決める。
  - `.plugin-creator-work/` があれば、組み立ての前である。`parts/manifest.json` がなければ1から、あれば2から続ける。
  - `.plugin-creator-work/` がなければ、組み立ては終わっている（終わると消えるため）。生成プラグインのフォルダは、作業フォルダの中の git のリポジトリで、最初のコミットの説明が「生成プラグイン <名前> を plugin-creator で組み立てた」のものである。そこにタグ `plugin-creator-generated` がなければ4から続け、直しの回数が会話から分からなければ、残りを1回とする。タグがあれば4の8から続け、すでに示した説明と、出した Issue の案は繰り返さない。

## 1. 部品の分け方を決める

高い推論力が要るので、自分で決める。

- 生成プラグインの名前と1行の説明。名前は作業が分かる英語で、1〜64文字の英小文字・数字・ハイフンにし、ハイフンで始めず・終えず、`--` を含めない。`plugin-creator` にはしない。同じ名前だと、できあがるプラグインのツール（`plugin-creator_open` など）とマーケットプレイスの名前が、plugin-creator のものと重なるためである。作業フォルダにまだないフォルダの名前にする（作り直しでは、元のプラグインのフォルダと別の名前）。
- 入口のスキルの名前（決まりは生成プラグインの名前と同じ）と description。description は日本語で、何ができあがるかを手順でない短い1句で書き、続けて呼ばれる場面（ユーザーが頼むときの言葉を入れる）と、呼ばれてはいけない似た頼み（例：その作業についての質問、プラグインの試験）を書く。手順の要約は書かない。
- 説明と description は、1行・1024文字以内にし、`<` と `>` を入れない。
- どの手順をスクリプトにし、どこを AI に任せるか。決まった処理はスクリプトにし、推論が要ることだけを AI に任せる。
- 作業役の AI の数と呼び名（作業の定義の案と同じ）、要る MCP サーバー。合否の判定にコマンドの結果が要る基準は、成果物を書き換えない確かめのスクリプトを、確認役の AI の MCP のツールにする。
- 公開のプラグインを使うと決めた部分は作らない。
- 部品の分け方は、生成前の確認でよいと答えた振る舞いの案の中で決める。案にない振る舞い（「決まっていない」と答えたことの扱いなど）を、ここで足さない。ユーザーが確かめていない振る舞いが、プラグインに入るためである。

決めたら、次の順にする。manifest.json を最後に書くのは、コンパクションの後に、1を終えたかを manifest.json があるかで見分けるためである。

1. シェルで次を写す。作業エージェントは文書や画像のファイルを写せないためである。
   - `.plugin-creator-work/draft/task.json` を `.plugin-creator-work/parts/task.json` に
   - 流用するファイルを `.plugin-creator-work/parts/files/` の下の、生成プラグインで使う場所に
2. 課題の仮の入力のファイルを、生成前の確認で示した中身のまま、`.plugin-creator-work/parts/files/tests/eval/<課題の番号>/inputs/<名前>` に書く。
3. `<作業フォルダ>/.plugin-creator-work/parts/manifest.json` を書く。形：`{ "plugin_name", "plugin_description", "entry_skill": { "name", "description" }, "workers": [{ "agent", "label", "extra_tools": [] }], "verifier": { "extra_tools": [] }, "eval_inputs": [{ "from", "to" }] }`。
   - `extra_tools` は MCP のツール（`サーバー名/ツール名`）など、役ごとに足すツールである。
   - `eval_inputs` は、課題の実物の入力のファイルの一覧である。`from` は実物の絶対パスで、`plugin-creator_confirm` の入力のファイルの `path` に書いたものと同じにする。`to` は `tests/eval/<課題の番号>/inputs/<名前>`。同じ実物を2つ以上の課題で使うときは、課題ごとに1項目ずつ書く（`from` は同じで、`to` はそれぞれの課題のフォルダ）。組み立てのスクリプトが写すので、実物は `parts/files/` に写さない。同じ場所が両方にあると、組み立てが断る。

## 2. 作業エージェントに書かせる

`task` ツールで `plugin-creator:worker` に頼む。頼みの初めに「生成プラグインの部品」の仕事だと書く。作業エージェントは会話を見ていないので、次をすべて渡す。渡していないことは、生成プラグインに入らない。

- 作業フォルダ、`.plugin-creator-work/parts/`、ひな形（`<スキルのフォルダ>/../../template/`）の、`..` を畳んだ絶対パス
- よいと答えたナレッジの一覧（番号、種類、項目、文、例、例外）
- 振る舞いの案と、1で決めた部品の分け方
- 試験の課題：課題の番号、頼むときの言葉、入力のファイルの置き場所（`tests/eval/<課題の番号>/inputs/<名前>`。eval.json の `inputs` には、課題のフォルダからの `inputs/<名前>` で書く）、作業の画面に入れる設定の値、基準にするナレッジの番号と採点のしかた（文字や形で決まるものはプログラム、それ以外はモデル）。頼むときの言葉、入力のファイル、設定の値、基準の組は、`plugin-creator_confirm` に渡した課題（state.json の `confirmation.evalTasks`）と同じものを渡し、eval.json にそのまま写すよう伝える。組み立てのスクリプトが、eval.json が確かめた課題と同じかを確かめ、違うと断るためである（仮のファイルの置き場所は、confirm の `path` に書いた `tests/eval/<課題の番号>/inputs/<名前>`）。
- 流用する資産と写した場所、使うと決めた公開のプラグイン。写した流用のファイルは書き換えず、合わないときは「足りなかったこと」に書いて返すよう伝える。ユーザーが流用すると決めた部品を、作り直さないためである。
- 作り直しなら、元のプラグインのフォルダ、引き継ぐことと変わること

- よいと答えた内容が会話にないとき（コンパクションの後など）は、会話の要約から書き起こさず、`plugin-creator_state` の返り値の「お話を聞くことの記録（state.json）」のファイル（ナレッジと、生成前の確認で示したもの）から写す。
- 量が多いときは、いくつかに分けて、1つずつ頼む。
- 作業エージェントが足りないことを返したら、補って頼み直す。補えるのは、生成前の確認でよいと答えた内容と、1で決めたことだけである。ユーザーにしか分からないことが足りないときは、推し量って補わず、何が足りないかを、できたことの説明で示す。

## 3. 組み立て

1. `plugin-creator_state` の返り値の「お話を聞くことの記録（state.json）」で、その場所を見る。
2. 次を動かす。
   `python3 <スキルのフォルダ>/scripts/scaffold.py build --hearing <state.json の場所> --work <作業フォルダ>/.plugin-creator-work --out <作業フォルダ>/<生成プラグインの名前>`
3. 断られたら、返った理由を見て直し、もう一度動かす。
   - 理由が、manifest.json、写したファイル、仮の入力のファイル、出力先のことなら、自分で直す。自分で書いたものだからである。
   - 理由が、作業エージェントが書いた `parts/slots/` か `parts/files/` のことなら、頼みの初めに「生成プラグインの部品の直し」と書き、返った理由を作業エージェントに渡して直させる。この直しも、4の直しの回数に数える。直しが限りなく続かないようにするためである。
4. 終わると、生成プラグインのフォルダが git のリポジトリになり、`.plugin-creator-work/` は消える。

## 4. 試験と直し

1. `python3 <生成プラグインのフォルダ>/tests/run.py` を動かす。結果は `<生成プラグインのフォルダ>/tests/results/latest.json` にある。
2. 道具が足りないと出たら、`python3 <スキルのフォルダ>/../test-plugin/scripts/check_tools.py --plugin <生成プラグインのフォルダ> --scope stage12` で、足りない道具と、入れ方と、入れる場所を見る。
   - 道具ごとに何に使うかを1句添えて示し（例：Playwright は、できたプラグインの作業の画面を自動で操作して確かめるのに使う）、入れてよいかを聞く（承認の問い）。問いの例：「試験には、次の道具をこのパソコンに入れる必要があります。（道具と、何に使うかと、入れる場所）入れてよいですか？」選択肢は「入れない」「入れてよい」の順にする。
   - よいと答えたら、同じコマンドに `--install` を付けて動かし、1に戻る。
   - 入れないと答えたときと、答えが来なかったときは、試験をせずに7に進む。試験をしていないことは、5の5で示す。
3. 不合格なら、頼みの初めに「試験で落ちたところの直し」と書き、落ちた試験とその理由を作業エージェントに渡して、生成プラグインのフォルダで直させる。ナレッジが抜けたときは、抜けたナレッジの文も渡す。流用したファイルがあれば、生成プラグインのフォルダの中のその場所の一覧を渡し、変えないよう伝える。自分では直さない。生成プラグインのファイルを書き直すのも、作業エージェントの分担だからである。
4. 直させたら、`python3 <スキルのフォルダ>/scripts/scaffold.py check-base --out <生成プラグインのフォルダ>` で、土台のファイルがひな形と同じかを見る。違えば不合格とし、`--restore` を付けて動かしてひな形から入れ直し、土台を変えずに直すよう作業エージェントに伝える。
5. 1に戻る。直しは3回までにする。3回直しても合格しないときは、直すのをやめて7に進む。残った不合格の試験とその理由は、5の5で示す。
6. 合否は、生成プラグインのフォルダで動かした試験の結果で決める。自分でも作業エージェントでも、合否を決めない。不合格の原因が生成プラグインのファイルにないと思っても、別の場所に写して試験し直したり、自分の判断で合格としたりせず、3のとおりに直させる。直らなければ、残った不合格の試験とその理由を、5の5で示す。
7. 生成したときの印を付ける（合格しても、上限で止めても、試験をしなかったときも）。後で、ユーザーが直したところを、この印からの差分で見分けるためである。
   - 直したところがあれば（`git -C <生成プラグインのフォルダ> status --porcelain` に出れば）、`git -C <生成プラグインのフォルダ> add -A` の後に、`git -C <生成プラグインのフォルダ> -c commit.gpgsign=false commit --no-verify -m "plugin-creator: 試験に合わせて直す"` でコミットする。`git -C <生成プラグインのフォルダ> config user.name` か `git -C <生成プラグインのフォルダ> config user.email` が空なら、`commit` の前に `-c user.name=plugin-creator -c user.email=plugin-creator@localhost` も付ける。組み立てのスクリプトの最初のコミットと同じ決め方で、名前とメールがなくても失敗せず、署名とコミット前の確かめで人の操作を待たないためである。
   - 続けて `git -C <生成プラグインのフォルダ> tag -f plugin-creator-generated` を動かす。
8. 結果のファイルがあれば、`plugin-creator_results` にその絶対パス（`<生成プラグインのフォルダ>/tests/results/latest.json`）を渡し、plugin-creator の画面に出す。相対パスは、作業フォルダから探されるためである。

## 5. できたことの説明

次の6つを示す。言葉は `references/words.md` に従い、見出しも内部の言葉で書かない。

1. できたプラグインのフォルダの場所。入れ方と使い方は、そのフォルダの README.md にあること。
2. 組み込んだ仕事のやり方や決まり
3. 使ったあなたのファイルや道具。公開のプラグインを使うときは、その入れ方（`copilot plugin install <プラグイン>@<マーケットプレイス>`）
4. できたプラグインが、見つけた直すべきところを GitHub の Issue に出せるようにする手順：GitHub に公開する。`plugin.json` の `repository` にそのリポジトリの URL を書く。そのあと、手元のフォルダからインストールしたときは Copilot CLI を終了して起動し直す。GitHub からインストールしたときは、直した `plugin.json` を GitHub に送り、プラグインをアンインストールしてから、もう一度インストールする。gh を入れて、`gh auth login` でログインする。
5. ファイルの形の検査と、動きの試験の結果（段階ごとの合否）。不合格が残ったときは、何が合わなかったかを、試験の名前だけで示さず、words.md の言葉で短く言い直して示す。試験をしなかったときは、そのことと理由を示す。
6. 試験のしかた：ファイルの形の検査と動きの試験は、できたプラグインのフォルダで `python3 tests/run.py` の1つのコマンドで動き、AI クレジットを使わない。試しに動かして採点する試験は、plugin-creator に試験を頼むと行われ、AI クレジットを使う。

作り直しのときは、元のプラグインから変わったことと、作り直したものを元のリポジトリに入れ替えるやり方（新しいフォルダの中身を、`.git` を除いて元のリポジトリに写してコミットする）も示す。元のプラグインのフォルダは変えていない。
