# ユーザー役の AI で人を模擬するときの注意

外側の EVAL では、人間との会話を、ユーザー役の AI で模擬する。公開の研究と、試作で分かったこと（2026年10月）。設計への反映は [試験の設計](../../docs/design/testing.md) の6章にある。試作のコードは、ブランチ `claude/test-prototype` の `prototype/` にある。

## 公開の研究で分かっていること

- 模擬したユーザーは、人の代わりとして信頼できない（Lost in Simulation、2026年）。
  - ユーザー役のモデルを変えるだけで、同じエージェントの成功率が最大9ポイント変わった。
  - 難しい課題では出来を低く、中くらいの課題では高く見積もった。
  - 人とは違う話し方の癖や、人とは違う失敗のしかたが出た。
- ユーザー役の答えに答えが漏れると、評価の結果が良く出る。1つのプロンプトで、ユーザー役を思いどおりに動かすのは難しい（How Reliable is Your Simulator?、2024年）。
- τ-bench は、ユーザーを言語モデルで模擬するベンチマークである。同じ課題を何回も試して、振る舞いの信頼性を測る（pass^k）。

## 試作で分かったこと

- Haiku のユーザー役は使えなかった。
  - 大まかな質問（「守らないと困ることは？」）に、隠すべきナレッジを話した（25回中3回）。自分への指示を説明する中で話してしまうこともあった。
  - ナレッジにない決まりを作った。選択肢の言葉だけで答えた。
- Sonnet にし、それまでのやり取りを渡し、答え方の決まりを足すと、ユーザー役の試験のすべての観点に通った。
  - やり取りを渡さないと、「その2つ以外の見出しを足してもいいですか？」の「その2つ」が分からないことがあった。
- いくつかのことを1つにまとめた質問に、「締めくくりについても聞かれているので、答えます」のように、自分への指示に沿った説明を口にしたことがあった（外側の EVAL で1回。同じ質問を8回聞いても再現しなかった）。まれでも人はこう話さないので、決まりを足し、ユーザー役の試験でも見る。
- 話し方の指示は、答え方の決まりと食い違うと守られなかった。「あいまいに答える」でも、「具体的に答える」という決まりのほうに従った。答えの長さと言い方は話し方を優先すると書くと、最初はあいまいに答え（16回中5回）、聞き直されると具体的に答える（8回中8回）ようになった。
- ただし話し方を変えると、ユーザー役の誤りも増えた。外側の EVAL で、あいまいに答えるユーザー役が、締めくくりを具体的に聞き直されても答えないことがあった（2回中1回）。クリエイターは正しく聞き直していた。
- 答える条件を「〜について聞かれたときだけ」と狭く書いたナレッジは、人なら答えそうな質問にも答えなかった。例として「決定事項と意見を混ぜない」と挙げた質問に、決定事項の印のことを答えなかった。
- 大まかな質問しかしない対照のクリエイターでは、聞かれないと話さないナレッジが組み込まれなかった（2回とも 0.71）。試験が、落ちるべきときに落ちることを確かめられた。
- 週報の模擬ユーザーに合わせて手順を書いた試作のクリエイターは、議事録の模擬ユーザーでは、聞かれないと話さないナレッジを引き出せなかった（2回とも 0.71）。
- 内側の EVAL で、プラグインなしのときもユーザー役が返事をすると、自分から話すナレッジ（ファイル名や金額の書き方）は、プラグインがなくても伝わった。

## 対策

- 使う前に、ユーザー役だけを試験する。観点は、漏らさない、答える、まとめて答える、作らない、前の話を踏まえる、選択肢で済ませない、指示のことを話さない。
- ユーザー役のモデルと指示は、試験に通ったものに固定し、比べる EVAL のあいだで変えない。
- 対照のクリエイターで、試験が落ちることを確かめる。
- スコアが下がったら、クリエイターが聞かなかったのか、ユーザー役が答えなかったのかを分けて見る。ナレッジごとに、聞いたか・答えたか・組み込まれたかを記録すると見分けやすい。
- 模擬ユーザーは、いくつかの分野で用意し、クリエイターを直すときに見ていない模擬ユーザーでも確かめる。
- 結果は、同じ条件での比べ合いに使う。人と話したときの出来は、ここからは分からない。

## 外側の EVAL を実装して分かったこと（2026年10月、Agent SDK 0.3.310）

- **ユーザー役に渡すもの**：それまでのやり取りに加えて、AI が質問の前にチャットに書いた文も渡す（人は読んでいるため）。最初の実装は、質問と選択肢と過去の質問・答えだけを渡しており、コードの読み取りで気づいた。渡さないと、「上のまとめ」のように前の文を指す問いに、ユーザー役は中身を知らないまま答える。
- **急ぐ合図**：話し方の指示の1文に頼らず、試験の仕組みが決まった回数の後に、答えへ足す。位置を記録しておくと、「合図のあとに、進め方を選ぶ問いが出たか」を機械的に採点できる。
- **中身の見えない問い**：これまでのやり取りにも前の文にも中身がない問い（「上のまとめに違いはありますか」）には、「違いはない」と答えず、「上の〜とは、どれのことですか」と聞き返す、と指示に足した。
- **選択肢の丸写し**：ユーザー役が、選択肢の「名前（説明）」を丸ごと写して答える癖が出た（週報の会話例で29か所）。指示に、「選ぶときは名前だけを書き、名前の後に自分の言葉で中身を続ける」を足した。今のユーザー役の試験は、選択肢が名前だけなので、この癖を測れない。選択肢に説明を付けた問いを足すと測れる。
- **決まりの確かめ**：確かめられた文の中に、足す中身がすでに書いてあるのに、ユーザー役が「そうしないときもある」を選び、次に「例外はない」と答えて矛盾した。「このとおり」を選ぶ決まりを指示に足した。
- 指示を変えたら、使う前にユーザー役の試験をやり直す（上の対策）。「中身の見えない問い」「選択肢の丸写し」「決まりの確かめ」の3つの指示は、やり直していないので、効き目は本物のモデルでは確かめていない。
- **偽の API のはずが、本物のモデルに届いた**：偽の API につなぐ試験で、ユーザー役の呼び出しだけが本物のモデルに届いたことがある（ユーザー役に接続先の環境変数を渡していなかった。Sonnet の短い約17回。費用はごくわずかだったが、承認の前だった）。偽の API に向いていない呼び出しは、呼ぶ前に例外で止める守りを足し、本物の SDK を使う試験は必ずこの守りを通す。

## 新しい模擬ユーザーで不合格が出たとき（2026年10月、test-ng-pick）

- 新しく作った模擬ユーザーで外側の EVAL をして問題が出たら、クリエイターの弱さと決める前に、模擬ユーザーの `markers`（採点で、クリエイターの問い・ユーザー役の答え・生成プラグインのファイルを見分ける正規表現）と `volunteer` の誤りを疑う。
- test-ng-pick の1回目で出た4つ（不合格の観点2つ〔task:cold-chamber、not-embedded:author〕と、ユーザー役が聞かれる前に話したとされた2つ〔leaked cold-chamber、leaked hold〕）のうち3つが、模擬ユーザーのファイルの誤りだった。本当のクリエイターの弱さは task:cold-chamber だけだった（[試験で見つかったクリエイターの弱いところ](creator-weaknesses.md)）。
- [FORMAT.md](../../tests/dev-eval/personas/FORMAT.md) の一般論にない、具体的な落とし穴：
  - `excluded` が、生成プラグインに書かれた禁止の文（「「作成：」の行は書かない」）に当たった。書き方そのもの（名前つきの行。`` 作成[：:][^」』`\s] ``）に絞った。
  - `asked` に、クリエイターが実際に使った聞き方（「いつもと違う」）が入っていなかった。会話の記録で実際の問いを見て足した。
  - 毎週の手順で自然に話す決まり（判定が「保留」の項目は NG に数えない）を `volunteer: false` にしたら、先週の流れを話しただけで漏れと数えられた。`true` にした。
  - `leak` に普通の言い回し（「代わりに」）を入れると、関係ない答え（「Word のメモの代わりに」）に当たった。

## 会話例にするとき

外側の EVAL の会話は、ユーザーに見せる会話例にする（[作る流れの要件](../../docs/specs/creation-requirements.md) REQ-037）。

- 点数の高さだけで選ばない。ユーザー役が隠すべきナレッジを漏らすと、点数が上がるためである。すべての観点に合格し、ユーザー役の誤りがない会話から選び、最後は全文を読んで確かめる。
- 会話例を、クリエイターの AI に読ませない。例の分野の決まりを別の分野の生成プラグインに持ち込んだり、外側の EVAL で模擬ユーザーが隠しているナレッジを先に知ったりするためである。
- クリエイターを直すときに見ないことにしている模擬ユーザーの会話は、リポジトリに載せない。このリポジトリで作業する AI が読んでしまうためである。
- 冒頭に、AI が演じたユーザーとの会話であることを書く。人と話すと、質問の数や順番が変わる。
- 会話例の下読みでは、週報の模擬ユーザーの1つの会話（約700行）から、ユーザー役の人なら言わない答えが7種類見つかった：（1）ある質問で「そうしないときもある」と答え、あとで「例外はない」と言う矛盾、（2）中身のない「上のまとめ」に確認なしで「違いも不足もない」、（3）「こちらでは見えません」という役の外のことば、（4）毎週の作業の本人が「先週何を見て書いたか覚えていない」、（5）「この作業の目的は分かりません」、（6）頼む場面や基準を「特に決まっていません」、（7）選択肢の丸写し。
  - 原因は分けて直す。（1）（3）（7）はユーザー役の指示。（2）は、ユーザー役に文を渡していなかったことと、クリエイターが問いに中身を入れていなかったこと（実際の会話では、渡す文が元からなく、原因はクリエイター側だった）。（4）（5）（6）は、模擬ユーザーに、毎週の作業の本人なら知っている知識（先週何を見たか、頼む場面、出してよい基準）を持たせていなかったため。
