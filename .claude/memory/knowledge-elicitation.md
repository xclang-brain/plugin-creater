# 人からナレッジを引き出す手法

- 人から必要なことを引き出す手法は、SWEBOK の「要求の引き出し」にまとまっている。
- SWEBOK V3（2014）の手法の一覧は7つ（インタビュー、シナリオ、試作品、進行役のいる打ち合わせ、観察、ユーザーストーリー、その他）である。V4（2024、v4.0a は 2026年8月）は一覧が違い、プロトコル分析、弟子入り（apprenticing）、タスク分析などが加わった。
- V3 にも V4 にも、インタビューの進め方の手順はない。V4 には「引き出しは受け身でない」「要求の多くは暗黙である」という注意だけがある。
- 主な手法：

  | 手法 | 内容 |
  | --- | --- |
  | インタビュー | 相手に直接聞く |
  | シナリオ | 具体的な場面を想定してもらい、その中でのやり取りを聞く |
  | 試作品 | 画面の案や初期版などを見せて、反応を聞く |
  | 進行役のいる打ち合わせ | 複数の関係者で、進行役のもと、順序立てて話し合う |
  | 観察 | 相手が実際に作業している様子を見る |

## 文字のチャットで使えた手法（2026年10月の対話の設計で調べた）

- **実際の1件をたどる（Critical Decision Method）**：最近実際にあった1件を、話してもらう、時系列にして直してもらう、深掘りする、の順になぞる。「なぜそうしたか」より「何を見て、何をしたか」を聞くほうが確かな答えになる。時系列の抜けは、聞き漏らしの合図になる（Freeman ほか 1991、Hoffman 2005）。
- **見分け方をたどる（laddering）**：「見やすく」のような基準のない言葉は、「どうやって見分けるか」を1〜5段たどると、数や有無のような測れる基準になる（Sherlock & Rugg 2003）。
- **はい・いいえの確認は「はい」に偏る**：人は内容をよく見ずに同意しやすい（約10%。疲れると増える。Krosnick 1999）。チャットボットの確認では、本人の「はい」を正解にすると、第三者の判断より約19ポイント甘く出た（Barari ほか 2026）。答えを並べて選んでもらう、当てはまらないときを聞く、理解を返して直してもらう、が勧め。
- **文書と実際は違う**：本人の説明や文書の決まりは表向きになりやすい。先にファイルを読み、実際の1件と照らし合わせる（Hoffman 2005）。
- **よくある失敗**：最も多いのはあいまいな質問。終わりに要約しないことも多い（Bano ほか 2019）。
- **チャットは時間がかかる**：対面の約2倍の時間がかかり、集中が落ちる。回を分けるのが勧め（Opdenakker 2006）。1人への聞き取りで聞き終える判断の研究は見つからない。項目の一覧との照合と、「ほかに」への答えが出なくなることが物差しになる。
- クリエイターでの使い方は [ヒアリングの設計](../../docs/design/hearing.md) にある。

## 決まりではないと答えたことに、聞く側が案を作ってしまう（2026年10月、外側の EVAL の1回目）

- 起きたこと：模擬ユーザー（AI が演じた）が、題名の日付の書き方を「決まりではなく、たまたま」と答えたので、クリエイター（Claude Opus 5.5）はその候補を外した。ところが生成前の確認で、クリエイターは「決まっていないので、AI の案として入れるもの」を自分で作って示し、「違うところはありますか」の問いに模擬ユーザーが選択肢「違うところはない」を選ぶと、それを、ユーザーが足した決まりとして記録した。決まりではないと答えた書き方が、作業エージェントへの指示と生成プラグインに入り、採点で不合格になった。
- 「決まっていない」「たまたま」と答えたことに、聞く側が案を作らない。決まりがないところは、決まりがないまま渡す。AI の判断を入れてよいのは、ユーザーが「任せる」と言ったときだけである。
- 示したものに「違うところはない」と答えただけでは、決まりを足したことにならない。確かめただけである。上の「はい・いいえの確認は『はい』に偏る」と同じ形で、示した案への同意は、その案が正しい証拠にならない。
- 記録に添えるユーザーの言葉（抜き書き）は、要約や、複数の答えのつなぎ合わせにせず、1つの答えの言葉をそのまま写す（間は「…」）。1回目では、手順を矢印でつないだ要約が抜き書きになり、ユーザーがそう言ったことを確かめられず、「全項目を聞いた」の観点で不合格になった。
- 意味は機械で確かめられなくても、形は確かめられる。抜き書きが前のユーザーの答えの中にあるか、選んだ選択肢の文だけでないかは、記録のツールが断れる。手順の文を直し、この守りを入れたあとの2回目では、同じ不合格は出なかった（1回の比較で、どちらが効いたかは分けていない）。

## 聞きすぎも試験で見る（2026年10月、既存のプラグインを直す機能）

- 起きたこと：開発者が既存のプラグインを直す機能（change-plugin）を試し、一部を作り変えるだけなのに質問が多すぎると言った。依頼文に書いたことや、既存のファイルを読めば分かることまで聞かれた。
- 外側の EVAL（改善）の、質問についての採点の観点は、聞き足りないと落ちるもの（rules-list-once、added-rule-confirmed、last-time-asked）がいくつもあった。聞きすぎで落ちるのは、画面を変えない依頼で画面のことを聞いたときだけだった（no-screen-questions。unchanged-items も画面の項目を聞くと落ちる）。
  - 採点で落ちたのは、1回目の rules-list-once と4回目の added-rule-confirmed（どちらも確かめが足りない）。2回目の last-time-asked も落ちたが、採点の正規表現の誤りだった。
  - 1回目の書き足した決まりの確かめ漏れは、採点では合格になり、記録を読んで気づいて採点を厳しくした。画面を聞いて落ちた1回目の unchanged-items は、主に試験の誤り（頼みが画面の初めの値を変えていた）として、採点と模擬ユーザーを直した。
  - 画面のほかの聞きすぎは採点で落ちず、記録を読んで気づいたもの（スクリプトの使い方やひな形の文を決まりかと聞いた、要約の重ねなど）だけが、問いを減らして直された。
- 依頼文に書いたことの聞き直しのような聞きすぎが残ったのは、これが原因の1つと考えられる。手順書・プログラム・設計書と、試験の記録から調べた推定で、開発者が試したときの会話の記録は見ていない。ほかの原因は、依頼文を答えに数えていなかったこと、読み取った決まりを話に出ていても1件ずつ確かめたこと、確かめ済みのことを示し直したこと、作る流れの段階を変更の大きさに関係なく使ったことである。
- 防ぎ方：聞き漏らしだけでなく、聞きすぎも試験で見る。
  - 問いの数では落とさない。数で落とすと推し量りで閉じる向きの力が働き、模擬ユーザーは疲れないので数では負担を測れないためである（[試験の設計](../../docs/design/testing.md) 6.8）。
  - 聞いてはいけない問いを決めて、それを聞いたら落とす。今回、依頼文に書いたスキルの場所やプラグインのフォルダを聞き直したら落とす観点（request-not-reasked）を足した。
- 聞きすぎを減らすときも、次の守りは外さない。
  - 直すときに依頼文を答えに数えるのは、項目「前回の1回」を除く。
  - 話に出ていない読み取った決まりと、作った後に書き足された決まりは、1件ずつ確かめる（開発者が決めた）。上の「はい・いいえの確認は『はい』に偏る」ためである。
- 直した後に、ユーザー役の AI で動かす試験は、まだ回していない。
- 詳しくは、[ヒアリングの設計](../../docs/design/hearing.md) 3.4 と11章、[試験の設計](../../docs/design/testing.md) 6.8。決めた経緯は `wip/change-plugin/decisions.md` の21。

## インタビューの難しさ

- 相手が当たり前だと思っていることは、話されにくい。
- 専門用語で、話がかみ合わないことがある。
- ハーネスづくりで引き出したいのは、まさにこの「本人には当たり前で、AI が知らないこと」である。
