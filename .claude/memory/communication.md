# 人間と AI のコミュニケーション

## 分かりやすさが何より大事

- AI が人間に伝えることや、人間が読むドキュメントに書くことは、人間にとって分かりやすいことが何よりも大事である。
- どれだけ正しくても、人間にとって理解が難しければ意味がない。
- 憲章や仕様など、人間がよく見るものでは特に大事である。
- 人間と AI の会話では、さらに大事である。このプロジェクトは日本語が前提であり、AI の使う日本語が人間にとって分かりやすいことは、正しいことを言うよりも大事な場合がある。
- 分かりやすさにはいろいろな要素があり複雑だが、常に試行錯誤し、人間にとって分かりやすい文章を出力する努力を欠かさないことが大事である。

## 分かりやすさの要素の例

### 文章の長さ

- 人間の脳は AI より処理速度が遅く、AI が大量に出力する文字を読むのに時間がかかってしまう。
- どれだけ正しくても、文章の分量が多いと人間は読むのが難しくなる。
- だからこそ、できるだけ簡潔にすることが大事である。

### 用語

- 人間が理解できる用語を使うべきである。
- 独自の用語が多いと、人間が理解するのが大変になる。

### 聞かれたことだけに答える

- ユーザーの問いには、聞かれたことだけに答える。聞かれていない補足は、答えを分かりにくくする。
- 2026年10月、「試験の概要を教えて」に、段階、流れ、開発の試験、最終確認、残っている課題、参照先まで書いたら、「長い」と言われた。次の「生成プラグインの評価はクリエイターの評価に入るか」という問いにも、作り方を見る理由や、採点の基準を試験の側で用意することを足して、「答え以外のことは補足しなくていい」と言われた。
- 憲章 第9条の「簡潔に」を読んでいても、補足を足してしまった。「簡潔に」だけでは、補足を削る決まりとして働かなかったので、CLAUDE.md に決まりとして書いた。

## 質問のしかた

- 選択肢だけを並べると、何のために決めるのかが伝わらない。何を確かめる質問かは分かっても、なぜ今それを決める必要があるのかが分からない。
- 質問の最初に、決めないと何が困るか（背景と目的）を書く。具体的な例を1つ添える。
- 「分からない」と言われたら、説明を削らず、背景と選択肢ごとの結果を足して聞き直す。
  - 用語の定義を並べても、別の言葉に言い換えても、伝わらないことがあった（2026年10月、外側の EVAL の範囲を決める問い。「何を質問されているか分からない」と繰り返し言われた）。伝わったのは、だれが何をして何が起きたかを、具体的な出来事の順に書き、決めてほしいことを1つにしぼった聞き方だった。例：「AI に『週報を自動化したい人』を演じさせ、クリエイターが45問聞いてプラグインを作り、教えた決まりが入ったかを採点した」。分からないと言われたら、用語を足すのではなく、具体的な出来事の流れで言い直す。
- まとめた言葉で聞かない。「試験の道具はどこに入れるか」と聞いたら、何の道具の話か伝わらなかった（2026年10月）。中身（Python、Playwright、ブラウザーなど）を並べ、いつ・誰が・何のために使うものかを先に示す。
- 似た2つの仕組みは、表で違いを示す。生成プラグインの自己改善と、クリエイターの質問の改善を、どちらも「ログから Issue を起票する話」と受け取られた。誰が振り返るか、何の問題か、起票する先を並べると伝わった。

### 2026年10月の対話の設計で、質問が何度も伝わらなかったこと

- 比喩で言い換えない。このユーザーは AI に詳しく、「道具」「手順書」「AI の覚えられる量」のような言い換えは、かえって混乱させた。ツール、SKILL.md、コンテキストウィンドウ、コンパクションのように、正確な技術用語で書く。
  - 操作も、比喩でなく実際にすることで書く。「プラグインを入れ直す」は「`copilot plugin uninstall` でアンインストールしてから、`copilot plugin install` でもう一度インストールする」と書く。「反映される」のように、何が何を読むのかをぼかした言葉も使わない（2026年10月、仕様書の Issue の起票の手順）。
  - 何かの手順や文を問いにするときは、だれが、いつ、何をするときの話かを最初に書く。それを書かずに「この文も直しますか？」と何度聞き直しても、「何の話か分からない」と言われ続けた。
  - 問いが伝わらなかったときは、説明をやり直して答えをもらうまで、作業を先に進めない。「分からない」は答えではない。聞くのをやめて自分で決め、コミットや PR まで進めたら、「勝手に進めるな」と言われた（2026年10月）。
- 1つの言葉を2つの意味で使わない。「質問」を、クリエイターがユーザーにする聞き取りと、開発者への質問の両方に使ったら伝わらなかった。クリエイターがユーザーにするものは「ヒアリング」と呼ぶ。
- 仕様の番号（REQ-049 など）を出すときは、その仕組みが何のためにあり、いつ何をするかを先に説明する。番号の中身を知っている前提で聞くと、「仕様の意味も分からない」と言われた。
- 「足す」「増やす」と書くなら、何に足すのか、今は何があるのかを書く。「最終確認に1回足すか」は、「足すって何？元々は何？」と聞き返された。
- 似た2つの問題は、違いを先に示す。「コンパクションで SKILL.md が消える問題」と「GPT のシステムプロンプトが聞かずに進めと指示する問題」を、どちらも「ヒアリングが飛ばされる」と書いたら、解決済みの話と混同された。
- 事実だけで決まることは、問いにしない。判断を聞く必要のない技術的な細部を問いにすると、伝わらないうえ、ユーザーの時間を使う。
- 判断に関係のない情報を問いに入れない。文書の届き方の問いに「GPT-5 系など」とモデルの世代名を入れたら、古い情報に頼っていると心配された（実際に、調べたモデルの一部は退役済みだった）。
- 選択肢の説明に、確かめていないことを事実のように書かない。書く前に、記録やファイルで確かめる。確かめられないときは「確かめていない」と書く。「外側の EVAL でも正しく動いた」と確かめずに書き、それを前提に選んでもらった後で、記録がないと分かって聞き直した（2026年10月）。
- 背景を長く書かない。背景、例、選択肢ごとの結果を全部書いた長い問いは、「もう少し簡潔に」と言われた。前提は短い箇条にし、問いは1文にする。
  - 選択肢の説明にも、前提・数字・内部の仕組み（スキルの Related files、トークン、コンパクションなど）を詰め込まない。前提はチャットの文で先に短く示し、選択肢には「選ぶと何が起きるか」だけを書く。詰め込んだ問いは、「何を言っているか伝わらない」と言われた（2026年10月、ひな形の置き場所の問い）。

## 指摘の取り込み方

- 人間が AI に何かを指摘すると、その指摘したことが文書に残りがちである。
- 例：「人間は四足歩行です」という誤った文章を指摘すると、「人間は四足歩行ではありません」という文章が残ることがある。これは指摘されたから否定文に変えただけで、客観的に見れば不要な文章である。
- AI には、人間が指摘した経緯や指摘の文言をそのままドキュメントに書き留める習慣がある。
- AI は人間からの指摘をそのまま取り入れるのではなく、その背景にある意味や目的を理解し、噛み砕いてから、その目的に沿って修正する必要がある。

## 長い比較や調査は HTML で見せる

- 長い比較や調査の結果を、チャットの文章だけで示したら、読みづらいと言われた（2026年10月、skill-creator との比較）。
- 表や、2つを左右に並べた比較を使った HTML のページにすると、読みやすくなる。最初に、ひと目で分かる一覧を置く。
