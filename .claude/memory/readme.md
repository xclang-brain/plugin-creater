# README の書き方

## 最大の目的

- README を読んだユーザーが、プラグインの概要と使い方をすぐに理解できること。
- 2026年10月、クリエイターの README を3回書き直した。1回目と2回目は、どちらも「めちゃ分かりづらい」と言われた。
  - 1回目：チャットの言い換えの言葉（「試しに動かして採点する試験」など）で、補足と例を多く書いた。
  - 2回目：憲章の用語に変えたが、補足と例の多さは変えなかった。
  - 3回目：読む人と、初めに書くことを先に決め、初めの部分の下書きを見てもらってから、全文を書いた。これで「分かりづらいところはない」と言われた。

## 書く前に決めること

- 読む人：クリエイターの README は、Copilot CLI の利用者に向けて書く。Copilot CLI の用語（スキル、エクステンション、`/model` など）は説明せずに使い、plugin-creator 独自の言葉だけを説明する。
- 初めの部分（開いてスクロールせずに見える範囲）：できることと始め方だけを書く。
- 全文を書く前に、初めの部分だけを下書きして、ユーザーに見てもらう。書き方のずれは、そこで直す。

## 書き方

- 本筋だけを書く。補足、例、比喩を減らす。補足が多いと、本筋が捉えにくくなる。
  - 3回目で外した補足の例：始め方の中の週報の例、「初回だけ必要です」、読み込みの確認の詳しい説明。
  - 比喩の例：「仕事のやり方を聞き取る」は、「作業の手順やルールを質問する」と書く。
- コマンドは、Copilot CLI の中で打つスラッシュコマンドだけを書く（`/plugin install`、`/settings experimental on` など）。`copilot --experimental` のような起動のときの書き方と2通り書くと、文章が長くなる。
- 1つの言葉を2つの意味で使わない。例：`--experimental` は「実験的機能」と書き、生成プラグインの「試験」と分ける。
- 節を一覧で見せて聞くときは、節の名前だけで示さない。だれがいつ何をする場面の話かを、例の出来事で書く（「途中でやめて、後で続ける」「読み込むときの確認」は、名前だけでは何を指すか伝わらなかった）。
- 仕様書や設計書が「README に書く」と決めている内容を外すときは、ユーザーに確かめ、仕様書と設計書も直す。
- 文の書き方と点検は、[人間と AI のコミュニケーション](communication.md) の「書くときの型と、送る前の点検」を当てはめる。

## 書く前に読むもの

- ナレッジの索引だけでなく、すべてのトピックのファイルを読む。2026年10月、索引と3つのファイルだけを読んで書いた README は、ナレッジに沿わないところが多いと言われた。
