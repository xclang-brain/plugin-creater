# README の書き方

## 最大の目的

- README を読んだユーザーが、プラグインの概要と使い方をすぐに理解できること。
- 2026年10月、開発者からクリエイターの README が読みづらいと言われ、この目的で一から作り直した。それまでの README の中身は次のとおりだった。
  - 使い方の前に、インストールと準備（試験的機能、読み込みの確認の4つの選択肢と意味）の長い説明があった。
  - 何ができるかは、初めの2文だけで、具体的な例がなかった。

## 書く順番

1. できること：何を伝えると、何ができあがるか。具体的な例を1つ添える（クリエイターでは、週報のプラグインの例と、会話例へのリンク）。
2. 使い方：番号付きの手順で書く。初めに「使う前に準備を1回行う」ことだけを書き、準備の中身は後に回す。
3. 使うために要る準備、知っておくこと（答えが来ないとき、記録の置き場所など）、うまく始まらないとき。

- 生成プラグインの README も、初めの2つの節を「できること」と「使い方」にしている（仕様 REQ-050）。
- 仕様書が README に書くと決めている内容は、順番を変えても消さない。

## 言葉

- 憲章の用語（ナレッジ、ヒアリング、生成プラグイン、統括エージェント、Web管理画面、EVAL、構造の検査など）と、Copilot CLI の正確な技術用語で書く。チャットの言葉の表（`skills/make-plugin/references/words.md`）の言い換え（「試しに動かして採点する試験」など）は使わない（[人間と AI のコミュニケーション](communication.md) の「比喩で言い換えない」）。
- 用語は、初めて出るところで説明する。
- 1つの言葉を2つの意味で使わない。例：`--experimental` は「実験的機能」と書き、生成プラグインの「試験」と分ける。
- 文の書き方と点検は、[人間と AI のコミュニケーション](communication.md) の「書くときの型と、送る前の点検」を当てはめる。
- 書く前に、ナレッジの索引だけでなく、すべてのトピックのファイルを読む。2026年10月、索引と3つのファイルだけを読んで書いた README は、ナレッジに沿わないところが多いと言われた。
