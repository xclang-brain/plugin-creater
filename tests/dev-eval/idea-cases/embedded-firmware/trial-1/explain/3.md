# ビルドのたびの map 差分を、壊れたアドレスの周りに絞る

## ひとことで言うと
直してビルドしたら変数が壊れ始めた。そのとき、前回と今回の map ファイルを比べ、壊れたアドレスの近くで変わったものだけを、メモリマップ Excel の言葉で返す道具。

用語：map ファイル＝リンカ（部品をつないで1つのプログラムにする道具）が出す、変数や関数をメモリのどこに置いたかの一覧。GNU ld＝GCC 系で使うリンカ。RAM＝動作中のデータを置くメモリ。DMA＝CPU を通さずにデータを運ぶ仕組み。Copilot CLI＝GitHub Copilot を、文字で命令する画面（ターミナル）から使う道具。業務ではこれを使う。Claude Code＝Anthropic 社の同じ種類の道具。作る人が開発と試験に使う。Zed＝プログラムを書くエディタの1つ。

## 誰が・どの場面で・何に困っているか
- 誰が：RAM の残りが少ない製品で、1日に何度もビルドする FW 担当。
- 場面：直した後に、関係なさそうな変数が壊れる、DMA の転送先がおかしい、などが急に出たとき。壊れたアドレスか変数名は分かっている段階。
- 困りごと：変数を1つ足すと後ろの配置がずれる。数千行の map を2つ手で見比べることになる（仮説：時間は測っていない）。

## どう動くか
入力：前回と今回の map、リンカスクリプト（領域の境と名前を取る）、症状のアドレスか変数名、見る範囲、メモリマップ .xlsx。道具はビルドもリンクもせず、できた map を読むだけ。
「変化」として数えるもの：追加・削除・大きさの変更・領域の移動。アドレスがずれただけのものは数えない。症状の変数のずれは数えずに別の行で示す。
見る範囲の目安：前後 256 バイトから始め、0件なら広げる（仮説）。

出力の見本（数値は例）：

| 項目 | 見本 | 誰が |
| --- | --- | --- |
| 変化の数 | map 全体で 38 件、範囲内 2 件 | スクリプト |
| 症状の場所 | g_motor_cfg：0x20001A40、SRAM1（Excel：DMA 可）。256 バイト後ろにずれた（数えない） | スクリプト |
| 範囲内の変化 | s_uart_rx_buf（256 バイト）を追加、直前に入った／s_log_buf が 64→128 バイト | スクリプト |
| 候補 | 1位 s_uart_rx_buf（決め方 (1)）、2位 s_log_buf（(3)） | スクリプト |
| 次に見る1か所と理由の文 | s_uart_rx_buf の書き込み。直前のバッファがあふれると後ろを壊すため | AI |
| 原因の確定と直し方 | — | 人 |

決め方：(1) 症状のアドレスの直前にあるバッファで、新しく来た、大きくなった、またはずれて新しく隣になった既存のもの（最後のものは件数には入れない）、(2) 症状の変数が DMA 可否の違う領域に移った、(3) それ以外で近い順。

## AI なしと AI ありの違い
- AI なし：順位つきの候補の一覧と、決め方の番号まで。理由の文は出ない。社外に何も送らない。
- AI あり：1位の候補を理由の文にし、Excel の言葉で説明する。症状の文から入れる変数を挙げる。同じ順位が並んだときに1つを選ぶ。
- 送るもの：表の中身（数十行）、変数名、アドレス、Excel の領域名。ソースは送らない。
- ソースを読む使い方：同じ順位の候補を、ソースの書き込み箇所を読んで絞る。これは既定では使わない別の使い方にする。使うと、読んだソースの一部が送られる。
- 送る範囲の保証：手順書の指示だけでは保証にならない。CLI の権限設定（AI が読めるファイルを決める設定ファイル）で、map の結果以外を読めなくする。設定ファイルはリポジトリに置き、変更はレビューを通す。管理する人は課で決める。

## 効かないところ
- 壊れたアドレスが分からない段階には効かない。実機でウォッチポイント（書き込みで止める機能）を張るほうが早い場面もある。どちらが早いかは測っていない。
- スタックやヒープ（実行中の作業領域）のあふれは、境が近いことまでしか分からない。
- 前回の map はビルドで上書きされる。ビルドの最後に map を日付付きで残すスクリプトを付ける。
- 最初は GNU ld だけ。IAR・Keil は形式が違う。社内で GNU ld を使う製品の数は、まだ数えていない。
- Zed の中のターミナルで CLI を開いて使う。

## 似たものとの違い
MemBrowse、esp-idf-size、Bloaty などは「どれだけ増えたか」を見る。こちらは「症状の近くで何が動いたか」を見る。

## 管理職が決めること
- 今決めること：1人に、AI なしでの試作（GNU ld の map を比べる部分）をさせるか。これには Python と openpyxl（.xlsx を読む部品）を入れる許可と、map を残す設定が要る。工数は、試作にかかった時間から見積もる。
- 試作の後に決めること：
  - AI を使うか、ソースを読む使い方を許すか（社内規程）。
  - 送った内容の保存と学習の扱い（契約で違う）。
  - 今の Copilot 契約で Copilot CLI が使えるか。Claude Code の契約が課にあるか（無ければ、試験も Copilot CLI で行う）。
  - HW 担当と Excel の列（領域名、開始・終了、DMA 可否）を合意し、誰が最新に保つか。
- 導入の基準：過去の値化けの事例と当時の map が何件残るかを数え、「何件で試し、当たりが何割以上、時間が手作業より短ければ導入」を先に数字で決める。

## 確かめ方（まだ試していない）
- 当たりの定義：不具合票や修正の記録に残る原因の変数・バッファと、出した1か所が同じなら当たりとする。記録の無い事例は数えない。判定は試作した人がし、もう1人の FW 担当が確かめる。
- 時間：答えを知らない担当が、手で比べた場合と道具を使った場合で測る。
- 両 CLI：スクリプトの出力は同じになる。違いが出るのは AI の部分だけ。それぞれが記録の原因と合うかを、上の当たりの定義で判定する。

## 技術の補足
- 形：SKILL.md（AI に読ませる手順書）と Python スクリプト。Excel は起動しない。
- 前回：既定では、直前に残した map と比べる。日付を指定すれば、それより前の map とも比べられる。
- 変数名は今回の map でアドレスを引く。
- static 変数：-fdata-sections でビルドしたときだけ、map に名前が出る。それが無いときは、オブジェクトファイルの単位で示す。
- 範囲内の変化が0件のとき：「変化なし」と出し、範囲を広げるか、スタックかヒープを疑うよう示す。
- Excel とは、領域の名前ではなく開始・終了アドレスで対応づける。
- ELF（ビルドで出る実行ファイルの形式）とデバッグ情報から行番号まで戻すのは、後で足す。
