# 書き込みの直前に「この基板でよいか」を短く確かめるスクリプト

## ひとことで言うと
基板にファームウェアを書き込むコマンドの頭に .\flash.ps1 を付けて打つと、1秒以内（目標）に判定を返す。止めるのは取り違えと、全消去などの取り返しのつかない操作だけで、ふだんの書き込みは1行出してそのまま進む。

用語：
- 書き込み：作ったプログラムを基板のマイコンに入れる操作。
- プローブ：PC と基板をつなぐ書き込み用の機器（J-Link など）。
- S/N：プローブ1本ごとの製造番号。
- MCU：基板に載ったマイコンの型番。
- 読み出し保護：マイコンの中身を外から読めなくする設定。外すと中身が全部消え、誤ると書き込めなくなることがある。

## 誰が・どこで・何に困っているか
- 誰が：1日に何十回も書き込む組み込みの開発者。
- どこで：Zed（コードを書く道具）の端末で、自分でコマンドを打つとき。
- 困りごと（仮説・頻度は未計測）：基板が2枚以上あると別の基板に書いたり、全消去を履歴から打ち直したりし、「直したのに変わらない」とプログラムを疑って時間を失う。

## どう動くか
使う開発者本人が先に1回、.debug/target.txt に S/N と MCU を書く。
```
probe_sn: 0672FF485550755187123456
mcu: stm32f407vg
```
スクリプトが照らすもの（3つ）：
1. 接続中のプローブに、target.txt の S/N があるか。
2. コマンドの -u（使うプローブの S/N の指定）が target.txt の S/N の先頭と同じか。短く書いてよいが、8文字未満なら止まる（8は案）。-u がなく、プローブが2本以上つながっていても止まる。
3. コマンドの --target（MCU の指定）が target.txt の MCU と同じか。

判定（照らして決めるのはスクリプト、そのあとどうするかは開発者本人）：
- 進む：1〜3がすべて一致し、消去一覧（下記）の文字列を含まない → 「進む」の1行だけ出し、書き込む。
- 止まる：1〜3のどれかが合わない → 書き込まず、3行を出す。
- 確認待ち：1〜3は一致し、消去一覧の文字列を含む → 3行を出し、本人が yes と入れたときだけ書き込む。

出力の見本：
```
PS> .\flash.ps1 pyocd flash -u 0670FF48 --target stm32f407vg build\app.hex
止まる
理由：2が外れ。-u の 0670FF48 は target.txt の S/N と違う
次に見る：コマンドの -u
```
```
確認待ち
理由：1〜3は一致。--erase chip（全消去）を含む
次に見る：よければ yes、やめるなら Enter
```
複数外れたときは、理由にすべて書き、「次に見る」は1→2→3の順で最初の1つ（案）。

消去一覧：コマンド行に出る文字列の一覧（例：--erase chip、pyocd erase）。試作する開発者が見本を作り、課で1つを共有する（案）。

## 効くこと・効かないこと
- 効く：プローブ2本で別のプローブを指した。型番の違う基板を指した。全消去を打ち直した。
- 効かない：プローブ1本のままケーブルだけ別の基板に差し替えた（基板固有の ID は見ない）。.\flash.ps1 の付け忘れ。ビルド忘れ・別の hex。
- 手間が残る：同じ型番の基板を替えるたびに target.txt を書き直す。基板ごとにファイルを持って切り替える形は次の版の案。
- まだ効かない：デバッガの起動から自動で書き込む流れ、make flash、west flash（コマンド行に S/N も型番も出ないため）。
- 広げる順（案）：試作の2週間で、デバッガ起動からの書き込みが多いと分かればそれを先にする（デバッグ設定の書き込みの前にこのスクリプトを呼ぶ形。できるかは仮説）。次に make・west、次に pyocd 以外の書き込み道具。

## 似たものとの違い
調べた範囲では、書き込みの道具には S/N でプローブを選ぶ機能はあるが、型番と全消去まで照らして止めるものは見つからなかった（詳細は技術の補足）。AI が打つコマンドを止める仕組みはあるが、人が打つ書き込みには効かない。

## 試し方
- 2週間使い、①本当に取り違えだった停止、②取り違えでない停止、③増えた時間を比べる。
- 記録はスクリプトがログに残す（時刻・判定・理由・yes の有無・かかった時間）。①か②かは止まった直後に1文字で入れてもらう。手間が続くかは仮説。付け忘れはスクリプトから見えないので、端末の履歴から数える（仮説）。
- 使う前の比べる数がまだない。先に聞き取り（短い）か2週間の記録を取る。記録なら試す期間と合わせて最大4週間。

## 管理職が決めること（段階に分けて承認できる）
1. 今：開発者1人が手元の道具1種類で試作する工数。スクリプトだけで、PC の外にデータは出ない。工数は試作の時間を記録して出す。
2. 試作のあと：2週間試すこと。試す前に、やめる基準（例：②が1人1日に何回を超えたらやめる）を管理職と試す開発者で決める。保守する人と引き継ぐ人も決める。
3. 別に、後でよい：AI 相談を使うか。送られるのは S/N・コマンド行・止まった理由（ソースは送らない）。型番に顧客案件の情報が含まれうるので、送ってよいか、保存・学習に使われないかを契約と規程で確かめる。
AI 相談を認めなくても、1と2はスクリプトだけで進められる。

## 技術の補足
- 形：PowerShell スクリプト（必要なら Python）と SKILL.md（AI に target.txt の作り方や止まった理由の読み方を教える手順書ファイル。試作者が書く）。Copilot CLI と Claude Code が同じに読むかは仮説。
- 接続一覧は pyocd list で読む。1秒を超えるかは未計測。超えて読み取りを省くと、1と「-u なしで2本以上」が照らせなくなる。
- 書き込みの道具の出力と終了コードはそのまま返す。止まったときの終了コードは試作で決める。
- 似たもの：pyOCD・J-Link・west（Zephyr という組み込み OS の道具）は S/N でプローブを選べる。RIOT-OS（組み込み OS）の書き込み設定は S/N がないときだけ止まる。LinuxCNC（工作機械の制御ソフト）の設定ツールは書く前に基板の一致を確かめる（検索結果の要約のみで確認）。Claude Code のフック（AI がコマンドを打つ前に検査する仕組み）と Copilot CLI の許可の設定は AI のコマンドだけを止める。
- yes が習慣になる恐れは、ログの yes の回数と②で見る。
