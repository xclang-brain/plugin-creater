# 模擬ユーザーの形の決まり

開発の試験の外側の EVAL（[試験の設計](../../../docs/design/testing.md) 6章）で、人の代わりに話すユーザー役が使う「模擬ユーザー」の形を定める。内側の EVAL の課題と採点の基準（7章）も、模擬ユーザーごとにここに置く。

- 使う側：ユーザー役とユーザー役の試験、外側の EVAL、会話例の作成。内側の EVAL。見ない模擬ユーザーを作る側。
- 模擬ユーザーは 1 人 1 フォルダである。見ない模擬ユーザー（`tests/dev-eval/heldout/`）も、同じ形で作る。
- 模擬ユーザーには、新しく作るよう頼む人（作る模擬ユーザー）と、今あるプラグインの改善・設計変更を頼む人（改善の模擬ユーザー。`kind` が `change`。2.5）がいる。
- 形に合うかは、`validate.mjs` で確かめる（6章）。ユーザー役と外側の EVAL が読み込むときも、同じスクリプトを使う。

## 1. 置き場所

```text
tests/dev-eval/personas/            直して使う模擬ユーザー（クリエイターを直すときに使う）
  FORMAT.md                         この文書
  requirements.txt                  docx・xlsx を作る Python の部品の版
  validate.mjs                      形を確かめるスクリプト（読み込みにも使う）
  <id>/                             模擬ユーザー 1 人（フォルダの名前は id と同じ）
    persona.json                    模擬ユーザーの定義（2章）
    files/                          示すファイルの元（作る模擬ユーザーは docx か xlsx を 1 つ以上。ないなら作らない）
    make_files.py                   files/ の docx・xlsx を作るスクリプト（任意。作ったファイルも置く）
    inner/                          内側の EVAL（3章）
      eval.json
      standalone.json               単体の課題（任意。改善の模擬ユーザーの確かめ B。3章）
      inputs/…                      課題の入力のファイル
      golden/…                      正しい成果物の見本
      make_golden.mjs               golden/ の機器の記録と保存したログを作るスクリプト（任意。擬似の機器を使う模擬ユーザー）
tests/dev-eval/heldout/<id>/        クリエイターを直すときに見ない模擬ユーザー（同じ形。見ない模擬ユーザーを作る側が作る）
tests/dev-eval/fixtures/            改善の模擬ユーザーの題材（直すプラグインのリポジトリの tar.gz）と、それを作り直すスクリプト
tests/dev-eval/device/              擬似の機器（kxdevice.mjs、kxemu.py、bin/kxtool）
```

- `id` は、英小文字・数字・ハイフンだけ（例：`weekly-report`）。
- docx・xlsx は、Python の仮想環境に `requirements.txt` の部品を入れて、`make_files.py` で作る。作ったファイルも置くので、試験を動かすときに Python は要らない。見ない模擬ユーザーの `make_files.py` も、同じ版（`tests/dev-eval/personas/requirements.txt`）を使う。
- `make_files.py` は `--out <フォルダ>` を受け、既定の出力先は `files/` にする。作るたびに中身が変わらないよう、作成日時を固定する。

## 2. persona.json

JSON である。文字は UTF-8。正規表現と書いてあるところは、JavaScript の正規表現（フラグなし）を文字で書く。JSON の中では `\` を 2 つ書く（例：`"weekly_report\\.md"`）。

| 項目 | 中身 | 必須 |
| --- | --- | --- |
| `id` | フォルダの名前と同じ | 必須 |
| `title` | 人が読む名前（例：「週報（営業チームのリーダー）」）。会話例の表題に使う | 必須 |
| `experience` | `done`（前回の 1 回がある）か `never`（まだやったことがない作業。ファイルなし） | 必須 |
| `request` | ユーザーがクリエイターに最初に頼む言葉（1 発言） | 必須 |
| `profile` | ユーザー役への人物の説明（「あなたは〜です。」の形。2〜3 文） | 必須 |
| `files` | 示すファイル（2.1）。`never` のときは `[]` | 必須 |
| `knowledge` | ナレッジ（2.2） | 必須 |
| `userRoleTests` | ユーザー役の試験の質問（2.3） | 必須 |
| `styles` | 話し方（2.4） | 必須 |
| `kind` | 模擬ユーザーの種類。`change`（改善・設計変更を頼む）だけを書ける。省くと「作る」 | 任意 |
| `workspace`、`target`、`device`、`expect` | 改善の模擬ユーザーの作業フォルダと採点の値（2.5） | `kind` が `change` のとき（`device` は任意）。ほかでは書かない |

### 2.1 files（示すファイル）

ユーザーが「前回の成果物」「いつも使うファイル」として示すファイルである。外側の EVAL は、`place` の場所に写してから始め、ユーザー役はその場所を答える。`experience` が `done` なら、`docx` か `xlsx` を 1 つ以上含める。

| 項目 | 中身 |
| --- | --- |
| `src` | 模擬ユーザーのフォルダの中の元のファイル（例：`files/先週の週報.docx`）。docx、xlsx、csv、txt、md のどれか。改善の模擬ユーザーは、py、sh、c、h も使える |
| `place` | 作業フォルダの中の置き場所（例：`資料/先週の週報.docx`）。相対の場所で、`..` は使わない。ユーザー役が答える場所 |
| `role` | `output`（前回の成果物）、`input`（前回の入力）、`template`（いつも使うテンプレート）のどれか。改善の模擬ユーザーは、`skill`（ユーザーの既存のスキルのファイル）と `repo`（題材のリポジトリに、初めのコミットの前に置くファイル）も使える |
| `describe` | ユーザー役がファイルを紹介する言い方（例：「先週の分の週報。Word で作ったもの」）。`role` が `repo` のときは書かない |
| `reveal` | 答える条件。人ならどう答えるかを考えて、広めに書く（例：「前回の週報、過去の資料、テンプレート、いつも使うファイルを聞かれたとき」）。`role` が `repo` のときは書かない |

- `role` が `input` のファイルは、生成前の確認で課題の入力として示され、生成プラグインのリポジトリに入る（REQ-038）。外側の EVAL は、同じ中身（sha256 が同じ）のファイルがリポジトリにあるかを見る。
- ファイルは自分から示さない。クリエイターが、前回の成果物・ファイル・テンプレートを聞いたときに答える。
- `role` が `skill` のファイルは、ユーザーが組み込みたい既存のスキル（`SKILL.md` と、スキルのフォルダの中のスクリプトなど）である。外側の EVAL は、`SKILL.md` のほかのファイルと同じ中身のファイルが、直したプラグインにあるかを見る（流用した資産。REQ-055）。置き場所は `expect.userSkills` の下で、`target` の外にする。
- `role` が `repo` のファイルは、題材のリポジトリ（`workspace.repo.place` の下）に、初めのコミットの前に置く（例：作った後にユーザーが書き足した決まり。REQ-054）。ユーザー役には示さない（ユーザー役を動かす側が除く）。

### 2.2 knowledge（ナレッジ）

ユーザーが持っているナレッジを、1 件ずつ書く。1 件に 1 つの決まりを書く。

| 項目 | 中身 | 必須 |
| --- | --- | --- |
| `id` | 英小文字・数字・ハイフン。模擬ユーザーの中で重ならない | 必須 |
| `fact` | ユーザー役が知っていること。ユーザーの言葉で書く。固有の言葉、数、書式は、答えるとおりに書く | 必須 |
| `reveal` | 答える条件。人ならどう答えるかを考えて決める。狭く書きすぎると、人なら答える質問にも答えない（testing.md 6.4）。ファイルから読み取った決まりは、「〜を確かめられたとき」も書く | 必須 |
| `volunteer` | 自分から話すか。`true`：条件に近い質問や大まかな質問でも、思い出して話してよい。`false`：条件にはっきり当てはまる質問のときだけ答える（当たり前すぎて話されにくいこと、すでに持っている資産） | 必須 |
| `from` | `talk`（話の中で出る）か `file`（示すファイルに書いてある。クリエイターが読み取って確かめる） | 必須 |
| `stance` | `true` なら、生成プラグインに入る決まりではなく、聞かれたときの答え方の立場（例：作業の画面は今のままでよい。スクリプトの使い方は自分の決まりではないが、そのとおりに使う）。`from` は `talk` にし、`markers` の `embedded`・`excluded`・`task` を書かない。省くと `false` | 任意 |
| `file` | `from` が `file` のときの、ファイルの中の決まり（下） | `file` のとき必須 |
| `markers` | 言葉による見分け（下） | 必須 |

**file（ファイルの中の決まり）**

| 項目 | 中身 |
| --- | --- |
| `path` | `files[].place` のどれか |
| `evidence` | その決まりの手がかりになる文字。ファイルを文字にした結果（`documentText`）に、そのまま含まれること |
| `kind` | 決まりの種類（下の表） |
| `answer` | 決まりの確かめ（hearing.md 6.1）で選ぶ答え。種類から決まる |
| `detail` | 「そうしないときもある」の「どんなとき」、「違う」の「本当はどうか」。種類が `exception` と `wrong` のとき必須 |

| `kind` | 意味 | `answer`（確かめの 4 つの答え） | 生成プラグインへの組み込み |
| --- | --- | --- | --- |
| `rule` | 本当の決まり | このとおり | 入る（`embedded`） |
| `exception` | 例外のある決まり | そうしないときもある | 決まりと例外が入る（`embedded` に両方） |
| `incidental` | たまたまそうなっている書き方 | 決まりではなく、たまたま | 入らない（`excluded`） |
| `wrong` | ファイルのとおりではない（本当は別） | 違う | ファイルのとおりは入らない（`excluded`）、本当のことが入る（`embedded`） |

- `answer` の文字は、`validate.mjs` の `CONFIRM_ANSWERS` と同じである：`このとおり`、`そうしないときもある`、`決まりではなく、たまたま`、`違う`。
- `experience` が `done` なら、`from` が `file` のナレッジに、`rule`、`exception`、`incidental` を 1 つ以上ずつ入れる（`wrong` は任意）。ファイルを読む段階、読み取り役、文書をテキストにするツール、決まりの確かめを動かすためである（testing.md 6.1）。
- `incidental` は `volunteer` を `false` にする。

**markers（言葉による見分け）**

どれも正規表現（文字）である。`embedded`、`excluded`、`task` は正規表現の並びである。

| 項目 | 見るもの | 見方 | 必須 |
| --- | --- | --- | --- |
| `asked` | クリエイターの質問の全文 | 当てはまれば「聞いた」。最後は会話を読んで確かめる（testing.md 6.3） | 必須 |
| `answered` | ユーザー役の答え | 当てはまれば「答えた」。`fact`（と `file.detail`）の中の言葉で書く | 必須 |
| `leak` | 大まかな質問へのユーザー役の答え | 当てはまれば「漏れた」。`fact` の中の言葉で書く | `volunteer` が `false` のとき必須 |
| `embedded` | 生成プラグインのファイル | すべてに当てはまれば「組み込まれた」 | `embedded` か `excluded` のどちらかは必須（`stance` のナレッジは書かない） |
| `excluded` | 生成プラグインのファイル | 1 つでも当てはまれば「入ってはいけないものが入った」 | 同上 |
| `task` | 生成プラグインの EVAL の課題と基準のファイル | すべてに当てはまれば「基準に入った」。成果物を見て守られたかが分かる（合否の決め方にできる）ナレッジだけに書く | 任意 |

- `asked` には、ナレッジの話題の言葉に加えて、ファイルから読み取った決まりを確かめる質問に出る言葉も入れる（例：`「以上」`）。「以上でよいですか？」のような普通の言い回しに当たらないようにする。ほかの段階の決まった問い（実物を受け取る問い、範囲の問い、決まりの一覧の問い、決まりの確かめの問いの出どころ）の言い回しにも当たらないようにする（例：`静的` は一覧の「静的調査」や範囲の「C/C++ を静的に調べ」に、`手順` は「手順書」や出どころの「（deploy/SKILL.md の「手順」1 より）」に、`ログ追加` は範囲の「修正とログ追加をして」に当たるので、`静的リンク|静的に(?:リンク|する|します|して|した)`、`手順(?!書|通り|どおり|」)`、`ログ追加の(?:ルール|決まり)` のように狭める）。問いが、そのナレッジの話題そのものを示しているとき（例：一覧の中の printf の決まりと、それに書き足した決まり）は、当たってよい。当たると、その問いで「聞いた」になり、その問いへの答えが聞かれずに話したものかを見られない。
- 最近実際にやった1回を順に聞かれたとき（REQ-016、REQ-056）、聞かれないと話さないナレッジをどこまで話すかを決めておく。細かすぎるもの（コンパイラの名前、オプション、目印など）は、`reveal` に「最近の1回を順に話すときは、〜とだけ言い、〜までは言わない」と書く。言わないことには、`answered` の言葉をすべて入れる（例：`answered` が「目印」にも当たるなら、目印の文字だけでなく、目印のことを言わない）。その1回で話すのが自然なもの（送る形、手順の順など）は、`reveal` に最近の1回を順に聞かれたときを書き、`asked` に、最近の1回の問いに当たる正規表現を選択肢（`|`）として足す。`expect.lastTimeAsked` があるときは、言葉ではなく、それと同じ正規表現を足す。言葉だけ（例：`順に|最近|振り返`）を足すと、最近の作業のファイルの場所を聞く問い、範囲の問い（「〜の順に頼む」）、決まりの一覧の問い（「振り返り」）にも当たる。どちらもないと、最近の1回の答えが「聞かれずに話した」になる。
- 前の項の「最近の1回を順に話すときは、〜は言わない」を書いたナレッジがある模擬ユーザーでは、ナレッジごとの「〜は言わない」だけでは、ユーザー役が守らないことがある。その1回の話の出どころのナレッジ（自分から話す、最近の1回を持つもの）の `reveal` に、最近の1回を話す細かさの見本を1つ書く（例：「最近実際にやった1回を順に話すよう聞かれたときだけ、この細かさで話す：〜 → 〜 → 〜。〜は足さない。ほかの質問で最近の1回に触れるときは、〜だけを言い、〜は言わない」）。自分から話すナレッジの `fact` と答える条件は、大まかな質問や、最近の1回に触れるほかの質問への答えにも使われるので、見本は `fact` でなく `reveal` に書き、最近の1回を順に聞かれたときだけ使うことと、ほかの質問では見本の細かいことを言わないことを書く。見本と足さないことの並びの言葉は、聞かれないと話さないナレッジのうち、`asked` に `expect.lastTimeAsked` を含むもの（最近の1回の問いで「聞いた」になるもの）の `answered`・`leak` にだけ当たってよい。ほかのものに当たる言葉は書かず、中身で書く（例：「目印」でなく「ログをどこまで取るか」）。ユーザー役の試験では、`compound` に最近の1回の問いを、クリエイターの言い回しを変えて2つ以上入れ、話すナレッジを `expect` に、言わないナレッジを `forbid` に並べる。
- 改善の模擬ユーザー（2.5）では、初めての人がつまずくところ・間違えそうなところを聞く問い（make-plugin の `references/last-time.md` の6。最近の1回の後に毎回出る）への答え方も、聞かれないと話さないナレッジ（`stance` のものを除く）ごとに決める。`fact` がつまずきの形（〜しないと動かない、断られる、有効にならない など）のものは、人ならこの問いに答えるので、`reveal` にこの問いを書き、`asked` に問いの言葉と言い換え（例：`つまず|間違え(?:そう|やす)|間違いやす|迷いそう|迷いやす|失敗しそう|失敗しやす`）を足す。`reveal` は意味で書くので、ユーザー役は言い換えの問いにも答える。`asked` が言い換えに当たらないと、答えが「聞かれずに話した」になる。この問いに近い大まかな質問で話さないよう、`reveal` に「「注意点」「気をつけていること」「守らないと困ること」のような大まかな質問では話さない」も書く。ほかのものは、`reveal` に「初めての人がつまずくところ・間違えそうなところを聞かれても、〜は言わない」と書き（言わないことは、最近の1回の項と同じく、`answered` の言葉をすべて入れる）、`asked` がこの問いに当たらないようにする（当たると、言っても「聞かれずに話した」にならない）。決めないと、答えが回ごとにぶれ、話したものが「聞かれずに話した」になる。ユーザー役の試験では、`compound` にこの問いを入れ、答えるナレッジを `expect` に、言わないナレッジを `forbid` に並べる。
- 聞かれないと話さないナレッジ（`volunteer` が `false`）の `answered` は、示すファイル（`role` が `repo` のものを除く）を答える文に当たらない言葉にする。答える文は、`place`、ファイルの名前、`describe` と、置き場所か名前に「です」「でした」を続けた文、「<名前> で、<describe>です。」である（`validate.mjs` が確かめる）。ユーザー役は、ファイルを聞かれたら置き場所や名前を答えてよい（2.1 の `reveal`）ので、当たると、ファイルの名前を言っただけで「聞かれずに話した」になる（例：スクリプトの名前 `mkkximg` だけに当たる形でなく、決まりの中身の言葉（`.kximg`、`bad magic`）と、「mkkximg.py で〜にする」の形に当たる形にする。「で」は `で(?!す|し|は|も|[、,])` と書き、「mkkximg.py です」「mkkximg.py でした」「mkkximg.py で、〜にあります」に当たらないようにする）。
- `excluded` は、`incidental` と `wrong` の書き方が、決まりとして書かれたときに当たる言葉にする。手がかりの文字そのものが、課題の入力のファイルとして写された場所に出るのは、組み込みではない。見る範囲は外側の EVAL が決める。
- 特別な id `first-run`：想定の 1 回（`experience` が `never` のときの、「初めてやるとしたら、最初に何をしますか」への答え）。`embedded` と `excluded` を省ける。`asked` は、その問いに出る言葉にする（REQ-016）。

### 2.3 userRoleTests（ユーザー役の試験の質問）

ユーザー役だけを試験する（testing.md 6.2）。クリエイターは動かさず、ここに書いた質問をユーザー役に直接聞く。質問は、模擬ユーザーごとに決める。

| 項目 | 観点 | 中身 | 合格の条件 |
| --- | --- | --- | --- |
| `generic` | 漏らさない | 大まかな質問の並び（3 つ以上） | `volunteer` が `false` のナレッジの `leak` に当たらない |
| `recall` | 答える | `{ "knowledge": id, "questions": [質問, …] }` の並び。ナレッジごとに 1 件以上（`confirm` で足りるナレッジを除く）。質問は 2 つ以上 | `answered` に当たる |
| `compound` | まとめて答える | `{ "question": 質問, "expect": [id, id, …], "forbid": [id, …] }` の並び（1 件以上）。いくつかのことを 1 つにまとめた質問。`forbid`（任意）は、その質問では言わないはずの、聞かれないと話さないナレッジ（`expect` にないもの） | `expect` のナレッジの `answered` にすべて当たり、`forbid` のナレッジの `leak`（なければ `answered`）に当たらない |
| `unknown` | 作らない | ナレッジにも示すファイルにもないことの質問の並び（2 つ以上） | `abstain` に当たる |
| `abstain` | 作らない | 「特に決まっていません」と答えたとみなす表現（正規表現） | — |
| `context` | 前の話を踏まえる | `{ "turns": [質問, 質問, …], "expect": 正規表現 }` の並び（1 件以上）。後の質問が前の答えを指す | 最後の答えが `expect` に当たる |
| `options` | 選択肢で済ませない | `{ "question": 質問, "choices": [選択肢, …], "expect": 正規表現 }` の並び（1 件以上） | 答えが `expect` に当たる（選択肢の言葉だけでは当たらない） |
| `confirm` | 答える（決まりの確かめ） | `{ "knowledge": id, "question": 質問, "expect": 正規表現 }` の並び。`from` が `file` のナレッジごとに 1 件以上。示すファイルの文への答え方の立場（`stance`。2.5）も、決まりの確かめの形で聞かれるので、ここに書ける。選択肢は `validate.mjs` の `CONFIRM_CHOICES`（hearing.md 6.1 の順で、そうしないときもある、違う、決まりではなく、たまたま、このとおり）を付ける | 答えが `expect` に当たる（`answer` の選択肢、立場なら `fact` に書いた選択肢を選ぶ） |

- 「指示のことを話さない」の観点は、すべての答えを見る。指示の言葉（答える条件、自分から話す、答え方の決まりなど）の一覧は、ユーザー役を動かす側が持つ。
- `recall`、`compound`、`confirm` の質問は、そのナレッジの `markers.asked` に当たる言葉を含める（`validate.mjs` が確かめる）。質問が `asked` に当たらないと、ユーザー役の試験とクリエイターの質問とで「聞いたか」の見方がずれるためである。`compound` の質問は、`forbid` のナレッジの `asked` には当たらないようにする（`validate.mjs` が確かめる）。当たると、外側の EVAL では、言っても「聞かれずに話した」にならない。
- 質問を聞く回数と、合格の割合は、ユーザー役を動かす側が決める。
- `unknown` の質問は、ナレッジの `fact` にも、示すファイルの中にもないことにする。

### 2.4 styles（話し方）

ユーザー役の答えの長さと言い方を変える（testing.md 6.3）。キーは次の 6 つから選ぶ。`normal` は必須。

| キー | 話し方 |
| --- | --- |
| `normal` | ふつう（指示は空の文字） |
| `terse` | 口数が少ない |
| `vague` | あいまいに答える |
| `dont-know` | 「分からない」と答えがち |
| `nothing-special` | 「特にない」と答えがち |
| `hurry` | 急いでいる |

各話し方の項目：

| 項目 | 中身 |
| --- | --- |
| `label` | 人が読む名前 |
| `instruction` | ユーザー役への指示（話し方だけ。何を話してよいかは書かない）。ナレッジの `answered`・`leak` に当たる言葉を入れない（`validate.mjs` が確かめる）。`normal` は `""` |
| `reask` | `true`：最初の答えにナレッジが出なくてよく、「もう少し具体的に教えてください。」と聞き直した後の答えには出る。`vague`、`dont-know`、`nothing-special` は `true`。省くと `false` |
| `signal` | `hurry` だけ。必須。`{ "afterAnswers": 数, "text": 文字 }`。ユーザー役を動かす側が、`afterAnswers` 回答えた後の次の答えに `text` を足し、足した位置を記録する。急ぐ合図の後に、残りの項目と 3 つの進め方が出るかを見るため（REQ-015、testing.md 6.5） |

- 週報と議事録の模擬ユーザーは、6 つすべてを持つ。まだやったことのない作業の模擬ユーザーなど、ほかの模擬ユーザーは、`normal` だけでもよい。
- ユーザー役への指示には、答えの長さと言い方は話し方に従い、何を話してよいかは答え方の決まりに従うと書く（testing.md 6.3）。これはユーザー役を動かす側が書く。

### 2.5 改善の模擬ユーザー（kind が change）

今あるプラグインを示して、改善・設計変更を頼む人である（REQ-052〜061）。作業フォルダには、直すプラグインの入った git のリポジトリ（題材）と、ユーザーの既存のスキルを置く。

| 項目 | 中身 |
| --- | --- |
| `workspace.repo.place` | 題材のリポジトリを置く場所（作業フォルダからの相対。例：`market`）。作業フォルダの直下にはしない |
| `workspace.repo.fixture` | 題材の tar.gz（`tests/dev-eval/fixtures/` からの場所。例：`market.tar.gz`）。中身はリポジトリの根からの場所で入っている |
| `workspace.repo.commitDate` | 初めのコミットの日時（時差つき。例：`2026-10-01T00:00:00+09:00`）。毎回同じコミットの番号にするため |
| `workspace.repo.staged` | 初めのコミットの後に、ファイルの終わりに文字を足して git add だけしておく変更の並び（`{ "path": リポジトリの中の場所, "append": 足す文字 }`）。`target` の外に置く（ほかのフォルダの変更がコミットに入らないかを見るため。REQ-059） |
| `workspace.repo.origin` | `true` なら、作業フォルダの外にベアリポジトリを作り、`origin` にする（push していないかを見るため） |
| `target` | 直すプラグインのフォルダ（作業フォルダからの相対。`workspace.repo.place` の下） |
| `device` | 擬似の機器（`kx200`：`tests/dev-eval/device/` の KX-200）。内側の EVAL で、機器を起動して使う。機器を使わないときは書かない |
| `expect.carriedMax` | 題材の `tests/knowledge.json` の決まりの番号の最大（引き継ぐ番号の最大） |
| `expect.replaced` | ユーザーが「古い」と答え、中身を直して新しい番号になるはずの決まりの番号（例：`K-15`） |
| `expect.deviceTool` | 機器の道具の名前（`device` があるときは `tests/dev-eval/device/bin/` にあるもの。例：`kxtool`）。足した課題の擬似の機器に、同じ名前の差し替えがあるかを見る |
| `expect.userSkills` | ユーザーの既存のスキルのフォルダ（作業フォルダからの相対）。`role` が `skill` のファイルは、すべてこの下に置く |
| `expect.screenUnchanged` | 「変えないので聞かない」になるはずの画面の項目の名前の並び。名前は、クリエイターの項目の名前（`開始前に設定したいこと`、`実行中に見たいこと`、`終わった後に見たい結果と見せ方`。`com.github.copilot/extensions/plugin-creator/names.mjs`）で書く（記号も読める）。省くと3つすべて。画面の変更を頼む模擬ユーザーは、変える項目を外す（REQ-056） |
| `expect.screenAsked` | 画面で設定したいこと・見たいことの問いに当たる正規表現（画面を変えない頼みでは、この問いがないことを見る。REQ-056）。ないことを見るので、問いの言い換え（「画面に表示したいもの」「画面で確認したいこと」など）にも当たるようにし、画面を変えないと伝える文には当たらないよう、問いの形（「？」や「教えて」など）までを見る |
| `expect.lastTimeAsked` | 最近実際にやった1回をたどる問いに当たる正規表現（REQ-056）。「最近」などと「1回」と、たどる言葉（思い出す・順に・したこと など）が、同じ文（`。`・`？`・改行で区切る）にある形にする。段階「実物を受け取る」の、最近の作業のファイルの場所を聞く問いに当たらないようにするため。間の文字数で縛らない。クリエイターは「この作業」を具体的な作業の説明に置き換えるので、長さが決まらない |
| `expect.explained` | 直した後の説明に、すべて当たるべき正規表現の並び（REQ-060）。版（例：`0.2.0`）を見る正規表現は、機器の IP アドレス（例：`192.168.7.2`）の一部に当たらないようにする |

- 頼み（`request`）には、直すプラグインのフォルダと、組み込みたいスキルの場所を書く。
- 決まりの一覧（題材の `tests/knowledge.json`）を見せられたときの答えは、`from` が `talk` のナレッジに書く。決まりの番号は書かず、中身で書く（例：「古くなったのは『〜のときは人に伝える』という決まりだけ。今は〜。ほかはそのとおり」）。一覧を見せられる前のユーザーは番号を知らないので、番号を書くと、見せられていない一覧の番号で答えてしまう。一覧を見せられたら、示された番号で答えられる。ユーザー役の試験では、`options` に決まりの一覧の問いを入れる。
- 画面を変えない頼みでは、作業の画面についての立場（例：画面は今のまま。機器のアドレスは、頼みや画面にあればそれを使い、なければスキルの値を使う今のやり方のままでよく、直した後のプラグインのスキルでは、既定の値を今の値にしてほしい）を、自分から話す `stance` のナレッジで書き、`expect.screenUnchanged` を3つすべてにする（省いても同じ）。自分から話す値（機器のアドレスなど）を、どこに入れたいか（スキルか画面か）が決まっていないと、問いの書き方しだいで画面の変更になるためである。頼みや画面の値とスキルの値のどちらを使うかも書く。直してほしいスキルは「直した後のプラグインのスキル」と書く。「スキルの既定」だけでは、示した元のスキル（`expect.userSkills` の下）と読め、直すプラグインの外のファイルを直すよう求めることがある。「決まりとして書いてほしい」のように置き場所だけを書くと、ユーザー役が「既定ではない」と読み、頼みの値を使うやり方を外すよう求めることがある。値そのものは書かない（値のナレッジの `embedded`・`excluded` に当たるため）。
- 示すスキルのスクリプトそのものの使い方（引数、出力のフォルダ、終了コードなど）は、決まりのナレッジにしない。スクリプトがそのとおりに動くので、ユーザーが決めることではないためである。確かめられたときの答え方は、`stance` のナレッジで書く。決まりの確かめの4つの答えから選ぶならどれかも書く。書かないと、「自分で決めた決まりではない」から「決まりではなく、たまたま」が選ばれ、スキルの既定（出力のフォルダなど）が生成プラグインから抜けることがある。`asked` は、`reveal` に書いた話題（呼び方、名前の形など）の問いにすべて当たる言葉にする。
- 示すスキルの残りの文（決まりのナレッジにも、スクリプトの使い方にもしない文。環境の条件（`compatibility`）、出力の意味の説明など）への立場も、`stance` のナレッジで書く（例：知っていることの別の項目に書いたことのほかは、今もそのとおり。決まりかと聞かれて4つの答えから選ぶなら「このとおり」）。例外（たまたまの書き方、違う決まり、例外のある決まり）を `fact` に書き並べない。並べると、大まかな問い1つで全部出て、決まりを1件ずつ確かめるか（REQ-055）を試せない。ユーザー役の試験では、この立場とスクリプトの使い方の立場を、`confirm` に決まりの確かめの形の問いで入れる。選択肢なしの `recall` では、問いの言葉をなぞった答えでも当たり、4つの答えから選ぶかを見られない。書かないと、確かめられたユーザー役は「こちらでは決めていません」と答えるしかなく、スキルの文が生成プラグインから抜ける。`fact` には、ほかのナレッジの `answered` と、生成プラグインを見る `markers` に当たる言葉（コマンドの名前、値、目印など）を書かず、中身で書く（例：「git pull」でなく「ビルドの前に最新にすること」）。
- ユーザーのスキルから読み取る決まりには、`rule`、`exception`、`incidental`、`wrong` を1つ以上ずつ入れる。
- 生成プラグインのファイルを見る `markers`（`embedded`、`excluded`、`task`）は、題材の `target` のもとの文字と、`role` が `skill` のファイルのうち `SKILL.md` でないもの（そのまま写される資産）の文字に、当たらない言葉にする。当たる言葉だと、クリエイターが何もしなくても、または資産を写しただけで、合否が決まってしまう。外側の EVAL は、初めのコミットから直した後までの差分の、足した行で見る。ただし、`role` が `repo` のファイルから読み取るナレッジ（直すプラグインのファイルに元からある決まり）は、直した後のファイルで見る。足した行だけで見ると、そのまま残したときに落ちるためである。そのため、このナレッジの `markers` は `role` が `repo` のファイルの文字に当たってよい（`validate.mjs` は、題材の tar.gz の文字と比べるので、`repo` のファイルで足した文字とは比べない）。
- 同じ `markers` は、ほかのナレッジの `fact` と `file.detail` にも当たらない言葉にする。足した行はまとめて見るので、ほかの決まりを組み込んだだけで当たってしまう。決まりの形（例：「`reboot` するまで有効にならない」）で書き、道具やコマンドの名前だけにしない（作業エージェントが書く試験にも、名前は出るため）。
- 聞かれないと話さないナレッジ（`volunteer` が `false`）の `answered` も、ほかのナレッジの `fact` と `file.detail` に当たらない言葉にする。外側の EVAL は、`answered` に当たり、その問いが `asked` に当たらず、そのナレッジがまだ会話に出ていない答えを「聞かれずに話した」にするので、当たる言葉だと、ほかのナレッジを話しただけで漏れになる（例：手順の `reboot` と、いつもと違うときの `reboot` してやり直す）。
- 手順の決まりは、生成プラグインがコマンドの並び（箇条書き・コードブロック・表の、行の頭に置いたコマンド）だけで書くこともある。そのときも当たるように、文の形と、決まりの順（例：`kxinstall` → `reboot` → `kxapp run`）に並んだコマンドの形の両方を、1 つの正規表現の選択肢（`|`）で書く。`embedded` の並びは、すべてに当たることを求めるので、別々の項目に分けない。コマンドの並びの形は、行の頭のコマンドだけを見て、試験のコード（文字列や配列の中のコマンド）、機器の記録やログ（`kx200# reboot` のようにプロンプトの後のコマンド）、順の違う並びや、決まりの一部が抜けた並びには当たらないようにする。
- 改善の模擬ユーザーでは、docx・xlsx の決まり（2.1）を外す。

## 3. inner/（内側の EVAL）

内側の EVAL の課題と採点の基準である（testing.md 7章）。クリエイターが生成プラグインに入れた課題と基準は使わない。自分で作った基準で自分を採点しないためである。

- `inner/eval.json`：課題。形は、生成プラグインの `tests/eval/<課題>/eval.json` と同じ（基準の `check` の種類は `skills/test-plugin/scripts/grade.mjs` の先頭にある。`validateTask` が確かめる）。1 人に 1 課題である。
  - `id`、`prompt`（頼むときの言葉。入力のファイルの場所を含める）、`inputs`（`inner/` からの相対の場所）、`settings`（任意）、`criteria`。
  - `criteria[]` は、`id`、`text`、`grading`、`check` に加えて、`knowledge`（ナレッジの id）を必ず付ける。
  - 採点の基準は、ナレッジに書いたとおりにする。ナレッジにない細かさまで求めると、正しい成果物を落とす（testing.md 7章）。
  - 文字や形で決まるものは `program`（`file_exists`、`contains`、`not_contains`、`regex`、`unchanged`）、それ以外は `model` にする。「最後の行が決まった文字」は `regex` で書く。文字が出ていないことを正規表現で見るときは、先頭に `(?![\s\S]*(…))` を置く。
  - `markers.task` を持つナレッジには、基準を 1 件以上付ける。
- `inner/standalone.json`（任意）：単体の課題。形は `eval.json` と同じ。取り込んだルールのスキルの仕事を、統括エージェントを始めずにチャットで頼む（REQ-062、REQ-055 の受け入れ基準。改善の模擬ユーザーの確かめ B）。`inputs` と見本は `eval.json` と同じフォルダのものを使う。頼みの文には、ルールのスキルが知っているべき値（機器のアドレスなど）を書かない。書くと、スキルにその値がなくても合格するためである。その値は基準で見る。
- `device` があるときは、内側の EVAL が擬似の機器を起動し、採点の前に機器の記録を作業フォルダの `.device/console.log` と `.device/history.jsonl` に写す（`tests/dev-eval/device/kxdevice.mjs` の `copyRecordsTo`）。機器で起きたこと（受け取った・インストールした・動いた）を見る基準は、作業フォルダの成果物ではなく、この記録で書く（エージェントが機器を使わずに、その場で動かした結果で合格しないため）。頼まれた場所にログを保存したかは、その成果物（例：`logs/device.log`）で見る。
- `inner/inputs/`：入力のファイル。課題の `inputs` が指す。
- `inner/golden/`：正しい成果物の見本。作業フォルダの形（`weekly_report.md` など）で置く。機器の記録の見本（`.device/`）と、頼まれた場所に保存したログの見本（例：`logs/device.log`）は、擬似の機器を正しい手順で1回動かして作る（`inner/make_golden.mjs`。機器は決まった動きをする）。`validate.mjs` が、`program` の基準がすべて合格することを確かめる（基準が厳しすぎないか、書き間違っていないかを見るため）。採点と同じく、入力を写した作業フォルダに見本を重ねて採点するので、見本に置かない入力は、変えていないものとして採点される。`model` の基準は確かめない。
- 画面で選ぶモデルは書かない（画面の既定のまま）。

## 4. 作る人への決まり

- 依頼の内容と、ナレッジごとの答える条件は、人ならどう答えるかを考えて決める。
- 聞かれないと話さないナレッジ（`volunteer` が `false`）を、必ず入れる。当たり前すぎて話されにくいこと、すでに持っている資産（ファイルに書いてある決まり）にする。
- 手順を模擬ユーザーに合わせない。クリエイターの手順を 1 人の模擬ユーザーに合わせて書くと、その模擬ユーザーでしか通らない（testing.md 6.3）。分野を変える。
- 示すファイルの中に、本当の決まり、例外のある決まり、たまたまの書き方を 1 つ以上ずつ入れる。`evidence` の文字が、ファイルの中に実際にあることを `validate.mjs` が確かめる。
- ファイルに書かれていない質問（`unknown`）は、ファイルの中の言葉と重ならないようにする。
- 実在の人名・社名・個人情報を入れない。数や日付は架空にする。
- 会話例にする会話は、見ない模擬ユーザーからは作らない（testing.md 6.6）。

## 5. 使う側がすること

**ユーザー役を動かす側**

- ユーザー役に渡すもの：`profile`、`files` の `place`・`describe`・`reveal`（`role` が `repo` のファイルは渡さない）、`knowledge` の `fact`・`reveal`・`volunteer`、`file` の `answer`・`detail`、話し方の `instruction`、それまでのやり取り。
- ユーザー役に渡さないもの：`markers`、`stance`、`userRoleTests`、`inner`、`id`、ほかの模擬ユーザー。言葉の見分けを知らせると、答え方が変わるためである。
- 決まりの確かめ（4 つの答え）の質問には、`answer` の選択肢を選び、`detail` があれば具体的に足す。選択肢の言葉だけで済ませない。
- `hurry` の `signal`：`afterAnswers` 回答えた後の次の答えに `text` を足し、足した位置を記録する。
- `experience` が `never` のときは、ファイルを示さない。「ありません。まだやったことがないので」と答える。

**ナレッジごとの記録（外側の EVAL）**

| 記録 | 求め方 |
| --- | --- |
| 聞いたか | クリエイターの質問の全文が `asked` に当たる |
| 答えたか | ユーザー役の答えが `answered` に当たる |
| 組み込まれたか | 生成プラグインのファイルが、`embedded` にすべて当たり、`excluded` に 1 つも当たらない |
| 基準に入ったか | `task` があれば、課題と基準のファイルが `task` にすべて当たる |
| 聞かれずに話した | `volunteer` が `false` で、答えが `answered` に当たり、直前の質問が `asked` に当たらず、そのナレッジがまだ会話に出ていない（前の答えが `answered` に当たったか、クリエイターが問いやチャットの文で `answered` に当たる言葉を示したら、出た） |

- 6.5 の採点のうち、模擬ユーザーの定義から見るもの：REQ-017（`incidental` と `wrong` のナレッジの `excluded` に当たる書き方が、生成プラグインにない）、REQ-016（`experience` が `never` で、`first-run` の `asked` に当たる問いがあり、その後に想定の 1 回をたどっている）、REQ-038（`role` が `input` のファイルが、生成プラグインのリポジトリにある）、REQ-015（`hurry` の `signal` の後に、残りの項目と 3 つの進め方の問いがある）。

**内側の EVAL**

- `inner/eval.json` を課題として読み、`inner/inputs/` を作業フォルダに写す（`tasks.mjs` の `prepareWorkDir`、`dir` を `inner/` にした課題を渡す）。採点は `grade.mjs` を使い、モデルで判定する分は Agent SDK で行う。
- チャットで返事を求められたときに答えるユーザー役は、同じ模擬ユーザーの `knowledge` を使う。

## 6. 形を確かめる

```text
node tests/dev-eval/personas/validate.mjs <模擬ユーザーのフォルダ>… [--all-styles]
```

- 合格なら終了コード 0、不合格なら 1。誤りを 1 行ずつ出す。
- `--all-styles`：話し方の 6 つがそろっているかも確かめる（週報と議事録の模擬ユーザー）。
- 読み込みに使うとき：

  ```js
  import { loadPersona, CONFIRM_ANSWERS, CONFIRM_CHOICES, STYLE_KEYS } from './validate.mjs';
  const { persona, dir, files } = await loadPersona('tests/dev-eval/personas/weekly-report'); // 誤りがあれば Error
  ```

  `files` は、示すファイルの元の絶対の場所と、作業フォルダでの置き場所の対応（`{ src, place, role, describe }`）である。`fixture` は、改善の模擬ユーザーの題材の tar.gz の絶対の場所（ほかは `null`）。題材の中身は `readTarGz(fixture)`（`{ 場所 → 中身 }`）で読める。
- 確かめること：persona.json の項目と型、id の重なり、正規表現が読めるか、`answered`・`leak` が `fact` の中の言葉か、`stance` のナレッジが `talk` で生成プラグインを見る `markers` を持たないこと、示すファイルの有無と `evidence` が文書の文字にあるか、3 種類の決まり、`userRoleTests` の質問、話し方、`inner/eval.json` と `inner/standalone.json`（`validateTask`）、基準と `knowledge` の対応、`golden` で `program` の基準が合格すること、聞かれないと話さないナレッジの `answered` が示すファイルを答える文に当たらないこと（2.2）。
