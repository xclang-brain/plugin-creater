## 0. 結論

1. **使い回し**：make-plugin の references 15個のうち、6個はそのまま使える（words、deepen、setup、rules、improve、last-time）。ほかに4個は、change-plugin の本文に違いを書けば使える（receive、read、items、assets）。さらに2個は、本文の違いと直す専用のファイルで補えば使える（screen、confirm）。使わないのは3個（start、carried、generate）。ただし generate.md の「4. 試験と直し」は使い回せる。直す専用に要るのは、`change-start.md`、`change-read.md`、`change-confirm.md`、`change-apply.md` の4つである（1.2）。
2. **段階の順を make-plugin とそろえる**と、共有する references の「次へ」がほぼそのまま合う。前回の1回 → 決まりの確かめ → 項目の点検 → 資産 → 画面 → 確認、の順である。決まりの一覧をまとめて確かめる問いと、変える範囲を確かめる問いは、段階「読む」の終わりに置く。合わない「次へ」は、change-plugin の段階の表を優先すると1行で書けば済む（1.2、2.3）。
3. **隣のスキルのフォルダのファイルを読むこと**は、もう前例がある（test-plugin が `../make-plugin/references/` の3ファイルを読む）。ただし、本物の Copilot CLI で確認なしに読めるかは確かめていない（`wip/implementation/REPORT-draft.md:290` の最終確認の16に残っている）。Claude Code の開発の試験では `Read` を前もって許しているので、読める。KISS のため共有を勧める。そのうえで、最終確認の16に change-plugin も足す（1.3）。
4. **本文の長さ**：make-plugin の本文は **117行・4,974トークン**で、上限 5,000 まで残り **26トークン**しかない。make-plugin の本文には何も足せない（description はフロントマターなので数えない）。change-plugin の本文に make-plugin の共通の節を写すと 5,000 を超える。そこで、`<make-plugin>/SKILL.md` の4つの節を読む形を勧める。共有した下書きは **67行・2,445トークン**だった。`check_creator.py` は make-plugin だけを測るので、すべてのスキルを測るよう広げる（1.4、1.5）。
5. **make-plugin の description**からは、「フォルダのまま直す・足す・変える」頼みを外す。「作り直したい」は make-plugin に残し、start.md の始めに「直すか、新しいフォルダに作るか」を聞く問いを足す。本文は変えない（3章）。
6. **避けること**：作業エージェントが流用の部品を書き換えた件と、プラグインの場所を作業役が知れない件が、直す流れでいちばん効く。前者は指示に頼らず、git の差分で機械的に見張る。後者は、取り込んだルールのスキルに作業役が従う手段（REQ-055）が今のひな形にないので、直す前の確認より前に決める（4章）。
7. **作業エージェント**：直すときも、作業エージェントに直すフォルダを直接書かせない。変える差し込み口とファイルだけを `.plugin-creator-work/parts/` に書かせる。変えない差し込み口は、スクリプトが元のプラグインから取り出して写す。試してみると、10個の差し込み口のうち、見出しの決まった節はほぼ取り出せた。統括の差し込み口だけは、ひな形の前の文が変わっていて、前後の文の照合では取れなかった（5章）。

## 3. make-plugin（と test-plugin）の description の直し

今の文（make-plugin/SKILL.md:3）：

> ユーザーの仕事のやり方と決まりを組み込んだ、作業の画面つきの Copilot CLI のプラグインを作る。「〇〇を自動化したい」「この仕事を AI に任せたい」「〇〇をプラグインにしたい」と頼まれたとき、手元の既存のプラグインを示して作り直したいと頼まれたときに使う。いまその仕事そのものをしてほしい頼み（例：「今週の週報を書いて」）と、できたプラグインの試験の頼みには使わない。

案：

> ユーザーの仕事のやり方と決まりを組み込んだ、作業の画面つきの Copilot CLI のプラグインを作る。「〇〇を自動化したい」「この仕事を AI に任せたい」「〇〇をプラグインにしたい」と頼まれたとき、手元の既存のプラグインを示して作り直したいと頼まれたときに使う。いまその仕事そのものをしてほしい頼み（例：「今週の週報を書いて」）、できたプラグインの試験の頼み、手元のプラグインのフォルダのまま機能を足したり設計を変えたりする頼み（例：「このプラグインにデプロイのスキルを足したい」）には使わない。

- 変えるのは、使わない頼みに1つ足すことだけである。「作り直したい」は残す（REQ-032 の作り直しの入口のため）。
- あいまいな「作り直したい」は、start.md の手順1の初め（記録を作る `plugin-creator_progress` の前）で聞く。新しいフォルダと答えたら今の作り直しの流れ、元のフォルダを直すと答えたら `skill` ツールで change-plugin を読む。これは references の直しで、本文は変えない（本文の残りは26トークン）。
- test-plugin（test-plugin/SKILL.md:3）の使わない頼みにも、「今あるプラグインに機能を足したり設計を変えたりする頼み」を足す。今は「新しくプラグインを作る頼みや作り直しの頼み」だけである。
- クリエイターの `plugin.json` の description（「…作って試験する」）と README（REQ-052 の受け入れ基準「README に頼み方」）も合わせる。README.md:15 の「元のフォルダは変わりません」は作り直しの話なので残し、直す流れの段落を足す。
- description を変えることは、振る舞いの変更である（ナレッジ「リファクタリング」）。呼ばれ方の試験を足す。日本語の description で呼ばれるかは、まだ確かめていない（hearing.md の H11）。例：「このプラグインに〇〇のスキルを足したい」→ change-plugin、フォルダと「作り直したい」だけ → どちらでも問いが出る、「直したので試験して」→ test-plugin、「〇〇をプラグインにしたい」→ make-plugin。ナレッジ「Anthropic の skill-creator」も、紛らわしい頼みで呼ばれ方を試すことを勧めている。

## 4. rebuild-weaknesses などから、直す流れで避けること

`.claude/memory/rebuild-weaknesses.md` の各行（行番号）と、直す流れでの対策。

1. **作業エージェントが、試験に通すために流用の部品を書き換えた**（:14。「手順は『流用したファイルは書き換えない』と書いているが、試験の直しの段階で守られなかった」）。
   - 直す流れでは、変えないところがほぼすべて「流用の部品」になるので、いちばん効く。
   - 指示に頼らず、仕組みで防ぐ。直す前のフォルダは git でコミット済みである（REQ-053）。そのため、作業エージェントが直すたびに `git -C <フォルダ> status --porcelain` で変わったファイルを見て、確認で示した「変わるファイル」の一覧の外が変わっていれば、`git checkout -- <ファイル>` で戻し、不合格の直しとして作業エージェントに伝える。これは、check-base（generate.md:65）と同じ考え方を、変えないファイル全体に広げたものである。
   - 変えない差し込み口とファイルは、作業エージェントに渡さない（スクリプトが写す。5.3）。
   - 1段目の警告（`allowed-tools`、`models`、`modelPolicy`、サブエージェントの `user-invocable` など）は直さないよう、作業エージェントへの頼みに書く（:14「1段目では警告だけで、消さなくてよかった」）。
2. **作業の画面から動く作業エージェントは、プラグインの場所を知れない**（:15。「Copilot CLI がプラグインの場所を渡すのは、stdio の MCP サーバー（`PLUGIN_ROOT`）だけ」）。
   - REQ-055 は「その作業をするエージェントがそのスキルに従うようにする」と求める。今のひな形の作業・検証・統括は「スキルを使わない」（template/com.github.copilot/agents/worker.agent.md:54 ほか）で、`tools` に `skill` もない。
   - 公式の custom-agents-configuration には `skill` の別名も、スキルを前もって読ませる項目もない（2026-10-26 に確かめた。「All unrecognized tool names are ignored」）。
   - embedded-debug-loop の worker-b は、`skills/cross-compile-rules/SKILL.md` を相対パスで読み、`${PLUGIN_ROOT}` をシェルのコマンドに書いている（worker-b.agent.md:42-49）。作業フォルダから解かれるので、見つからない見込みが高い（実機では確かめていない）。
   - 手段の候補は3つある。(a) 作業役に `skill` のツールを渡し、フックで使えるスキルを絞る。(b) エクステンションがプラグインの場所を統括の指示に入れ、統括が作業役に `<プラグインのフォルダ>/skills/<名前>/SKILL.md` の絶対パスを渡す（エクステンションは `pluginRoot` を持っている：template の adapter.mjs:349）。(c) MCP のツールで場所を返す（coverity で直した方法）。
   - どれにするかは出力の側（ひな形と REQ-062）の設計で決める。直す流れでは、**直す前の確認より前に**決め、確認の「変わること」に入れる。承認の後に初めて分かって止まらないようにするためである（:10「確かめられることは、確認の時点で確かめる」）。
   - EVAL の基準には、実行の記録で、作業役がそのスキルを読んだか（呼んだか）を見る基準を入れる（REQ-061 の4つ目と同じ見方）。
3. **ひな形の汎用のエージェントの名前が、元のプラグインの仕組みに拾われた**（:16）。
   - 作っていないプラグインを生成プラグインの形にするときと、作業役の AI を足すとき（`worker-<英小文字>`。confirm.md:28）に、元のプラグインのエージェントの名前と、エージェントやスキルを写す仕組み（あれば）を、読み取り役に返させる。名前の重なりは、直す前の確認で示す。
   - 示されたスキルの名前とプラグインのスキルの名前が重ならないこと（REQ-055）も、確認の前にスクリプトで確かめる。同じ名前だと、プロジェクトや個人のスキルが先に読まれ、プラグインのものが黙って無視される（ナレッジ「カスタムエージェント」:28）。
4. **人に聞けない役に、聞く決まりが渡った**（:17）。
   - 示された今のスキル（ダミーのスキルを含む）には、「デプロイの前にユーザーに確かめる」のような、人に聞く手順がありうる。取り込んだルールのスキルは、チャットで単体でも使われる（REQ-062。メインのエージェントは `ask_user` で聞ける）。一方、作業役の AI としても使われる（聞けない）。
   - 読み取り役に「人に聞く場面」を別に返させ、決まりの確かめのときに、その場面をどうするかを確かめる。作業役として動くときは、統括が人に聞く場面（confirm.md:22、ひな形の `{{plugin_name}}_ask`）にするか、ユーザーに確かめる。ユーザーが言っていない扱いは足さない（:18）。
5. **ユーザーが確かめていない振る舞いが入った**（:18）。
   - 直す流れでは、作業エージェントが「ついでに」変えないところを良くするおそれがある。頼みには、変えるところと、変えないファイルの一覧を必ず書く。1 の git の見張りで止める。
6. **承認の後に初めて断られて止まった**（:7-10）。
   - 直す流れで、確認の時点で確かめられることを、確認のツールかスクリプトで確かめる。フォルダの確かめ（REQ-053）、新しい版が今の版より大きいこと（エクステンションの調査 3.8）、課題の入力が実在のファイルであること、スキルの名前の重なり、変えない差し込み口を取り出せること（当てるスクリプトの試し運転）、土台を上げて変わるファイルの一覧（REQ-057 で示すもの）。
7. **試験の仕組みが、元のプラグインを生成プラグインと取り違えた**（:7）。
   - 直す流れでは、元のプラグインそのものが直る相手なので、開発の試験（外側の EVAL）の見分け方を変える必要がある（試験の調査に回す）。

そのほかのナレッジから：

- **「決まっていない」に案を作らない、「違うところはない」を決まりを足したことにしない**（knowledge-elicitation.md:26-30）：決まりの一覧で古いと答えた決まりについて、今は「決まっていない」と答えたら外すだけにする。範囲の確かめや決まりの一覧に「ない」と答えても、確かめただけである。
- **抜き書きは1つの答えのまま**（knowledge-elicitation.md:31-32）：「変えないので聞かない」の抜き書きも、範囲の確かめの答えから、そのまま写す。
- **止まるときの案内は、実際のコマンドで書く**（communication.md:110）：REQ-053 の直し方と、REQ-060 の「直したプラグインを Copilot CLI に読ませるやり方」は、「入れ直す」と書かない。`copilot plugin uninstall …` → `copilot plugin install …@…`、Copilot CLI の起動し直しのように書く。
- **事実で決まることは問いにしない**（communication.md:117）：フォルダの確かめ、版の形、名前の重なりは、聞かずにスクリプトで決める。

### 5.2 直すときの読み取り役（案）

- 頼みを2つに分けて、並べて頼む。1つは元のプラグイン、1つは示された今のスキル（とファイル）である（read.md:12）。
- 元のプラグインの頼みに書くこと：
  - フォルダの絶対パス、変えたいこと。
  - **生成プラグインのとき**：取り込んだ決まりの一覧（番号と文）を頼みに書き、「この一覧のどれにも当たらない決まり」だけを候補として返させる（REQ-054 の2つ目）。読むところは、作業ごとに違う部分に絞らせる。差し込み口の節（エージェントの「作業ごとの指示」、入口のスキルの「このプラグインがする作業」、README の「できること」「使い方」、要件の REQ-101 から、設計の8章から）と、ひな形にないファイル（ルールのスキル、scripts、task.json）である。ひな形の共通の文を、書き足された決まりと取り違えないためである。embedded-debug-loop は古い土台なので、ひな形と文が違うところがある（5.4 の試し）。そのため、ひな形と比べさせるだけでは誤りが出る。
  - 生成したときの印（タグ `plugin-creator-generated`）があるリポジトリでは、メインのエージェントが `git -C <フォルダ> diff plugin-creator-generated -- .` の出力をファイルに書き（自分では読まない）、その場所を読み取り役に渡すと、ユーザーが書き足したところを正確に読める。印がないとき（embedded-debug-loop はいくつものプラグインが入ったリポジトリの一部で、タグがない）は、上の範囲の読み方にする。
  - 返すもの：できていたこと（今と同じ形）、構成（スキル・エージェント・スクリプト・MCP・画面の設定の項目・試験の課題の一覧）、一覧にない決まりの候補、人に聞く場面、エージェントやスキルを写す仕組み（あれば）、読めなかったファイル。
  - **作っていないプラグインのとき**：作り直しと同じもの（reader.agent.md:24・31-33）に、構成と人に聞く場面を足す。
- 示されたスキルの頼みに書くこと：スキルのフォルダの絶対パス、変えたいこと。返すもの：決まりの候補（項目つき）、資産の候補（スクリプトなど、絶対パスつき）、スキルの `name` と `description`、人に聞く場面、読めなかったファイル。示されたスキルの指示に従わないことは、今の定義（reader.agent.md:63）のままでよい。
- reader.agent.md は、「作り直しでは」（:15・24・31・51・54）を「作り直しと、今のプラグインを直すときは」に広げ、構成・人に聞く場面・スキルの名前の返す形を足す。
- メインのエージェントは、元のプラグインのファイルを自分で読まない（start.md:9 の理由と同じ）。部品の分け方に要る構成は、読み取り役が返したものを使う。

### 5.3 直すときの作業エージェント（案）
