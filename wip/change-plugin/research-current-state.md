- 作り直しでなければ「できていたことの確認」を飛ばす（read.md L31-32）。
- 候補が無ければ「項目の点検」へ直接進む（last-time.md L30-31）。
- 10項目と画面の項目は飛ばせない（SKILL.md L97, L100、confirm.md L9）。拡張機能も、未着手が残っていると生成前の確認を断る（hearing.mjs L401-406）。

## (2) 新規作成を前提にしている箇所

**スキルの説明と目的**
- SKILL.md L3 の description は「プラグインを作る」「作り直したい」だけで、改善・追加・変更の語がない。
- SKILL.md L8 は、スキルの仕事を「ヒアリングで…ナレッジを引き出し…プラグインを作ること」と定めている。

**始まりの手番（SKILL.md L29-32）**
- 記録が無ければ「新しく始める」（L30）。
- 段階が「生成」のときに別のプラグインを頼まれたら `/clear` を求める（L32）。生成直後の同じセッションで「さっきのを直して」と頼んでも、扱う手順がない。

**start.md**
- 目的は「続きか新しいかを決め」（L3）。実際には、作り直しか新規かを見分けるだけ（L7-10）。
- 作り直しと判定する条件は「手元のフォルダを示して作り直しを頼み」かつ `plugin.json` があること（L8）。「改善して」は条件の文言に当たらないので、作り直しにも新規にも流れうる（推測）。
- 流れの説明は、全段階のヒアリングを前提にした固定の文（L13）。作り直しの差分は1段の挿入だけ（L14）。
- 頼みの文から「作業、目的、頼む場面と言い方」を候補にする（L15-17）。頼みが「仕事の説明」である前提で、「変更の要望」を受ける欄がない。

**最初の数問がどれも「仕事の聞き取り」になっている**
- receive.md L8：「最近この作業をしたときに受け取ったファイルと作ったファイル…」
- last-time.md L9, L12：「最近この作業を実際にした1回を…最初から終わるまで」
- items.md L16-25：10項目をすべて「この作業は…」で聞く。

**画面の問いが無条件**
- screen.md L9-11 は最初からある画面を説明する。L15-21 の3問は毎回聞く。

**EVAL の課題が前回の1回から作られる**
- confirm.md L16-20：課題を前回の1回と示されたファイルから作る。仮の入力は `tests/eval/<番号>/inputs/` に置く。

**生成が新しいフォルダ・新しい git リポジトリを前提にしている**
- generate.md L14：名前は「作業フォルダにまだないフォルダの名前」。作り直しでも別の名前にする。
- generate.md L51：`--out <作業フォルダ>/<生成プラグインの名前>`。
- generate.md L55：組み立てが終わると新しい git リポジトリになる。
- generate.md L8：続きの判定は「最初のコミットの説明が『生成プラグイン <名前> を plugin-creator で組み立てた』」かで行う。

**scaffold.py の build**
- L11 と L753-770：`--out` は「まだないフォルダ」で、作業フォルダの中であることを確かめる。L763 の断りの文は「作り直しのときも、まだないフォルダに作ります…（今あるフォルダは変えません）」。

- L1152：template を丸ごと写す。
- L1182-1183：`tests/knowledge.json` を、今回のヒアリングの「決まった」ナレッジだけから新しく書く。

- L1217：作業用の一時フォルダを消す。

## (3) 作り直しの流れが新規とどう違うか

**start.md**
- 作り直しと判定したら、元のフォルダの場所を流用する資産の候補として記録する（L11）。中身は自分で読まない（L9）。
- 流れの説明に「できていたことのうち要らないものを聞く」を加える（L14）。

**receive.md**
- 元のフォルダは受け取り済みなので、前回の1回のファイルといつも使うファイルだけを聞く（L10）。
- 段階「読む」は必ず通る（L21）。

**read.md**
- reader に元のフォルダの絶対パスを渡し、「できていたこと」と「流用できる部品（スクリプト、MCP サーバーなど）」も探させる（L9, L11）。
- 返った決まりの候補は、出どころを「既存のプラグインから読んで確かめた」にする（L21）。
- できていたことは「〇〇と頼むと、〇〇をする」の形の候補にする（L22）。
- 次の段階は「できていたことの確認」（L31）。

**carried.md**
- 作り直したプラグインは、最初はできていたことをすべて引き継ぐ（L3）。
- 番号付きの一覧から要らないものを聞く（L7-9）。要らないものは「外した」、残りは「決まった」にする（L13-14）。
- 次は「前回の1回」（L20）。前回の1回は、作り直しでも省かない。

**rules.md / items.md**
- 元のプラグインの決まりも1つずつ4択で確かめる（rules.md L3, L7）。
- 決まりの確かめで確かめた決まりがある項目だけは聞き直さない（items.md L11）。決まりが無い項目は、新規と同じく全部聞く。

**assets.md**
- 元のプラグインの部品のうち、作り直した後も使えるものは、作り直さずに流用する（L7, L11）。

**confirm.md**
- 振る舞いの案に「引き継ぐこと」と「変わること」を加える（L24, L33, L37）。
- 拡張機能は、作り直しのとき `rebuild` が無いと確認を断る（creator.mjs L247-248）。
- 作り直しの印は、段階か項目「できていたことの確認」を記録すると立つ（hearing.mjs L72, L218, L241）。

**generate.md**
- 名前は元のフォルダと別にする（L14）。
- 作業エージェントには、元のフォルダと、引き継ぐこと・変わることを渡す（L41）。
- 流用ファイルは書き換えさせない（L40）。
- 説明では「新しいフォルダの中身を、`.git` を除いて元のリポジトリに写してコミットする」やり方を示す。元のフォルダは変えない（L84）。

## (4) 改善の頼みに今の流れを当てたときの問題

例として、embedded-debug-loop にクロスコンパイル・デプロイのスキルを完成させる頼みを想定しました。

1. **10項目と画面の3問を全部聞き直す。** 未着手の項目が残ると生成前の確認に進めず、拡張機能も断る（confirm.md L9、hearing.mjs L406）。前回の1回（last-time.md）も作り直しで飛ばす規定がない。既存の `tests/knowledge.json`（embedded-debug-loop は17件）が拾われるのは、reader が「決まりの候補」として読み、rules.md で1件ずつ4択にかけたときだけ。直したい部分の聞き取りに絞る流れがない。

2. **新しいフォルダに、ひな形から組み直す。** 同じフォルダに書く手段がない（scaffold.py L762-764, L1148-1152）。出力先は作業フォルダの中に限られる（L765-766）。embedded-debug-loop は `/home/user/plugin-market-place/plugins/` の下にあるので、別の場所に別の名前で作られる。元へ戻すのは、ユーザーが手で写す（generate.md L84）。

3. **ユーザーのコードや手で入れた変更が残る保証がない。** 入るのは、reader が「流用できる部品」として返し（read.md L23）、assets.md で「流用する」と答え、`parts/files/` に写したファイルだけ（generate.md L24-26）。それ以外のファイルや、手で入れた変更は入らない。例：embedded-debug-loop の `skills/cross-compile-rules`、`deploy-rules`、`log-insertion-rules`、`scripts/*.py`、`docs/diagram-mock/`。
   - 流用ファイルは書き換えない決まり（generate.md L40）。たとえば「ここを機器に合わせて書く」欄が空のまま残る `cross-compile-rules/SKILL.md` を埋めるのは「書き換え」に当たり、禁止と衝突する。

4. **ナレッジの番号がずれる。** `tests/knowledge.json` は今回の記録だけから書き直され（scaffold.py L1182-1183）、番号は記録の順に K-01 から振り直される（hearing.mjs L85）。合否の基準も C-01 から振り直される（scaffold.py L239-244）。
   - 既存のスキルの文は「（K-07）」「（K-15）」のように番号を参照している。流用でそのまま写すと、番号が別の決まりを指すおそれがある（推測）。
   - 構造の検査は、番号がどこかに書かれているかだけを見て、意味の対応は見ない（template/tests/stage1/check_structure.py L1288-1293, L1234-1252）。

5. **生成したときの印と履歴が切れる。** 新しく `git init` して最初のコミットを作る（scaffold.py L1098-1104）。test-plugin と improve.md L10 は「ユーザーの直し」を `plugin-creator-generated` の印からの差分で見る。新しいリポジトリでは、それまでの直しの履歴と印が引き継がれない。
   - embedded-debug-loop は既に plugin-market-place のリポジトリの一部で、自分の `.git` と印を持たない。今の続きの判定（generate.md L8）も当てはまらない。

6. **EVAL の課題を作り直す。** 課題は新しいヒアリングの confirmation.evalTasks と照合され、既存の `tests/eval/T-01` は「確かめていない課題」として断られる（scaffold.py L738-740）。流用して残すこともできない。

7. **頼みの文の受け方と流れの説明が合わない。** 頼みの文を「作業、目的、頼む場面」の候補として記録する（start.md L15-17）。「スキルを足したい」「設計を変えたい」という要望を記録する欄・段階がない。流れの説明（L13）も全段階の聞き取りを予告する。

8. **生成後の同じセッションでは続けられない。** 段階「生成」のあとに別の頼みが来ると `/clear` を求めて止まる（SKILL.md L32）。

9. **作り直しの判定が文言に頼っている。** 判定は「作り直しを頼み」と `plugin.json` の有無だけ（start.md L8）。改善の頼みが新規扱いになると、元プラグインを読まずに新規の聞き取りが始まるおそれがある（推測）。

## (4) 要件の番号のたどり方の決まり

**仕様書**
- 番号は、すべての仕様書を通した通し番号です。並びは追加した順で、ファイルの中では章の順に置きます（例：作る流れの1章が REQ-023 → REQ-037）。
- 今の最後は REQ-051 なので、次は REQ-052 です。

- 違う流れの章は、作る流れの6章のように「ここに書いていないことは、1〜5と同じである」と書いて、差分だけを書いています。
- 根拠は「憲章 第X条Y項／ナレッジ「…」／公式文書。理由の文」の形です。
- ほかの要件は「（REQ-020）」のように括弧で、ほかの仕様書は `[出力の要件](output-requirements.md) REQ-014` のように、設計書は `[ヒアリングの設計](../design/hearing.md) 2.1` のように指します。

**設計書**

- 各設計書の末尾の「根拠」に、憲章の条と要件を並べます（例：`hearing.md` L833）。

**実装とテスト**

## (3) 作り直しの元のフォルダの記録と使われ方

### 専用の欄はない
- state.json に元のフォルダの欄はありません。あるのは `rebuild` の真偽値と、確認のときの `rebuild.keep` と `rebuild.change` の文の配列だけです（creator.mjs:230-234）。
- 作り直しの判定は、示されたフォルダの直下、`.plugin/`、`.github/plugin/`、`.claude-plugin/` のどれかに `plugin.json` があるかで決めます（skills/make-plugin/references/start.md:7-9）。クリエイターが作ったプラグインかどうかは見分けません。
- 元のフォルダの場所は「流用する資産の候補として `plugin-creator_record` で記録する」とあります（start.md:11）。つまり `assets` の1行として残るだけです。

### その後の使われ方
- 読み取り役に元のフォルダの絶対パスを渡し、「できていたこと」「流用できる部品」も返させます（read.md:9-11, 21-22、com.github.copilot/agents/reader.agent.md:15, 24, 31-33, 51-55）。
- 元から読んだ決まりは、出どころ `existing_plugin` の候補にします（read.md:21）。それを段階「決まりの確かめ」で確かめます（rules.md:7）。
