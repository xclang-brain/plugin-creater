## 2. 設計図からのずれ（理由つき）

1. **最終確認の置き場所**：BLUEPRINT 1.2 は「`agent_ran` が見る `agentName` の形」も hearing.md 14章に足すとしているが、testing.md 9章（最終確認）に置いた。ヒアリングでなく test-plugin の EVAL のことで、9章が EVAL の最終確認の一覧のため。あわせて C3 のメモの「エージェントが動かすシェルが `PATH` を受け継ぐか」も 9章に置いた。「インストールした写しのルールのスキルを作業エージェントが読めるか」は BLUEPRINT のとおり hearing.md 14章（H25）に置き、generated-plugin-structure.md 4.7 から指した。
2. **5 C5 の表にない節も直した**：creator-structure 3.1・3.5、hearing 3.2・6.1・9章・10.1・13章、generated-plugin-structure 3.4・4.3・8章・9章、testing 2章・9章・10.3。要件から節をたどれるようにすることと、C1・C3 のメモの頼み（9章のツールの表、4.3 の指示文）のため。
3. **creator-structure 4.1 の見出しを変えた**（「生成した直後と直した後の試験と直し」）。直す流れの試験と直しを同じ節に置いたため。見出しの文字で指している所は、ほかになかった（grep で確かめた）。
4. **確認のツールの断る順**：BLUEPRINT 4.1 には順の決まりがないので、C1 の実装（メモの3章）のとおりに書いた（4 を直すときの内容と版に広げ、7 の後に「変えたところを試す課題がない」を足して、10 まで）。
5. **ルールのスキルのフロントマター**：BLUEPRINT は「S1〜S9 を短く」とだけ書く。C3 の `worker.agent.md` の実装（`name` と `description`、要るときだけ `license`・`compatibility`・`metadata`、`allowed-tools` は書かない）に合わせた。
6. **`${PLUGIN_ROOT}` の理由の書き方**：C3 は「展開されるのは mcp.json の stdio のサーバーの設定だけ」と言い切るが、BLUEPRINT D38 は「展開されない見込み」なので、設計書では「見込み」と書いた。

## 3. 統括に知らせること（取り決め・ほかの組）

- 取り決め I1〜I11 は、設計書の文として写しただけで、変えていない。
- testing.md 6.8 の観点の名前、7章の置き場所（`tests/dev-eval/device/`、作業フォルダの `.device/`、`inner/eval.json`・`inner/standalone.json`、腕 `standalone`）、6.9 の頼みの8件、6.8 の `persona.json` の項目（`kind`・`workspace`・`target`・`device`・`expect`）は、BLUEPRINT 5 C6・7.3 のとおりに書いた。C6・C4 が実装で名前や件数を変えたら、設計書も合わせる必要がある（C6 はこのメモを書いた時点で作業中）。
- creator-structure 3.4 の子コマンドの説明は C2 のメモの実装に合わせたが、C2 がメモに書いた細かい足し（`change` が `manifest.json` の名前の違いを断る、`change` でも版を確かめる、変更がないときの `commit` など）は、設計書には書いていない（KISS。実装の細部のため）。要るなら足す。
- 仕様の直し（BLUEPRINT 8.2 の2つ）は、仕様に入っていることを確かめた（REQ-057・059 の作業用の一時フォルダ、REQ-062 の入口のスキルの除外）。設計書はこの仕様の文に合わせた。

### 退けたこと・頼みと違えたこと

- **ルールのスキルの description の書き方を、設計書のほうを実装に合わせた**（generated-plugin-structure 4.9、hearing 10.1）。前の設計書（点検1で私が書いたもの）は「入口のスキルと同じ形（何ができあがるかの短い1句、呼ばれる場面、呼ばれてはいけない似た頼み、日本語）」だったが、C4 の `change-confirm.md` は「Agent Skills の仕様のとおり、何をするかといつ使うか、ユーザーが頼みに使った言語、1行・1024文字以内、`<`・`>` なし、誰が読むかを書かない」にした。頼みが「実装に合わせる」で、実装の形は公式の仕様に沿い、設計図に決めがないため、設計書を実装に合わせた。hearing 10.1 の形は、クリエイターのスキルと入口のスキルだけに当てはまるとした。入口のスキルと同じ形に戻すなら、C4 の change-confirm.md 2 を直す。
