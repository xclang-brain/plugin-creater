## 診断・better_fix からのずれ・決めたこと

1. 一時フォルダの残りを消すのは、change-start.md の5（`change-check` が `"ok": true` を返した後）にした。段階「始まり」では、このセッションはまだ `<W>` に書かない（`<W>` に初めて書くのは、段階「読む」の印のタグからの差分）ので、記録がまだないときも、記録が段階「始まり」で残っているときも、残りは前の直しのものと決まる。前の6の「新しく記録を作ったとき」の条件は要らなくなった。
2. 5で消した後に `change` が断ったとき（決まりの一覧の項目の名前が合わないなど）も、`<W>` は消えたままになる。前の直しの残りなので、古い下見を使わない点では同じである。同じ作業フォルダで別のセッションが途中で止まっているときに消してしまうのは、前の形（記録を作ったら消す）と同じ。
3. `change` の返り値の2行目は、「まだ書いていなければ」の条件を外し、「次は、ほかのツールを呼ぶ前に、まず、これからの流れをチャットの文に書いてください。」にした。新しく記録を作ったときにだけ付く行で、そのときは流れをまだ書いていないためである（読み直した後の扱いは change-start.md の7のまま）。返り値にファイルの名前（change-start.md の7）は書かない（拡張の返り値は、スキルのファイルの番号を指さない）。
4. (2) の「答えの言葉は抜き書きに使ってよい」は、確かめて正しいと答えたときの記録の抜き書きに、一覧の答えの言葉を使ってよい、と読んだ（better_fix の括弧の置き場所が「確かめる」の後ろのため）。「違う」と答えたときには使わない。
5. (3) の「同じ中身の新しい番号が2つあれば、その1か所に両方の番号を添える」は、(2) の後に起こりうる形（下の残り1）で、同じ行がまた2か所になるのを防ぐために足した。worker.agent.md の B の「合否の決め方と手順が同じことを言うときは1か所にまとめて両方の番号」と同じ形である。

### 指摘の直し方からのずれと、採らなかったこと

1. 指摘3の1つにまとめる文は、指摘の案（表の「元のプラグインの決まりの候補」の行）でなく、表の後の項に置いた。消した3の文は、示されたスキルの候補（出どころ「ファイルから読んで確かめた」）も対象にしていたので、表の1行に置くと、示されたスキルの候補の扱いが抜けるためである。3の文の「一覧の決まりは4で確かめる」の部分は、4の「範囲の確かめの答えで…この問いは省かない」と記録のツールの断りで足りるので、移していない。
2. 指摘3の文から、前の直しの「（正しいと答えたら、抜き書きに、この答えの言葉を使ってよい）」を外した。指摘の案の文にないことと、確かめの問いへの答えを抜き書きにするふつうの形で足りるためである（KISS）。
3. 指摘2の「確認でメインが『文は今のまま残す』と決める側（change-confirm.md か change-apply.md）に1行置く」は採らなかった。4回目の「文は今のまま残す」は、候補を確かめずに外したことから出たもので、指摘3と前の (2) の直しで、その外し方を止めている。確かめて正しいと答えた候補は「足す決まり」になり、change-confirm.md の「入れない決まり…ほかは文を今のまま残す」には入らない。change-confirm.md は 19,979 バイト（余り21バイト）、change-apply.md は 19,929 バイトで、1行を置くにはほかの文を削る必要もある。
4. 頼みに「残して」とはっきり書かれたときの、頼みと D の新しい項の先後は書いていない。作業エージェントは頼みに従う（確認でユーザーがよいと答えた内容のため）。残すと頼まないよう、メインの側（上の3）で止める。
5. 流れの文を返り値に移したので、change-start.md の7には流れの例を残していない（流れの文を2か所に持たない）。記録がもうあるときの返り値（「記録は、もうあります」）には、流れの文を入れていない。読み直した後に流れが書かれていないことは、記録を作ってから段階を進めるまでの数秒の間にコンパクションが起きたときだけで、まれなため（KISS）。
