## 2. 設計図からのずれ（理由つき）

1. **`plugin-creator_change` の返り値の文（取り決め I7）**：作っていないプラグインのときの文を「決まりの一覧（tests/knowledge.json）と com.github.copilot/extensions/<name>/task.json がそろっていないので、plugin-creator が作っていないプラグインとして扱います。読み取った決まりは、1件ずつ確かめてください。新しい決まりは K-NN から付きます。」にした。理由：①`words.test.mjs` が、ユーザーに見える文を持つソースに「クリエイター」を書くことを禁じている（X2-18）。②D29 では task.json がないときも作っていないプラグインになるので、knowledge.json だけを理由に書くと誤り。生成プラグインのときの文は設計図のとおり（件数が1件のときは「K-01 の1件」）。足したもの：決まりが0件の生成プラグインの文、同じフォルダで呼び直したときの文（「直すプラグインの記録は、もうあります（…）。変えたいことを置き換えました。決まりは取り込み直していません。」）、今の版がないときは「今の版 なし」。
2. **状態取得の3行目（I7）**：作っていないプラグインのときだけ「引き継いだ決まり：0件（plugin-creator が作っていないプラグインなので、読み取った決まりは1件ずつ確かめる）」と括弧を足した。N は取り込んだ数（`change.carried` の数）。
3. **`applyChange` の引数**：`{ folder, wants, plugin }` でなく `{ folder, wants, readPlugin }`（読み取りの関数）。作る記録・違うフォルダの断りを、プラグインを読む前に出すため。内部の関数で、取り決めではない。
4. **`confirmWord` の置き場所**：`creator.mjs` でなく `hearing.mjs`（creator・report も使う）。`change.mjs` は `hearing.mjs` の `Refusal` を使うので、循環を避けた。
5. **`readPluginForChange` の返り値**：`taskRel`（task.json の場所）を足した（返り値の文に使う）。記録の `change` には入れない（I1 の形のまま）。
6. **`maxId`**：生成プラグインでないときも、knowledge.json があればその番号を数える（I1 は「carried と removed の最大」）。生成プラグインでは同じ値。作っていないプラグインの knowledge.json の番号と、新しい番号が重ならないようにするため（大きい側に倒れるだけで、組み立ての②の確かめには必ず合う）。
7. **D29 の読み方を組み立て（C2 の `plugin_kind`）にそろえた**：knowledge.json は一覧か、task.json は `{ }` かだけを見て、合わなければ断る。生成プラグインのときだけ、行の形（番号・種類・聞くこと・文）、knowledge-removed.json、task.json の `criteria`、eval.json の prompt を確かめ、壊れていれば断る。作っていないプラグインでは、中身の形と knowledge-removed.json を見ない。
8. **`unchanged` → `unchanged`**：同じ状態にし直すのは受け付ける（コンパクションの後の呼び直しで断らないため）。聞いた・決まりなし・保留からは断る（「未着手からだけ」はこのとおり）。
9. **作るときに `version` を渡すと断る**（「新しい版の案（version）は、今のプラグインを直すときだけ渡してください。」）。設計図は「直すときだけ記録」とだけ書いている。黙って捨てないため。
10. **付け直した元の行**：「決まった」に戻すことに加え、直すことも外すことも断る（「K-05 は、中身を直して K-06 にしました。直すときは K-06 を渡してください。」）。付け直した新しい行を「外した」にすれば、元の行をまた扱える（元に戻す道）。
11. **付け直した新しい行の欄**：状態は渡されなければ「決まった」、出どころは渡されなければ「ヒアリングの答え」、`itemName` は項目の日本語の名前。元の行の `quote` は付け直しの抜き書きで上書きする。
12. **`confirmationView.change`**：設計図の欄に `name` を足した。`hearingView.change` は `{ folder, name, version, generated, wants, carried(件数) }`。
13. **ツールの並び**：`change` は DEFS の最後に足した（今までのツールの並びを変えないため）。

## 3. 統括に知らせること（取り決め・ほかの組）

- **C5（そのほか）**：hearing.md 7.1〜7.3 の記録の欄（`change`、`unchanged`、`carried`、`replaces`、`confirmation.version`・`criteria`）、8章の差し込みの文、generated-plugin-structure.md 9章のツールの表（9つ）。
- **C4（change-plugin のスキル）**：①`rebuild.change` の文は、画面で1件ずつ並ぶので、下見の結果（上書きされる土台のファイル、消すファイル、1段目で落ちるところ、重なる機能、名前の重なり、試せない本物の手順）は、それぞれ別の項目にするとよい。②「変えないので聞かない」の抜き書きは、範囲の確かめの答え（ask_user の答えか打った発言）から写す必要がある（頼みの文は数えない）。③決まりの一覧の問いの答えは、record に番号つきで一度に渡せる（`{ id, status: '決まった', quote }` を並べる）。違う・古い決まりは、文などを渡せば、エクステンションが新しい番号に付け直し、返り値に「K-15 の中身を直したので、K-15 を外して K-18 にしました」と出る。④`plugin-creator_change` は、同じフォルダなら何度呼んでもよい（取り込み直さない）。
- **C2**：記録の `confirmation.criteria` は `[{ id, knowledge }]`、番号の小さい順の決まりから作る。取り込んだ行の `itemName` は knowledge.json の `item` の文字のまま（4.2 の①で比べられる）。付け直した新しい行の `itemName` は項目の日本語の名前。
