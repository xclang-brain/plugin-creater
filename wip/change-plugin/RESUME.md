# 改善・設計変更（change-plugin）：中断に備えたメモ（再開用）

改善・設計変更の機能を足す作業の途中経過である。憲章・仕様書・設計書・実装資産のどれでもない。作業が終わったら、このフォルダは消す（残すべきことはナレッジ `.claude/memory/` に移す）。

## ユーザーの指示（2026-10-26、原文の要旨）

1. 既存プラグインの改善・設計変更を本格的に仕様に足す。決まったことは `decisions.md`。仕様は `docs/specs/improvement-requirements.md`（REQ-052〜061）。
2. 仕様の後は、ユーザーに質問せず、すべて自律的に進める。設計 → 実装 → 試験まで行う。
3. 試験は embedded-debug-loop（`xclang-brain/plugin-market-place` の `plugins/embedded-debug-loop`）を題材にする。
4. 既存のクロスコンパイルとデプロイのスキルを、ダミーで作る。スキルの仕様には沿うが、plugin-creator とは無関係のものにする。無関係のものを理解して取り込めるかが大事。
5. 生成プラグインの部品は疎結合で、モジュール強度が高く、単体でも動くことが望ましい（例：クロスコンパイルのスキルは、単体でも完結していると素晴らしい）。
6. 実機は使えないので、エミュレーターを用意して試験する。

## 決めたこと（自律で決めた設計上の判断）

- D1 擬似の機器：emulator.md の KX-200 の形（kxemu.py をサンドボックスの外で動かし、メーカーの道具 `kxtool` を PATH の先頭に置く。サンドボックスからは、プロキシを通した HTTP の1ポートだけを許す）。ダミーのスキルは KX-200 向けに書き直す（skill-spec.md の KF-7 案は使わない）。
- D2 置き場所：擬似の機器は `tests/dev-eval/device/`、ダミーのスキルと改善の模擬ユーザーは `tests/dev-eval/personas/`（kind: change）と `tests/dev-eval/fixtures/`。
- D3 エージェントがルールのスキルを読む手段：土台の直し。統括への最初の指示に、プラグインのフォルダの絶対パスを入れ、エージェントは SKILL.md を絶対パスで読む。すべての生成プラグインに効く。
- D4 土台を上げる：元のプラグインから差し込み口の中身を取り出し、今のひな形で描き直す（scaffold.md の案）。土台のファイルで今の版と違うものは、直す前の確認で一覧にして示す（上書きされることを伝える）。作ったときの版の記録は足さない（KISS）。
- D5 外した番号：別のファイル `tests/knowledge-removed.json`（knowledge.json を読む箇所を変えずに済む）。
- D6 記録：`state.change`（直すフォルダ、名前、今の版、クリエイターが作ったか、取り込んだ番号、これまでの最大の番号）。項目の状態に「変えないので聞かない」を足す。段階の名前は変えない。
- D7 始める前の確かめ（REQ-053）：`scaffold.py change-check`（エクステンションは子プロセスを gh にしか使わない決まりのため）。
- D8 作業用の一時フォルダ：今までどおり `<作業フォルダ>/.plugin-creator-work/`。change-check の未コミットの確かめとコミットからは外し、終わったら消す。ひな形の .gitignore にも足す。
- D9 印のタグ：リポジトリの直下のプラグインは `plugin-creator-generated`、サブフォルダのプラグインは `plugin-creator-generated-<name>`。直すたびに付け直す。improve.md の差分はフォルダに絞る。
- D10 部品の独立性（REQ-062）：入口のスキルは除く。ルールのスキルとそのスクリプトは、そのスキルのフォルダに置く（worker.agent.md の `files/scripts/` の決まりを直す）。
- D42 ルールのスキルの description：直すときはメインが決めて渡し、作るとき（make-plugin）は今までどおり作業エージェントが書く（統合の直しで作る流れを壊さないため）。
- D11 試験：外側の EVAL（改善の模擬ユーザー）、内側の確かめ A（直したプラグインで、擬似の機器を相手にデバッグの課題）、B（ルールのスキルだけに頼む単体の試験。REQ-062）。
