# {{plugin_name}} の仕様書

{{plugin_name}} が、ユーザーから見てどう振る舞うかを定める。上位は [憲章](../constitution.md) である。

- 1つの要件は、要件（満たすべきこと）、根拠（もとになった憲章の条）、受け入れ基準（満たしたと判断できる条件）の3つで書く。
- 1章〜6章の共通の要件は、plugin-creator が作るどのプラグインにも同じ番号で入っている。作業ごとの要件は、7章に REQ-101 から付ける。

## 1. 受け取るもの

### REQ-001 受け取るもの

- 要件：ユーザーは、{{plugin_name}} のリポジトリ一式を手にできる。そこには、プラグイン本体とテストに加えて、憲章・仕様書・設計書が入っている。テストには、構造の検査と部品の試験を1つのコマンドで動かすものと、EVAL（実際のモデルで課題を実行して採点する試験）の課題と合否の基準が入っている。
- 根拠：憲章 第6条1項
- 受け入れ基準：
  - リポジトリに、憲章・仕様書・設計書・プラグイン本体・テストがそろっている。
  - テストに、構造の検査と部品の試験を動かすコマンドと、EVAL の課題（入力のファイルを含む）と合否の基準がある。

### REQ-002 憲章

- 要件：ユーザーが {{plugin_name}} の憲章を読むと、次の2つが書かれている。
  - 成果物の優先順位は、憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 であること
  - 開発と保守は、憲章 → 仕様書 → 設計書 → 実装資産 の順に行うこと
- 根拠：憲章 第6条2項、第7条
- 受け入れ基準：
  - 憲章に、上の2つが書かれている。

### REQ-003 要件のたどり方

- 要件：ユーザーは、仕様書の要件の番号から、その要件を実現している設計書の箇所・実装資産・テストをたどれる。
- 根拠：憲章 第6条3項
- 受け入れ基準：
  - 仕様書のどの要件からも、設計書の箇所・実装資産・テストを番号でたどれる。

## 2. インストール

### REQ-004 インストール

- 要件：ユーザーは、{{plugin_name}} を Copilot CLI にインストールし、すべての機能を使える。{{plugin_name}} は、Agent Plugins 1.0.0 の形式に沿っている。使うには、次の準備が要る。この準備は、README に書かれている。
  - Copilot CLI の試験的機能を有効にする（初めて使うときに `copilot --experimental` で起動する。次からは付けなくてよい。起動した後なら `/settings experimental on`）。
  - {{plugin_name}} を読み込むときにチャットに出る確認を許可する。確認で「このフォルダでは常に許可」を選ぶと、そのフォルダでは次から確認が出ない。

  準備をしていないときにチャットで作業を頼むと、直し方が示され、作業は始まらない。
- 根拠：憲章 第5条、第9条1項／Agent Plugins 1.0.0／Copilot CLI プラグインリファレンス。Copilot CLI 1.0.98 では、Web管理画面を出す仕組みは試験的機能で、有効にしないと使えない
- 受け入れ基準：
  - Copilot CLI でインストールし、README の準備をすると、{{plugin_name}} の機能を使い始められる。
  - README に、上の準備が書かれている。
  - 準備をしていないときにチャットで作業を頼むと、直し方が示される。
  - Agent Plugins 1.0.0 の公式スキーマの検査に通る。

## 3. 使い始める

### REQ-005 Web管理画面

- 要件：ユーザーが Copilot CLI のチャットで {{plugin_name}} に作業を頼むと、Web管理画面の URL が示される。ユーザーは、ブラウザーでこの画面を開き、開始前の設定をして開始ボタンを押す。実行中の監視と、終了後の結果確認も、この画面で行う。

  実行中にエージェントが求める確認（ファイルの書き込みやコマンドの実行の許可、AI クレジットの上限の確認、エージェントからの質問、統括エージェントが人に判断を求める質問〔REQ-051〕）には、Copilot CLI のチャットで答える。画面には、チャットで確認を待っていることと、何の確認かが示される。任せたいツールを前もって許可するしかたは、README に書かれている。
- 根拠：憲章 第20条〜第22条／Copilot CLI コマンドリファレンス（ツールを前もって許可するしかた）
- 受け入れ基準：
  - チャットで作業を頼むと、Web管理画面の URL が示される。
  - 示された URL を開くと、Web管理画面が表示される。
  - 開始ボタンを押すと、チャットでもう一度頼まなくても、頼んだ作業が始まる。
  - 設定・監視・結果確認が、すべてこの画面でできる。実行中の確認への答えは、チャットで行う。
  - 実行中にエージェントが確認を求めると、画面に、チャットで確認を待っていることと、何の確認かが示される。
  - README に、任せたいツールを前もって許可するしかたが書かれている。

### REQ-029 サーバーの起動と終了

- 要件：ユーザーがチャットで作業を頼むと、Web管理画面のサーバーが起動する。使いたい番号（ポート）をほかのプログラムが使っていても、空いている番号で起動する。Copilot CLI を終えると、サーバーも終わる。
- 根拠：憲章 第20条1項
- 受け入れ基準：
  - チャットで作業を頼むと、サーバーが起動し、示された URL で画面が開ける。
  - いつもの番号をほかのプログラムが使っていても、別の番号で起動し、その番号の URL が示される。
  - Copilot CLI を終えると、サーバーのプロセスが残らない。

### REQ-006 接続の制限

- 要件：Web管理画面は、最初の設定では、{{plugin_name}} を動かしているマシンのブラウザーからしか開けない。
- 根拠：憲章 第20条2項
- 受け入れ基準：
  - 最初の設定で、同じマシンのブラウザーからは開ける。
  - 最初の設定で、ほかのマシンからは開けない。

### REQ-007 開始前の設定

- 要件：ユーザーは、開始前に Web管理画面で次を設定できる。
  - 役割（統括・作業・検証）ごとに使うモデル。最初は、統括と検証に思考力の高いモデル、作業に費用の低いモデルが選ばれている。
  - エージェント（統括、作業エージェントのそれぞれ、検証）ごとの思考の深さ（Copilot CLI の reasoning effort）。最初は「変えない」が選ばれていて、エージェントの定義のとおりに動く。
  - 繰り返しの上限の回数

  Copilot CLI のモデルが Auto（Copilot CLI がモデルを自動で選ぶ設定）のときは、役割ごとのモデルが効かないことがあり、そのことと、実際に動いたモデルが画面に示される。
- 根拠：憲章 第20条1項／Copilot CLI の決まり（モデルが Auto のときは、カスタムエージェントの定義に書いたモデルが効かない）
- 受け入れ基準：
  - 設定を変えて開始すると、変えた設定で実行される。ただし、モデルが Auto のときの役割ごとのモデルと、選んだモデルが受け付けない思考の深さは除く。
  - モデルが Auto のとき、役割ごとのモデルが効かないことがあることと、エージェントごとに実際に動いたモデルが、画面に示される。

### REQ-031 作業ごとの画面

- 要件：Web管理画面には、共通の表示に加えて、{{plugin_name}} を作るときにユーザーと決めた、その作業だけの設定・実行中の表示・結果の見せ方がある。これらは、作業の定義（`task.json`）に決まった形で書かれ、共通の画面の部品で表示される。
- 根拠：憲章 第20条〜第22条
- 受け入れ基準：
  - ユーザーと決めた設定と表示が、すべて画面にある。
  - その作業だけの設定を変えて開始すると、変えた設定で実行される。

## 4. 実行中

### REQ-008 実行中の表示

- 要件：実行中、ユーザーは Web管理画面で次を見られる。表示は、ページを再読み込みしなくても更新される。
  - 各エージェントの役割（統括・作業・検証）、状態、担当している作業
  - 今が計画・実行・評価のどれか
  - エージェント間のデータの受け渡しを表した図

  実行中に Copilot CLI で `/clear`（チャットの会話を消すコマンド）をすると、画面の更新が止まり、前の画面の URL では開けなくなる。このときは、チャットでもう一度頼み、示された画面を開くと、前の実行が途中で切れたことが示される。実行中は `/clear` をしないよう、画面とチャットで示される。
- 根拠：憲章 第19条1項、第21条／Copilot CLI 1.0.98 では、`/clear` をすると、Web管理画面を出す仕組みが読み込み直され、画面のサーバーも止まる
- 受け入れ基準：
  - 実行中に、上の3つが表示される。
  - 統括エージェント1体、作業エージェント1体以上、検証エージェント1体が表示される。
  - エージェントの状態が変わると、再読み込みしなくても表示が変わる。実行の最初から最後まで、更新が止まらない。ただし、実行中に `/clear` をしたときは除く。
  - 実行中に `/clear` をした後に、チャットでもう一度頼み、示された画面を開くと、前の実行が途中で切れたことが示される。
  - 実行中は `/clear` をしないことが、画面とチャットで示される。
  - 画面の表示が、実際の状態とずれない。たとえば、終わったエージェントが「実行中」のまま残らない。

### REQ-009 止める

- 要件：ユーザーが Web管理画面の止めるボタンを押すと、作業の途中でも、この実行の統括・作業・検証のエージェントが止まる。ユーザーがチャットでしているほかの作業は止めない。押してから10秒を目安に、画面が終了の表示になる。止めきれないエージェントが残ったときは、そのエージェントと止め方が画面に示され、そのエージェントはツールを使えない。
- 根拠：憲章 第21条
- 受け入れ基準：
  - 止めるボタンを押すと、この実行の統括・作業・検証のエージェントが止まり（止めきれないエージェントは下のとおり示される）、押してから10秒のうちに画面が終了の表示になる。
  - 止めるボタンを押しても、チャットでしているほかの作業は止まらない。
  - 止めた後に、ツールを使って作業を続けるエージェントがない。
  - 止めきれないエージェントが残ったときは、そのエージェントと止め方が画面に示される。

### REQ-010 作ることと判定することの分担

- 要件：成果物の合否は、成果物を作った作業エージェントではなく、検証エージェントが判定する。検証エージェントは成果物を直さず、指摘だけを統括エージェントに返す。
- 根拠：憲章 第19条2項
- 受け入れ基準：
  - 結果に示される合否は、すべて検証エージェントが出したものである。
  - 検証の前と後で、成果物の中身が変わっていない。

### REQ-011 計画・実行・評価の繰り返し

- 要件：{{plugin_name}} は、計画 → 実行 → 評価 を1回の試行として繰り返す。毎回、実行の前に評価基準を決め、検証エージェントの指摘を次の計画に生かす。評価基準には、{{plugin_name}} を作るときにユーザーと確かめた合否の基準（作業の定義 `task.json` の合否の基準）が必ず入る。統括エージェントは評価基準を足せるが、ユーザーと確かめた基準を外したり、ゆるめたりはしない。頼まれた作業の文が、ユーザーと確かめた合否の基準と食い違うときは、基準を優先する。統括エージェントは、頼みの文の食い違う部分を使わないことを、計画とまとめに書き、画面で見せる。基準を変えたいときは、ユーザーが {{plugin_name}} を直す。評価基準をすべて満たしたら終わる。満たさないまま上限の回数に達したら止まる。人の判断待ちの答えで、終えるよう言われたときも終わる（REQ-051）。
- 根拠：憲章 第23条
- 受け入れ基準：
  - ユーザーは、試行ごとに、評価基準と、評価基準ごとの合否・指摘を見られる。
  - どの試行の評価基準にも、ユーザーと確かめた合否の基準がそのまま入っている。
  - 頼みの文が合否の基準と食い違う実行では、基準で判定される。頼みの文の使わなかった部分が、計画とまとめに書かれ、画面で見られる。
  - 2回目以降の試行の計画に、前の試行の指摘への対応が含まれている。
  - 評価基準をすべて満たした試行で、繰り返しが終わる。
  - 上限の回数に達すると、繰り返しが止まる。

### REQ-051 人の判断待ち

- 要件：{{plugin_name}} を作るときにユーザーと決めた、人が判断する場面（作業ごとの指示に書かれている）になると、統括エージェントは人に質問して待つ。待っているあいだも、実行は終わらない。
  - Web管理画面には、「人の判断待ち」と、質問の文と、チャットで答えてほしいことが示される。
  - チャットにも、同じ質問が示される。
  - ユーザーがチャットで答えると、その答えが、要約も言い換えもされずに統括エージェントに渡り、同じ実行が続く。試行の番号と繰り返しの上限の回数は、待つ前のまま続く。計画・実行・評価の記録も、1つの実行の結果にまとまる。
  - 答えが、ここで終えるよう言っている（例：「やめて」「ここで終わりにして」）ときは、統括エージェントは、評価基準を満たしていなくても、上限の回数に達していなくても、そこで繰り返しを終え、ほかの終わり方と同じく、まとめと Issue の案を作る。終わった理由は「人の指示で終えた」になる。それまでの試行の結果と、Issue の案は残る。
  - 判断を任せる答え（例：「判断して進めてください」）では、統括エージェントは終えずに続ける。
  - 終えるよう言っているかがはっきりしない答えでは、統括エージェントは終えずに、もう一度人に聞く。答えが終えるよう言っているかは、統括エージェントが答えの言葉から決める。
  - 「人の指示で終えた」で終わるのは、終えるよう言う答えが届いた、その直後だけである。人の答えが届いていない実行と、続けるよう言う答え（例：「続けて」）の後は、統括エージェントが自分の判断で「人の指示で終えた」で終えることはない。
  - 後で終えるよう言う答え（例：「あと1回だけ試して、だめなら終えて」）では、統括エージェントは、いまは終えずに続ける。言われた試行が評価基準を満たさず、まだ上限の回数に達していないときは、終えるかを、もう一度人に聞いて待つ（例：「試行 2 も評価基準を満たしませんでした。ここで終えますか？」）。聞かずに終えることはない。
  - 待っているあいだも、止めるボタンで止められる（REQ-009）。
  - 待っているあいだに `/clear` をするか Copilot CLI を終えると、ほかのときと同じく、実行は途中で切れる（REQ-008、REQ-012）。
  - 答えを統括エージェントに渡せなかったときは、そのことがチャットで示され、実行は「途中で終わった（人の答えを統括エージェントに渡せなかった）」で終わる。
  - 渡せたかが分からなかったとき（時間切れ）は、そのことがチャットで示され、実行は人の判断待ちのまま残る。ユーザーは、もう一度チャットで答えるか、止めるボタンで止められる。前の答えが届いていて統括エージェントが続きを始めていれば、もう一度は渡さない。
- 根拠：憲章 第21条、第23条
- 受け入れ基準：
  - 統括エージェントが人に質問すると、実行は終わらず、画面に「人の判断待ち」と、質問の文と、チャットで答えてほしいことが示される。
  - チャットに、同じ質問が示される。
  - チャットで答えると、答えがそのまま統括エージェントに渡り、同じ実行が続く。続いた後の試行の番号は、待つ前の続きで、上限の回数は変わらない。終わった後の結果に、待つ前と後の試行が、1つの実行としてまとまって示される。
  - 評価基準を満たしていない試行の後の判断待ちに「やめて」と答えると、上限の回数に達していなくても、まとめと Issue の案が作られて実行が終わり、終わった理由に「人の指示で終えた」が示される。それまでの試行の評価基準・合否・指摘と、まとめと、統括エージェントが足した Issue の案が、結果に示される。
  - 終えるよう言っていない答えでは、実行が続く。
  - 人の答えが一度も届いていない実行は、「人の指示で終えた」で終わらない。
  - 「続けて」と答えた実行は、その後にもう一度聞かれて終えるよう答えるまで、「人の指示で終えた」で終わらない。
  - 「あと1回だけ試して、だめなら終えて」と答えると、もう1回試行する。その試行が評価基準を満たさず、上限の回数に達していなければ、終えるかを聞く質問が、画面とチャットに示される。そこで「終えて」と答えると、まとめと Issue の案が作られ、「人の指示で終えた」で終わる。
  - 待っているあいだに止めるボタンを押すと、REQ-009 のとおりに止まる。
  - 人の答えを待っていた時間は、課題の一覧の「エージェントが詰まったり止まったりしていないか」に数えない。
  - 答えを統括エージェントに渡せなかったときは、渡せなかったことがチャットで示され、実行が「途中で終わった（人の答えを統括エージェントに渡せなかった）」で終わる。
  - 渡せたかが分からなかったときは、そのことがチャットで示され、実行は人の判断待ちのまま残る。もう一度答えると、統括エージェントが待ったままなら渡り、続きを始めていれば渡さない。答えが統括エージェントに2回届くことはない。

## 5. 終了後

### REQ-012 結果の確認

- 要件：終了後、ユーザーは Web管理画面で次を見られる。
  - 各エージェントの実行結果
  - 検証結果（評価基準ごとの合否と指摘）
  - 実行全体のまとめ
  - 終わった理由（評価基準をすべて満たした、上限の回数に達した、人の指示で終えた〔REQ-051〕、ユーザーが止めた、途中で終わった のどれか）。途中で終わったときは、その理由（例：統括エージェントの失敗、チャットからの中断、AI クレジットの上限、`/clear` で切れた、人の答えを統括エージェントに渡せなかった）も示す。

  止めきれなかったエージェントがあったときは、終わった理由にそのことを添えて示す。
- 根拠：憲章 第22条
- 受け入れ基準：
  - 終了後に、上の4つが表示される。
  - わざと途中で終わらせた実行で、「途中で終わった」ことと、その理由が示される。
  - 止めきれなかったエージェントがあった実行で、終わった理由にそのことが添えて示される。

### REQ-013 課題の一覧

- 要件：終了後、ユーザーは Web管理画面で、今回の実行で見つかった課題の一覧を見られる。課題は、実行の記録を振り返り、次の観点で洗い出されている。
  - 何かの実行に失敗していないか
  - エージェントが詰まったり止まったりしていないか
  - データがきれいに流れているか

  最後まで繰り返したとき（評価基準をすべて満たした、上限の回数に達した）と、人の指示で終えたとき（REQ-051）は、統括エージェントが記録を振り返って課題を足す。ユーザーが止めたときと、途中で終わったときは、エージェントを動かさず、実行の記録から機械的に分かる課題だけを示す。
- 根拠：憲章 第21条、第24条1項
- 受け入れ基準：
  - 終了後に、課題の一覧が表示される。
  - わざと失敗を起こした実行では、その失敗が課題の一覧に出る。
  - 最後まで繰り返すか人の指示で終え、統括エージェントが振り返りまで終えた実行では、統括エージェントが振り返って足した課題が、課題の一覧に出る。
  - ユーザーが止めた実行と、途中で終わった実行では、課題を洗い出すためにエージェントが動かない。

### REQ-014 Issue の起票

- 要件：課題の一覧には、{{plugin_name}} 自身を改善するための Issue の案（タイトルと本文）が並ぶ。ユーザーが Web管理画面の課題の一覧で、案ごとに承認ボタンを押すと、その案が {{plugin_name}} 自身の GitHub リポジトリに Issue として起票される。起票できるようにするには、次の手順が要る。起票できないときは、案は並び、この手順が画面に示される。
  1. {{plugin_name}} を GitHub に公開する。
  2. {{plugin_name}} の設定ファイル（マニフェスト。`plugin.json`）の `repository` に、そのリポジトリを書き、書いた後の `plugin.json` を Copilot CLI に読ませる。読ませるやり方は、{{plugin_name}} をどこからインストールしたかで違う。
     - 手元のフォルダからインストールしたとき：Copilot CLI を終了して起動し直すか、`/clear` で新しい会話を始める。
     - GitHub からインストールしたとき：直した `plugin.json` を GitHub に送り、{{plugin_name}} をアンインストールしてから、もう一度インストールする。
  3. gh（GitHub の公式のコマンド）を入れて、ログインする。
- 根拠：憲章 第24条2項・3項
- 受け入れ基準：
  - 承認ボタンを押した案は、{{plugin_name}} のリポジトリに Issue として作られる。
  - 承認ボタンを押していない案は、作られない。
  - 起票できない状態では、案が並び、起票できるようにする手順が示される。
  - 手順のとおりにすると、起票できる。

## 6. 見た目と伝え方

### REQ-030 見た目

- 要件：Web管理画面は、plugin-creator が作るどのプラグインとも同じ画面の構成と見た目（配色、文字、部品）でできている。見やすく、崩れない。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - 共通部分の画面の構成と見た目が、plugin-creator が作る別のプラグインと同じである。
  - 今が計画・実行・評価のどれかと、各エージェントの状態が、画面を開いてすぐ、スクロールせずに見える。
  - ノートパソコンから大きな画面まで、ブラウザーの幅を変えても、文字や部品が重なったり、はみ出したりしない。
  - 各エージェントの出力の全文など、長い内容は最初は畳まれていて、押すと開く。
  - 文字と背景の色の差が十分あり、文字を大きくしても崩れない（Web のアクセシビリティの国際基準 WCAG 2.2 の、色の差と文字の拡大の基準を満たす）。
  - 状態は、色だけでなく文字でも示される。

### REQ-025 分かりやすい表示

- 要件：Web管理画面の表示と Issue の案は、簡潔で、説明のない専門用語を使わない。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - Web管理画面の表示と Issue の案に、説明のない専門用語がない。
  - 同じことを繰り返して書いていない。

### REQ-050 README

- 要件：README は、{{plugin_name}} を使う人に向けて書かれている。README を開くと、まず、{{plugin_name}} で何ができるか（何を渡すと、何ができあがるか）と、どう使うか（チャットでどう頼むか、何を用意するか、できたものがどこにできるか）が分かる。使う前の準備、実行中に気をつけること、うまく始まらないときの直し方、Issue の起票と試験のしかたは、その後に書かれている。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - README の最初の2つの節が、「できること」と「使い方」である。
  - 「できること」に、{{plugin_name}} に渡すものと、できあがるものが書かれている。
  - 「使い方」に、チャットで頼むときの言葉の例と、用意するものと、できたものの場所が書かれている。
